## 偏差

有，逐条如下：

1. **importlinter_v2.toml 一行配置改动（票面文件边界外）**：现象→「V2 runtime 只经 tools 接触世界」契约红灯——runtime→tools→fake/handlers→retrieval 传递链被判违。原因→该契约默认查间接 import，而 modules.md 边界规则表原文是「runtime **引用** tools 以外引擎（knowledge/query/retrieval）＝直接引用才禁」；tools 包装引擎正是设计路径；V2-05 起 runtime 空壳（零 import）故契约从未被真测过。处置→该契约补 `allow_indirect_imports = true`（机器闸语义对齐设计规则原样，红线收紧面零变化：runtime 直接引引擎仍即红）。若 L0 判应保持间接禁，备选＝runtime 内复制引擎缝类型——不建议（第二真源）。
2. **迁移 0022 含 checkpointer 三表（票面点名 run/step 两表之外）**：任务行「＋PG checkpointer」的存储物理面——官方 langgraph-checkpoint-postgres 直连 psycopg 违 B3（全平台唯一 DB 出口），自写 PgCheckpointer 需自有载体表；表名同 agent_v2_ 前缀隔离族。
3. **自写 PgCheckpointer 替代官方 PG saver**：同上 B3 理由；存储模型镜像官方（checkpoint 行＋channel blob 去重＋task 级 write），serde 用框架序列化器——跨版本兼容面与官方 saver 同构。
4. **二轮校验拒收口＝如实拒答（非 need_clarify ASK 帧）**：行为约定 3 字面「校验不过→repair 一次→仍不过→need_clarify 转 ASK 帧」——骨架落法：repair 一轮后仍 bad_args 且用户无新输入→拒因原样转答＋notice refused（不无限澄清循环）。此落法同时是接线④「今天维持 refuse」的可达路径（「今天」的窗界越界经 validate→bad_args 通道，clarify 救不了窗界）。与约定 3 字面的取舍见疑点 2。
5. **「今天」问句的拒答通道＝failed(bad_args, 窗界越界) 而非 V2-05 回报所述 failed(refused)**：窗界校验在 query.validate（data_query 前置面）而非 run 联合态——V2-05 回报第 136 行描述与工具层实际映射有出入。runtime 侧行为不变（拒因如实转答、零数值）；登记备查。
6. **阐述草稿的模型调用落在 verify 步内**（caller=v2.runtime.answer_draft）——行为约定 5「核验步检查阐述草稿」要求草稿先于核验存在；answer 步为确定性收口（拼引用块＋摘要，不调模型）。六步模型调用分工：understand/plan/verify 三步各携一次（caller 三分段），tool/observe/answer 确定性。
7. **PG 门控测试落 tests/infra/test_v2_checkpoint_pg.py**：checkpoint 落 PG 是 infra 面（派工单「测试写 tests/infra|domains|api 对应 test_v2_*」的 infra 位）；TEST_DATABASE_URL 约定同 test_db_pg.py（默认 skip——全量闸门链输出中 103 跳含此）；本机已带 env 跑绿（11 passed）。
8. **spec 验收表文件名 v2 前缀映射**：specs/agent-loop.md 验收表 runtime 侧对应 tests/domains/test_agent_loop.py、test_agent_verify.py——按派工单总则 test_v2_* 命名落为 test_v2_agent_loop.py/test_v2_agent_verify.py，测名 1:1 不变。
