## 一、总定性（Owner 2026-10-14 拍板）

**重构 ＝ 理清逻辑 → 在现状逻辑之上修改出新业务逻辑 → 照新逻辑重写。**

- 不是「整理/等价搬迁」——旧代码是**证据**（事实是系统曾这样跑），不是施工材料；旧码在重写中**逐块废弃**；
- 原话依据：「我说的重构是理清逻辑, 重写这一块的代码, 不是整理这一块的代码」；「原来的设计有很多是错的！我们现在要把现在的逻辑整理出来, 在现在的逻辑之上修改出新的业务逻辑, 然后重写」。

## 四、调研判据（已定稿并执行）

- **三腿站立**：每条业务规则须有「代码腿（file:line）＋测试腿（测试锚点）＋票面腿（票/拍板出处）」；缺腿项进雷区清单（重写风险区）；

## 五、疑点处理决议

**不做全量 triage**（不封顶：结构性噪音随重写自然消失，在旧结构里结账＝乱上加乱）。疑点定位：修订素材＋重写参考；行为类疑点在写各模块修订提案时按需消费。

## 六、修订工序（第 5 步作业方式）

**逐模块修订提案**，每份四条，Owner 逐份裁决：

1. 现状逻辑（引分片报告编号，不重抄）；
2. 已证问题（引事故/病理/票面/疑点编号——**无证据不算问题**）；
3. 新业务逻辑提案（重新表述；错的设计直接推翻重拟，不打补丁）；
4. delta 清单（相对现状行为改动的逐条清单＝测试网目标清单）。

顺序：先主干（理解 → 澄清 → 匹配 → 前置 → 批量 → 作答 → 核验），后枝叶。

## 七、重写纪律

- 链条：**模块规格定稿 → 织测试网（特征钉钉住必须保留的现状行为＋新规格钉钉新逻辑）→ 重写实现 → 废弃旧码 → 全量测试＋六闸绿**；
- **网没织好，不开写**；**修订没定稿的模块，一行不动**；
- 一模块一票；旧码逐块删除，不许残留旁路。
