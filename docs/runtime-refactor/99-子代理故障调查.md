## 根因假设（按可能性排序）

**H1. opencode-go-chat 网关（opencode.ai/zen 第三方中转）链路间歇性断流——"网络连接失败"形态的主因（可能性最高）**
- 支持：三形态里它最常见；同一分片重派有时成功（间歇性）；跑得久/上下文大更容易失败（流越长越易被中途断开）；E10 有中继断开记录；E3 错误不落本机日志（断点在链路层而非本地代码路径）。
- 反证/待验证：E8 当前可达 200；E5/E9 同期同模型有成功记录；本机无网络错误明细。验证法：故障复现时并行 `curl` 探活、查网关状态页；若不同模型同时出现该错误，优先归因网关。

**H2. deepseek-v4.1-flash 思考模式（thinking）协议不兼容——"reasoning_content" 形态的主因**
- 支持：`The reasoning_content in the thinking mode must be passed back to the API` 是 DeepSeek 系 API 的标准报错——多轮工具循环中，客户端未把上一轮 assistant 消息的 reasoning_content 原样回传（或被网关剥离）即被拒；轮次/工具调用越多，踩中概率越高，与"跑得久更易失败"吻合；本调查子代理自身即运行在 opencode-go-chat/deepseek-v4.1-flash（子代理默认模型佐证）。
- 反证/待验证：本机无该错误落盘（E3），无法统计频次；同模型 00:08 成功（E9），说明非必现——可能是特定轮次状态（如历史压缩/裁剪后丢失 reasoning_content）才触发。验证法：把子代理 thinking 调低/关闭做 A/B；能拿到 request_id 344fcda8... 的请求体更好。

**H3. 20:38 配置改动 + 20:54 重启是故障窗起点（时间强相关，因果待验证）**
- 支持：配置改动（E1）→ 重启（E2）→ 21:00 起故障，时间线严丝合缝；改动把 opencode-go-chat 从"无显式 api 块"变为显式 `openai-chat-completions`，协议路径可能随之改变（进而暴露 H2）。
- 反证/待验证：20:36 的备份里本来就没有 api 块，无法证明"改动前一定正常"；20:48（改动后）仍有 glm-5.3-flash 成功。验证法：以 bak2 配置做受控 A/B（需 Owner 拍板后由用户操作，本调查未执行）。

**H4. 宿主/父进程侧取消或等待超时——"cancelled before the subagent returned findings" 形态的主因**
- 支持：该形态措辞指向父窗侧行为（批等待结束/事件投递丢失/后台启动失败即取消），非 provider 错误；最后一批 5 个全为该形态；E5 有子代理会话事件被 skipped。
- 反证/待验证：无法区分"子代理被上游卡死后由宿主取消"与"宿主误取消"；本机无取消明细。验证法：单独跑一个长任务，观察是否在固定时限/固定事件后必被取消。

**H5. 本地资源问题（低可能性，基本排除）**
- 支持：无。反证：内存采样正常（rss 148–172MB，周期采样无异常），无崩溃转储（E7），无 OOM/句柄错误。

## 解决方案建议（按性价比排序）

**立即可用（绕行）**
1. 子代理换模型：从 opencode-go-chat/deepseek-v4.1-flash 换到 glm-5.3-flash（new-provider 或 opencode-go-chat 均可）——一步同时绕开 H2 的思考模式协议问题；故障窗内 glm-5.3-flash 会话均有完成记录（E9）。若必须留用 deepseek，把子代理思考级别调到最低/关闭 thinking，减少 reasoning_content 依赖。
2. 降并发：批量派发并发从 5 降到 2（最少 1）。间歇性链路错误下，5 路大流同时打同一网关，任一路断即整批残缺；并发低则单路更稳、定位更容易。
3. 切片变小：控制单个子代理"上下文 < 约 10 万 token、工具调用 < 约 80 次、运行时间 < 20–30 分钟"。失败率随体量与时长上升（已知规律），小片重派代价低。
4. 重试策略：失败分片等 30–60 秒后**新开会话**原样重派（不续跑失败会话——reasoning_content 卡死的会话续跑大概率继续报错），最多 2 次；分片设计成幂等，保证重派不产生重复副作用。
5. 关键分片不走后台启动（background launch）路径，前台等待返回；规避第三形态"background launch 完成前被取消"。

**需要配置/等待**
6. 配置 A/B（需 Owner 拍板）：把 provider_config.json 回退到 `bak2.20261014_203657` 做对照实验，验证 H3；注意 bak2 中该 provider 无 api 块，回退前先确认旧版可用性（建议先查 3.15.3 发布说明或问官方支持）。本调查只读，未执行。
7. 上游观测：关注 opencode.ai/zen 网关状态与变更（H1）；若三种错误在不同模型上同时出现，优先归因网关而非单一模型。
8. 备选路线：若 deepseek 必须留用且协议错误持续，改用"山火"provider（Volces ark，anthropic-messages 协议）下的 deepseek-v4.1-flash，协议路径不同或可规避 reasoning_content 问题（需实测）。
9. 取证改进：子代理失败时在父窗保留 request_id 与服务端错误原文（现本机日志不落 provider 错误，E3），下次复现可直接对照。
