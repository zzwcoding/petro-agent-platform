### 方案主张 A-P5b1-01｜三层分离总构想（§0）

- 主张内容（综述）：现行设计把「系统指令、模型过程原话、对话」三种东西混在一条消息历史里，产生三个后果——上下文随过程膨胀（库里单 run 最高 60.5 万字）、每次调用全量携带（token 浪费 70%+）、模型把过程记录当对话模仿（方案称这是复读/标签照抄/误判直答的「全部根因」）。重构为业界标准三层分离：对话层（自然对话）、任务层（每次调用现拼、不入史）、过程层（结构化轨迹、按需有界渲染）。预期「每次调用 token 降 ~70%，模仿面清零，存储有界」。
- 解决的问题/动机：Owner 下令「我需要的是一个高性能高可用的企业 agent，不是临时修补的玩具——调研正常的 agent 对话设计，分析数据库里各种对话上下文，给我详细完整的重构方案」。
- 落地形态（方案里写的机制要点）：总纲性质，机制拆在 §3 各节、实施拆在 §6 五票。
- 与现状的关系：已落地（79a–79e 全量；23 场景对话纯度零违例实测见 `eval/results/V2-79-重构验证/报告.md`）。**但「每次调用现拼、用完即弃」这条主纪律次日后被 V2-80h 改向**——0ffe722 记录 Owner 指正「V2-79『用完即弃』矫枉过正（病灶根因是伪标注 assistant 轮而非过程在场）」，改为对话链追加式（RunState.messages 只追加、相位合同/每轮增量追加入链，f58ada9 实装，schema v3）。
- 疑点（只列不判）：
  - 「~70%」是单 run 模型总消耗口径；79e 验证报告实测为全 run 合计 −44.2%（19 对可比），报告自称与预估「子集口径相容」——单调用口径的独立实测数未见。
  - 本方案不含「对话链追加」形态，后出的 V2-80 §9 对其定性为「矫枉过正」；两方案（替代/修正/并存）在本方案文本内无对照说明，待合成核对。

### 方案主张 A-P5b1-02｜现状诊断（§1）

- 主张内容（综述）：全库实测（2026-10-13）——1740 个 run 有历史，历史总字数 58,818,042；单 run 中位数 32,001 字；最大单 run 605,190 字（194 轮失控循环）；一句「你好」的 run 带 108,980 字上下文。历史轮次聚合构成里前四类全是过程/指令/原话（其他用户轮 8,277 轮 2,234 万字、任务书 820 轮 272 万字、其他助手轮 5,044 轮 221 万字、模型原话 1,738 轮 13.6 万字），真正的对话内容不到总量 5%。每次调用消息＝[system 角色红线, history(截断 ≤12000 tokens), 当前指令轮]，一次 run 2~4 次调用每次全量重发（中位每次约 8k tokens、95% 为过程内容），截断是「保首尾、弃最旧中间」的任意丢弃，checkpoint 侧无界存储。已暴发症状（伪标注照抄＋逐轮累积、复读 7 遍、连答两轮、误判直答、同参重投）被归为同一根因「过程记录以助手轮角色在史」。
- 解决的问题/动机：为重构提供数据与事故依据（方案头部引用 Owner 指令）。
- 落地形态：诊断转化为 §2 铁律与 §3 目标架构；§1.3 单 run 实例全文另存 `eval/results/run-4435a7ce-全对话上下文.md`。
- 与现状的关系：诊断主体已被证据链继承（79e 验证报告以「改造前混装史」为对照基线）。**但根因判定被 80h 收窄**——0ffe722 把病灶重新定位为「伪标注 assistant 轮而非过程在场」，故「其他用户轮＝过程垃圾、入史即冗余」的定性部分不再等同现行答案（80h 后任务书/台账行改为入链在场）。
- 疑点（只列不判）：
  - §1.2 把 8,277 轮「其他用户轮」整体定性「过程垃圾——入史即冗余」；80h 后其中任务书类内容改为入链在场——两版的在场/不落史清单差异无对照表，待合成核对。

### 方案主张 A-P5b1-03｜业界四条铁律（§2）

- 主张内容（综述）：四条铁律——①消息历史＝自然对话（user 原话 ↔ assistant 最终回答；没有框架把 prompt 模板或系统指令记进对话历史）；②系统指令走 system 通道、每次调用现拼、不入史不重放（方案引 Anthropic 口径「trust the per-call assembly」）；③过程轨迹独立于对话（工具调用用结构化条目、思考/决策不入 messages；要给后续轮看时有界、结构化、按需渲染）；④长对话治理是标配（token 预算＋旧轮摘要化，摘要替代原文而非丢弃）。本系统反模式对照：任务书入史（违 1、2）、决策 JSON/台账以助手轮在史（违 3）、伪标注轮（违 1、A4）、无摘要的任意截断（违 4）。
- 解决的问题/动机：给重构立外部权威判据（对应 Owner 令中的「调研正常的 agent 对话设计」）。
- 落地形态：铁律即 §3 各机制的判据；出处映射表在附录 A5。
- 与现状的关系：铁律本身留档有效；**②③④的工程落法在 80h 后被重新解释**——②「不入史」改为「相位合同/任务书首入追加入链一次」（防重发但仍留链）；③的 process_notes 面保留（§3.4 的渲染面仍在 graph.py 活着）；④的 compaction 族退役（80h：compaction 退为超视窗最后手段）。①对应的「自然对话形、零伪标注」在 79 形有 23/23 纯度实证，80h 链形下未按同判据重扫。
- 疑点（只列不判）：
  - 铁律①的 alternating user/assistant 读法与 80h 链形（任务书/台账行/合同包以 user 消息入链）不是严格交替——80h 后铁律①的准确读法待合成核对。

### 方案主张 A-P5b1-04｜三层定义（§3.1）

- 主张内容（综述）：对话层 `dialogue`＝用户原话、助手终稿、澄清/审批等真实用户输入，「一条不多」，run 生命期＋追问播种传承，以 user/assistant 消息轮进模型面；任务层（现拼）＝system 角色红线＋本轮任务书/指令＋观察材料＋常驻台账块，单次调用用完即弃，以 system＋当前 user 轮进模型面但**不入史**；过程层 `process_notes`＝[{phase, title, digest}] 紧凑过程档案（理解一句话、决策要点、台账一行摘要、拒因，每轮 ≤200 字），run 生命期，追问轮可选有界渲染进当前指令、**永不以对话轮出现**。
- 解决的问题/动机：把混装史拆成三类东西各自归位（对话可传承、指令可现拼、过程可结构化承载）。
- 落地形态：79a 实装双字段（`appv2/runtime/state.py` 曾为 dialogue/process_notes/schema_version）；79e 清账后 schema 面只剩这两层＋版本字段。
- 与现状的关系：部分落地后被 80h 重构——process_notes 层保留且活着（`graph.py:1278 _render_process_notes`＋各节点 `_notes_with` 写入）；dialogue 层概念被 messages 链取代（`state.py:184-196`：messages 为对话链，dialogue 标注「【V2-80h 兼容死字段】零读写，仅保 v2 快照读入不炸；追问种子降级抽取用它」）；「任务层不入史」纪律被 80h 推翻（任务书入链）。
- 疑点（只列不判）：
  - dialogue 死字段「零读写」与「追问种子降级抽取用它」「播种 v2 支消费」并存（state.py 注释点名、executor `_seed_messages` 三态）——精确读法待合成核对。
  - §3.1 「任务层生命周期＝单次调用」与 §1.5 同参重投根因的张力（过程不入史后防重靠 79c 渲染＋V2-37 闸兜底）是否为 80h 改向的动因，80 系列文档未在 79 文本内留下对照。

### 方案主张 A-P5b1-08｜追问播种新形（§3.5）

- 主张内容（综述）：播种种子＝前轮 checkpoint 的 `dialogue` 通道（只有自然对话：问、答、澄清、审批回收）；旧格式 checkpoint（history 字段）走读兼容抽取（4.2）；可选附前轮过程摘要一段（≤300 字，Owner 拍板是否开）。新形下「我刚刚问了什么」类问题模型直接看到用户问＋助手答两轮即可复述，无需任何标注。

### 方案主张 A-P5b1-09｜compaction 长对话治理（§3.6）
