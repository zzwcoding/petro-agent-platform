## ADR 部分

### ADR-0001｜架构图 V2 过审（阶段 2 验收）

- 决策内容：阶段 2 验收通过 `docs/architecture-v2.md`，定为 7 模块划分（api/runtime/tools/knowledge/query/retrieval/infra）＋V1 双向禁引边界，Owner 逐节点过完无修改。同时两条附加裁决：模块粒度维持三分引擎（knowledge/query/retrieval 不合并、不升层）；Verifier 定位为 runtime 内 loop 的一步，不独立成模块。后续变更须回阶段 2。
- 约束力：硬约束（模块拓扑与边界不可私改）。
- 对重写工程的影响：重写只能在既有 7 模块骨架内动 runtime；Verifier 不得抽成独立模块——重写若拟拆分/升模块须回阶段 2 走变更，不在本仓私改。
- 关键原文：
  > 模块粒度维持三分引擎（knowledge/query/retrieval 不合并且不升层）；Verifier 作为 runtime 内 loop 一步，不独立成模块。
- 疑点：「V1 双向禁引」在本 ADR 无细目（具体边界须查 architecture-v2.md 与 import-linter 契约）；「后续变更卡须回阶段 2」的触发口径未量化（哪些改动算模块拓扑变更）。

### ADR-0002｜Harness 编排层采用 LangGraph（带三红线）

- 决策内容：阶段 2/3 间框架决策——采用 LangGraph，限定为 `appv2/runtime` 模块的实现技术。理由：StateGraph＋条件边对应 loop 原语；interrupt/Command(resume) 对应 ASK 挂起与 /resume 恢复两个硬需求；checkpointer（PG saver）落既有 PostgreSQL，避免自造持久执行状态机的高危坑。附三条红线（进边界规则与票面验收）：①langgraph/langchain 只许 runtime 内部 import，禁渗入 api/tools/engines 与 SSE 契约；②全 LLM 调用经自写 ChatModel adapter 走 `gateway.complete`，禁 langchain 自带 provider 直连；③run/step 状态 schema 自有（step 类型/Manifest/ASK 帧自定义），checkpointer 仅作存储机制。
- 约束力：框架选型＋硬约束（三红线）。
- 对重写工程的影响：重写默认沿用该框架；三红线＝框架红线——import 边界（langgraph 不出 runtime）、LLM 单点（adapter→gateway.complete）、状态 schema 自有；依赖树进 lockfile 与 import-linter 契约、CI 时长略增的代价在重写中延续。
- 关键原文：
  > 采用 LangGraph，限定为 `appv2/runtime` 模块的实现技术。
  > 全部 LLM 调用经自写 ChatModel adapter 走 `gateway.complete`（B6 归因/预算/审计保留），禁止 langchain 自带 provider 直连；
- 疑点：本报告所读 6 个 ADR 内未见对 ADR-0002 的后续修订——重写若拟收窄/更换框架用法须回审（是否已有回审记录本次未确认）；「框架升级跟随 langgraph 节奏」未给版本锁定策略。

### ADR-0003｜LLM 调用并发模型：单实例 asyncio＋全局闸，不上消息队列，预留 RunCommand seam

- 决策内容：Owner 问询后拆解：多任务并发沿用 V1 全局并发闸＋预算熔断；loop 内 LLM 调用天然串行（步间数据依赖）；长过程以 waiting_ask 事件流＋checkpointer 落库收束，不占连接/进程；崩溃恢复靠每步落 PG＋重启清扫器。决策本期单实例 asyncio＋全局闸、不上 MQ——队列的真触发条件是跨进程水平扩展/升级不打断在跑任务，一上队列须连带租约/围栏/幂等一整套复杂度，本期量级不值。预留接缝：runtime 以 RunCommand（ask/resume）→执行器→RunEvent 流建模，命令入口与执行器之间为显式 seam，将来换 Redis Stream 消费者时 api/tools/事件契约零改动。附三个反转条件（双实例部署；单实例 P99>60s；在跑任务要求跨升级存活）。
- 约束力：背景说明＋设计接缝约束（含三个反转条件）。
- 对重写工程的影响：重写保留「RunCommand→执行器→RunEvent」 seam 与单实例案，不顺手引入队列；并发闸/预算熔断/每步超时照旧；触发反转条件才回审本决策。
- 关键原文：
  > 本期单实例 asyncio＋全局闸，不上 MQ。
  > 将来水平扩展时执行器换 Redis Stream 消费者，api/tools/事件契约零改动（书：编排层与 Runtime 解耦，接口是任务与状态）。
- 疑点：正文引「书」未给书目全名；反转条件②的 P99 监测手段未写；seam 的具体代码落点（api 与执行器边界）本 ADR 未指文件，重写须自行对代码确认。

### ADR-0004｜ReAct 重构：六节点线性流水线 → 自主循环（Owner 拍板 2026-10-09）

- 决策内容：六节点线性流水线（understand→decision⇄(discover/execute→observe)→answer→verify 收口）退役，改 ReAct 自主循环；背景为 Q12 对账实证检索域 81 题整域失效，根因在设计（模型当三工位、输出合同闭世界、校验失败兜底一刀切）而非模型能力。Owner 十条拍板（全按 L0 推荐）：预算 ≤3 轮×轮内（发现 ≤2＋主执行 ≤2）＋单段 300s＋单工具 30s；schema 校验失败取消自动 repair、拒因回喂重决策；verify 节点保留（零 LLM，INV-1/4 机器底线）；发现探查范围＝agg 三表＋sem 五账＋kb 片段清单（raw/lake 不开放）；SSE wire 允许演进（subtype 在位）、V1 超集兼容保留到 web V2 批完成；澄清分级（时间窗歧义自动默认近 30 天＋注记／目标对象口径 ASK／越集审批）；Skill 指南＝ontology 资产；不用 LangGraph prebuilt ToolNode；答案起草挪 answer 节点；P-022/P-023 撤回。后果：specs/agent-loop.md 行为约定 3/7 等条款失效（由 V2-36 重写），并催生 ADR-0005。
- 约束力：硬约束（十项行为底线，进票面验收）。
- 对重写工程的影响：重写的行为规格直接继承十条——预算数、澄清分级、verify 零 LLM 底线、发现工具范围；工具调用必须走 ToolRegistry.call 受控链（不用 prebuilt ToolNode）；SSE subtype 契约允许演进。
- 关键原文：
  > 决策：**ReAct 自主循环**取代六节点线性 loop
  > LangGraph prebuilt ToolNode 不用（与"工具只经 ToolRegistry.call 受控链"冲突），自有节点承载
- 疑点：P-022/P-023 补丁内容与撤回落地状态本 ADR 未展开；「V1 超集兼容保留到 web V2 批完成后放宽」的放宽时点依赖 web V2 批进度（当前状态未在 ADR 内，未确认）。

### ADR-0005｜子任务图＋前置条件机（Owner 设计拍板 2026-10-09）

- 决策内容：一轮＝四相位——①业务澄清（LLM＋discover，产出带台账注释的问题组，子问题 ≤4）→②工具匹配（LLM 提议子问题→工具/链，schema 收口）→③前置条件机（纯固定代码、零 LLM：逐子问题过闸判四态 pass/blocked_ask/blocked_refuse/note）→④批量执行＋LLM 汇总（verify 收口）。铁律：LLM 出语义，代码出判定。轮语义：整循环 3 轮，轮 1 得部分答案，轮 2/3 只带失败/缺失子问题＋拒因回炉；成功结果保留不重跑；ASK 挂起不占轮；澄清相位发现调用 ≤10 且每次计数埋点。词典层：台账小（46 行级）第 1 轮全量注入（注入胜检索），semantic_query 转钻取。增补三条（P-033 追认）：轮预算按「每用户输入周期 3 轮」计、resume 重置轮预算合法；词典每轮常驻注入（clarify/toolmatch）、历史整块收窄防 token 放大；预算驱动 discover 免轮例外只留首次，第 2 次起转占轮、总 ≤10 不被绕过。
- 约束力：硬约束（四相位结构与铁律；含增补三条）。
- 对重写工程的影响：重写的运行时主骨架＝四相位＋前置信条件机；前置条件机零 LLM 的四态闸是业务红线；轮语义（per 用户输入周期、resume 重置、失败子集回炉、成功保留、ASK 不占轮）是重写状态机核心；词典常驻注入节奏是上下文/预算设计输入。
- 关键原文：
  > 铁律：**LLM 出语义（澄清/分解/提议），代码出判定（前置条件机零 LLM）**——V1 十七站瀑布教训的落点。
  > 轮预算按「**每用户输入周期 3 轮**」计——澄清回收（resume）重置轮预算（rounds=0）合法，ASK 挂起等人工不计轮。
- 疑点：闸数与判定序三处口径不一（本 ADR 列 5 项检查／裁决图文件头「六闸」／裁决图 T5 列 8 项判定序）——重写须以 precondition.py 为代码真源对账；P-033 C3/C2/S2 编号出处（L0 追认记录）未在 ADR 内给出；「token 量化对照账随实施拍报 L0」是否已报未确认；V2-28「五站能力」的具体迁移物在 ADR 外。

### ADR-0006｜ReAct 循环真多轮对话化（消息历史簿记进上下文）

- 决策内容：认定伪多轮（每步模型调用是全新 system＋user 两条消息、run 状态重序列化进单条 user 消息）是病灶：执行历史不在上下文、被拒尝试被过滤出模型面；实证 P-026 复测 16 题中 9 题同参重复执行烧满 3 轮。决策：所有循环都必须做多轮对话、历史信息必须放进上下文（含 10 次 discover 小循环、3 轮大循环、用户追问）。落字三层：①run 内消息历史簿记（模型调用与输出、工具参数与结果含闸拒拒因、拒因回喂全作为消息轮次进历史，后续在完整历史上续写、不再每次重序列化）；②执行台账段（「参数→结果：N 行／闸拒（拒因）」落史，同参重投由模型自己避免）；③追问续会话（追问＝会话线程新轮，历史随追问进上下文；实现形态归 V2-38 票面）。影响：新增 V2-38 排在 V2-34 前；V2-37 同参重投闸降级为兜底；历史增长须带 token 预算/截断策略（截断显式进 Manifest）；[n] 引标与 verify（INV-1）语义不变；ScriptedCompleter 按消息历史形态重写。被否：伪多轮＋机器闸（拦得住同参拦不住变参空转）；只加台账不建追问线程。
- 约束力：硬约束（Owner 拍板「所有循环都必须做多轮对话」＋三层结构与工程约束）。
- 对重写工程的影响：重写上下文层＝消息历史续写（不是每次重序列化）；历史簿记必须含负信息（拒因）；token 预算/截断显式进 Manifest；追问承接的具体形态待 V2-38/V2-79 系落点；ScriptedCompleter 有重写义务。
- 关键原文：
  > **所有循环都必须做多轮对话，历史信息必须放入上下文**——包括 10 次 discover 的小循环、3 轮的大循环，以及**后续用户在对话框的追问**（追问同样是多轮对话的一部分）。
- 疑点：与裁决图中 V2-79「上下文只装对话、过程细节（查了什么/被拒原因）留任务档案不进上下文」的口径变化，本 ADR 未见回填/修订记录——第 2 层「执行台账段进史」是否已被 V2-79 取代/收窄，须查 V2-79 系票与 P5b1 后方可定论；ScriptedCompleter 重写状态本 ADR 未更新。

### 裁决图结构

- 节点总数/场景数：**38 节点 / 19 场景**（与 JSX 实际对账：V2_ROOT 树 key 38 个；NODE_EXEC 38 键；PATHS 19 条路径；V2_SCENARIOS 19 条，双向吻合。文件头注释写「35 节点」为陈旧值，见疑点 1）。
- 结构分层：主干 11 节点（T0–T9）＋分支/横切 27 节点；3 个横切 guard（reconnect/followup/budget，树中 dashed）＋4 个流程内 guard（T1/T2n/T2a/T5a）；19 个叶节点各挂场景 key（sc）。
- 19 场景 → 叶节点对账：data-clean（主链至 T9）、ban（T2a-1）、ban-exempt（T2a-2）、discover（T3b）、clarify（T3d）、clarify-capped（T3e）、extable（T5b-1）、extable-deny（T5b-2）、caliber（T5c）、off-ledger（T5d）、chain-switch（T5e）、engine-ask（T6a）、refurnace（T6b）、rewrite（T8a）、split（T8b）、chitchat（T2b）、injection（T2n-1）、exfil（T2n-2）、write（T2n-3）。
- 主干链路节点序列（data-clean 场景，FRONT＝T1,T2,T3,T3c,T4,T5,T6,T7,T8,T9，加根 T0）：
  - T0 发起提问——所有路径起点，建流并把任务在数据库建档（中间状态也存，可续跑）。
  - T1 入口阀——开流前的程序检查（空问题/格式/身份/任务号/续跑状态的错误码都在流打开之前给出）。
  - T2 理解问题——第一次模型调用，先回「我理解这道题是在问…」（流式），纯寒暄走例外直答。
  - T3 意图澄清——模型三选一：查资料（钻取）／拆问题／向用户反问。
  - T3c 分解问题——大问题拆成 ≤4 个小问题，每个带台账逐字注释并标路线（数据链/文档链）。
  - T4 工具阀——给每个小问题配工具（查数或找文档）并做闭世界对账，拒因回喂模型重配。
  - T5 前置条件阀——纯普通代码逐个小问题过固定判定序，出四态（放行/挂起/拒答/注记）。
  - T6 查询执行——逐个小问题真去执行（查数表/搜报告），已成功的不重跑。
  - T7 汇总作答——模型把结果整理成带出处编号的答案，流式一段段推给页面。
  - T8 核验收口——逐句核验（零 LLM 兜底），无据改写/矛盾分列，出核对结果卡。
  - T9 收尾归档——黑匣子归档＋操作日志＋结束信号（done），任务状态落「已完成/失败」。

### 各节点的分支条件与去向（规则条目）

**T0／横切 guard 组（reconnect/followup/budget）**
- A-P7b-01：T0 接受两种带任务号的进入方式——断线重连（T0x）与追问（T0y）；两种不能同时给，同时给报 409 冲突。
- A-P7b-02：reconnect（T0x）：页面拿任务编号＋最后收到的消息序号重连；后端把之前发过的内容重发一遍，不重复、不漏；任务编号不存在→404。
- A-P7b-03：followup（T0y）：追问＝上一问彻底结束后接着问（上一问没结束→409；编号错→404）；带进新任务上下文＝对话层（上一问的问题、最终答案、澄清选择）；执行过程细节（查了什么／被拒原因）留在任务档案里可查、不再塞进上下文（V2-79）。
- A-P7b-04：budget（T0z 预算收敛）：执行限额——最多 3 个决策轮；查资料最多 10 次（每轮最多 2 次）；每轮执行最多 2 次；单个阶段最多 300 秒；单次工具调用最多 30 秒。到限不卡死：先交付已拿到材料＋notice 列清没做完的；停下来等人回答不计时；用户答完续跑轮数重新计。

**T1 入口阀**
- A-P7b-05：开流前程序检查，所有拒绝都在「流打开之前」：问题为空→400；消息序号格式不对→400；没带身份→401；任务号不存在→404；任务没在等待状态却要续跑→409；检查过了才放进主流程。

**T2 理解问题**
- A-P7b-06：系统定位开场说清（V2-80d）：本系统只回答与查询，不执行动作。
- A-P7b-07：纯寒暄且确定无关→走 T2b 例外直答（V2-80a）；其余一切输入照常读题。
- A-P7b-08：记录分层（V2-79 改后）：对话记录只装「自然对话」（用户原话／最终答案／澄清选择）；模型过程输出与每步细节走「过程档案」，上下文里不再堆过程材料。
- A-P7b-09：上下文追加式（V2-80h）：链尾追加〔任务书〕→〔理解原文〕——任务书永久留在链上。

**T2n 词面安全阀（guard，模型调用之前）**
- A-P7b-10：三类词面闭世界匹配——注入指令／外发请求／写意图（动词＋对象同句共现）；命中＝零模型硬终止＋固定话术，两步收口。
- A-P7b-11：注入命中→T2n-1，回复「这类要求不会被执行，平台规则不可能被对话内容覆盖」。
- A-P7b-12：外发命中→T2n-2，回复「本系统只读——未配置外发通道」。
- A-P7b-13：写意图命中→T2n-3，回复「本系统只读——不做任何写入或调整，如需变更走线下流程」。

**T2a 禁用词检查（guard）**
- A-P7b-14：直接用废弃旧叫法要数（跨句拼接也算）→T2a-1 直接终止——不按废弃口径代答，回复里说明现行叫法是什么；这句拒答话术也会走后面的核对步（无数据断言，原样通过）。
- A-P7b-15：问句里有「旧称／以前叫／现在叫／还叫／原名」这类词、或旧叫法被引号包着→T2a-2 放行＋notice＋记一条操作日志；原问题照常走完整流程。

**T2b 无关业务直答**
- A-P7b-16：chitchat 两步收口：以油田数据问答助手的身份友好回应并引导提问；不自称任何系统环节，不编造数据。

**T3 意图澄清**
- A-P7b-17：模型只有三个动作可选——查资料（T3a）／拆问题（T3c）／向用户反问（T3d）。
- A-P7b-18：时机规则：时间范围能从问句确定＝不许反问；问句里的时间词能解析＝直接定范围；没有时间词＝默认「近 30 天」并注明。
- A-P7b-19：指标台账全部内容（含别名、结构卡）每轮完整放进上下文——模型不用猜词。

**T3a 资料查找（discover）**
- A-P7b-20：模型提议→代码真去调查询工具（按名字找对象／找报告资料／查数据表结构）；限额每轮最多 2 次、整个任务最多 10 次；每次都留记录（用了什么词／命中多少／有没有查到）。

**T3b 材料入上下文（observe）**
- A-P7b-21：把工具查回来的材料放进上下文（每份带编号、来源、可信度、内容）。
- A-P7b-22：防原地打转：第一次「到预算还想查」不算轮数，从第二次起就算占一轮。

**T3c 分解问题（decompose）**
- A-P7b-23：把大问题拆成最多 4 个小问题；每个小问题必须带从台账逐字抄来的注释；每个标好路线：数据链（查数表出数字）／文档链（搜报告出答案）。

**T3d 澄清反问（clarify）**
- A-P7b-24：问题要问的对象／口径确实有歧义→发「反问卡」（问题＋选项）停下来等用户选；等待不占 3 轮限额；用户选完从停下的地方接着跑，重新进澄清相位。
- A-P7b-25：连续反问 6 次到上限→转 T3e（上限＝合同值 6）。

**T3e 澄清截断（clarify-capped）**
- A-P7b-26：不再追问，把手头已拿到的材料如实交付（notice 标明「连续澄清截断」）；没有材料就如实说没拿到——不编造。

**T4 工具阀（toolmatch）**
- A-P7b-27：数字题→数据查询（必须附带查询计划）；报告题→找文档（必须写明要找什么）。
- A-P7b-28：程序对账：每个小问题必须恰好配上一条——漏配／多配／编号对不上都拒绝；拒绝原因发回给模型重新配（不做自动修补）。

**T5 前置条件阀（precondition）**
- A-P7b-29：判定顺序固定（第一个命中的定结果）：禁用词→外部表→口径→台账→绑定状态→井的范围→新鲜度→单井支持。
- A-P7b-30：逐个小问题判，结果只有四种：放行／需要用户处理（停下来等）／如实拒答／放行但带注记。

**T5a 禁用词阀**
- A-P7b-31：查数据和搜报告两条路线都不豁免：合法地问旧名→放行并注记；直接要数→如实拒答。

**T5b 外部表审批（extable）**
- A-P7b-32：查询计划用到本平台之外的表（如 ERP）→先停下来找用户审批——模型和流程都无权自己批；双保险：执行前再扫一遍，扫到没审过的照样拦。
- A-P7b-33：用户点「批准」→T5b-1：这张表进白名单、按原计划继续查（查询计划不重排）；接着回前置检查再判一遍。
- A-P7b-34：用户点「驳回」→T5b-2：这个小问题如实拒答（不重试）；汇总时如实把「被驳回」讲出来。

**T5c 口径阀（caliber）**
- A-P7b-35：问句里有「月报／正式／化验」这类场景词→按台账直接定口径（对不上→拒）。
- A-P7b-36：没有场景词、指标有两种口径：问句是判断题（是否／超过／达标／高于／低于…）→必须反问用户按哪口径；是要数的题→按默认口径出数，答案里「血缘卡」把两种口径都列出。
- A-P7b-37：模型报了个不存在的口径→拒（非法口径不代答）。

**T5d 台账阀（off-ledger）**
- A-P7b-38：数字题给的指标名必须在台账里查得到（编号／名称／别名都行）——查不到→如实拒答（不在目录不代答）。
- A-P7b-39：例外：台账本身是空的（平台配置缺失）时不一票全拒——以查询引擎的校验为准。

**T5e 工作流阀（chain-switch）**
- A-P7b-40：触发两种情况——指标在台账但没绑定汇总表的列（出不了数）；或问句点名的井全都不在数据表的井名单里（硬查出来也是错的范围）。
- A-P7b-41：处理：带拒因和提示回到澄清相位，改走「搜报告」路线重做一次（占一轮、不停下来）；一次为界；坚持原路线同样参数再来一次→如实拒答收尾（不允许无限循环）。

**T5f 备注放行（note）**
- A-P7b-42：四件「放行＋注记」：指标名／别名先归一成台账编号；模糊时间词（最近／近期／前段时间）＋模型自作主张定了时间范围→把范围清空让引擎反问用户补（用户已答过时间的不改）；时间范围上沿比数据水位还晚→注记；查单井还没支持→照常查全井，答案里如实注明读的是哪些井的行。

**T6 查询执行（batch）**
- A-P7b-43：逐个小问题执行（查数表／搜报告）；已经成功的小问题不重跑（回炉时保留原结果）；每次执行都记账（参数／回来多少行／或被拒原因）。
- A-P7b-44：T6a（engine-ask）：查询工具返回「缺参数，要问用户」（如「最近」解析不出具体时间范围，给三个选项）→停下来等用户答；答完回到澄清相位继续跑。
- A-P7b-45：T6b（refurnace）：有小问题查失败→在轮数限额内只带失败的（附拒因）回澄清相位重做——成功的小问题结果保留绝不重跑；时间范围缺口的补救过程用 notice 记录（window_miss_reentry）。

**T7 汇总作答（answer）**
- A-P7b-46：把所有小问题结果整理成一份答案（每句都带出处编号），流式一段段推给页面；被拒答的小问题如实写进汇总。
- A-P7b-47：到预算上限时，已拿到但还没核验的材料会标注「未及核验」。

**T8 核验收口（verify）**
- A-P7b-48：逐句检查答案：每个数据断言是否有工具返回的材料撑着；一点实质材料都没有→把闸的依据如实转成答复，不冒充出了数；输出核对结果卡（多少句有支撑／改写了几句／有没有分源／引用了哪些材料）。
- A-P7b-49：T8a（rewrite）：答案里在材料里找不到依据的句子→改写成「未找到／材料未披露」＋发 notice；规则：没有依据的话，一句也不许进答案。
- A-P7b-50：T8b（split）：两个来源给的数对不上→答案把两边分开列、各带出处——不强行调和；引用材料与问句点名的井／对象对不上号时，再发一条 notice 提醒。

**T9 收尾归档**
- A-P7b-51：黑匣子归档（本次任务完整记录提炼后入库），归档写失败也发 notice、不留无声缺口；操作日志（建任务／挂起时的决定／收尾）统一写进专门日志库；最后发结束信号（done）；任务状态落成「已完成」或「失败」。
