# 前端答案展示重设计 · 设计稿（第二步产物 · 待 Owner 过目）

> 2026-10-17 · 依据 `frontend-redesign-调研.md`。本文是**讨论稿**：Owner 过目拍板后才动工。
> Owner 现况评价：「中间只有对话，很单调，没有加载中/思考中/调用中状态；右侧过程对人类而言看不懂」。
> 参考系：Wekenora（Tencent/WeKnora v0.8.3，源码实证）＋ Kimi Web 截图形态。

## 1. 设计目标（按 Owner 痛点对齐）

| 痛点 | 设计响应 |
|---|---|
| 中间单调、无过程感 | 答案卡上方加**过程折叠条**（Wekenora 同形）：折叠一行摘要，展开树状时间线——检索/调用/核验都在对话流里「长出来」 |
| 无加载中/思考中/调用中 | 阶段叙述 + 进行/完成态图标 + 完成统计行（本地计时，诚实标注） |
| 右侧过程看不懂 | 右栏改为**「引用与口径」辅助面板**（人话）；机器腔过程只留在折叠条展开态里，默认收起 |
| 引用不友好 | 引标 hover 切片预览（零请求）+ 点击开抽屉定位高亮 + 血缘卡回答「这数哪来的」 |

## 2. 信息架构（⚠️ 动架构，需 Owner 拍板）

现状：左 250 对话列表 / 中对话流 / 右 330 过程面板。方案二选一：

**方案 A · Wekenora 式内联（推荐）**
- 中栏每轮答案卡内：**过程折叠条 → notice 带 → 答案正文 → 血缘卡/追加面（折叠）→ 统计小字行**。
- 右栏改为**「引用与口径」**：与当前轮联动的引用列表（按来源分组）、血缘卡详情、追加面。点正文 `[n]` / 折叠条上的引用数 → 右栏定位高亮。
- 优点：对话流自包含，像 Wekenora/Kimi 截图；右栏从此有人话。
- 代价：动信息架构 → **需 Owner 确认是否同步 teach 仓原型**（AGENTS.md 第 0 条：本仓 web/ 是快照，真源在 teach-petro-agent/prototype/app）。

**方案 B · 保守增强**
- 不动三栏结构；只把右栏过程面板改人话（阶段化时间线+进行态），中栏补折叠条与血缘卡。
- 优点：不动架构、不需同步 teach；缺点：左右两栏都有过程信息，略重复。

> 推荐 A，但按纪律**先停在这里等 Owner 答复**再动工。

## 3. 答案卡内布局（自顶向下，方案 A）

```
┌ 用户问句 ──────────────────────────────┐
├ 🔍 检索完成 · 引用了 3 篇文档 · 11 步 · 2 次工具 · 38s ▾ │ ← 过程折叠条（展开=树状时间线）
├ ⚠ 黄条：这次回答只用到检索到的 24/67 条材料…            │ ← notice 带（分级）
├ 🧠 我理解为：问去年各井配产量…（灰折叠条）              │ ← understanding
├ 答案正文 Markdown…[1][3][7]                            │ ← AnswerView 保留
│   （引标 hover 出切片小卡，点击右栏定位高亮）             │
├ 📖 这数哪来的 · 查询口径（可展开）                      │ ← 血缘卡（supplement lineage / payload）
├ ⚖ 各来源说法不一 · 点开对照（split）／按来源列出（attribution）│ ← 追加面折叠
├ ✅ 已核验：有据 3 条 · 改写 0 条 · 分列 0 条             │ ← verdict 徽标行
├ run-f39e6707 · 档案已存档 40 KB                        │ ← blackbox 小字
└──────────────────────────────────────────┘
```

各展示位细则：

### 3.1 过程折叠条（新增，核心）
- **数据源**：step/tool/citation/observation 计数；排序按信封 id，工具挂到同 `data.seq` 的步下。
- **折叠态**一行：状态词（检索中/检索完成）· 引用数 · 步数 · 工具数 · 本地计时。进行中步名可给白话对（decision→正在分析问题 / discover→正在检索 / execute→正在取数 / verify→正在核验 / answer→正在作答），工具名映射（doc_retrieve→查文档库 / semantic_query→查指标台账 / data_query→取数 / faq_lookup→查常见问题 / table_schema→查表结构）。
- **展开态**：树状时间线（左竖线，antd `Timeline`），每步=图标+白话标题+状态（进行中 Spin/完成 ✓/失败 ✗）；C 级 notice 收进对应步下。
- **加载中**：提问→首帧期间折叠条以「正在分析问题…」占位，替代现在那颗孤 Spin。

### 3.2 答案正文（AnswerView 保留，两处增强）
- 保留 marked lexer→React 元素与 `[n]` 锚点。
- 新增：**引标 hover 预览**——antd `Popover` 受控实现，内容直查内存 `materials[index].content`（零请求，与 WeKnora 每次发请求不同）；无材料不弹。React 冒泡委托，不逐引标挂 handler。
- 历史轮 answer 含旧式块文本则原样渲染（不解析）， supplements 非 null 的新历史轮照常出引用。

### 3.3 引用抽屉（增强，方案 A 中为右栏面板）
- citation↔observation 配对保留；**按 `source` 去重分组**（Wekenora `mergeDocumentReferences` 同思路）；trust 白话徽标（权威台账/台账/报告/系统注记）。
- 点击定位高亮保留；无配对保留「材料未在回合内渲染」，**不虚构**。
- `trust=notice` 的条目按程序声明渲染，不伪装成文档。

### 3.4 血缘/查询口径卡（新增）
- 数据源优先级：① `observation.payload.lineage`（结构化键值，首选）；② `supplement{block:'lineage'}.text`（纯文本兜底）。
- 形态：可展开卡，五要素分行（口径/来源表/过滤条件/数据截至批次/收口注记）；`payload.limit.hit` 时加一行「结果超上限，只取了前 N 条」。
- 白话注解：卡头给一句「这里说明上面的数字从哪来、按什么口径算、数据更新到哪天」；五要素内工程腔（M-01 两步缝等）保持原样但在卡内小字折叠。
- 空态：无血缘（非数据题）不渲染该卡。

### 3.5 程序追加面（新增，次要位）
- `split`（各来源说法不一）与 `attribution`（按来源列出）渲染为答案卡下方**折叠区**，单条限高（如 6 行，展开看全文）——真机 split 单条可达 700+ 字。
- `citations` 块与引用抽屉同源，不重复占位，仅作历史轮/无抽屉场景的兜底。

### 3.6 notice 带（补全）
- 按调研 §3 三级映射实现；A 级 Alert、B 级灰折叠条、C 级默认收起（点开见原文）。
- C 级三型（unsupported_claim/contradiction_split/attribution_split）加白话摘要模板（如「核验时删去了 N 条没有依据的说法」），原文收起。
- 修现状 bug：notice 目前在答案卡和右栏重复渲染两遍——重设计只出一次。

### 3.7 过程面板右栏（方案 B 才保留）/ blackbox 小字
- blackbox 小字行：run 号、步数/材料数（counts）、档案 KB；时长本地计时并标注「本地计时」。
- verdict(verify) 徽标行：有据/改写/分列计数；`cited[]` 用于给引标打「已核验」小角标。

### 3.8 历史轮降级
- 新历史轮（supplements 有值）：血缘卡/追加面可渲染；引用列表 supplements.citations 兜底。
- 旧历史轮（supplements=null）：正文 + 灰字「本轮为旧版记录，无引用/口径明细」；`[n]` 保持纯文本。

## 4. 与 WeKnora 的对照（能抄/不能抄）

| Weknora 交互 | 我方决策 |
|---|---|
| 折叠条一行摘要↔展开树状时间线 | ✅ 照搬形态（antd Timeline） |
| 引标 hover 切片 popover | ✅ 做，但零请求（内容已在内存） |
| 点引标→打开原文全文+定位高亮 | ❌ 短期做不了：无切片→原文位置锚点接口（`source_id` 形如 f4/ensum-hex 前端无法解析）。降级=右栏定位到切片卡。已记后端需求 |
| 全部引用侧栏+拖拽调宽 | ✅ 做列表态（宽度固定即可，拖拽调宽可后置） |
| 思考条完成自动折叠 | ✅ 照搬（Kimi 同形） |
| 统计行权威耗时 | ⚠️ 后端无耗时字段，本地计时并标注 |
| 原文多格式渲染器 | ❌ 量级不匹配，不做 |
| 事件委托引标交互 | ✅ React 冒泡委托等价实现 |
