### `parse_understanding`（L439-L469）｜understand 应答两级宽容解析（先两行式、再 JSON 降级）

- 消费：无 state 字段（参数 content 为模型应答原文）。
- 调用：caller=understand_node（L1610）；输入＝understand 模型应答全文（两行式「理解：／指标候选：」或 JSON 裸产/围栏产/散文包裹产）；失败＝返回 ("", []) 空值，不抛异常、不产拒因（下游照走决策轮）；零额外模型调用。
- 分支表（逐行扫描，非 elif 链，两分支可同时命中不同行）：
  1. 行 strip 后以 `_CANDIDATE_LINE`（"指标候选"）开头 → 冒号（中文冒号优先，无则英文冒号，两者都无则整行）后内容按 `[、,，]` 切分、去空白、丢弃空串与"无"→ 覆盖 candidates（后者覆盖前者）。
  2. 行以"理解"开头且未命中上一分支 → 中文冒号优先、无则英文冒号、两者都无则整行 → 覆盖 understanding（后者覆盖前者）。
  3. `understanding or candidates` 任一非空 → 直接返回两行式结果（不再走 JSON 降级）。
  4. 两者皆空 → `extract_plan_json(content)` 提取首个平衡 {} 块。
  5. 提取结果为 dict → 逐 `_UNDERSTANDING_JSON_KEYS`（"理解"/"understanding"）取首个真值键作 understanding；逐 `_CANDIDATES_JSON_KEYS`（"指标候选"/"metric_candidates"）取首个存在键，经 `_json_candidates` 归一。
  6. 提取结果为 None/非 dict → 跳过降级。
  7. 两级全空 → 返回 ("", []) 如实上报。
- 副作用：无。
- 返回：tuple[str, list[str]]——(understanding, metric_candidates)。
- 规则条目：
  - R-A1-16 两行合同式（行首"理解"/"指标候选"）优先；两行全缺才降级 JSON 子串提取（裸产/围栏产/散文包裹产同路，共用 extract_plan_json 平衡块单点）。
  - R-A1-17 降级形逐合同键取值（中文主键在前、英文别名在后）、缺键不编造；候选值统一经 `_json_candidates` 归一。
  - R-A1-18 两级全空＝("", []) 如实上报，不判非法、不产拒因——下游照走决策轮。
- 耦合：`appv2.runtime.subtask.extract_plan_json`、标准库 `re`。
- 疑点：
  - D-A1-08 冒号回退在无冒号时取整行：单独一行"指标候选"→ 候选值为 ["指标候选"]；单独一行"理解"→ understanding＝"理解"（前缀词本身被当值）。
  - D-A1-09 同类行多次出现时后者静默覆盖前者（逐行覆盖语义），先出现的行内容被丢弃，代码无注释说明。

### `parse_decision`（L574-L665）｜决策应答解析＋schema 校验（拒因回喂、无 repair）

- 消费：参数 content（决策模型应答原文）、max_discovers（默认＝`MAX_DISCOVERS_PER_ROUND_CONTRACT`＝2）、max_executes（默认＝`MAX_EXECUTES_PER_ROUND_CONTRACT`＝2）；调用方 decision_node 以 state.budget 覆盖后传入（L1684-1693、L1729-1731）。
- 调用：caller=decision_node（L1728-1732，经 `_parse_with_quote_repair` 包裹）；输入＝模型应答 JSON（裸产/围栏产/散文包裹产同路）；失败＝返回 str 拒因，由节点写入 decision_error 回喂重决策（轮照耗、无 repair 桶）。
- 分支表（穷尽）：
  1. `extract_plan_json(content)` 返回 None → 返回 `json_syntax_feedback(content, 兜底句)`（V2-57 带 JSON 定位的拒因）。
  2. `action not in ACTION_KINDS` → 返回拒因（action 缺失或越界，四种合法值列出）。
  3. action == ACTION_DISCOVER：
     3a. discovers 非 list 或空数组 → 拒因（须非空数组 1~2 支）。
     3b. 支数 > max_discovers → 拒因（超出轮内上限）。
     3c. 逐支：非 dict 或缺 "tool" 键 → 拒因。
     3d. 逐支：tool 名不在 DISCOVER_TOOLS 三值闭世界 → 拒因（未知发现工具）。
     3e. 逐支：`raw.get("args") or {}` 结果非 dict → 拒因（args 须对象）；None/缺省/假值归一空 dict 放行。
     3f. 全支合法 → `replace(emission, discovers=tuple(items))` 返回。
  4. action == ACTION_EXECUTE：
     4a. task_type 不在 TASK_KINDS 三值 → 拒因。
     4b. task_type 为 data 或 mixed 且 plan 非 dict → 拒因（缺 plan 对象）。
     4c. 同上且 `plan["metric_slot"]` 去空白后为空 → 拒因（metric_slot 必填非空）。
     4d. task_type 为 knowledge 或 mixed 且 retrieval_need 非 dict → 拒因（缺 retrieval_need 对象）。
     4e. 同上且 `retrieval_need["question"]` 去空白后为空 → 拒因（question 必填非空）。
     4f. executes＝2（mixed）或 1（data/knowledge） > max_executes → 拒因（文案固定写 task_type=mixed 超上限）。
     4g. 全过 → `replace` 定型 task_type/plan/retrieval_need（plan/need 各做 `dict(...)` 浅拷贝）返回。
  5. action == ACTION_ASK：
     5a. payload["ask"] 非 dict → 拒因（缺 ask 对象）。
     5b. options 非 list → 归一为 []；是 list → 逐项 str 化、strip、丢弃空串。
     5c. prompt 去空白后为空 → 拒因（ask 缺 prompt）。
     5d. options 个数不在 2~4 → 拒因（缺 options 或个数越界）。
     5e. 全过 → `replace(emission, ask_prompt=prompt, ask_options=tuple(options))` 返回。
  6. action == ACTION_FINALIZE → 直通返回 emission（零附加载荷，不校验 FINALIZE 约定载荷不存在）。
  7. 其余键（thought/note 之外的未知键）在所有分支都被静默忽略，不进 emission。
- 副作用：无（纯解析；step/notice/回喂由调用方产生）。
- 返回：DecisionEmission（合法）或 str（拒因文本）。
- 规则条目：
  - R-A1-29 JSON 不可解析 → 带定位的拒因（json_syntax_feedback），无自动 repair、拒因回喂 LLM 重决策。
  - R-A1-30 action 四值闭世界校验（discover/execute/ask/finalize）；越界或缺失即拒。
  - R-A1-31 discover 配方校验：非空数组、≤max_discovers 支、每支 dict 含 tool、工具名 ∈ {semantic_query, table_schema, faq_lookup}、args 须对象（假值归一空对象）。
  - R-A1-32 execute 配方校验：task_type 三值闭世界；data|mixed 须 plan 对象且 metric_slot 非空；knowledge|mixed 须 retrieval_need 对象且 question 非空。
  - R-A1-33 execute 轮内主执行上限：mixed 计 2 支、其余计 1 支，超 max_executes 拒。
  - R-A1-34 ask 配方校验：ask 须对象、prompt 非空、options 个数 2~4（非 list 归一空集后按个数拒）。
  - R-A1-35 finalize 零附加载荷直过。
  - R-A1-36 校验边界＝结构与闭世界；plan 深形字段细节不在此校验，归工具层 args_schema（bad_args 同路回喂——两道闸一个去处）。
- 耦合：`appv2.runtime.subtask.extract_plan_json`、`appv2.runtime.subtask.json_syntax_feedback`、`appv2.runtime.budget.MAX_DISCOVERS_PER_ROUND_CONTRACT`、`appv2.runtime.budget.MAX_EXECUTES_PER_ROUND_CONTRACT`、`appv2.tools.SEMANTIC_QUERY`/`SCHEMA_PROBE`/`FAQ_LOOKUP`（经 DISCOVER_TOOLS）、标准库 `dataclasses.replace`。
- 疑点：
  - D-A1-14 `executes = 2 if task_type == TASK_MIXED else 1` 以常量 2 代表 mixed 支数，拒因文案硬编码「task_type=mixed 超出轮内主执行上限」——当 max_executes ≤0 时 data/knowledge 也会被拒而文案仍指 mixed。
  - D-A1-15 发射中 action 之外的未知键无严格模式——多余键静默忽略，无拒因、无日志。
  - D-A1-16 `raw.get("args") or {}` 以真假值归一：args 为 0/""/[]/None 一律归一空对象放行（非 dict 但真值才拒），该宽容语义注释未说明。
  - D-A1-17 thought/note 用 `str(... or "")` 强转——dict/list 等非字符串值被字符串化后静默进入发射，无类型拒。
  - D-A1-18 max_discovers/max_executes 由调用方从 state.budget 覆盖——本函数默认值（契约常量）与 run 级预算（≤10 发现）不同闸，两级上限关系仅在注释中叙述。
