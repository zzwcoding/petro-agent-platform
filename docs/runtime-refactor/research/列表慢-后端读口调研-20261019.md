# 对话列表「后端读口」调研（列表慢 · 2026-10-19）

范围＝`GET /api/v2/chat/runs`（`appv2/api/chat.py:189 list_runs`）及其 persistence 读口。
纪律＝只读；未起服务、未跑 git。本文所有行号现场 `read`／`grep` 核对；实测数字见 §1。

## 0. 结论速览

- **根因一句话**：列表读口**行集与行投影都不按 limit 收敛**——对注册表里**每一个** run 调一次
  `store.run()` 之后才 `[:limit]`（`appv2/api/chat.py:202-206`），行投影 `RunListItem` 又随行带
  全文 `answer`（`:156`）；V2-136 换源后这一层会变成「**全表读＋全行投影＋Python 排序**」
  （`scan_all`，设计文档 §七-3 已登记），limit 依旧一次读都不省。
- **今天能实测到的**：生产挂内存件（`appv2/api/app.py:409` ＋ `persistence/tables.py:163`），
  2055 行全量读实测 **7.5 ms**——**后端读口在现网 13 行量级下不足以解释「很慢」**（§1 末条）。
- **推荐**：不新开「换源」票（V2-136 已覆盖）；新票只做 **limit 下推 ＋（可选）列表项瘦身**；
  更省的做法是把 limit 下推**并入尚未开工的 V2-136**（见 §6）。

## 2. 现状与成本（逐条 file:line）

### 2.1 读口实现／单次成本／可否按 limit 批量／现成列表口

- **实现**：`RunStore.run()` ＝ `appv2/runtimev2/persistence/store.py:164-167`，底层
  `self._tables.get(TABLE_RUN, (run_id,))`（`:166`）＋`_run_record_of`（`:261-274`）。
- **底层是什么**：`Tables` 端口（`persistence/tables.py:72-89`）——**今天生产是内存件**：
  `appv2/api/app.py:409` 逐字 `    store = RunStore()`（未传 tables）→ `store.py:75`
  `current_tables()` → `tables.py:163` 逐字 `_DEFAULT_TABLES: Tables = MemoryTables()`；
  全仓 `configure_tables(...)` 调用点**只有 tests/**（如 `tests/api/test_v2_asks.py:134`）。
  ⇒ **今天 `store.run()`＝进程内 dict 取行＋`deepcopy`（`tables.py:130-132`），非 PG、非文件**。
- **单次成本**：2055 行全量循环 7.5 ms ⇒ ≈ **3.6 µs/行**（内存件）；行体越大越贵（deepcopy 全文 answer）。
- **可否按 limit 批量**：**不能**。端口只有 `get`（主键取一行）／`scan`（列等值全扫）／
  （V2-135 将加）`scan_all`（全表）；**无任何带 limit/order 的读口**，limit 只能在 api 层截断。
- **现成列表读口**：**有，但 V2 不可用**——`appv2/runtime/store.py:156-164` `RunStore.list_runs(limit)`
  （SQLAlchemy `order_by(created_at.desc()).limit(limit)`）属**旧 runtime**；R5 闸明禁
  `appv2.runtimev2 → appv2.runtime`（`tools/importlinter_v2.toml:92-96`）。V2 侧**无** `recent_runs`。

### 2.2 表／索引现状

- run 记录落 `agent_v2_run`（`persistence/tables.py:24`）；DDL 真源＝迁移
  `migrations/versions/20261009_0022_agent_v2_runtime.py:28-40`（run_id PK／question／actor／status／
  answer／error／manifest_digest／created_at／updated_at）；后续加列：`20261013_0025`（followup_of）、
  `20261017_0026`／`_0027`（supplements＋server_default）。
- **`agent_v2_run.created_at` 无索引**：0022 只建了 `ix_agent_v2_step_run_id`（`:52`）；全仓
  `create_index` 命中 `agent_v2_run` 的**零处**（0025/0026/0027 均无）。
  ⇒ 一旦改成 SQL 侧 `ORDER BY created_at DESC LIMIT n`，PG 走 seq scan＋top-N sort（2055 行无感；
  上量后需索引，见 §6 步 2）。
- `agent_v2_blob` 表在 PG **不存在**（R-3，设计文档 §1.2）——V2-135 迁移 0028 补。

### 2.3 注册表语义

- `RunStreamRegistry.run_ids()` ＝ `appv2/api/bridge.py:142-145`，返回 `list(self._streams)`——
  **本进程内存**的 run 号（`bridge.py:124-135`，`_streams: dict[str, RunStream]`）。
- **重启后为空**：`_streams` 只活在进程内（模块 docstring `bridge.py:27-29` 自陈跨进程归 ADR-0003），
  且**只登记本进程服务过的 run**——持久库中非本进程服务过的历史 run 永远不进列表。
- 与「最近任务」语义的差距：列表**行集**＝进程生命周期×本进程，而**语义**要的是库内全量最近 N 条。
  另注：`_streams` **无淘汰**（`bridge.py:130-135` 只增不删），每个 run 的 `_frames` 全量驻留
  （`bridge.py:62`）——该注册表本身是不封顶的内存累积面（第二序问题，归属 ADR-0003）。

## 6. 推荐实施方案（分步、可独立收票）

- **步 1（推荐：并入 V2-136，不新开票）**：V2-136 尚未开工（票面「状态: 待开工」），其 `list_runs`
  实现（`V2-136 §2.1`）现在是 `scan_all`＋内存排序＋`[:limit]`——**把这一处改成端口侧 limit 下推**
  （同票内落地 `scan_recent`／等价口＋`PgTables` 的 `ORDER BY created_at DESC LIMIT n`）。理由：
  ①改动面最小（该票本来就要动 `tables.py`／`pg_tables.py`／`store.py`）；②避免 V2-135/136 先落一版
  「全表读」再由第三票返工；③票面新增验收判据「PG 侧只取 limit 行」可机检。
  **须先与 V2-135/136 窗口对账**（同批改同一文件，防撞车）。
- **步 2（同批或紧随）**：迁移加 `agent_v2_run(created_at DESC)` 索引（0029）——步 1 的 SQL 排序要它才
  长期不退化；2055 行实测无感，但这是步 1 的配套，晚做＝返工一次迁移。
- **步 3（另票，前端）**：真分页（案 c）替换「扩大 limit 重拉全量」——须 Owner 重裁
  `specs/frontend-redesign.md:119` 的「零按钮零提示／扩大 limit」既定交互；**不要**与步 1 混票。
- **步 4（另票，需 Owner 裁 wire）**：案 b 列表项瘦身——收益大（wire −87%）但破 `specs/agent-loop.md:78`
  与 `specs/modules.md:663`，且要详情读口补 answer；**建议先做步 1/2**（把读口成本压到 O(limit) 后，
  wire 体积才成为主项）。
- **不做**：给左栏加 loading 提示（回退 Owner 打磨批⑦ 决定，见 §2.5）。

## 7. 证据不足项

1. **云端「很慢」当次耗时分布未取到**：现网 13 行、后端为内存件，实测后端读口量级 <1 ms（2055 行也仅
   7.5 ms）——**不足以解释「很慢」**。可复现的慢成分指向：①点开一链 N 次顺序 `getRunV2`
   （`A1V2R.jsx:376-378`，每次带全部 steps＋payload）；②前端 5 次全量重拉；③进程长跑后注册表
   **无淘汰**导致的内存累积（`bridge.py:62,130-135`）。需一次真机网络面板／后端耗时日志取样才能定权重。
2. **PG 侧 `scan_all` 的真实传输耗时未测**：`PgTables` 尚未实现（V2-135 待开工），无法实测「2055 行全表
   经 `_run_sync` 取回」的墙钟与传输量；本文 7 MB 系按行体字节推算（2055×3.39 KB）。
3. **前端 `updated_at` 无消费点**：grep 未命中，但可能经解构／透传间接使用——未做全仓 AST 核对。
4. **`RunStream` 帧缓冲的驻留字节未测**：`bridge.py:62` 无淘汰属实，但实际驻留量取决于帧 payload
   （citation/observation），本次未取样。
5. **V2-135/136 的最终措辞可能已变**：两票为「待开工」伪代码稿、设计文档为未跟踪件（另一窗口在写）——
   本文按其 2026-10-19 现值判读，开工前应复核一次。
