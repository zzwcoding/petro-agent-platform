## 一、一句话结论

**业界已经收敛到一条主线：把「确定性编排（状态机/流水线 + 阶段门禁）」当骨架，把「模型判断」只放在它必须待的地方（理解、分类、起草），路由只回答「该走哪个入口」而绝不回答「结果对不对」；入口安全必须做成确定性策略（只读不变量落数据层、指令与数据分离），词面/模型护栏只当补充信号；多轮一律靠「外置状态 + 会话标识」承接，不靠对话历史自己记住。** 对本仓（只读、单租户、无写操作的问答平台）而言：编排骨架、路由分权、只读不变量、会话外置四条**高度适用**；自主循环、多租户配额、写操作补偿那一套**不适用**。

## 二、主题① 流程编排（线性流水线 vs 自主循环；状态机；阶段门禁）

### 2.1 业界主流做法

1. **默认确定性编排、按需才升级自主。** Anthropic《Building Effective Agents》给的顺序是：先优化单次调用 → 需要多步就用工作流（预定义代码路径）→ 只有当步骤无法预先确定时才用自主 Agent；「Agent 系统通常用延迟和成本换任务性能，要谨慎权衡」。来源：https://www.anthropic.com/engineering/building-effective-agents
2. **骨架是「稳定内核 + 可插拔能力」，不是越复杂越好。** Loop 最小可抽象为五阶段 Prepare→Model→Act→Observe→Verify；每加压缩/计划/权限/路由能力都在生命周期点挂钩子，不在内核里塞条件分支。来源：技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md（4.1.1、4.5.1）
3. **把「计划/待办」变成外部控制对象，并做阶段门禁。** 三档控制：轻量 Todo / Plan Mode（只读探索→写计划→人工确认→执行）/ Planner-Executor；阶段门禁要回答「输出是什么、证据在哪里、谁来确认」。来源：同上（4.2.1、4.2.2）
4. **状态机是显式外置的。** 任务状态集合（CREATED/RUNNING/WAITING_INPUT/WAITING_APPROVAL/WAITING_EVENT/PAUSED/VERIFYING/COMPLETED/FAILED/CANCELLED）必须机读；「WAITING 不是失败、PAUSED 不是结束」。来源：技术书籍/ai-agent-handbook/06_第 4 章…（4.1.2）；异步版状态机（waiting/queued/running/hold/succeeded/failed/killed/skipped/mark_successed）见技术书籍/ai-agent-handbook/13_第 10 章 Agent 异步任务与自动化流程.md（10.2.3.3）
5. **图编排把「确定性步骤」和「模型驱动的步骤」混在同一张图里。** LangGraph 定位是低层编排运行时，可「mix deterministic, hand-coded steps with LLM-driven agentic steps in the same graph」，并对每步状态做持久化与恢复。来源：https://docs.langchain.com/oss/python/langgraph/overview
6. **「完成」由证据决定，不由模型自述。** 模型只能「申请完成」，Harness 才能「提交完成」；验证强度分级：结构→环境→确定性→独立模型→人工。来源：技术书籍/ai-agent-handbook/06_第 4 章…（4.6.2）
7. **子 Agent / 隔离是「用隔离代替压缩」。** 大范围探索交给子 Agent，只回传几百 token 的结论摘要，主上下文不被中间过程污染。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md（「隔离优于压缩」小节）
8. **Graph 工程把节点/边/状态显式化是新近共识。** 「节点承担能力、边规定路由与依赖、结构化状态沿边传递并在关键边界持久化」；LangGraph / Microsoft Agent Framework / Google ADK 官方文档分别叫图编排或 graph-based workflow。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（第 333-335 行脚注）

### 2.2 分歧 / 取舍

- **「先简单」vs「高代价场景必须硬编排」。** Anthropic 与 ai-agent-book 都讲「先最小方案」，但前提是任务可接受失败重试；对本仓这种「编造直达用户」代价高的场景，**骨架必须确定性**，模型只填空。
- **工作流 vs 自主循环的分界线是「路径能不能预先写出」。** 能写就写死（阶段门禁、可测）；写不出（开放式研究）才给循环。本仓 9 段路径已知，天然偏工作流一侧。
- **单 Agent 流水线 vs 多子 Agent。** 只有当「上下文隔离、能力/权限隔离、可并行」三者收益超过通信与合并成本时，委派才划算（技术书籍/ai-agent-handbook/06_第 4 章… 4.3.1）。本仓只有第 ⑥ 段批量执行、第 ③ 段探查天然可并行。
- **状态机粒度。** 细到每步（可恢复、可观测）还是粗到每相位（开销小）：HandBook 主张「状态外置 + Checkpoint 含恢复所需关键状态」（当前阶段、已完成/未完成步骤、工具结果引用、等待条件、状态版本），本仓 RunState 53 字段（见 runtime-refactor/synth/S5-RunState字段矩阵.md）正对标此清单。

### 2.3 反例 / 踩坑

- **滑动窗口砍历史 → 丢工具结果 → 反复重试死循环**：窗口把第 2 轮拿到的关键工具结果滑出后，模型「忘」了已获得，会反复执行同一工具。来源：技术书籍/ai-agent-book/…/book/chapter2.md（「常见的错误上下文管理模式」）
- **动态系统提示词（如把时间戳塞进 system）破坏前缀缓存**：首 token 延迟 0.5s→3-5s、账单翻倍。来源：同上（KV Cache 一节）
- **把「模型自述完成」当完成**：任务「看起来完成」但结果不可信；Verifier 必须返回结构化缺口而不是一句结束。来源：技术书籍/ai-agent-handbook/06_第 4 章…（4.6.2）
- **自动降级改变业务契约**：降级模型协议层能返回工具调用，但多步任务丢中间约束，产生「结构合法却结果错误」的执行。来源：技术书籍/ai-agent-handbook/03_第 2 章 Agentic Application 参考架构.md（2.2.1）

## 三、主题② 路由 / 意图判定（一句话该不该走完整流程；模型判断 vs 程序闸；默认倾向）

### 3.1 业界主流做法

1. **路由层只判「该用哪个入口/能力」，不判「结果对不对」。** 明确把路由与结果判定分权；目录能力标签只提供候选集合，仍需校验版本、授权、环境。来源：技术书籍/ai-agent-handbook/12_第 9 章 AI 网关与统一流量治理.md（9.4.3）
2. **经典路由 = 先分类、再分派给专门路径。** 「Routing classifies an input and directs it to a specialized followup task」，适用于类别清晰、分类可靠的任务；可用小模型处理常见问题、大模型处理少见问题。来源：https://www.anthropic.com/engineering/building-effective-agents
3. **「模型出结构化决策 + 代码执行路由」是主流落法。** LangGraph：结构化输出的模型「chooses the route」，由代码 dispatch 边把它送过去。来源：https://docs.langchain.com/oss/python/langgraph/workflows-agents
4. **coordinator（协调者）模式把「意图分类→动态分派」制度化。** 中央协调者分解请求、把子任务分给专门 Agent；「use of an AI model to orchestrate and dynamically route tasks」。来源：https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system
5. **先单 Agent、撑不住再拆。** 判据是「prompt 条件分支太多」或「工具名/描述重叠」；OpenAI 建议先把工具名/描述写清楚再考虑多 Agent；超过 15 个不同工具、或少于 10 个但重叠的工具都会让单 Agent 吃力。来源：https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf
6. **开源实现两派并存。** Dify 的 Question Classifier 节点用 LLM 按语义把输入分到用户自定义的类，每个类连下游分支（模型分类派）；来源：https://docs.dify.ai/en/guides/workflow/node/question-classifier 。WeKnora 则把工具收敛为「四只读工具：search / read document / ask / list knowledge bases」，并支持 MCP 工具逐个审批（能力白名单派）。来源：https://github.com/Tencent/WeKnora
7. **混合路由：语义判断帮理解，确定性规则做约束、执行和留痕。** 「模型可以参与理解任务内容、给出候选成员建议，但最终选择还要校验团队边界、权限、数据范围…更实际的方向是混合路由」。来源：技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md（11.6.5）
8. **语义层「显式锚定优先的检索瀑布」可当路由的升级版。** S0 固定边界→S1 显式锚定（@Entity/@Metric/Stable ID）→S6 资格与歧义（过滤/重排/拒答）——逐级升级、可早停，而不是全库向量搜。来源：资料/data - AI - 演讲/已完成/从业务本体到持续进化.知识.md（S0–S8）

### 3.2 分歧 / 取舍

- **模型分类器 vs 确定性词面闸。** 模型派（Dify、Anthropic 路由）泛化好但「同类问句结果天差地别」正是本仓已知病灶；词面派（本仓 N0/N1、字节 SOUL.md 边界条款）稳定可测但会误伤正常问句。业界共识落在**混合路由**：模型负责理解与候选，确定性规则负责约束与执行。
- **默认倾向：该不该走完整流程。** Anthropic 的默认是「先单次调用，不行再加」，倾向「能简单就简单」；但本仓「直答免核验」正是编造直达用户的病灶，**默认倾向应反过来——业务类问句默认走完整流程，直答只做确定性可判的窄口**（如纯寒暄、台账已锚定的定义问）。这条是本仓与通用建议的显式分歧点。
- **分类本身也有成本与错误。** 「分类错误会改变输出质量，分类本身也有成本」（技术书籍/ai-agent-handbook/12_第 9 章… 9.2.3）。语义路由要有明确回退路径。

### 3.3 反例 / 踩坑

- **把路由和结果判定混在一处。** 「路由层只判该用哪个入口，不判执行结果」被 llama 写进结论，混了就没有干净的核验层。
- **能力可见 = 有权执行。** 「一个工具出现在清单中，只说明它被服务端通告」；`tools/list` 过滤只能减少误选，`tools/call` 必须再鉴权。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.3.1、9.3.5）
- **开放任务才给自主循环**：把可预判路径也交给模型自决，会同时放大成本与复合错误（技术书籍/ai-agent-book/…/book/chapter1.md 编排模式一节）。

## 四、主题③ 入口安全拦截（只读不变量；注入/越权；区分「指令与数据」）

### 4.1 业界主流做法

1. **核心一条：区分指令与数据。** 网页、邮件、文档、MCP Server、工具结果、远程 Agent 返回都属于不可信输入，不得改变平台政策、授权范围或当前工具集；Harness 应保留内容来源，限制外部文本进入高优先级指令层。来源：技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md（6.4.4）
2. **「致命三件套」：私数据 + 不可信内容 + 对外通信，三者同现即可被利用。** LLM「无法可靠地区分指令的重要性基于来源」，所以「告诉模型别听」不可靠；一旦摄入不可信输入，就必须让「该输入不可能触发任何有后果的动作」。安全边界靠**能力限制**（只读、无外发）拿掉其中一条腿。来源：https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/
3. **护栏分层、按「被绕过的难度」排：上下文层 → 执行层 → 数据层。** 越靠下越不依赖模型判断：数据层靠数据库行级安全、只读视图、约束校验器，「即使提示注入得手、代码漏写权限判断，越权仍会在数据层被拒绝」。来源：技术书籍/ai-agent-book/…/book/chapter1.md（护栏与安全性一节）
4. **护栏是补充信号，不是唯一边界。** 可编码的权限/资源限制用 Policy + Sandbox；模型/分类器只识别语义风险并作为额外信号。来源：技术书籍/ai-agent-handbook/08_第 6 章…（6.4.4）
5. **工具风险分级（低/中/高）驱动处置。** OpenAI 用「read-only vs write access, reversibility, required account permissions, financial impact」评级，高风险函数执行前暂停检查或转人工。来源：https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf
6. **ADK：把「只读」落成工具侧的确定性约束，而非提示词。** 工具以 Agent/服务账号运行、权限由外部授权；「With read-only permissions to a resource, the tool is prohibited from performing write actions」；工具用确定性 Tool Context（而非模型给的参数）强制「SELECT-only / 允许表白名单」；before-tool callback 可在执行前按状态/参数拦截。来源：https://adk.dev/safety/
7. **护栏工程化：输入/输出/工具三类护栏 + 断路器（tripwire）。** 输入护栏并行跑、失败 fast-fail；工具护栏包住每次调用（执行前查输入、执行后查输出）；触发 tripwire 直接停。来源：https://openai.github.io/openai-agents-python/guardrails/
8. **企业级身份链「人 → Agent → 能力 → 行为 → 资源」与只读场景的准入。** 只读查询型内部系统可推荐允许，但「仅开放 GET/查询类 API」「配置最小权限身份」「Skills 中避免返回超出需要的字段」；网络默认拒绝、按需开白。来源：资料/字节安全白皮书.md（7.2 关键安全能力、7.2.2 网络边界管控）
9. **只读 SQL 不能靠字符串前缀判断。** 「使用字符串前缀判断『只读 SQL』并不可靠，应结合受限数据库账户、受支持的查询接口与资源端权限」。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.3.7）
10. **注入面随能力增长而扩大：Skill 也是注入面。** 「Skill 的本质是把外部内容当作指令加载」，第三方 Skill 要像审代码一样审。来源：技术书籍/ai-agent-book/…/book/chapter2.md（提示注入一节）

### 4.2 分歧 / 取舍

- **词面闸/模型闸 vs 确定性策略。** 词面闸便宜、可测、可解释，但**必然误伤**（正常问句里出现敏感词共现即命中）；模型闸泛化但不确定；真正的兜底是**确定性策略 + 数据层只读**。三者的正确分工应是：数据层只读做兜底（硬约束），策略/权限做判定，词面或模型护栏只做廉价预筛与提示。
- **无豁免 vs 有豁免。** 本仓现状：N1 禁用词闸有「元问/引用形」豁免通道，而 N0 注入/外发/写意图三族**无豁免分支**（runtime-refactor/recon/B2-档案渲染与安全闸族.md，疑点 D-B2-01）——这正是「安全闸误伤正常问句」的机制来源。业界（ADK、HandBook）都主张「先窄后宽、给合法例外留通道」。
- **「只读」用提示词声明 vs 用数据层强制。** 字节白皮书用 SOUL.md 条款（提示词）；HandBook/ADK/Simon Willison 都指出提示词不可靠，硬约束要落到数据层与工具权限。**两派不冲突：提示词做第一道，数据层做最后一道。**

### 4.3 反例 / 踩坑

- **护栏拦截率当作安全边界。** 「声称拦住 95% 的攻击」在 Web 安全里是「very much a failing grade」。来源：https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/
- **把工具结果混进 user 消息。** 等于亲手抹掉模型辨别来源的标记，注入防护从源头失效。来源：技术书籍/ai-agent-book/…/book/chapter2.md（指令与数据分离一节）
- **状态栏/记忆投毒。** 状态摘要若来自可被外部污染的数据源，其高信任度会被反向利用。来源：同上（提示注入一节）
- **审批超时自动降级为只读执行**：会改变原始请求含义、可能造成意外数据暴露；超时/撤销应保持未执行，不自动降级。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.5.4）
- **只读靠前缀词判断**（见上 4.1-9）——本仓 N0 写意图族正是「动词×对象词面共现」式判定，同类风险。
- **SSRF 出口不收敛**：REST-to-MCP 模板会因可变主机/路径变成 SSRF 入口；WeKnora 用「SSRF-safe 出站 + 白名单模式」处理。来源：https://github.com/Tencent/WeKnora

## 五、主题⑨ 多轮对话与追问（会话承接；上下文如何进对话）

### 5.1 业界主流做法

1. **会话承接靠外置状态，不靠对话历史。** LangGraph：Checkpointer 做「thread-scoped 短期记忆」（对话连续性、HITL、断点恢复、容错），Store 做「跨 thread 长期记忆」；`thread_id` 传进 config 即绑定一个会话，同一 thread 跨轮承载状态并支持中断/暂停恢复。来源：https://docs.langchain.com/oss/python/langgraph/persistence
2. **状态与对话历史分家。** 「消息历史记录了模型和用户曾经交换的内容，却不应成为任务状态的唯一来源」；Task 跨 Session 续跑需显式装载授权 Task State，不默认两个 Session 共享上下文。来源：技术书籍/ai-agent-handbook/06_第 4 章…（4.1.2）、13_第 10 章…（10.1.1）
3. **多轮 = 每次调用把完整消息列表送回去（无状态 API）。** 追加而非改写；「对话链只追加不改写」是缓存与可审计的前提。来源：技术书籍/ai-agent-book/…/book/chapter2.md（多轮交互一节）
4. **追问/HITL 有两种承载：interrupt 挂起 与 工作流人工节点。** LangGraph 用 interrupts「inspect and modify agent state at any point」；HandBook 用调度器暂停 Task + 外部审批回调（事件载荷含 Task ID、审批版本、决策结论，接收方重投前校验未过期/未重复/与当前状态兼容）。来源：https://docs.langchain.com/oss/python/langgraph/overview ；技术书籍/ai-agent-handbook/13_第 10 章…（10.2.5）
5. **澄清要「只在歧义实质改变交付时才问」，且要封顶。** 「只有歧义会实质改变交付内容、责任或执行边界时，才需要进一步澄清」；多轮澄清要有上限与停止条件（避免机械确认与无限追问）。来源：技术书籍/ai-agent-handbook/14_第 11章…（11.4.1）；本仓已有 `CLARIFY_ASK_CAP_CONTRACT=6` 连续澄清封顶（runtime-refactor/recon/E1-澄清节点.md，R-E1-18）
6. **交接用「最小充分共享」，不是共享一切。** Handoff 只传四类：目标 / 已确认事实 / 待处理事项 / 可用引用；完整搜索过程与未验证中间推理不原样传。来源：技术书籍/ai-agent-handbook/14_第 11章…（11.5.1、11.5.5）
7. **长对话压缩要有纪律，且不破坏前缀。** 压缩发生在两次调用之间、只压工具结果；分层压缩（工具结果预算→噪声删除→API 层微压缩→归档式摘要→全量压缩，全量带熔断器）；「保留决策、约束、失败与来源」。来源：技术书籍/ai-agent-book/…/book/chapter2.md（上下文压缩策略、生产级分层压缩机制）
8. **压缩/恢复之外还有「结构化笔记」外置。** 「Agent regularly writes notes persisted to memory outside of the context window」，或维护 Task State/Artifact 作为「当前事实」。来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents ；技术书籍/ai-agent-handbook/14_第 11章…（11.5.3）
9. **开源实现的会话能力可对照。** WeKnora 支持「append requirements to a running turn, fork from any earlier question, rewind in place with sandbox checkpoints」及跨会话长期记忆、上下文压缩、prompt-cache 标记。来源：https://github.com/Tencent/WeKnora

### 5.2 分歧 / 取舍

- **上下文进对话的方式：整链回灌 vs 有界摘要。** 整链回灌缓存友好、可复核，但会膨胀；有界摘要省 token 但「有损投影」，只保留「预想会被问到的维度」，一旦问到没算过的维度就断崖式失准（技术书籍/ai-agent-book/…/book/chapter2.md，状态栏维护两点注意）。本仓现有「过程档案摘要 ≤400 字 + 截断必披露」是折中（runtime-refactor/recon/B2…，R-B2-02/03）。
- **澄清靠 interrupt 挂起 vs 一次性问满。** 挂起（本仓 ask 帧 + pending_ask）资源可控但要处理恢复时序；HandBook 也警告审批/追问回传必须校验版本与时效。
- **会话边界定义。** Session 与 Task 不要求一一对应；把「一个 IM 线程 = 一个 Task」写死会在跨入口时出问题（技术书籍/ai-agent-handbook/08_第 6 章… 6.5.2）。

### 5.3 反例 / 踩坑

- **滑动窗口导致「忘记已获取的信息」并死循环**（同 2.3 第一条）。
- **把用户新要求直接追加到长历史末尾**：可能无法覆盖已进入执行队列的旧计划；Steering 应表示为高优先级任务事件，由状态机在安全点处理。来源：技术书籍/ai-agent-handbook/08_第 6 章…（6.4.3）
- **把任意消息队列等同于任务账本**：需具备完整事件、顺序、保留和重建契约才能算权威状态。来源：技术书籍/ai-agent-handbook/14_第 11章…（11.6.6）
- **状态栏投毒 / 状态栏算错**：「模型几乎无条件相信状态栏」，数量统计应由代码逐条维护而非 LLM 批量统计。来源：技术书籍/ai-agent-book/…/book/chapter2.md（状态栏一节）

## 六、对本项目 9 段流程的适用性

前提（本仓约束）：**只读（不改任何生产数据）、单租户、无写操作、无对外发信通道、答案是「带出处的问答」**。据此逐段判：

| 段 | 对应业界做法 | 适用性判断 |
| --- | --- | --- |
| ① 进门（收请求/认身份） | 身份链「人→Agent→能力→行为→资源」；会话外置（thread_id） | **部分适用**。身份桩（X-Dev-User）到位即可；多租户/配额/委托令牌那一套**不适用**（单租户），不要提前建。 |
| ② 理解（读题/入口安全闸/定路由） | 路由只判入口不判结果；混合路由；护栏分层；指令与数据分离 | **高度适用**。这是病灶集中区：路由要「模型出结构化决策 + 代码分派」，安全闸要从「词面共现硬终止」升级为「数据层只读兜底 + 策略判定 + 词面只做预筛」，并给正常问句留豁免/元问通道。 |
| ③ 澄清（拆小问题/反问） | 只在歧义实质改变交付时才问；追问封顶；interrupt 挂起 | **适用**。已有 CONSECUTIVE 封顶与 ask 挂起机制，方向正确；可用「子 Agent 隔离」承载大范围探查（第 ③ 段的 discover）。 |
| ④ 匹配（给子问题配工具） | 渐进式披露；能力白名单；coordinator 分派 | **适用**。工具白名单 + 分层披露可直接用；「能力可见≠有权执行」要落到每次调用校验。 |
| ⑤ 前置检查（能不能查/审批） | 工具风险分级；read-only 落工具侧；HITL 只在真正需要判断处；审批超时保持未执行 | **部分适用**。本仓只读→多数「写/外发」审批**不适用**；真正需要的是「这问题能不能查/该不该查」的资格判定与拒答，样本见 S0–S8 的 S6 资格与歧义（资料/…/从业务本体到持续进化.知识.md）。 |
| ⑥ 批量执行（查数/搜报告） | 子 Agent 隔离；大结果退出窗口不退任务；执行结果≠业务完成 | **适用**。大结果应落 Workspace/引用，窗口只留摘要 + 稳定可寻址引用；并行探查用隔离子 Agent。 |
| ⑦ 作答 | 作答只组织已核验材料；引用溯源 | **适用**。答案逐句带出处，落地在装配层，不做成模型自由生成。 |
| ⑧ 核验 | 完成由证据决定；验证强度分级；路由与结果判定分权 | **高度适用**。「直答免核验」应改为「任何对外答案都必须过最小核验」；核验强度可按答案类型分级。 |
| ⑨ 收尾 | 状态外置、事件/帧留痕、可恢复 | **适用**。RunState 外置 + checkpointer 已是正确骨架；对照 Checkpoint「关键状态清单」查漏。 |

**明确不适用（不要抄）**：自主写操作与补偿/撤销（无写操作）；多租户配额与财务归属（单租户）；外部发信/支付类高风险审批（无外发通道）；跨厂商重试乘积与故障转移（在网关单点内即可，见主题⑧调研）；训练/评测沙箱分叉（非本研究范围）。

## 七、值得抄的三条 / 要警惕的三条

**值得抄的三条**

1. **路由与结果判定分权 + 「模型出结构化决策、代码执行分派」**（技术书籍/ai-agent-handbook/12_第 9 章… 9.4.3；LangGraph workflows-agents）——直接对应本仓②段与⑧段解耦，能同时治「同类问句结果天差地别」。
2. **只读不变量下沉到数据层 + 指令与数据分离**（技术书籍/ai-agent-book/…/book/chapter1.md 数据层护栏；08_第 6 章… 6.4.4；Simon Willison 致命三件套）——只读是硬约束就该硬落地，词面闸只当预筛。
3. **会话/状态外置成显式对象（checkpointer/thread + 任务状态清单）**（https://docs.langchain.com/oss/python/langgraph/persistence ；技术书籍/ai-agent-handbook/06_第 4 章… 4.1.2、13_第 10 章… 10.1.1）——本仓 RunState 已是此形，补「恢复关键状态清单」查漏即可。

**要警惕的三条**

1. **词面共现闸无豁免**（本仓 N0 三族，runtime-refactor/recon/B2… D-B2-01）：会把「能不能删除数据」这类元问题当越权拒答——误伤面只能靠扩表控制，必须补豁免/反问通道。
2. **直答通道免核验**：本仓 V2-78 直答分流（runtime-refactor/recon/C-理解与legacy决策节点.md，R-C-10）让模型判定「无关业务」即直出；业界「完成由证据决定」要任何对外答案都过最小核验，这条要收窄成确定性窄口。
3. **把「模型自述完成/无关」当结论**（4.6.2 反面）：无论编排还是核验，都别让模型自证。
