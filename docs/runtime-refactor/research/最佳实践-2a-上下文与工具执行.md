## 一、一句话结论

**两条主线在业界都已收敛。**（④上下文）上下文是有限资源，模型只擅长「查找」不擅长「统计归纳」，所以长对话要么**压缩成结构化事实**、要么让大结果**退出窗口只留引用**，同时缓存经济性要求**静态前缀不动、动态只追加末尾**——本仓 V2-80h「对话链只追加不改写」正是在吃这个红利。（⑤工具）工具调用只是模型发出的**意图**，真正执行由 Harness 负责，所以工具必须有**稳定契约**（名称/描述/schema/错误分类/幂等键/超时），错误必须**先分类再决定能否重试**，只有**只读**工具才能安全并发。对本项目（只读问答、单租户、小固定工具集、9 段固定流水线）而言：**追加链 + 结构化事实落 RunState + 大结果退出窗口 + 错误三分类 + 指纹幂等**高度适用；**工具主动发现、沙箱隔离、多租户配额、写操作审批/补偿**不适用。

## 二、主题④ 上下文与记忆管理

### 4.1 业界主流做法（每条注出处）

1. **上下文是有限资源，且存在「上下文腐化」（装得下但找不到）。** 随 token 增多，模型召回准确率下降，注意力预算被稀释；目标是「最小的高信号 token 集」。来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents ；技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md（下文简称 book/chapterN.md）「上下文腐化」小节（context rot：溢出是装不下、腐化是装得下但找不到，后者更隐蔽）。

2. **上下文学习的内部机制是「检索而非推理」——模型擅长从已有内容里查找，不擅长在一次前向里主动归纳统计。** 这是「状态栏」与「压缩」两套做法的共同理论支点：状态栏把**算好的结论**加进上下文，压缩把臃肿的原始记录**换成**算好的结论。来源：book/chapter2.md（第 861-871 行「上下文窗口是一台只有一半的检索引擎」、第 999-1014 行）。

3. **缓存经济性不是事后优化，而是架构前置约束。** 静态前缀（顺序：工具定义 → system → 消息）必须字节级稳定，动态信息一律追加末尾。来源：https://platform.claude.com/docs/en/build-with-claude/prompt-caching （「Cache hits require 100% identical prompt segments」；前缀创建顺序 `tools`→`system`→`messages`；改工具定义使整段缓存失效）；book/chapter2.md（第 437-451 行「KV Cache 友好三结论」、第 556-572 行「缓存作为架构约束」）。

4. **前缀缓存是跨请求机制，命中要求前缀「完整匹配成一个缓存单元」，且有门槛/TTL/价格倍率。** 各厂商门槛不同：Anthropic 最小 512/4096 token（视模型）、默认 5 分钟 TTL、读为基准价 0.1×；DeepSeek 磁盘缓存默认开启、按公共前缀单元命中、best-effort 且小时到天级清除。来源：https://platform.claude.com/docs/en/build-with-claude/prompt-caching ；https://api-docs.deepseek.com/guides/kv_cache 。**本仓已实测不同模型门槛**：方舟通用 1,024 token、glm-5-3-flash 8,960，主模型 MiniMax-M3 无公开缓存文档——来源：runtime-refactor/arch/P6a-票堆V2-80系列前半.md（A-P6a-12）。

5. **压缩不是普通摘要，是四步有纪律的状态迁移：Commit → Compact → Rebuild → Validate**，且必须保留八类事实（原始目标/成功标准/不可变约束；已确认事实及来源并区分事实/假设/建议；已做决定及原因与被否决方案；已执行行动/工具结果/副作用；当前 Plan/Todo/阻塞/下一步；Artifact 与外部对象 ID；用户偏好/审批结果/权限模式；失败尝试及原因），并从 Task State 确定性提取高风险事实、只让模型压缩叙述性内容。来源：技术书籍/ai-agent-handbook/07_第 5 章 信息：上下文、状态与可复用能力资产.md（下文简称 handbook/chN.md）5.2 节。

6. **大结果应「退出窗口、但不退出任务」**：原始结果写入 Workspace/Artifact，活动上下文只留摘要、首尾片段与稳定可寻址引用（带权限与读取版本）。来源：handbook/ch5 5.2 节；book/chapter2.md（第 1056-1064 行分层压缩第 1 层「工具结果预算控制」）。

7. **压缩在两次 API 调用之间做、只压 tool results、接近阈值才批量压。** System Prompt 与工具定义永不动。来源：book/chapter2.md（第 1020-1028 行；第 1044-1052 行「自适应窗口化」：>80% 窗口才触发、批量压、`[COMPRESSED]` 防重复压）。

8. **生产级是分层压缩（不同类型信息不同保质期）**：①工具结果预算控制（大输出落磁盘）②噪声直接删（不做摘要）③API 层微压缩（服务端移除前缀）④归档式摘要（逐轮独立记录，像 git log 不 squash）⑤全量压缩（最后手段＋连续失败熔断器）。来源：book/chapter2.md（第 1056-1064 行）。

9. **隔离优于压缩**：大范围探索交给子 Agent，只回传几百 token 结论，中间过程不进主上下文、主前缀不受影响。来源：book/chapter2.md（第 1079-1085 行）。

10. **状态栏把隐式状态显式化**（TODO、工具调用计数、详细错误、环境状态），由代码逐步维护（绝不让 LLM 一次性批量统计——模型几乎无条件相信状态栏）。来源：book/chapter2.md（第 849-979 行）。

11. **记忆分层与区分**：Call（秒-分钟）/ Session（分钟-天）/ Task（可跨进程）三种边界不可合并；Memory 分 Working/Episodic/Semantic/Procedural 四类；Knowledge（企业事实，带来源权限时效）与 Memory（经验，带可信度适用条件）治理责任不同。来源：handbook/ch5 5.3、5.4 节。

12. **跨会话用户记忆**（个性化）与轨迹（append-only）是两件事：轨迹只增不改用于追溯/审计，长期记忆反复改写/合并/淘汰。四类存储格式（Simple Notes / Enhanced Notes / JSON Cards / Advanced JSON Cards）按「关键且少量 vs 大量且非关键」混合选用。来源：book/chapter3.md（用户记忆系统一节）。

13. **框架侧做法**：LangGraph 把记忆分 short-term（thread 作用域 + checkpointer）与 long-term（store），并列出管理历史的四种手段——trim messages、删除消息（RemoveMessage）、**摘要化早期消息后删除**（如「保留最近 2 条，其余摘要」）、checkpoint 存取。来源：https://docs.langchain.com/oss/python/langgraph/add-memory

### 4.2 分歧 / 取舍

- **压缩 vs 隔离。** 压缩有损、要额外 LLM 调用、且会断缓存；隔离让噪声从一开始就不进主上下文，主 Agent 前缀完全不受影响。取舍看子任务能否被切分与并行——能切且需并行探索用隔离，单链内历史膨胀用压缩。来源：book/chapter2.md（第 1079-1085 行）。
- **替换式状态更新 vs 持久追加式更新。** 每轮替换旧状态（省 token、状态最新，但移除点之后缓存失效）；持久追加（完全缓存友好，但陈旧状态累积、占 token）。决策点可用粗略公式：设每条状态 S token、两次更新间新增后缀 R token、预计更新 N 次、缓存输入单价为普通输入 α 倍——`C_替换 ≈ (N-1)(1-α)R`、`C_追加 ≈ αSN(N-1)/2`。来源：book/chapter2.md（第 945-953 行）。
- **静态前缀规模。** 全量工具定义常驻（缓存友好、但占 token 且工具集变动即击穿缓存）vs 按需把 schema 追加到轨迹末尾（省 token，但要求模型后训练见过「工具定义出现在对话中间」，仅较新模型支持）。来源：book/chapter2.md（第 698-708 行）。
- **是否每轮重建提示词。** 本仓曾有一轮教训：V2-79「每相位现拼、用完即弃」导致任意两次调用互不为前缀延伸、缓存全 miss；V2-80h 改为「每步在完整历史续写」。来源：runtime-refactor/arch/P6a-票堆V2-80系列前半.md（A-P6a-10 关键拍板原文）。
- **跨会话用户记忆要不要做。** 个性化收益 vs 记忆污染/跨用户串味风险；handbook 主张写入前先判断「是否有可预期价值、是验证事实还是模型推测、属谁、是否敏感、该增还是并、谁能纠正」，并强调遗忘要连原文/摘要/索引/派生关系一起处理。来源：handbook/ch5 5.4 节。

### 4.3 反例 / 踩坑

- **动态系统提示词注入时间戳** → 前缀从时间戳位起全失效，首 token 延迟 0.5s→3-5s、月度账单近乎翻倍。来源：book/chapter2.md（第 439-441 行）。
- **滑动窗口砍历史** → 破坏前缀一致性、且最严重的会丢关键工具结果：Agent「忘记」已获得，反复执行同一工具陷入循环。来源：book/chapter2.md（实验 2-3，第 540-554 行）。
- **文本格式化（`USER: … ASSISTANT: …`）** → 偏离模型训练时的标准角色格式，导致重复执行/忽略工具结果/该调工具却输出文本。来源：book/chapter2.md（同上）。
- **工具定义动态排序（按使用频率调整）** → 缓存从首个变动工具起失效；实验显示固定顺序对模型选工具几乎无影响、对性能提升显著。来源：book/chapter2.md（同上）。
- **状态栏是对原文的有损投影、且模型几乎无条件相信它** → 一旦状态值有 bug（尤其 LLM 批量统计导致），模型会当真；删除原始上下文只留状态栏，一旦问题涉及状态栏未计算的维度，准确率断崖式下降。来源：book/chapter2.md（第 976-979 行）。
- **只压缩不做 Validate** → 摘要把可复用经验、架构决策、约束理由、失败路径一起抹掉，恢复后行为漂移。来源：handbook/ch5 5.2 节（「压缩最容易丢失的是早期的架构决策、约束背后的理由和失败的路径」）。

## 三、主题⑤ 工具调用与受控执行

### 5.1 业界主流做法（每条注出处）

1. **工具调用只是「行动意图」，不是执行。** 完整行动链是：Schema 校验 → 身份绑定 → 策略（ALLOW/DENY/ASK）→ 审批 → 执行 → Observation → 写入 State/Trace。来源：handbook/ch6 6.1.1 节。
2. **三件事必须分开**：①模型看见某工具（描述进了 Context）②Harness 注册了该工具（知道怎么调用/解析）③当前用户与任务**获得执行授权**（这次具体行动可以发生）。「出现在 Tool Schema 里」≠「可以调用」。来源：handbook/ch6 6.1.1 节；工具网关侧同理见 handbook/ch9 9.3.1 节。
3. **用统一 Action 契约约束不同能力**：`capability_id/version`、参数与输出 schema、`actor`、`purpose/current stage`、环境与资源范围、`side-effect/reversibility/risk`、`idempotency key/timeout`、审批与审计要求。模型自由文本只能作 `purpose` 候选，名称/类型/范围/身份必须由确定性代码解析校验。来源：handbook/ch6 6.1.2 节。
4. **Action 结果要结构化，不能只有可读文本**：成功/失败/未知/部分完成状态、结构化数据＋面向模型的紧凑 Observation、原始结果/日志/Artifact 引用、**错误类别＋可重试性＋是否已产生副作用**、实际执行身份与环境版本、对 Task State 的候选 Patch、可供 Verifier 使用的证据。来源：handbook/ch6 6.1.2 节。
5. **工具设计对齐「目标」而非底层 API（ACI）**：默认「通用工具优于专用工具」，只在四情形退回专用——①安全/权限/审计 ②屏蔽平台差异或给更好反馈 ③使用频率极高 ④参数结构复杂（嵌套/多字段联合校验）。来源：book/chapter4.md（第 36-66 行）。
6. **工具描述说清「何时用、何时不用」**：核心是边界与反例（「大多数失败根因不是不知道能做什么，而是不知道不能做什么」）；参数用具体例子代替抽象规范；附 1–5 个真实调用示例（部分基准准确率 72%→90%）。来源：book/chapter4.md（第 70-86 行）。
7. **参数保真：禁止静默输入转换与静默参数注入。** 模型感知的世界与工具操作的世界之间不能有系统性偏差，否则制造模型无法自诊断的死循环（弯引号被静默转直引号、`git commit` 被静默附加参数）。来源：book/chapter4.md（第 88-98 行）。
8. **参数校验用严格 schema 强制**：`strict: true`，要求 `additionalProperties: false` 且所有字段 `required`（可选字段用加 `null` 类型表达）；不合规请求直接拒绝，而非 best-effort。来源：https://developers.openai.com/api/docs/guides/function-calling
9. **工具数量与选择精度**：超过约 100 个易选错；应对三层——层次化组织/按需加载、主动工具发现（模型声明缺口、系统按需注入；MCP-Zero 约 2800 工具省约 98% token）、检索式预筛（Anthropic 实验 Opus 4 工具使用准确率 49%→74%）。来源：book/chapter4.md（第 133-171 行）。
10. **错误分类先于重试**：限流（结合重置时间/配额/替代端点）、5xx（仅在语义允许时重试）、认证错误（终止修复凭证）、上下文超限（不该简单截断历史「解决」）各自不同；且「尚未收到响应体」≠「上游尚未执行」（可能已计费甚至已触发副作用）——重试许可需同时看接口幂等性、上游执行不确定性、客户端协议。来源：handbook/ch9 9.2.4 节。
11. **超时分层、不可互相代替**：连接超时、首字节超时、TTFT、流式空闲超时、总截止时间。例：持续发心跳的流可一直不触发空闲超时，却始终没有有效内容。来源：handbook/ch9 9.2.5 节。
12. **重试预算必须跨层传递，否则乘积放大**：SDK 3 次 × 网关 3 次 = 一次用户可见调用最多到上游 9 次。总截止应是绝对时间；每次尝试用稳定 `call_id`/`attempt_id` 关联；切 provider 前要检查工具/结构化输出/数据地域/模型能力兼容。来源：handbook/ch9 9.2.4 节。
13. **幂等是超时/打断处理的核心**：①操作携带唯一标识、服务端去重；②先查询后变更。不可逆操作（发邮件/转账）用「预检-确认」两段式，失败不盲目重试而回主模型重规划。来源：book/chapter4.md（第 361-367 行）；统一为 Preview→Approve→Commit→Verify：见 handbook/ch6 6.4.2 节。
14. **并发：只读工具可安全并行、执行工具需严格顺序。** 感知工具不改变外部世界，结果可安全缓存、多个调用可放心并行；执行工具有副作用，调用顺序必须严格控制。来源：book/chapter4.md（第 228 行）。模型侧并行调用能力与开关：https://developers.openai.com/api/docs/guides/function-calling （`parallel_tool_calls`）。
15. **执行安全分层**：输入验证（快速失败，不尝试「智能」修正）→ 权限控制 → 提议者-审核者（事前审批/事后验证）与 Sidecar（与主流式输出并行门控单次调用，拒绝熔断器转人工）→ 沙箱隔离（venv 不是沙箱）→ 可观测性。来源：book/chapter4.md（第 274-359 行）。
16. **MCP/网关安全边界**：`tools/list` 过滤只能减少误选、`tools/call` 必须**再鉴权**；权限取「调用者原有授权 ∩ 工作负载授权 ∩ 任务委托范围 ∩ 资源侧限制」；网关只有在**凭证不下发、出口受控、直连被禁**时才谈得上「不可绕过」。来源：handbook/ch9 9.3.5 节。协议级：token passthrough 明令禁止、会话不能用于认证、防 SSRF、最小 scope。来源：https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices

### 5.2 分歧 / 取舍

- **专用工具 vs 通用执行器/Skill**：四维判据——安全与权限、参数复杂度、变更频率、模型能力。稳定、高频、高权限、参数复杂 → 专用工具；频繁变化、参数简单、强模型 → Skill + 通用执行器。来源：book/chapter4.md（第 59-64 行）。
- **审批放哪一层**：事前审批（提议者-审核者，不可逆操作）/ 事后验证（模态切换，如渲染成图再看）/ Sidecar（与主流式并行、门控单次调用、可做权限分类/记忆筛选/输出摘要）。三者执行时机与审查对象不同，见 book/chapter4.md 表 4-2。**注意**：Sidecar 审的是「较简单的分类问题」故轻量模型够用；提议者-审核者审「开放式思考」故需能力相近模型。
- **超时放在哪一层**：单层（应用内，简单可解释）vs 多层（SDK+网关+上游）。多层要付出「预算跨层传递」的复杂度，否则乘积放大。来源：handbook/ch9 9.2.4 节。
- **失败后重试 vs 回炉重决策**：参数错误/业务拒绝重试无意义（应修参或改链）；限流/抖动才值得同参重试。这正是「错误必须先分类」的理由。来源：handbook/ch9 9.2.4 节。
- **幂等怎么实现**：唯一 ID 去重 / 先查后变 / 请求指纹。指纹方案适合「同参不重跑」的查询型工具；唯一 ID 方案适合有外部副作用的写操作。

### 5.3 反例 / 踩坑

- **静默输入转换 / 静默参数注入**（弯引号→直引号、commit 被附加参数）→ 模型反复失败且无法归因，见 5.1-7。
- **多层重试乘积放大 9×** —— 每层各自以为上限是 3，端到端没有 3 这个约束，重试/并发/费用以乘积放大且无法归因。来源：handbook/ch9 9.2.4 节。
- **流式响应已向客户端提交后仍透明重放整段结果** —— 网关通常做不到，且可能已计费/已触发副作用。来源：handbook/ch9 9.2.4 节。
- **把「审批超时」自动解释为「改成只读执行」** —— 改变原始请求含义、可能造成意外数据暴露；应形成新的、可见的、重新授权的请求。来源：handbook/ch9 9.5.4 节。
- **把「工具可发现」当「已授权/健康/可执行」** —— `server/discover` 与 `tools/list` 只说明被通告。来源：handbook/ch9 9.3.1、9.3.3 节。
- **工具描述投毒 / 同名工具遮蔽**：description 原样进模型上下文，可夹带指令；恶意服务器可遮蔽正规工具。缓解：接入前审查描述（当不可信输入审计）、锁定版本、最小权限凭证。来源：book/chapter4.md（第 123-131 行）。
- **只靠字符串前缀判「只读 SQL」** → 不可靠，应结合受限数据库账户、受支持的查询接口与资源端权限。来源：handbook/ch9 9.3.7 节。
- **把「工具执行成功」当「业务完成」** —— 执行成功只等于执行成功，业务完成需另判；Verifier 必须返回结构化缺口。来源：handbook/ch6 6.6.2 节。

## 四、对本项目 9 段的适用性（只读问答、单租户）

按 9 段（①进门 ②理解 ③澄清 ④匹配 ⑤前置检查 ⑥批量执行 ⑦作答 ⑧核验 ⑨收尾）映射。**先给总判定**：只读、单租户、小固定工具集、无写操作这四条约束，把业界做法切成两半——「上下文组织/缓存/错误分类/幂等/只读并发」这一半**高度适用**；「工具探索/沙箱隔离/多租户配额/写操作审批补偿」那一半**不适用**。

### 4.1 上下文与记忆（主题④）

- **追加链吃缓存——已落地，继续守。** 本仓 V2-80h：`RunState.messages` 只追加；任意相邻两次调用互为前缀延伸（`后[:-len(尾段)] == 前` 有留痕 JSONL 自动断言，即 A-P6b-27「只追加性红线」）；相位合同/台账块只在首次进入相位时追加一次（`contracts_appended` 标记，A-P6b-25）；compile 退役为「追加内容渲染器」。真机实证：9 次调用链长 2→25，同 run 相邻调用 LCP＝前链全长（×7）。来源：runtime-refactor/arch/P6b-票堆V2-80系列后半.md（A-P6b-21~28）、P6a（A-P6a-10）。**适用**——这正是 Anthropic/DeepSeek 缓存机制要求的形态；纪律是**别在系统提示或常驻块里塞动态量**（时间戳/计数），动态一律追加末尾。
- **compaction（长对话摘要）——已规划，是最后手段。** A-P6b-29：messages 超 `dialogue_view_tokens` → 最旧的「对话轮对」（user+assistant，**非合同、非相位包**）摘要化；合同与相位包永不摘除；**触发即断缓存（可接受，超长对话才触发）**。来源：P6b A-P6b-29；P6a A-P6a-11（「追加式＝上下文单调增长，治理退为最后手段」）。**适用**——但要盯两个隐患：①P6a A-P6a-11 已登记「compaction 保留 vs 合入讯息称退役」的**矛盾**，现 `context.py` 未见 compaction 函数；②若真做 compaction，按 handbook/ch5 5.2 必须配 Commit（结构化事实先进权威状态）→ Compact → **Rebuild → Validate**，不能只摘要。本仓 run 内轮数上限 3、总时长 300s，run 内膨胀实际很有限。
- **结构化事实落 RunState——已落地，可当压缩自检表。** 本仓把状态外置成 `RunState`（53 字段，见 synth/S5-RunState字段矩阵.md）＋`process_notes`（有界摘要 ≤400 字）＋工具执行台账行（user 角色）。这与 handbook/ch5 的「压缩必留八类事实」是同一思路，但**counterexample**：对话链只追加时，模型看到的仍是散在链各处的原始过程，而非「算好的结论」——本仓的 `process_notes` 正是补这个缺（相当于 Agent 状态栏）。**适用**。
- **大结果退出窗口、不退出任务——部分适用、建议补。** 第⑥段批量查数/搜报告会产出大结果；本仓现状是 `render_materials` 对 report 族做 `max_observations=24` 截断并附披露句（runtime-refactor/recon/K-上下文事件指南预算.md R-K-21~23），**但未见「原始报告落 artifact + 窗口只留 index 引用」的落点**。按 handbook/ch5 5.2 与 book/chapter2.md 分层压缩第 1 层，报告全文不该反复进上下文。**适用（待落）**。
- **状态栏由代码维护——已落地且合规。** `process_notes`/台账行/工具计数均由代码生成（非 LLM 批量统计），符合 book/chapter2.md「状态栏尽量用代码维护」纪律。模型**无条件相信**状态栏，故这些摘要若错会被当真——见第五节警惕项。
- **跨会话用户记忆（个性化画像）——不适用。** 单租户、只读、无写操作，没有「记住用户偏好以跨会话个性化」的业务需求（且会引入污染/串味风险）。P6b A-P6b-23 的「追问播种＝前链＋新问」只是**单用户多轮连续性**（同一对话链的前缀延伸），不等于用户画像记忆。**不适用**。

### 4.2 工具调用与受控执行（主题⑤）

- **固定小工具集——不触发工具爆炸，无需主动发现。** 本仓工具为 `data_query`/`doc_retrieve` 及决策面 `semantic_query`/`table_schema`/`faq_lookup`（少量），远低于「超 100 易选错」门槛。**不适用**：层次化检索、主动工具发现、按需加载 schema、工具网关。
- **工具契约 + 参数校验——已落地，与业界一致。** 合同册（`specs/api/*.md` 端点号）＋闭合世界对账（`parse_tool_match` 拒收缺 matches/支非对象/缺 id/id 不在组内/重复/chain 越界/chain-tool 不一致/data 缺 plan 或 metric_slot 空/knowledge 缺 retrieval_need 等——recon/E2 R-E2-06）＋`argscheck` 子集校验（不合→`failed(bad_args)`、引擎零调用）。这与 OpenAI strict schema（`additionalProperties:false`＋全 required）同向。**适用**：继续用确定性对账当参数闸，别放松成「模型自证」。
- **错误三分类 + 指纹幂等——已落地，属业界推荐做法。** `registry.classify_exception`：超时/网络/5xx/429 限流→`retryable`；上游其余 4xx/`ValueError`/网关 `UpstreamRejected`→`bad_args`；越权→`refused`（终局）；配合 `executed_payloads` 指纹「成功不重跑」（recon/G R4、R-G-16；`registry.py` 头注 1-11 行）。与 handbook/ch6 6.1.2「错误类别＋可重试性＋是否已产生副作用」同构。**适用**。
- **超时——单层、已落地；注意不要引入多层重试。** 本仓单工具超时 `TOOL_TIMEOUT_SECONDS_CONTRACT = 30.0s`（`asyncio.wait_for` 包装 `deps.registry.call`）、单段总时长 300s。这与 handbook/ch9 9.2.5 的「总截止 + 分层超时」相比是**单层简化**——单层没有乘积放大问题（handbook 9.2.4 的 9× 隐患不存在），但若将来在本仓外挂网关重试，必须按 handbook/ch9 9.2.4 传递总截止与尝试额度。**适用（守单层）**。
- **只读不变量落确定性策略——已落地，是正确方向。** 第⑤段前置检查机 `precondition.judge` 是**纯函数零 LLM**（recon/F R-F-01「LLM 无权判定」）；拒答/回炉/挂起全在固定代码。与 handbook/ch6 6.4.4「确定可编码的权限用 Policy，模型只作额外信号」一致。**适用**。
- **沙箱/高风险审批/Preview-Approve-Commit——不适用。** 本仓无写操作、单租户、无不可逆副作用，故执行工具沙箱、提议者-审核者、Sidecar、`Preview-Approve-Commit-Verify` 都没有对象。**不适用**。**但其中一条子原则适用**：「区分指令与数据」——第⑥段检索到的报告/网页内容属不可信输入，不得改变政策或权限（book/chapter2.md 第 730-738 行；handbook/ch6 6.4.4 节）。
- **只读并发——适用但需协调预算。** 第⑥段批量执行逐支串行、且遇引擎 `ask` 即 `break`（recon/G 分支 17）；只读感知工具天然可并行（book/chapter4.md 第 228 行）。可考虑把无依赖的 `data_query`/`doc_retrieve` 子问题并发，但受「轮内 execute ≤2」（budget.py）与 300s 总预算约束，收益有限。**适用（可选优化）**。
- **执行成功 ≠ 业务完成——适用，正是第⑧段。** 第⑧核验段（逐句核对有没有依据）对应 handbook/ch6 6.6.2「完成由证据决定」；本仓核验改写是 append-only 的**唯一例外**（A-P6b-28，链尾 assistant 就地替换为核验后文本）——业界核验一般也是独立的「提交完成」动作，此处例外合理但需与「只追加性红线」合成核对（见第六节）。
- **多租户配额/scope/网关不可绕过——不适用。** 单租户、无跨租户数据、凭证面简单。

## 五、值得抄三条 / 要警惕三条

### 值得抄三条

1. **静态前缀不动、动态只追加末尾（继续守 V2-80h 纪律）。** 缓存命中要求前缀字节级完整匹配（Anthropic/DeepSeek）；本仓「任意相邻调用互为前缀延伸」已实测（LCP＝前链全长×7）。落地动作：系统提示/常驻块/工具定义**禁塞动态量**（时间戳、计数、用户态）——动态一律作新消息追加链尾。出处：https://platform.claude.com/docs/en/build-with-claude/prompt-caching ；https://api-docs.deepseek.com/guides/kv_cache ；book/chapter2.md 第 437-451 行；本仓 P6b A-P6b-22/27。
2. **压缩是「结构化状态迁移」而非摘要：Commit → Compact → Rebuild → Validate ＋ 八类必留事实。** 若本仓启用 compaction，应先把关键事实落成 `RunState` 字段，压缩只处理叙述性历史，并**压缩后必须 Validate**（目标/未解决项/权限模式/关键证据完整性 + 续行用例）。八类事实可逐条对照本仓 S5 字段矩阵做自检表。出处：handbook/ch5 5.2 节。
3. **大结果退出窗口、不退出任务：原始报告落 artifact ＋ 窗口只留摘要＋可寻址引用。** 第⑥段查数/搜报告直接受益——报告全文不该反复进上下文；引用要稳定且带读取版本/时间。出处：handbook/ch5 5.2 节；book/chapter2.md 第 1056-1064 行。

（并列候选：错误「先分类再重试」＋指纹幂等——本仓已落地，可作为其他工具接入时的既有契约复用。）

### 要警惕三条

1. **滑动窗口砍历史。** 会同时砸掉「追加链」的缓存红利与关键工具结果，导致模型忘记已获得而反复重试同一工具、陷入死循环。出处：book/chapter2.md 实验 2-3（第 540-554 行）。本仓若为省 token 引入滑动窗口，即与 A-P6b-27 红线冲突。
2. **多层重试乘积放大。** 每层各自以为上限是 3，端到端没有 3；重试/并发/费用以乘积放大且无法归因。本仓当前单层无此病，**但若在本仓外新增网关/SDK 重试，必须跨层传递绝对总截止与尝试额度**，并给每次尝试独立 `attempt_id`。出处：handbook/ch9 9.2.4 节。
3. **把「执行成功」当「业务完成」，或状态摘要被无条件相信。** 查数工具返回有行 ≠ 答案可信——第⑧段必须由证据决定完成（handbook/ch6 6.6.2）。同时 `process_notes`/台账行/材料摘要都是**有损投影且模型无条件相信**，一旦摘要出错会被当真（book/chapter2.md 第 976-979 行）——摘要必须由代码逐步维护、禁止 LLM 批量统计，且不得让外部不可信内容直接写进摘要（投毒）。

## 六、疑点与不确定

1. **compaction 去留矛盾（需回 80h 票面取证）。** P6b A-P6b-29 写「compaction 机制 80d 保留」，但 P6a A-P6a-11 记录「80h 合入讯息称 compile/CompiledContext/compaction 族退役，现 `context.py` 未见 compaction 函数」——方案与实现两说。本文凡涉 compaction 的「适用」判断因此属**推断**。

3. **主模型缓存收益无实测证据。** 主模型 MiniMax-M3 用量面不上报 `cached_tokens`，故「改造收益＝缓存命中」在主模型面**不可闭环**，验收以「前缀延伸结构性验证」替代（P6a A-P6a-12）。引用「缓存收益」时须注明证据等级。
4. **「user 消息装系统合同」的跨供应商语义影响未展开。** 相位包（澄清/匹配合同、§A 指南）以 user 角色消息承载，P6a A-P6a-10 疑点指出该做法的跨供应商语义影响票面未讨论。本文不越界裁决。
5. **handbook 第 8 章（状态存储与语义资产）与第 11 章未逐字读。** 其 Event Log（只追加）/Checkpoint/Durable Execution 内容仅经「资料大纲-2-handbook.md」条目转述，**未作一手引用**，本文未采为做法出处；如需引用请先读原文。
