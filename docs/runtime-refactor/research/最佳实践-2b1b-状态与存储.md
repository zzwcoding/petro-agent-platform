## ① 一句话结论

**checkpoint 存的是「恢复所需的可恢复事实」，不是对话原文；挂起与恢复的本质是「在安全点落盘、从最近可信点读回」；而状态摘要是一次有损投影——实验证据表明模型几乎无条件相信摘要、不会自己重算，所以凡是会影响后续动作的事实，必须先落成权威状态字段、再由确定性代码（不是模型）生成摘要，且模型只能「申请完成」、由 Harness 按证据「提交完成」。**

出处：HandBook 第 8 章（`ai-agent-handbook/11_第 8 章…md`）§8.1–8.3；HandBook 第 5 章（`07_第 5 章…md`）§5.2–5.3；ai-agent-book 第 2 章（`ai-agent-book/ai-agent-book/book/chapter2.md`）「Agent 状态栏」节；HandBook 第 4 章（`06_第 4 章…md`）§4.6.2。

## ② 业界主流做法（每条注出处）

**1. 状态先按「四类」分开，各自配不同承载与一致性要求。**
运行时状态（事件日志/检查点/任务进度/租约/状态指针）、工作区与产物（文件/快照/版本/分支）、记忆与知识（会话摘要/偏好/向量索引）、业务语义与治理（本体/规则/权限/审计）——四类放在一起是「统一契约 + 分层承载」，不是塞进同一种存储。
一致性要求天然不同：运行时状态需要**顺序、原子更新、幂等、可恢复历史**；工作区需要**版本、快照、可回滚**；记忆需要**可检索、时效、来源可信、权限过滤**。
出处：HandBook 第 8 章 §8.1.2、§8.1.3、§8.1.4。

**2. 三件互补的表示，不可互相替代：Event Log / Snapshot / Checkpoint。**
- **Event Log** 记「发生过什么」，只追加、顺序性强，用于追踪因果、审计、重建；诊断日志和模型输出**不能**替代它作为重放依据。
- **Snapshot** 记「某一时刻的聚合状态」，适合快速读当前视图。
- **Checkpoint** 表示「可以安全恢复执行的位置」，除 Snapshot 外还要带 **Continuation（继续点）+ 幂等 + 环境依赖**。
出处：HandBook 第 8 章 §8.2.2；HandBook 第 5 章 §5.3「用状态事实支持恢复」。

**3. Checkpoint 的内容清单（不是上下文拷贝）。**
一个有效 Checkpoint 应含：当前任务阶段、已完成步骤、未完成步骤、工具调用结果**引用**、工作区版本、子任务状态、等待条件、状态版本。
出处：HandBook 第 8 章 §8.2.3（原文：「一个有效的 Checkpoint 不应只是模型上下文的简单拷贝，而应包含恢复所需的关键状态……」）。

**4. Checkpoint 的「安全点」边界。**
外部调用**发起前后**、长时间计算完成后、**人工确认前后**、工作区发生重要变更后、任务准备交接给其他 Agent 时。
频率与任务成本匹配：几秒可完成的查询型任务频繁落盘反而增加开销；调用外部系统/长链路/需人工介入的任务应在关键边界主动落盘。
出处：HandBook 第 8 章 §8.2.3。

**5. 跨副本恢复 = Durable Execution，靠「外层持久状态 + 快照加事件回放 + 执行租约 + 状态指针」。**
- 执行实例是可替换的计算单元，任务事实不归某个实例独有；新实例先读最新 Checkpoint，再**按需回放其后事件**（不必从头回放）。
- **执行租约**解决「谁有权继续执行」；状态写入带版本/围栏（fencing）标识，旧实例不能覆盖新结果。
- **状态指针**解决「当前可信状态在哪里」，把任务/事件/检查点/工作区快照/产物关联起来供恢复和审计。
- 明确边界：**Durable Execution 不等于外部动作恰好执行一次**；需靠幂等标识、结果确认、补偿机制兜。
出处：HandBook 第 8 章 §8.2.4；Temporal《What is Durable Execution?》https://temporal.io/blog/what-is-durable-execution （「Durable Execution is crash-proof execution」，崩溃后状态在新进程重建、工作透明续跑）。
Temporal 还给出重放的硬约束：**「Workflow code must be deterministic to support replay」**，代码重放时发出的 Command 与已有 Event History 比对，不一致即报 non-deterministic 错误；不确定逻辑要放进 Activity。
出处：Temporal Workflow Definition https://docs.temporal.io/workflow-definition

**6. 落地框架形态：LangGraph 把「短期线程状态」与「长期跨线程记忆」分成两个对象。**
- **Checkpointer**＝短期、线程内（thread-scoped）记忆，按 `thread_id` 把图状态存成 checkpoint；用途列「conversation continuity、human-in-the-loop、time travel、fault tolerance」。
- **Store**＝长期、跨线程（cross-thread）记忆，存用户偏好/事实/共享知识。
- 后端：`MemorySaver`/`InMemorySaver`（放内存，**进程重启即丢**）、`SqliteSaver`（本地开发）、`PostgresSaver`（`setup()` 建表建索引、可清理旧 checkpoint）。
- 陷阱：子图各自管自己的 checkpoint 命名空间，父图可能**看不到**子图更新（需共享 Store 或让子图写父 checkpoint）。
出处：LangGraph Persistence https://docs.langchain.com/oss/python/langgraph/persistence

**7. 状态摘要/压缩是「四步有纪律的状态迁移」，不是普通摘要。**
`Commit`（结构化事实先落 Task State/Workspace/资产库）→ `Compact`（把可叙述历史转成带来源与覆盖范围的摘要）→ `Rebuild`（用新摘要+当前状态+最近消息重构 Context，检查关键约束还在不在）→ `Validate`（对目标/未解决项/权限模式/关键证据做完整性检查，并用续行用例验证行为没漂移）。
压缩必须保留的 8 类事实：原始目标与不可变约束；已确认事实及来源（区分事实/假设/模型建议）；已做决定及原因与被否决方案；已执行行动/工具结果/副作用；当前 Plan/Todo/阻塞/下一步；Artifact 与外部对象 ID；用户偏好/审批结果/权限模式；失败尝试及避免重复的原因。
高风险事实「不能只由模型自由归纳」，最好从 Task State、工具结果、审批记录里**确定性提取**，再让模型压缩叙述性内容。
出处：HandBook 第 5 章 §5.2「Commit、Compact、Rebuild 与 Validate」。

**8. 状态摘要的技术形态——「Agent 状态栏」。**
把分散在上下文各处的隐式状态提炼成显式知识，作为一条 `user` 角色消息**追加到上下文末尾**（不修改 system，避免破坏 KV Cache），例如「phone_call 已调用 3 次（Xfinity 3/3 max）」。
实验（Qwen3-0.6B）显示：给出「提前算好的状态栏」后，较小开源模型准确率可接近前沿大模型，思考 token/延迟/花费降约一个数量级。
出处：ai-agent-book 第 2 章「Agent 状态栏」「Agent 状态栏在上下文中的具体位置」。

**9. 「完成」的判定权在 Harness，不在模型。**
模型只能**提出完成申请**，Harness 才能**提交完成状态**。验证强度与风险匹配，分五级：结构验证 → 环境验证 → 确定性验证 → 独立模型验证 → 人工验收。Verifier 返回**结构化缺口、失败证据、可修复性**；验证失败是新 Observation，由 Harness 决定修复/重规划/转交/失败。
异步任务侧同样划三层：执行状态（跑没跑完）、Evidence（被成功标准引用的候选证据）、业务 Outcome（由业务应用或获授权 Verifier 判定）；「LLM-as-a-Judge 是 Evaluation 的一种实现方式，不是 Outcome 的天然权威」。
出处：HandBook 第 4 章 §4.6.2；HandBook 第 10 章 §10.1.2。

**10. 会话历史管理的现成做法。**
OpenAI Agents SDK 的 Session：run 前自动取出该会话历史**拼到输入前**，run 后把新产生的 item（用户输入/助手回复/工具调用）自动存入 session；后端有 SQLite/Redis/SQLAlchemy/Mongo/Dapr 等；用 `SessionSettings(limit=N)` 只取最近 N 条。
重要信任边界（原文）：「A session ID selects conversation history; the session ID does not authenticate a user or authorize access to that history.」——会话 id 只用来选历史，不做认证。
出处：OpenAI Agents SDK Sessions https://openai.github.io/openai-agents-python/sessions/

## ③ 分歧取舍（业界没有唯一答案的地方）

**分歧 1：状态摘要「每轮替换」还是「持久追加」。**
每轮替换保证只有一份最新状态，但移除旧状态会让其后缓存失效（失效范围通常只一轮，前缀仍可复用）；持久追加对缓存完全友好（只追加不改），但**陈旧状态会在上下文里累积**，且要求模型自己认准「最新一条」。
给出的粗估分界：状态小、两次更新间消息多、会话受控 → 选持久追加；状态大、更新频繁、轨迹很长 → 选每轮替换。
出处：ai-agent-book 第 2 章「状态更新的两种实现与缓存代价」。

**分歧 2：Checkpoint 该多久落一次。**
短查询型任务（几秒、失败可低成本重试）频繁落盘是浪费；长链路/外部调用/人工介入型必须在安全点主动落。没有统一频率，按「成本—性能—恢复精度」三者划边界。
出处：HandBook 第 8 章 §8.2.3。

**分歧 3：强一致的边界划多宽。**
不必所有任务争同一条全局日志；合理边界通常是**任务/会话/业务对象**——同一任务内状态变化要有明确先后，独立任务可并发。这样既保正确性又避免全局串行。
出处：HandBook 第 8 章 §8.2.2。

**分歧 4：只留摘要删原文，还是保留原文。**
状态栏够用（计数、状态跟踪类）时可以删原文省大量 token；但只要有一个问题涉及状态栏**未计算的维度**，仅留摘要就会导致准确率断崖。
出处：ai-agent-book 第 2 章「状态栏的维护」第 2 点。

**分歧 5：恢复靠「读快照」还是「重放事件」还是两者结合。**
HandBook 主张**快照加事件**结合（既避免从头回放、又保留过程证据）；Temporal 走的是**事件历史重放**（因此要求确定性）；LangGraph 默认是**读线程最新 checkpoint**（语义偏向快照）。
出处：HandBook 第 8 章 §8.2.4；Temporal Workflow Definition（同 ②5）；LangGraph Persistence（同 ②6）。

## ④ 反例踩坑

1. **【最相关】模型无条件相信状态摘要。** 原文：「模型几乎无条件地相信状态栏——你写『打了 3 次电话』，它就当真是 3 次，不会自己重算。LLM 做数量统计本来就容易出错。」由此引出**状态栏投毒**风险；对策是状态栏尽量用代码维护，实在要用 LLM 也要逐条抽取再由代码汇总，绝不要一次性批量统计。
   出处：ai-agent-book 第 2 章「状态栏的维护」第 1 点。

2. **【最相关】有损投影 + 删原文 = 断崖。** 状态栏是「对原始上下文的一次有损投影，只提前算了你预想会被问到的那些维度」；一旦问题落在未计算维度，仅留摘要会导致准确率断崖式下降。
   出处：ai-agent-book 第 2 章「状态栏的维护」第 2 点。

3. **把每次状态保存都叫 Checkpoint。** 这会掩盖「某些工具事务仍在进行、不能安全重放」的事实；只有 Event Log 恢复成本随任务长度增长，只有 Snapshot 无法解释状态如何形成。
   出处：HandBook 第 5 章 §5.3。

4. **Checkpoint ≠ 外部副作用幂等。** 若外部写入已提交而 Checkpoint 尚未落盘，重跑仍会产生重复副作用；Checkpoint 必须明确「保存什么、由谁写、与业务 State 和外部系统提交如何排序」才能参与恢复语义。
   出处：HandBook 第 10 章 §10.1.3。

5. **用诊断日志或模型输出当重放依据。** 事件日志只有包含完整状态变更和必要输入时才能作重放依据；诊断日志与模型输出不能替代。
   出处：HandBook 第 8 章 §8.2.2。

6. **双副本同时推进。** 旧实例未完全退出、新实例又开始恢复，同一任务被两副本推进；仅更新任务表租约也无法阻止仍持有文件句柄的旧实例继续写工作区（需独占挂载/撤销旧端访问/私有分支）。
   出处：HandBook 第 8 章 §8.2.4、§8.3.4。

7. **任务状态恢复了、文件状态却变了。** 快照必须与运行时状态关联：Checkpoint 要记录对应的工作区快照引用，否则出现「状态已恢复、环境已变」的不一致。
   出处：HandBook 第 8 章 §8.3.3。

8. **大结果反复进上下文。** 一次日志查询/网页抓取可能返回数万行；原始结果应落 Workspace/Artifact，窗口只留摘要 + 稳定可寻址引用（带权限与读取版本），否则每轮都重复携带同一大结果。
   出处：HandBook 第 5 章 §5.2。

9. **会话 id 当身份用。** Session id 只选历史、不认证不授权（见 ②10）。
   出处：OpenAI Agents SDK Sessions。

## ⑤ 对本项目适用性（对照 `docs/runtime-refactor/` 现状）

本项目现状（读 `synth/S5-RunState字段矩阵.md`、`synth/S6-事件与帧目录.md` 得到，非推断）：

- 已有 **checkpoint 盘**：`LangGraph PG saver，3 表：checkpoint/blob/write`，由 H13「每步框架落」，**把 RunState 全 53 字段整体投影**。
- 另有 4 条盘：`runs` 表（H3 受理/终态 + M6 answer）、`steps` 表（整体 upsert）、`blackbox` 表（终态蒸馏）、`audit_log` 表（六类审计事件）。
- 已有**挂起/恢复骨架**：`pending_ask`（挂起帧投影，字段矩阵里注「挂起帧读」）、`resume_choices`、`approved_ids`；挂起帧 `ask` 的 kind 是闭世界 `{clarify, external_table_approval}`；`schema_version` 字段由 H13「checkpointer 读侧分流」用。
- 已有**核验雏形**：`draft_kind`（""=待核验 / "direct"=确定性直答）、`verdict`（M7 核验裁决）；`process_notes` 带「digest≤200」有界段。

对照结论：

- **【较贴合】Checkpoint 内容清单**（②3，ch8 §8.2.3）：本项目 53 字段里 `status`（任务阶段）、`steps`（已完成步骤）、`pending_plan/pending_retrieval/pending_discovers`（未完成步骤）、`last_result`（工具结果）、`pending_ask`（等待条件）、`schema_version`（状态版本）基本对齐「恢复所需关键状态」清单，缺的是**「工作区版本/产物引用」**这类字段（本项目只读、无工作区，此条可弱化——**推断**）。
- **【较贴合】安全点**（②4）：`M2 clarify` 与 `M4 blocked_ask` 落盘即天然安全点；`M5 execute` 外部调用前后是本项目最该确认「已落盘再放行/重跑」的位置。
- **【较贴合】完成判定权**（②9）：本项目 `verdict` + `draft_kind` 已把「逐句核验」独立成 M7，方向与「模型申请、Harness 提交」一致；建议把「本步是否已完成」的判定也明确落在字段/代码，而不是让模型自述。
- **【需核】是否存在真正的「上下文压缩摘要进模型」链路。** 我在资料里没有找到本项目做摘要进上下文的直接证据（`messages` 是「全链追加式」由 `_complete` 发整链）；`process_notes` 带 digest 是有损投影的候选点。**这是主题「状态摘要被模型信任」在本项目的落点，需回 `recon/K`（上下文片）取证。**
- **【需核】恢复是「读快照」还是「重放事件」。** 本项目 checkpoint 是「整 53 字段整体投影」，语义偏 Snapshot；S6 里没有「事件日志(只追加)可重放」的独立盘。若确为纯读快照，则没有真正的「事件重放」能力——需回 `appv2/runtime` 与 `recon` 片确认 LangGraph saver 的实际用法与是否 setup 了 store。
- **【可简化】多租户/围栏**：本项目只读、单租户，②5 里的多租户隔离与 fencing 可弱化；但「外部副作用幂等」仍适用（写 `runs/blackbox/audit_log` 需幂等键，避免重跑重复落账）——**推断**。
- **【可弱化】工作区/产物存储**（HandBook 第 8 章 §8.3）：本项目只读问答、无代码执行工作区，§8.3 大部分不适用；可只取「产物稳定引用 + 不可变」这一条思想用于报告/查数结果。

## ⑥ 值得抄三条 / 要警惕三条

**值得抄（三条）**

1. **三表示分开命名，明确「哪些点才是可安全恢复点」。** 别把每次 `save` 都叫 checkpoint；Snapshot（当前视图）/Checkpoint（可安全恢复）/Event（发生过什么）分名分义。
   出处：HandBook 第 5 章 §5.3。

2. **摘要四步 `Commit→Compact→Rebuild→Validate` + 「8 类必须保留事实」当自检表。** 直接拿来做本项目 `messages`/`process_notes` 收口与上下文重建时的 checklist；且「会影响后续行动的事实先落权威状态、再允许从活动上下文移除」。
   出处：HandBook 第 5 章 §5.2。

3. **高风险事实确定性提取 + 结构化 Schema 带覆盖范围/版本/来源，模型只压缩叙述性内容；完成由证据决定、模型只能申请。**
   出处：HandBook 第 5 章 §5.2；第 4 章 §4.6.2。

**要警惕（三条）**

1. **【最相关】别让模型无条件相信摘要。** 摘要是**有损投影**，模型「几乎无条件相信」且不会重算；凡摘要里出现计数/状态/结论，尽量由代码逐条抽取汇总生成，并把「摘要 vs 权威字段」的边界标清楚（例如字段旁写「摘要，非权威」）。
   出处：ai-agent-book 第 2 章。

2. **别为省 token 只留摘要删原文。** 只要问题涉及摘要未计算的维度，准确率断崖；本项目 `observations`/`messages`/`last_result` 的原文不要过早只留 digest。
   出处：ai-agent-book 第 2 章。

3. **Checkpoint 落盘时机就是「会重复副作用」的开关。** 挂起/审批/外部调用前后没落盘，恢复就会重复提交；本项目要确认 `M5 execute`、审批放行、`_finalize` 落账这些点的落盘与幂等顺序。
   出处：HandBook 第 8 章 §8.2.3、第 10 章 §10.1.3。
