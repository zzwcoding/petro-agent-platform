## 一、一句话结论

**网关这块业界的共识是「单点策略执行 + 分权」：模型网关只管「选哪个端点、限流降级、计量归因」，不判业务成败；重试要「先判断能否重试，再选目标」，且尝试预算必须跨层传递，否则 SDK × 网关的多层重试会以乘积放大；预算要分清「速率限制 / 余额配额 / 严格上限」三种完全不同的承诺，只有原子预留才算严格上限。** 评测回归这块共识是「用经过业务确认的题库把失败的题冻成可重复的回归项，评分优先确定性、只在没法机判时上 LLM 评判；端到端回归守整体、轨迹前缀回归钉单个决策边界；分数差要过统计噪声才算数」。对本仓（只读、单租户、无写操作、内部平台）而言：**统一出口、429 退避、调用留痕、账本归因四条高度适用且多数已实现；多租户配额、严格预算原子预留、MCP 工具审批那套不适用；评测侧的「黄金数据集 + 门禁子集」已经在做，最大缺口是「轨迹前缀回归」与「判分自动化」。**

## 二、主题⑧ 模型网关

### 2.1 业界主流做法

1. **统一出口 = 单点策略执行，且网关只保证「准入、转发、记录」一致，不判业务成败。** 三种可组合治理语义（LLM Gateway 管模型调用、MCP Gateway 管工具、Agent Gateway 管入口）可同数据面也可分离，关键是「身份映射一致、策略边界清晰、调用记录可关联，且同一次上游调用不被重复计费」。来源：技术书籍/ai-agent-handbook/12_第 9 章 AI 网关与统一流量治理.md（9.1.3、9.1.5）。本仓已有单点：`appv2/infra/gateway/service.py` 的 `GatewayService.complete`（B6 唯一出口），见本仓/appv2/infra/gateway/service.py:169。
2. **模型选择与端点选择分开**，并分四类路由：静态映射/权重、成本感知、语义、推理端点选择（各自适用条件与约束不同）。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.3 表）。业界开源实现同构：LiteLLM 的 `routing_strategy` 有 `simple-shuffle / usage-based-routing-v2 / latency-based-routing / least-busy / cost-based-routing`。来源：https://docs.litellm.ai/docs/routing
3. **重试：错误分类先于重试，先判断「能否重试」再选目标。** 限流响应要结合重置时间/账户配额/替代端点策略；服务端错误只在调用语义允许时重试；认证错误应终止修凭证；上下文超限不该靠截断历史「解决」。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4）。LiteLLM 把这条落成参数：`num_retries` 分级（header/请求体/部署/全局，最具体者胜），按错误类型分策略 `RateLimitErrorRetries / AuthenticationErrorRetries / TimeoutErrorRetries / InternalServerErrorRetries / …`，且「限流错误走指数退避，通用错误立即重试」。来源：https://docs.litellm.ai/docs/routing
4. **尝试预算必须跨层传递，防乘积放大。** 若 SDK 每次逻辑调用最多 3 次、网关每次转发又 3 次，一次用户可见调用最多打到上游 9 次。正确做法：总截止时间是绝对时间，剩余尝试额度由调用方给出、网关按 `call_id` 原子扣减，耗尽后返回明确的预算耗尽错误；每次尝试用稳定 `call_id` + `attempt_id` 关联。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4 表）。
5. **退避 + 抖动是所有远程客户端标配。** OpenAI 官方 cookbook 给 `wait_random_exponential(min=1, max=60), stop=stop_after_attempt(6)`，并强调「加随机抖动避免所有重试同时打回」。来源：https://developers.openai.com/cookbook/examples/how_to_handle_rate_limits ；AWS 架构博客把「Full Jitter」列为基准做法，结论是「不要去掉退避，要加抖动……抖动退避应视为远程客户端的标准做法」。来源：https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/
6. **预算语义三分，别混成一个超时值。** 请求速率限制（QPS/令牌桶）控准入速度、token 时间窗限制控累计用量、余额型配额是近实时额度、**严格预算**才承诺「不超过授权额度」，且要求「可证明的最大消耗 + 原子预留 + 幂等结算退款」。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.6 表与不变量）。业界开源多数只到「阈值/额度」而非硬预留：LiteLLM 的预算「在请求认证时检查一次」，且是 spend 阈值检查而非预留（可靠文档明说 primary attempt 本身永不因预算被拦）。来源：https://docs.litellm.ai/docs/proxy/reliability
7. **熔断/冷却与「摘除」是独立机制。** 连续失败到阈值后暂停选用该目标，靠冷却或健康检查恢复；真实探活会产生费用，应限频并避免多副本重复放大。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4）。LiteLLM 的对称参数：`allowed_fails`（默认 3）＋`cooldown_time`（默认 5s），429 立即触发冷却、「当前分钟失败 > 50%」也触发，冷却按部署（deployment）而非按模型组。来源：https://docs.litellm.ai/docs/routing
8. **审计留痕：结构化审计事件 + 默认元数据、内容按需。** 通用审计事件字段示意为 `event_type / subject_ref / task_id / call_id / attempt_id / policy_version / approval_ref / decision / execution_status / usage_status`；默认日志以元数据为主，prompt/completion/工具参数按风险与需求开启，并做截断、脱敏、访问控制、留存周期。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.5.5）。可观测性章进一步给出「审计最小证据链」要覆盖「主体与授权 → 目标与指令 → 模型调用 → 检索/记忆 → 工具调用 → 系统副作用 → 结果传播」，且**原始事实追加写、不因修正结论而改写**。来源：技术书籍/ai-agent-handbook/17_第 13 章 Agent 的可观测性.md（13.4.1、13.4.2）。企业侧印证：白皮书要求「每一次对企业内部系统的调用都记录审计日志」并按「人 → Agent → 能力 → 行为 → 资源」建审计链。来源：资料/字节安全白皮书.md（7.2.1 统一鉴权网关；2.x 身份七原则）
9. **调用归因要分层账本，不是只看 session。** 归因链路 `task_id → session_id → turn_id → model/tool call → attempt_id`；`task_id` 来自业务应用、网关可生成请求/尝试标识；入口收到关联头要绑定已认证主体并校验租户范围，防伪造 Task 转移费用；缺失可靠关联时记「待归因」，不自行编造业务 Task。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.4.2、9.4.5）。LiteLLM 的 spend 日志同样保留 group 名与「实际服务该请求的成员部署」，并在元数据里落 `attempted_fallbacks` / `original_model_group`。来源：https://docs.litellm.ai/docs/proxy/reliability
10. **流式：测量边界要分开，且不能透明重放。** 连接超时/首字节超时/TTFT/流式空闲超时/总截止各管一段、不互相代替；「尚未收到响应体」≠「上游尚未执行」（可能已计费甚至已产生副作用）；网关通常不能对已提交的流式响应透明重放整段。部分协议需显式请求流式 usage（如 `stream_options.include_usage`），缺 usage 不能记为零消耗，客户端取消也不能证明上游停止生成。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4、9.2.5、9.6.3）
11. **缓存键必须区分租户/权限范围/模型版本/系统提示/知识版本**，不能让语义相似绕过数据隔离；含副作用的工具调用不应简单重放缓存。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.8）
12. **网关自身的变更是受控发布链。** 观测→候选建议→构建验证→治理授权与发布门禁→灰度→回流；回滚不只是恢复配置文本，还要考虑已执行的副作用、未结算额度和在途任务。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.6.1、9.6.5、9.6.7）

### 2.2 分歧 / 取舍

- **网关能力边界：集中入口 vs 框架就地。** 工具少、边界清晰时可应用内搞定；多 Harness/团队/工具共享时才值得集中入口，代价是网关成为高价值安全目标。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.3.8）。业界开源分歧明显：Portkey 网关把限流/配额/重试/回退/缓存打包成产品能力。来源：https://portkey.ai/docs/product/ai-gateway
- **429 到底切不切厂商，业界并不统一。** 本仓现行策略是「429 不切、直抛调用方」（见本仓/appv2/infra/gateway/service.py:175-176 docstring）。LiteLLM 的默认却把「429 立即触发 cooldown 并转向 fallback」。来源：https://docs.litellm.ai/docs/routing 。这属于「限流是瞬时的、切厂商可能白切换」与「限流也可能持续、切厂商能救命」的取舍——**待裁**。
- **严格预算（原子预留）vs 阈值 + 告警。** HandBook 明确「请求前检查、响应后扣减」无法保证硬上限（余额 100，两笔各 80 同时通过 → 160）。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.6）。LiteLLM/Portkey 都只到额度阈值层。本仓现行熔断是「触顶改路由不拒绝」（本仓/appv2/infra/gateway/service.py:342-358），属软上限。**是否要硬上限属业务/财务裁决。**
- **审计内容详略。** HandBook 主张默认元数据、内容按需并脱敏；本仓 `calllog.py` 却默认**全量记录 messages 全文 + 返回全文**（本仓/appv2/infra/gateway/calllog.py 模块 docstring）。内部只读平台可接受，但 `logs/` 不入仓的纪律必须守。
- **降级模型可能改变业务契约。** 「自动降级」若让备用模型在协议层能返回工具调用、但多步任务丢中间约束，会产出「结构合法却结果错误」的执行。来源：技术书籍/ai-agent-handbook/03_第 2 章…（2.2.1，见《最佳实践-1》引用）；面试侧也强调降级要「用户告知已切换」。来源：资料/录音 面试考点速查.md（Q37/Q38）

### 2.3 反例 / 踩坑

- **多层重试乘积放大**：SDK 3 次 × 网关 3 次 = 上游最多 9 次；每层都以为自己的上限是 3，端到端却没有「3」这个约束。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4）
- **把「缺 usage」当零消耗、把「客户端取消」当上游已停**：都会让对账失真。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.5、9.6.3）
- **余额检查 + 响应后扣减**无法保证硬上限（见 2.2）。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.6）
- **只记「放行日志」不记「执行结果」**：审计既要有准入依据也要有实际结果，不能以放行代替成功。来源：技术书籍/ai-agent-handbook/12_第 9 章…（9.5.3、9.6.3 常见误区）
- **跨厂商搬运轨迹的凭证坑（实测反例）**：Anthropic 的思考带 `signature`、Google 的 `thoughtSignature` 挂在工具调用上；「直传能过不等于对」——把 Claude 的签名原样贴给 Gemini 能过，只是因为 Gemini 不校验谁的签名。法参数中途续写会静默写错：断点 `{"city":"东` 续写成 `{"city":"东"}`（JSON 合法，城市从「东京」变「东」）；且「元指令」恢复在每个单元都比整轮重发更贵。来源：技术书籍/ai-agent-book/ai-agent-book/chapter5/provider-failover/README.md
- **429 的文本子串判定会误伤**：本仓现行 `_is_rate_limited` 除了 `status_code == 429`，还把 `reason + str(exc)` 里含子串 `"429"` 判为限流，会把 token 数/端口号含 429 的异常误判成限流并退避重试。来源：本仓/docs/runtime-refactor/recon/L3-网关与支撑小件.md（R-L3-06/R-L3-07、D-L3-03）
- **退避总时长与总时限的先后未声明**：缺省退避序列最长约 3×60s×1.1≈198s，而 run 总时限合同是 300s——两者的先后关系代码未声明。来源：本仓/docs/runtime-refactor/recon/L3-网关与支撑小件.md（D-L3-11）

## 三、主题⑩ 评测与回归

### 3.1 业界主流做法

1. **黄金数据集 = 一组经过业务确认的任务，既有题目也有判定依据。** 五种用法：定「什么算回答好」、选模型/方案、验证一次修改（保留逐题前后得分）、防老问题重现（长期回归）、校准评估器。来源：技术书籍/ai-agent-handbook/26_第 21 章 Agent 黄金数据集.md（21.1、21.5）
2. **题库要按覆盖选择，不要只收低分题。** 应保留：高频问题、已发生过的问题、业务边界与高风险要求、**原本表现正常的题（发现退化）**、表述变化与多轮问题。来源：技术书籍/ai-agent-handbook/26_第 21 章…（21.4）
3. **参与优化的题与独立验证的题必须分开**：一旦反复看这些题并据此改 Agent，它们就已参与调优，应另留新验证题。来源：技术书籍/ai-agent-handbook/26_第 21 章…（21.6）
4. **评测任务三来源**：公开基准（粗筛与借手法）、自建业务集（可作选型/设计依据）、**生产轨迹回流**（成本最高、准确性最高）；上线后生产回流会成为主体。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md（「评估集的三个来源」）
5. **指标口径要分「能力上限」与「业务可靠性」。** Pass@k（k 次至少过一次，能力天花板）vs Pass^k（连续 k 次都过且不触发一票否决，业务可靠性）；`p=0.6,k=5` 时 Pass@5≈99% 但 Pass^5≈7.8%。评估报告须写清 k 的口径。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「评估指标：成功的定义」）
6. **验证器要核「机器可独立复核的事实」，不是 Agent 自我陈述。** SWE-bench Verified 用 FAIL_TO_PASS（修复前失败/修复后通过）+ PASS_TO_PASS（前后都过，证明没引入新缺陷）两个独立命题，并额外排除 flaky test。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「验证器」）
7. **能写成程序化断言的都用断言，LLM 评判只用于确实无法机械判定的维度。** 确定性验证更便宜、更稳定，也适合作为回归长期运行；向右（转 LLM 评判）不意味着放弃左侧。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「自动化评估方法」开篇）
8. **LLM-as-a-Judge 要配结构化 Rubric 并防偏差。** Rubric 四准则（基于专家指导 / 全面覆盖含 Pitfall / 按重要性加权含一票否决 veto / 评价标准自包含）；防长度偏差（惩罚冗长、配对比较控制长度相近、定期审计分数与长度相关性）；防同源模型 Goodhart 用多源异构评判；防位置偏差用「交换顺序各评一次」。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「LLM-as-a-Judge」「配对比较与模型排名」）。一票否决的现实价值有数据：180 次评判中幻觉否决触发 28 次。来源同上（表 7-3 讨论）
9. **失败归因＝定位「首个导致偏离的错误」**，后续错误多是连锁反应；结构化记录（引用步骤号/工具名/证据、区分根因与后果、判断可恢复性、给置信度）；「规则先筛嫌疑轨迹、LLM 再定位首错」比全喂 LLM 更便宜也更准。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「失败归因：从整条轨迹定位首个错误」）
10. **两类回归互补：端到端回归守整体、轨迹前缀回归钉单个决策边界。** 端到端从初始状态跑完整任务，最接近生产但难定位哪一步失败；轨迹前缀把首个错误之前的状态冻结、只验证下一步，成本更低、能隔离单个策略/工具问题，**对高可靠生产级 Agent 往往比端到端更重要**。答案应定义为「可接受动作集合」而非唯一动作。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「端到端回归任务与轨迹前缀回归任务」「实验 7-7」）
11. **统计显著性：小样本的分数差可能只是噪声。** 标准误 `SE(p)≈√(p(1-p)/n)`；100 题 70% 的 95% 置信区间约 ±9 个百分点；同批任务比两配置要**配对分析**（McNemar / 配对 bootstrap）而非相减两个独立成功率；每配置用 3–5 个随机种子报均值与波动；多重比较要收紧阈值或独立复跑。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「评估结果的统计显著性」）
12. **内部评估基础设施是持续能力**：消融开关（每特性可独立关闭、定期验证贡献）、AB 测试（多臂、区分机制指标与目标指标、设护栏指标、记基线统计）、双层特性开关（编译时/运行时）、提示词版本化 + 每次改动跑回归、隐私感知分析。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「从外部评估到内部评估」）
13. **看分数下降先查评测系统本身，再动 Agent。** 环境资源不足被杀、验证器 bug 把正确答案判失败、用例与生产脱节——在数字上都长得像模型退化，只有看完整轨迹才能区分。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「从 Benchmark 报告到系统改进」开篇）
14. **模型替换实验用来区分「模型能力不足」还是「Harness 设计缺陷」**：固定 Harness 只换模型，换强模型分数不涨说明瓶颈在 Harness。来源：技术书籍/ai-agent-book/…/book/chapter7.md（开篇段落）

### 3.2 分歧 / 取舍

- **规模 vs 统计功效 vs 成本。** 复杂 Agent 任务用前沿模型跑完一个数据集动辄数千美元；所以 SWE-bench Verified 发布前淘汰原始任务 71%（2294→500）来提信噪比、降成本。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「质量控制与长期维护」）。小样本「只用来决定下一步是否值得扩大测试，不能推断整体成功率」。来源同上（表 7-5 讨论）
- **确定性 vs LLM 评判。** 谱系两端各有代价：确定性可复现、可进 CI，但只能判最终结果对不对、给不出错误原因；LLM 评判能诊断但会波动、有偏差。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「自动化评估方法」）
- **平均分 vs 关键题不回退。** 候选总分提高但关键条款仍未通过，这轮不适合升级；只有一题改善而其他题退化，要回具体修改看是否把某种格式强加给所有问题。来源：技术书籍/ai-agent-handbook/27_第 22 章 Agent 优化：Badcase.md（22.6）
- **门禁「回归金丝雀」≠「质量天花板」。** 本仓的做法：冻结 60 题门禁子集，门禁只回答「没弄坏旧的吗」；「系统变好了没有」由当轮新题（移动靶）说了算。来源：本仓/eval/gold-v1/README.md（第一、二节）
- **同句可判不同层。** 本仓对同一句题干分两层判分（golden 判 QueryPlan 意图机器判、问数组判端到端答案），「同句不同判分层，非重复」。来源：本仓/eval/gold-v1/README.md（第三节）

### 3.3 反例 / 踩坑

- **被评测系统自身的 bug 误导**（见 3.1 第 13 条）。来源：技术书籍/ai-agent-book/…/book/chapter7.md
- **评估器只查关键词**：把泛泛介绍当作操作指导（评估器只检查是否出现「评估器」这个词）。来源：技术书籍/ai-agent-handbook/27_第 22 章…（22.2）
- **只看总分/只看低分**：小而不集中的失败簇容易被总分淹没；高分样本也要抽检，避免漏掉评估器未识别的严重问题。来源：技术书籍/ai-agent-handbook/27_第 22 章…（22.2、22.3）
- **奖励作弊 / Reward Hacking 与长度偏差**（见 3.1 第 8 条）。来源：技术书籍/ai-agent-book/…/book/chapter7.md
- **二元奖励掩盖「做对了但说错了」**：τ²-bench 704 次运行失败 240 次，其中 162 次是信息告知出错，80 次（占失败三分之一）环境状态正确但告知错误。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「做对了但说错了」问题）
- **对照基线本身有偏**：拿 Fish 参考音色去比通用 TTS，天然偏向 Fish——「选什么参考答案本身就是评估设计」。来源：技术书籍/ai-agent-book/…/book/chapter7.md（实验 7-5 讨论）
- **单次运行下结论**：单次运行只能筛方向，要多种子与配对分析。来源：技术书籍/ai-agent-book/…/book/chapter7.md（「评估结果的统计显著性」）
- **本仓实测的判分档波动**：C-正5 在 Q14 判 ⚠、Q15 判 ❌（「no_hit 闸转答」在两轮间波动）；另有「送窗口径差」——对账报告称「送窗 16~31 支」vs 逐腿机检「6~46 支」。→ 判分档位与口径不统一会污染回归信号。来源：本仓/docs/runtime-refactor/arch/P8b2-评测病理.md（K-P8b2-05、疑点§七.4）

## 四、对本项目 9 段的适用性

**总判：两项主题「高度适用」的是网关单点出口、429 退避、调用留痕、账本归因、黄金数据集门禁；「不适用」的是多租户配额、严格预算原子预留、MCP 工具审批、模型采购/计费。**

按 9 段定位（段号沿用任务背景 ①进门 ②理解 ③澄清 ④匹配 ⑤前置检查 ⑥批量执行 ⑦作答 ⑧核验 ⑨收尾）：

| 段 | 网关面适用性 | 评测回归面适用性 |
|---|---|---|
| ①进门 | 适用（弱）：身份→主体映射；本仓单租户、无委托，跳过「委托核验/凭证链」 | 适用：进门安全闸（注入/外发/写意图）需端到端回归题（本仓 N0 三硬闸已入仓，见 P8b2 K-P8b2-25） |
| ②理解 | 适用：LLM 调用点（caller=understand）经统一出口，限流/重试/留痕直接覆盖 | **适用（关键）**：直答判定边界宜做轨迹前缀回归（本仓 askback 误直答即此类，K-P8b2-24） |
| ③澄清 | 适用：caller=decision 的澄清发射走网关 | 适用：澄清环截断（clarify_capped 后零交付）宜有回归题（K-P8b2-07） |
| ④匹配 | 适用：工具匹配/路由判定是 LLM 调用点 | 适用：路由与结果判定分权；匹配错误宜轨迹前缀（K-P8b2-01 零观察 finalize、K-P8b2-08 误路由） |
| ⑤前置检查 | 不属 LLM 网关；但「审批挂起→批准后重新准入」的语义可借；本仓已有外表审批（approval_id） | 适用：前置条件机（blocked_refuse/note/budget_converged）行为需回归（K-P8b2-05/06） |
| ⑥批量执行 | 不属 LLM 网关（工具/DB 调用）；「执行结果 ≠ 业务完成」「幂等」，工具调用可借 | 适用：执行结果确定性断言（行集/血缘/截断注记）——本仓 gold-v1 判分锚点已覆盖 |
| ⑦作答 | 适用：caller=answer 的最大 token 消耗点，成本/限流最敏感 | 适用：内容纪律（诚实线/无据调和句/跨套混写）用 Rubric + veto（本仓三档判分正是此形，K-P8b2-03） |
| ⑧核验 | 适用（弱）：核验若调 LLM 也走出口 | 适用：核验「支撑 0 仍交付」需回归（K-P8b2-02） |
| ⑨收尾 | 适用：run_completed/failed/refused 审计留痕与归因链收口已实现（本仓/recon/J） | 适用：黑匣子/回放本身是评测数据来源 |

**具体到本仓已实现 vs 缺口（据 recon 与代码，非逐行核）：**
- 已实现：单点出口 `gateway.complete`；`runtime/llm.py` 的 429 退避重试（含 ±10% 抖动）；`gateway/calllog.py` 全量调用留痕（JSONL，旁路观测、写失败不影响调用）；`SpendRecord` 账本（含 caller/run_id/attempted_fallbacks 归因列）；`BudgetStore` + `fuse_latched` 熔断（触顶改路由不拒绝）；`_DynamicGate` 动态并发闸。
- 明显缺口：「轨迹前缀回归」在本仓未建（P8b2、gold-v1 均未提及）；门禁判分**仍由人对答案册**（`eval/results/tools/rerun.py` 只产「判分辅助表」），回归自动化卡在人工判分；网关层与 runtime/llm.py 的重试是否乘积放大，代码未声明统一口径。

## 五、值得抄三条 / 要警惕三条

### 值得抄（三条）

1. **重试「先判能否重试、再选目标」+ 尝试预算跨层传递 + `call_id`/`attempt_id` 关联。** 出处：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4）；配合 LiteLLM 的按错误类型分策略参数。本仓现状是 runtime/llm.py 与 gateway 各持一套重试，值得显式化两者的乘积关系与绝对截止时间。
2. **预算三语义分离 + 结构化审计事件字段。** 出处：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.6、9.5.5）。审计事件模板（`event_type/subject_ref/task_id/call_id/attempt_id/policy_version/approval_ref/decision/execution_status/usage_status`）可直接对照本仓 `audit.py` 的 `AuditRow` 与 `calllog.py` 记录面查漏。
3. **两类回归（端到端 + 轨迹前缀）+ 答案=可接受动作集合 + 配对统计。** 出处：技术书籍/ai-agent-book/…/book/chapter7.md。本仓 gold-v1 门禁已近端到端回归，「轨迹前缀回归」是可直接补的缺口，尤其对 ②理解/④匹配/⑧核验三个决策点。

### 要警惕（三条）

1. **多层重试乘积放大。** 出处：技术书籍/ai-agent-handbook/12_第 9 章…（9.2.4）。本仓 runtime/llm.py（缺省 3 次）与 gateway.service（`num_retries`）双层，需核对是否变成乘积、退避总时长（最长约 198s）与 run 总时限（300s）的先后关系。
2. **usage 缺失/取消/限流误判三条失真源。** 「缺 usage 当 0」「客户端取消当上游已停」（技术书籍/ai-agent-handbook/12_第 9 章… 9.2.5、9.6.3）+ 本仓 429 子串误判（recon/L3 D-L3-03）。
3. **别被评测系统本身与判分口径波动误导。** 分数下降先查评测系统（技术书籍/ai-agent-book/…/book/chapter7.md）；本仓已实测判分档波动（C-正5 ⚠→❌）与送窗口径差（P8b2 疑点§七.4），回归信号的可信度取决于口径先统一。
