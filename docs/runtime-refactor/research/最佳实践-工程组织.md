## 一、主题① 代码结构 / 分层与模块边界

### 1.1 做法

1. **先划分责任边界，再决定组件与框架；架构的难点不是罗列组件，而是划责任边界。** 明确四类必须先拆开的边界：Model 与 Harness、编排逻辑与 Runtime、Context 与 State、沙箱／权限／工具描述。来源：技术书籍/ai-agent-handbook/03_第 2 章 Agentic Application 参考架构.md（章首、2.1.3）。标记：**适用**（本仓 infra / runtime / tools / knowledge / query 分层正对应「先划边界」）。
2. **用「能力责任域」而不是「严格调用栈」来组织分层。** 书里给五域——业务与应用层、Agent 构建与编排层、生产运行层、治理与控制层、调优层；并明说「层用于组织架构责任，不表示严格的调用栈或建设顺序」。来源：同上（2.1.2）。标记：**适用**（可对照本仓 7 层的职责命名是否「按责任」而非「按调用栈」）。
3. **同一套系统用三个正交视图看：组件视图（由什么组成）、平台视图（在哪里运行／谁负责）、控制／生命周期视图。** 三视图不能互相推导，「组件齐全」不等于「责任清晰」。来源：同上（2.1.1）。标记：**适用**。
4. **逻辑边界不必对应独立服务或部署单元。** 「一个 SDK 可以同时包含 Harness 和本地 Runtime」，但架构设计仍要保留边界，否则无法判断故障归属与迁移成本。来源：技术书籍/ai-agent-handbook/05_第 3 章 范式：Harness 的主流构建方式和责任边界.md（3.1.1 表后段）。标记：**适用**（单体进程内分层即成立）。
5. **「一个模块」＝单一目的、可独立替换、有清晰输入输出契约的执行／能力单元。** 对应两条经典原则：单一职责（每个模块单一目的）、DRY（重复逻辑上收为可复用件）；「模块化」＝把逻辑分解为可被其他模块调用的更小块。来源：技术书籍/Fundamentals of Analytics Engineering/翻译稿/ch06_transforming_data.md（模块化 / DRY / SRP 小节，行 175-219）。标记：**适用**。
6. **按「逐层累加复杂度」做分层转换：清洗（Clean）→ 集成（Integrate）→ 富化与汇总（Enrich & Summarize）**；dbt 的 Staging / Intermediate / Marts 与数仓 ODS→DWD→DWS→ADS 同构，核心理念是「转换透明、可复用、易理解」。来源：同上（分层转换，行 45-64）。标记：**适用 / 待裁**（本仓 runtime 的 9 段流程是否照此「逐层叠复杂度」切，属设计取舍）。
7. **判断边界划得对不对的第一判据：下沉三原则——复用性、强制性、可验证性。** 一项能力「只有同时满足复用性，且至少满足强制性或可验证性，才具备下沉理由」；并区分「任务语义（终止条件、验收标准、上下文策展）不下沉，留在应用侧」。来源：技术书籍/ai-agent-handbook/52_第 30 章 从 Agentic Application 到 Agentic OS.md（30.2.1、30.3.3）。标记：**适用 / 待裁**（可直接当本仓「某能力该放 infra 还是 runtime」的判据参照）。
8. **判断边界划得对不对的第二判据：稳定接口。「不重写任务语义即可替换实现，并能用同一套评估证明等价」才算解耦成立**；并列了「破坏解耦的典型做法」（如编排层直接依赖某 Runtime 的内存结构／进程模型）。来源：同上（30.4.1、30.4.2）。标记：**适用 / 待裁**。
9. **别按抽象层数堆复杂度：保持简单、保持透明、从最少抽象开始。** 「每多一层抽象都会成为以后调试时新的盲区」；「清晰的代码优于聪明的抽象」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（构建有效 Agent 的核心原则，行 340 前后）。标记：**适用**。
10. **关键文档缺失时先补「架构概览 + 目录结构 + 运行指南」：主动读代码识别主要模块、核心抽象、组件间依赖关系。** 「知识的显式化是高效协作的前提」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（行 93 附近）。标记：**适用 / 待裁**（本仓 docs/ 已有 recon 与 synth，可对照覆盖度）。

### 1.2 本地缺口

- **无「按文件／行数／函数数划模块」的量化标准**：资料没有任何「一个模块不该超过多少行 / 多少文件」的硬指标。
- **无 Python 包／命名空间级模块划分指南**：所有「分层」讨论都在「能力责任域」层面，没有落到 `pkg.subpkg.module` 的划分与命名约定。
- **无「依赖方向契约怎么写成 import-linter 配置」的方法**：本仓 `tools/importlinter_v2.toml` 是自建闸，资料里没有任何对应的「怎么写、怎么维护依赖方向闸」的指导（handbook 52 只到「约束应位于被约束方之外」的概念层）。

## 二、主题② 技术选型（编排框架用还是不用）

### 2.1 做法

1. **默认「从简单到复杂」：先单次调用 → 需要多步且路径固定就用工作流 → 只有路径无法预先确定才用自主 Agent。** Anthropic 经验：「最成功的实现往往不是使用复杂框架，而是简单、可组合的模式」；并明确「Agent 系统用延迟和成本换任务性能，要谨慎权衡」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（编排模式：工作流与自主，行 370 前后）。标记：**适用**。
2. **工作流与自主 Agent 的分界线＝「路径能不能预先写出」。** 工作流两优势：严格流程控制（关键步骤不被跳过／乱序，规则用代码强制）、攻击面被限制在单节点内；主要局限：缺乏变通性。来源：同上。标记：**适用**。
3. **选框架的唯一判据是「能否用尽可能少的抽象层让你专注业务逻辑」，不是框架复杂度。** 「学会某个具体框架的用法并不重要」。来源：同上（主流框架对比表后段）。标记：**适用 / 待裁**（本仓已把 langgraph 只许在 runtime，见本仓/tools/importlinter_v2.toml，与「框架只待在被许可的薄层」同向）。
4. **图编排框架的定位与能力边界：LangGraph ＝ node + edge 编排，subgraph 拆子流程，checkpoint 状态持久化（可中断恢复，类似存档）。** 来源：资料/录音 面试考点速查.md（Q5：LangGraph 的 subgraph 和 checkpoint）。标记：**适用 / 待裁**。
5. **四类构建入口由「责任归属」区分，不由成熟度区分：自建高代码框架 / 产品化 Harness / 基于托管模型 / 基于云产品。** 选择时分别判断：「任务效果是否依赖修改 Loop 或 Context、数据和执行环境能否托管、团队是否愿意维护状态恢复与 Sandbox」。来源：技术书籍/ai-agent-handbook/05_第 3 章 范式…md（3.1.3、3.2.3）。标记：**适用 / 待裁**。
6. **能用现成扩展点就别在外部模拟：优先用已有 Harness 的 MCP / 插件 / 钩子，只有现成行为与成功标准不匹配时才考虑转自建。** 来源：同上（3.3.2）。标记：**适用 / 待裁**。
7. **框架的约束在不使用该框架时即失效；系统层的约束应在被约束方不配合时仍成立。** 二者「区别在于强制点位置」，不是层次高低。来源：技术书籍/ai-agent-handbook/52_第 30 章…md（30.2.2 第二条否定）。标记：**待裁**（本仓的「四层 + B1–B16」边界规则属哪一类，需 Owner 判）。
8. **警惕「补偿模型短板的脚手架」被固化进业务代码：适配层会随模型变强被模型自己内化。** 文中列举「few-shot、CoT 提示词、输出格式修复、提示词改写」都被新一代模型吃掉；「模型升级可能使某些补偿性 Prompt、工具或循环控制失效」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（文生图适配层实验）；技术书籍/ai-agent-handbook/03_第 2 章…md（2.2.2）。标记：**适用 / 待裁**。
9. **串并行取舍：优先串行（并行状态难掌控）；只有「上下文隔离、能力／权限隔离、可并行」三者收益超过通信与合并成本时才委派。** 来源：资料/录音 面试考点速查.md（Q21：Agent 串行 vs 并行「一定不要并行，状态难掌控」；Q23）；技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md（4.3.1）。标记：**适用**。
10. **编排结构选择要同时看四点：动态决策需求、路径稳定性、风险、维护成本；预定义工作流可减少重复规划并使控制路径可测，但不消除节点内模型错误／工具开销／失败重试。** 来源：技术书籍/ai-agent-handbook/13_第 10 章 Agent 异步任务与自动化流程.md（10.4.1）。标记：**适用**。
11. **DAG 优先、需要循环用「有界展开／子流程迭代」表达，图本身保持无环；真要带环的驳回重来就别硬塞进 DAG，改用状态机。** 节点分业务节点与逻辑节点（条件分支／并行／汇聚／循环／等待／错误处理／子工作流）。来源：同上（10.4.2）。标记：**适用 / 待裁**。
12. **低代码 / 工作流 / Agent 三者的适用面不同：流程固定用低代码，流程确定且有分支用工作流（LangGraph 编排），意图不明确才用 Agent。** 来源：资料/录音 面试考点速查.md（Q25 框架对比表）。标记：**适用**。

### 2.2 本地缺口

- **无任何具体框架的版本／替代／迁移评估**：资料没有 LangGraph、LangChain 的版本矩阵、升级代价、退出成本；也没比较「自建极简图引擎 vs LangGraph」的取舍。
- **无「框架依赖怎么收口到单点」的工程做法**：本仓有「langgraph 只许在 runtime」的红线，但资料未讨论「框架依赖隔离层怎么写、怎么测」。
- **无性能／成本对比数据**：除 Anthropic/OpenAI/Google 的经验法则外，本地资料不含可复现的框架性能基准。

## 三、主题③ 技术组织方式（依赖方向 / DI / 单例 / 公共件收口）

### 3.1 做法

1. **五条架构设计原则：① Model 与 Harness 解耦；② 编排层与 Runtime 解耦；③ 状态外置、执行实例可替换；④ 自主性必须与权限和可验证性匹配；⑤ 可观测、安全与评估是运行前提。** 并给出反面：这四类边界不清会在「任务变长、工具变多、租户变多」后集中暴露。来源：技术书籍/ai-agent-handbook/03_第 2 章…md（2.1.3、章首）。标记：**适用**（①②③ 与重写目标同向）。
2. **四个解耦面的「稳定接口对象」与「破坏解耦的典型做法」成对给出**：模型/Harness（请求响应格式、工具调用协议）、Harness/运行时（Run/Session/Checkpoint/Workspace 的状态语义）、能力/协议（工具描述、发现、调用与错误语义）、运行时/承载环境（沙箱契约、快照与恢复接口）。破坏方式如「编排层直接依赖某运行时的内存结构或进程模型」。来源：技术书籍/ai-agent-handbook/52_第 30 章…md（30.4.1 表）。标记：**适用 / 待裁**。
3. **边界交接的接口应是「任务与状态」，不是函数调用细节；编排层不得依赖某个 Runtime 的内存结构。** 编排层负责语义层决策，Runtime 负责物理层保障。来源：技术书籍/ai-agent-handbook/03_第 2 章…md（2.2.2）；技术书籍/ai-agent-handbook/10_第 7 章 Agent 运行时与沙箱.md（7.6.1）。标记：**适用 / 待裁**（本仓 runtime↔infra 的交接面是否「任务与状态」而非内部结构，属裁决）。
4. **三平面（执行面 / 数据与资源面 / 控制面）与「集中定义、分布判定、异步回送审计」：控制面不应成为每次模型或工具调用的强同步依赖。** 代价是策略传播延迟，高风险策略需强制刷新兜底。来源：技术书籍/ai-agent-handbook/03_第 2 章…md（2.3.2）。标记：**适用 / 待裁**。
5. **公共件收口之一：模型接触单点＝Gateway，且要「先声明支持的能力子集，再约定不支持参数如何报错，而不是静默忽略差异」；统一契约的价值是让计量／限流／统计复用明确字段语义。** 来源：技术书籍/ai-agent-handbook/12_第 9 章 AI 网关与统一流量治理.md（9.2.2、9.2.3）。标记：**适用**（正对应本仓 B6「litellm 唯一接触点」）。
6. **公共件收口之二：网关层单点做三件事——校验调用来源、生成 trace ID、检测 token 用量；trace ID 全程带（→ 工具 → 调用 → 日志）。** 来源：资料/录音 面试考点速查.md（Q26）。标记：**适用 / 待裁**（本仓审计唯一写口 security.audit、时间唯一 infra.clock 与 B12/B14 同向）。
7. **重试／超时预算必须跨层传递，不能让每层各自解释一个上限（否则次数以乘积放大）；每次实际尝试用稳定的 call_id / attempt_id 关联。** 「每一层都认为自己的上限是 3，端到端却没有 3 这个约束」。来源：技术书籍/ai-agent-handbook/12_第 9 章…md（9.2.4 表）。标记：**适用 / 待裁**。
8. **轨迹（trace）不该按任何一家的接口格式存储，应保存为中立格式**；每段思考拆成「可移植的文字」与「不可移植的凭证」，工具调用只记名称与参数。中立轨迹同时支撑评估重放、训练样本构造、经验提取。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（跨厂商的轨迹接管，行 205 前后）。标记：**适用 / 待裁**（本仓有 RunState / 事件帧留痕，是否「中立格式」需核）。
9. **约束优先于指导：能用代码强制的规则就不要只写在文档／提示词里。** 「Linter 规则、类型约束、CI 检查的价值远超系统提示词中『请遵循…』式的指导——前者是『做不了』，后者只是『建议别做』」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（通用设计原则第 1 条，行 160-165）。标记：**适用**。
10. **网关不是万能：多副本不等于没有单点；状态写入 Redis 不等于一致性自然成立**；共享存储、外部策略服务、内容检测服务的故障行为要逐项定义。来源：技术书籍/ai-agent-handbook/12_第 9 章…md（9.1.5）。标记：**适用 / 待裁**。
11. **框架底座骨架的既有做法（教学版参考）：路由注册、依赖注入、全局异常处理、请求日志中间件；模型配置外置（yaml）；统一 `chat()` 出口。** 来源：资料/计划:石油AI智能体项目学习计划.md（6.0 底座；5 技术栈规格）。标记：**待裁**（该文自述为「FastAPI 单体 + LangGraph 三 Agent + LiteLLM」**教学版**，提纲示明其架构 ≠ 本仓架构，只作接口／做法参考）。

### 3.2 本地缺口

- **资料几乎不涉及「依赖注入 / 单例 / 全局状态」字面**：全库检索命中极少（仅「学习计划」一句「依赖注入」）。**没有** Python 服务里「DI 容器 vs 构造函数注入 vs 模块级单例」的取舍指导，也没有「全局状态该不该有、怎么收」的纪律。
- **无配置分层（env / yaml / secret / 环境级）的规范**，只有「配置外置」一句。
- **公共件（日志 / 时钟 clock / 连接池）的收口做法无专章**：资料只在网关章覆盖「模型与工具调用的单点」，日志/时间/DB 连接这三类平台公共件在资料中没有对应论述（本仓 B3/B14 属自建纪律）。
- **无「依赖方向闸／分层闸」的工程写法**（同主题①缺口）。

## 四、主题④ 代码编写方式（规约 / 规模 / 可测试性 / 命名 / 注释 / 便于人和 AI 读）

### 4.1 做法

1. **编码规范落成可机检项：PEP 8——缩进 4 空格（不用 Tab）、行宽 ≤79（注释 72）、导入三组（标准库 / 第三方 / 自身）、无多余空格、引号风格统一。** 来源：技术书籍/Fundamentals of Analytics Engineering/翻译稿/ch10_writing_code_in_team.md（PEP 8 小节，行 237-249）。标记：**适用**。
2. **Linter + 自动格式化（Black / Flake8 等）「几乎非法不用」；轻量校验放 pre-commit，重型校验放 CI**（「不要在 pre-commit 里放重量级任务」）。来源：同上（Linters、Pre-commit hooks，行 273-296）；技术书籍/Fundamentals…/翻译稿/ch11_automating_workflows.md（Pre-commit hooks、代码格式）。标记：**适用**。
3. **命名与可读性：给表和列用别名，命名约定直观一致，列名在 SELECT 中显式引用并标出来源表（禁用裸 `*`）。** 来源：技术书籍/Fundamentals…/翻译稿/ch06_transforming_data.md（其他最佳实践，行 209-221）。标记：**适用**。
4. **注释边界：解释「为什么」而不是「怎么做」；好代码自解释，注释应解释「你为什么这么写」。** 来源：同上（行 219）；技术书籍/Fundamentals…/翻译稿/ch10…md（代码注释，行 337-344）。标记：**适用**。
5. **文档分四类：代码注释 / README / 入门指南 / 概念性文档**；README 应含主要功能、安装、排障、维护者、变更日志、示例；「新人第一天能 clone→跑通」是黄金标准，超过 1 天的 onboarding 视为团队债。来源：技术书籍/Fundamentals…/翻译稿/ch10…md（编写文档，行 318-374）。标记：**适用**。
6. **便于人和 AI 阅读，前提是把上下文写成显式物：目录结构、各模块职责划分、核心数据结构定义、团队代码规范。** 「没有这些，Agent 写出的代码可能语法正确但风格与本项目格格不入，甚至引入架构层面冲突」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md（行 15）。标记：**适用 / 待裁**。
7. **把隐性规范显性化为「可加载、可执行的约束物料」六类：规则、项目宪法、应用描述、架构文档、历史经验、编码规范；以统一索引入口按需加载。** 来源：技术书籍/ai-agent-handbook/36_从编码提效到端到端交付，云通信的人机协作实践.md（2.2 应用物料层）。标记：**适用 / 待裁**。
8. **可测试性靠模块化：单一职责 + DRY，把逻辑拆成「可隔离、可单独测试」的小块后，再做优化。** 「一旦代码被分解为简单、可理解的部分，就应执行优化——这允许隔离和测试每个逻辑片段」；「调试冗长复杂的查询像大海捞针」。来源：技术书籍/Fundamentals…/翻译稿/ch06…md（可读性和可重用性优先、模块化，行 141-215）。标记：**适用**。
9. **改动的验证要成对：边界集（应当改变的样本）+ 保留集（不应受影响的样本）；只测前者会把过拟合当进步，只测后者会把无效修改当安全。** 来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（贯穿全书的设计模式：Boundary Set + Retention Set）。标记：**适用**。
10. **「约束优先于指导、验证要自动化、反馈越快越结构化越好、回退要可靠」四条通用 Harness 设计原则可迁移到工程代码。** 来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（通用设计原则，行 160-165）。标记：**适用**。
11. **每个修改请求应是一份「可证伪的变更契约」**：列出失败证据、推断根因、归属组件、修改提案、预期修复行为、可能受损的既有行为，以及分别验证二者的用例；「可编辑组件都有文件级表示」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter9.md（行 190）。标记：**待裁**（本仓为一票一提交，可对照票面是否含此类契约）。
12. **PR 走「四眼原则」：至少 1 人独立审；大型 PR 拆小（经验值 <300 行）；PR 模板强制填「测试用例 / 影响范围」。** 来源：技术书籍/Fundamentals…/翻译稿/ch10…md（评审代码、Pull Request——四眼原则，行 298-316）。标记：**适用 / 待裁**。

### 4.2 本地缺口

- **无「函数 / 文件规模」的量化红线**：资料没有任何「函数不超过 N 行 / N 个参数、文件不超过 M 行」的硬指标（本仓背景里 appv2 已 21151 行、73 文件，此缺口直接相关）。
- **无 Python 类型标注 / typing / mypy 规范专章**；无 docstring 规范（只有通用「注释解释为什么」）。
- **无「给 AI 读的注释」与「给人读的注释」的区分标准**：只到「上下文要显式化」，没给注释层的具体写法规则。
- **无命名风格细则**：除 PEP 8 通用项外，资料不含「模块 / 类 / 函数 / 常量」的命名约定展开。

## 五、主题⑤ 大重写的施工顺序

### 5.1 做法

1. **迭代而非一锤子 spec：spec 驱动「写一版足够好的 spec 就完工」被直接点名等同 waterfall（「它从来没成功过」）。** 「真有大规模装机量和巨大流量时改软件，最好从一开始就假设全程迭代」；one-shot 只适合小应用。来源：资料/data - AI - 演讲/抽知识/Kent Beck：AI时代下的软件工程 ｜ Prodacity 2026 [BV1RfHp62Ehm].知识.md（六、one-shot 与 iterative）。标记：**适用 / 待裁**（重写纪律是「整块废弃重写」，与「全程迭代」哪一种，属 Owner 裁决）。
2. **futures vs features：功能与功能之间要停下来巩固（重构 / 消除重复 / 为可读性优化），否则一路烧掉「未来性」直到任何改动都弄坏别的东西。** 项目价值 ＝ 当前功能总和 + futures。来源：同上（五、futures 与 features）。标记：**适用**。
3. **最小 diff + 可回滚：每次修改尽量小、带来源、可单独回滚，而不是整体重写；让归因成为可能。** 来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（贯穿全书的设计模式：最小 diff + 可回滚）。标记：**适用 / 待裁**（与「整块废弃重写」相对，是本主题最核心的张力点）。
4. **渐进式落地：稳定优先、渐进放开。** 用「需求风险等级 R vs 能力等级 L」做门禁——R ≤ L 才接单，先只做小需求，跑稳了再扩大边界；连续成功若干次提升能力等级，多次不达标则收紧门禁。来源：技术书籍/ai-agent-handbook/36_从编码提效到端到端交付…md（三、渐进式与 Loop：3.3）。标记：**适用 / 待裁**。
5. **契约链：把每道工序的输入、输出与合格标准提前固化为契约，「上一道工序的输出恰好是下一道工序的输入」；强制交付物缺失即视为工序未完成、不许向下游推进；被打回则触发上游返工。** 方案级偏差锁定在编码开始之前。来源：同上（3.1 契约链）。标记：**适用**。
6. **工业界「工程演进四阶段」是叠加而非替代：提示词工程 → Harness 工程（设计文档/测试用例/规范进代码仓，人和 AI 共享同一事实源）→ Loop 工程（端到端闭环 + 硬性熔断）→ Graph 工程（交付全流程变成可恢复、可停机的节点图）**；「这层地基不能跳过」。Graph 工程用 Events、Gate、State 三种机制记录进入条件、产出证据与关闭结论，**可断点续跑、定点重试**。来源：资料/data - AI - 演讲/抽知识/2026云栖大会六场合集.txt（海信：认知框架——工程演进四阶段）。标记：**适用 / 待裁**。
7. **大规模代码迁移的关键不在模型强，而在三件事：知识必须存在于代码库本身（Agent 看不到的等于不存在）、约束编码进 Linter 和 CI 而非写在文档里、验证和纠正全链路自动化。** 来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（业界实践：大规模代码迁移案例）。标记：**适用**。
8. **CI 的目的是「防止错误代码合入主分支」；检查项＝编译测试 + 单元测试 + 格式检查；必须在隔离环境（干净镜像 + 临时 schema）里跑，避免污染生产，跑完清理。** 来源：技术书籍/Fundamentals…/翻译稿/ch11_automating_workflows.md（持续集成、使用 CI 流水线自动化测试、单独 schema）。标记：**适用**。
9. **持续＝以较小的块或批次增量地测与集成**，「确保仅以增量方式测试特定的代码更改」，而不是开发周期末尾一次性集成。来源：同上（持续）。标记：**适用**。
10. **灰度与版本回滚：开发 / 灰度 / 生产三套环境，按请求规则把部分真实流量导入灰度，用真实流量验证，异常直接回滚上一版本。** 来源：技术书籍/ai-agent-handbook/29_第 24 章 Agent 边缘运行时与全球优化.md（边缘灰度发布与版本管理）。标记：**适用 / 待裁**。
11. **重构＝「重组现有代码而不改变其外部行为」；技术债迹象＝难懂难改 / 重复代码 / 缺文档 / 缺自动化测试 / 僵化脆弱。** 来源：技术书籍/Fundamentals…/翻译稿/ch10…md（重构与技术债，行 412-427）。标记：**适用**。
12. **审计归因三路由（越用越强）：规则与模板缺陷 → 物料迭代；技能与工具问题 → 工具链整改；知识缺口 → 知识库台账。** 每一次问题沉淀为一条防复发规则。来源：技术书籍/ai-agent-handbook/36_从编码提效到端到端交付…md（3.3 Loop 闭环）。标记：**适用 / 待裁**。
13. **先写规格 / 架构文档再动手，且文档与代码共同演化**；「计划先于行动，验证贯穿始终」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（行 118-122 附近）。标记：**适用**。

### 5.2 本地缺口

- **本主题最大的缺口：资料里没有「整块废弃重写（greenfield / strangler）」的正面工程方法。** 没有任何 strangler pattern、增量替换、并行双跑对账的论述；Kent Beck 与 handbook 36 都站在「渐进迭代 / 小步放开」一侧，与本仓「重写不是改」的纪律形成**未在资料中解决的张力**。
- **无「新旧并存期」的技术方案**：如何路由流量、如何双跑比对结果、如何切换与回退，均无。
- **无数据迁移 / schema 演进（alembic 类）的具体方法**：资料侧的数据迁移只出现在 dbt/数仓语境，与本仓 alembic 迁移不对应。
- **无「人工半自动或并行 agent 施工的拆分粒度」方法**：除工业案例（handbook 36 的九工序、云栖的 Graph 五节点）外，没有可操作的「一次重写怎么拆成安全小步」的通用清单。

## 六、值得抄 / 要警惕

**值得抄的三条**

1. **先划责任边界、再选组件；用「复用性 / 强制性 / 可验证性」三判据决定某能力放哪一层，并用「不重写任务语义即可替换实现 + 同一套评估证明等价」当解耦质量的验收标准。** 来源：技术书籍/ai-agent-handbook/03_第 2 章…md（2.1.1-2.1.3）；52_第 30 章…md（30.2.1、30.4.1-30.4.2）。—— 这是全篇对本仓分层（api/runtime/tools/query/retrieval/knowledge/infra）最直接可核的「边界划得对不对」尺子。标记：**适用 / 待裁**。
2. **把「约束」写进 Linter / 类型 / CI，而不是只写进文档与提示词；「做不了」永远强于「建议别做」。** 来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter5.md（通用设计原则第 1 条；大规模代码迁移案例）。—— 与本仓「边界规则进 import-linter、两道机器闸」同一路子，可对照补齐「可机检的纪律清单」。标记：**适用**。
3. **公共件收口成单点并把责任写清：模型接触单点＝Gateway（先声明能力子集再报错）、网关单点做「校验来源 + trace ID + 用量检测」、重试预算跨层传递。** 来源：技术书籍/ai-agent-handbook/12_第 9 章…md（9.2.2、9.2.4）；资料/录音 面试考点速查.md（Q26）。—— 对应本仓 B6/B12/B14 的「唯一出口」设计。标记：**适用 / 待裁**。

**要警惕的三条**

1. **「一锤子 spec 写够好就完工」＝waterfall：资料明确判其「从来没成功过」，并要求大规模/高连续性场景「从一开始就假设全程迭代」。**（资料/data - AI - 演讲/抽知识/Kent Beck…知识.md 六）—— 与「整块废弃重写」纪律直接张力，**待裁**。
2. **把补偿模型短板的脚手架（few-shot、格式修复、提示词改写、循环控制）固化进业务代码：这些适配层会随模型变强被内化，并被模型升级击穿。** 来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（文生图适配层）；技术书籍/ai-agent-handbook/03_第 2 章…md（2.2.2）。标记：**适用**。
3. **「代码行数 / PR 数」类 effort 指标是度量陷阱：Goodhart 定律下「人们会把整个系统扭变形」。** 来源：资料/data - AI - 演讲/抽知识/Kent Beck…知识.md（七、effort → output → outcome → mission）。—— 对本仓「按文件/行数衡量重写进度」是一种反证。标记：**适用**。

## 七、疑点与不确定

1. **本仓分层（api/runtime/tools/query/retrieval/knowledge/infra）与资料「五能力责任域」不是同一套划分**：资料的责任域是「业务/编排/运行/治理/调优」，本仓是「技术层」。本文件只做对照，不给映射结论。**待裁**。
2. **「重写不是改」与资料主流的「小步迭代 / 渐进放开」存在方向差异**，本地资料**没有**为「整块废弃重写」提供工程方法（见 5.2 第一条缺口）。**这是本文件最大的本地缺口，也是全仓重写最需 Owner 裁决处。**
3. **本仓 `tools/importlinter_v2.toml` 的契约（层间单向、引擎互禁、langgraph 只许 runtime、litellm 唯一接触点）在本地资料中无对应方法学**：资料只到「约束应位于被约束方之外」，没有写依赖闸的指引。
4. **主题③的「DI / 单例 / 全局状态」在本地资料中几乎无覆盖**：本次结论只能给到「约束优先于指导」「公共件单点」层面，未覆盖具体注入与状态管理做法。
5. **本地资料多为工程博客/白皮书/教材，非可复现实验**：handbook 与 Fundamentals 的结论是经验法则，落地前应在本仓自己的规格与用例上验证。
6. **「学习计划」一份为教学版架构**（自述 FastAPI 单体 + LangGraph 三 Agent + LiteLLM，与本仓 appv2 九段流程不是同一套设计），本文件引用它时只作「做法/接口」参考，**不可当合同来源**（提纲已明示）。
