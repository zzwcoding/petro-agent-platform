## ① 一句话结论

业界的共识是：**分解不是默认动作，而是有明确触发条件的动作**——只有在「存在独立交付 / 不同责任 / 明确依赖」时才拆子任务（`handbook/14:187`），且必须**在开始前给分解封顶**（深度、子任务数、返工轮次，`handbook/14:209`）；拆出的子任务要带**可机读契约**（目标边界、已知上下文、能力权限、预算、输出证据、失败语义、验收条件，`handbook/06:188`），拆完的验收标准是「**子结果合起来能覆盖原目标**」（`handbook/14:215`）。**本地材料对「≤4 个子问题」这类具体数字没有直接论述**，只给了「封顶」原则与若干可换算的参照（详见 ⑦）。

## ② 业界主流做法（每条注出处）

### 2.1 什么时候该拆、什么时候不该拆（判据）

1. **核心判据＝「独立交付 / 不同责任 / 明确依赖」**。原文：「只有当工作存在独立交付、不同责任或明确依赖时才拆成子任务；同一成员连续完成的内部步骤不必逐项建成任务。」并强调子任务「其价值仍要回到父 Task 的目标上判断」——**拆不拆，看子任务能不能独立验收、能不能回到原目标**。——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:183,187`
2. **不该拆的信号＝目标单一 / 上下文集中 / 必须严格串行**。原文：「如果任务本身目标单一、上下文高度集中，或者执行步骤必须严格串行，那么使用单 Agent 往往更加简单有效。只有当专业分工、并行执行、故障隔离和过程治理带来的收益，能够覆盖沟通与协调成本时，Agent 团队才真正具有价值。」——`…/14_第 11章…md:37`
3. **委派的成本门槛**：「任务很短、步骤高度依赖或共享对象频繁变化时，委派会增加通信和合并成本。只有隔离、专业化或并行收益超过这些成本时，Subagent 才有价值。」——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:182`
4. **能固定就固定、别上自主分解**：「可以清晰分解为固定子任务的场景，考虑使用工作流；只有当需要动态决策和灵活的执行路径时，才使用自主 Agent。」——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:374`
5. **分解是模型的本质能力之一**：LLM 收到请求后「先解析真实意图……再将模糊或复杂的任务拆解成可执行的步骤」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:111`
6. **管理者模式的适用条件**：任务涉及大量子任务、需要动态调度或子任务之间存在复杂依赖时才需中心化协调（Manager）；否则对等协作更轻。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter10.md:286`
7. **信息够就往下走，别为形式而拆/重复**：「任务信息以能够支撑执行和验收为准。目标和约束已经清楚时，可以直接推进……已有材料能够证明结果时，也不必为了形式完整重复制作报告。」——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:189`

### 2.2 拆成几个、拆多深才合适（粒度与封顶）

1. **封顶要在开始前一次性约定**：「团队级停止条件需要在根 Task 开始前约定，包括总体时间或成本预算、**最大委派深度、派生任务数量**、单项任务的重试次数、**结果返工轮次**，以及连续多轮没有新增有效产物或状态进展时的处理方式。具体阈值由任务风险、成本和时效要求决定，**不在编排过程中无限追加**。」——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:209`
2. **封顶触及后的行为**：暂停新委派与自动返工，保留已完成结果/当前阻塞/剩余预算，把根 Task 标记为失败、已阻塞或等待人工判断——**不是静默截断**。——`…/14_第 11章…md:211`
3. **粒度太粗的代价＝上下文膨胀 + 单点瓶颈**：「Manager 需要维护整个任务的全局上下文，随着任务推进和 Agent 调用增多，上下文可能快速膨胀。因此需要特别注意 Manager 的提示词质量、上下文管理策略和**合理的任务分解粒度**。」——`技术书籍/ai-agent-book/ai-agent-book/book/chapter10.md:290`
4. **分解质量是天花板，钱要花在规划者身上**：Plan-and-Act 结论「弱规划者是整个系统最关键的瓶颈」；应「将最强的模型和最精心设计的提示词分配给 Manager（规划者），而不是将资源平均分配给所有 Agent」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter10.md:292`
5. **「何时拆、拆几个」本身可以学进模型**：Kimi K2.5 的 Agent Swarm「由主 Agent 动态创建上百个子 Agent 并行执行，把『何时拆、拆几个』的编排决策通过并行 Agent 强化学习直接训练进模型」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter10.md:489`
6. **预算项应含「子任务并发数」**：「步骤数、总时长、Token 与费用、工具调用次数、**子任务并发数**、高风险动作次数都应进入预算。」——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:83`
7. **展开上限有机制可循**：工作流 ForEach 节点「在运行时根据上游集合大小展开为 N 个子任务实例」、Loop 节点「设置最大迭代次数」——扩展开销要靠结构上限兜住。——`技术书籍/ai-agent-handbook/13_第 10 章 Agent 异步任务与自动化流程.md:237`

### 2.3 拆出来的子任务该带什么信息

1. **每个子任务带可机读契约（七项）**：目标与边界 / 已知上下文 / 能力与权限 / 预算 / 输出与证据 / 失败语义 / 验收条件。——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:188,190-198`
2. **父任务共同信息由子任务引用、别复制**：「父 Task 已经记录的共同目标和约束可以由子任务引用，子任务只补充自己的责任、交付物和特有条件，避免多份描述在后续修改中产生不一致。」——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:197`
3. **创建顺序 ≠ 执行顺序，依赖决定何时能开始**：「计划节点的创建顺序不等于实际执行顺序，依赖关系和可用条件才决定任务何时能够开始。」计划要回答「怎样划分交付单元、选择执行者、安排依赖，并利用可以安全展开的并行机会」。——`…/14_第 11章…md:191,193`
4. **依赖要显式建模（普通依赖 / AND Join / OR Join）**：节点就绪条件由依赖边类型决定；OR Join「未被选择的分支由引擎显式取消」，否则「会继续消耗资源、产生副作用」。——`技术书籍/ai-agent-handbook/13_第 10 章 Agent 异步任务与自动化流程.md:255,259-265`
5. **「路线 / 工具线索」＝混合路由思路**：路由「从『调用 Agent B』转向『寻找能够处理某类任务的 Agent』：系统先根据 Agent 声明的**能力**、当前任务语义和可用状态筛选候选者，再选择合适的执行者」；「语义判断帮助理解和选择，确定性规则完成约束、执行和留痕」。——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:333,335,337`
6. **并行判定＝「子问题之间有没有依赖」**：「模型发现两个子问题之间没有依赖关系，因此在一个输出中生成了两个工具调用请求」，框架检测到后并行执行——**依赖关系是决定能否并行的依据**。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md:424`
7. **委派与移交要区分**：Delegation＝父任务保留责任、子任务有边界地出去、结果回来后父仍整合验收；Handoff＝控制权转移、接收者成为责任人并拿到「目标/已知事实/待处理事项/可用引用」四类信息。——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:200`；`…/14_第 11章…md:237-246`
8. **外部记忆（TODO 列表）能减少遗漏子任务**：Manus 式 TODO 列表「起到了外部记忆的作用……实验数据显示：启用 TODO 的 Agent 平均 15 次迭代就能完成任务，而禁用时则需要 21 次且**经常遗漏子任务**」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md:963`

### 2.4 拆完怎么校验（是否覆盖原问题、有没有漏 / 重复）

1. **验收标准＝子结果共同覆盖原目标**：「根 Task 达到完成条件，则要求当前有效版本的成果**共同覆盖总体目标**」；且「执行者提交 ≠ 接受 ≠ 根 Task 完成，三者不能互相替代」。——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:215`
2. **交付时要显式说明覆盖情况**：「最终交付应说明当前有效产物**如何覆盖目标**、各项结果是否一致、仍有哪些限制」。——`…/14_第 11章…md:221`
3. **交叉验证分解结果**：（针对「如何确保 Manager 分解质量」）「Harness 手段：**分解结果先经审核 LLM 交叉验证，再交付执行**；要求 Manager 在分解任务时，为子任务定义明确的**验收标准与依赖关系**。」——`技术书籍/ai-agent-book/ai-agent-book/book/reference-answers.md:372`
4. **覆盖校验的可落地方法＝「需求 ↔ 实际做的事」逐条对照、做集合差**：失败归因「用 LLM 把原始需求与 Agent 实际做的事（动作序列）逐条对照，先定位第一处偏离」；「把 Agent 声称的影响面与真实影响面**做集合差，取第一个遗漏项**」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:448,452`
5. **覆盖度用 Recall 口径量**：事实完整性（Recall＝在所有应该给出的信息中，有多少被提及），「用于验证是否提供了所有相关信息而非遗漏关键内容」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:376`
6. **独立上下文检查「遗漏」是验证强度中的一档**：五级验证强度表里「独立模型验证｜使用独立 Context 检查质量与遗漏｜开放式分析和复杂内容」；Verifier 应「返回结构化缺口、失败证据和可修复性」。——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:385,388`
7. **重复/遗漏的根因常在协作机制本身**：「如果缺少清晰的分工、协作方式和状态管理，参与者越多，反而越容易出现**重复执行、信息不一致、任务遗漏和责任不清**。」——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:5`

## ④ 反例踩坑

**（a）拆得太碎 / 太粗**

1. **太细 → 通信与合并成本吃掉收益**：任务很短、步骤高度依赖时委派只增成本（`handbook/06:182`）；「主管在分派前提前解决业务问题、在交付后重复验证，造成**重复执行**」（`handbook/14:151`）。
2. **太粗 → 上下文膨胀 + 单点瓶颈**：Manager 要装全局上下文，任务一多「上下文可能快速膨胀」，还要额外注意「合理的任务分解粒度」（`book/chapter10.md:290`）。
3. **把一个概念拆成多个 id / 把两个相似表面形式误并**：开放式提炼里「这样不会因批次顺序把一个概念拆成多个 id，或把两个相似表面形式误并」——粒度错会造成「假重复」或「假合并」（`ai-agent-book/chapter9/ai-style-skill/README.md:27`）。

**（b）子任务互相依赖**

4. **把未完成的前序结果当有效输入**：计划要「明确测试使用哪个补丁版本，以及什么结果可以作为验证完成的依据。这样，成员可以并行准备，又不会把尚未完成的前序结果当成有效输入」（`handbook/14:195`）。
5. **OR Join 不显式取消未选分支 → 继续烧资源/产生副作用**（`handbook/13:265`）。
6. **多执行者改同一工作区靠「大家小心」**：「不能依赖『大家小心不要冲突』」，要隔离分支/对象级锁/补丁合并（`handbook/06:217`）。
7. **错误级联放大（传话游戏）**：去中心化组织的组织病清单含「谎称『已完成』」「错误级联放大（传话游戏）」「角色间循环移交」（`book/reference-answers.md:376`）。

**（c）覆盖不全 / 漏 / 重复**

8. **过早停止：只完成一部分就宣布完成**：「多目标任务只完成一部分；未穷尽合理方案就宣布不可能」被明确列为失败模式（`book/chapter7.md:456`）。
9. **漏条件 / 范围理解偏**：「漏掉需求里的一个条件、把范围理解宽了或窄了」（`book/chapter7.md:448`）。
10. **只判最终结果、不知错在哪一步**：「只能评估最终结果对不对，但不能给出错误原因……不会说明 Agent 是在线路选择环节出错、还是漏掉了流量充值步骤」（`book/chapter7.md:292`）——覆盖校验必须**定位到具体子问题**，不能只给总分。
11. **缺 TODO 外部记忆 → 经常遗漏子任务**（`book/chapter2.md:963`）。

**（d）反面案例（真实产品）**

12. **复杂任务规划脆弱、无法适应状态变化**：AndroidWorld 失败分析指出某类失败是「复杂任务规划和状态维护」——Agent 能删一个重复项，但管不了「当还有未处理重复项时循环处理」这种高层计划，UI 状态一变逻辑就乱（`ai-agent-book/chapter7/android-world/t3a_failed_analysis.md:92`）。

## ⑤ 对本项目适用性（只读问答、单租户）

1. **默认不拆、有判据才拆**：本项目 T3c 只做「大问题→≤4 个小问题」。按 `handbook/14:187` 的判据，触发条件应写成「**问题里含多个独立可验收的子问**」（多个对象/多个口径/多个时间窗）才拆；单一问题（一个对象一个口径）**不拆**，直接进下一相位（`handbook/14:187,37`）。
2. **封顶写成程序里的确定性规则，不交模型裁量**：`≤4` 已是现状（walk/08 已定），业界只给原则（「最大委派深度、派生任务数量」开始前约定，`handbook/14:209`）——**≤4 这个具体数字是本地材料的空白，属本项目自定**（见 ⑦）。可在统一预算表里集中声明（子问题 ≤4、反问 ≤6、发现 ≤10、返工 ≤3），与 walk/08 §06-A 一致。
3. **每个小问题带「注释（台账逐字）＋路线（数据链/文档链）」正是「可机读契约」的本项目裁剪版**：`handbook/06:190-198` 的七项契约中，与本项目最相关的是「目标与边界（查什么）」「能力与权限（走哪条链）」「输出与证据（要数字还是要答案）」「验收条件」。**注释＝逐字引用台账**，对应「父共同约束由子任务**引用**、别复制」的做法（`handbook/14:197`）——引用原文比模型改写更不易失真。
4. **路线标注＝混合路由的「候选能力声明」**：`数据链／文档链` 相当于给每个子问题声明它需要哪类能力，正合 `handbook/14:335`「先根据能力筛选候选者」；程序据此在下一相位配工具，符合「语义判断帮助选择、确定性规则完成约束与留痕」（`handbook/14:337`）。
5. **拆完的校验落成「闭合世界对账」，不做自动修补**：本项目现状是「模型出结构化发射、程序做闭合世界 schema 对账（四动作、子问题数、注释必带）＋拒因回喂自环」（walk/08 一）。这正对应 `handbook/06:385`「独立模型验证：检查质量与**遗漏**」与 `reference-answers.md:372`「分解结果先经审核 LLM 交叉验证」——**覆盖度校验（子问题是否覆盖原问）本地材料给了方法（需求↔实做集合差、Recall 口径），但本项目要不要上「审核 LLM」需 Owner 定**（见 ⑦）。
6. **单租户简化了「并行/隔离」开销**：本项目无需 `handbook/06:217` 的跨执行者工作区隔离（只读、无写副作用），子问题可安全并行。封顶只服务「不烦人 + 不烧 token」，不承担租户隔离职责。
7. **只读场景下「过早停止」风险更值得防**：相比写操作，只读问答的失败更常是**漏查/漏搜**（`book/chapter7.md:456` 的「只完成一部分」）。可用 `book/chapter2.md:963` 的做法——把子问题清单当**外部记忆显式写进状态**，降低「漏子任务」。

## ⑥ 值得抄三条 / 要警惕三条

**值得抄（3 条）**

1. **拆的判据一句话**：「只有当工作存在独立交付、不同责任或明确依赖时才拆成子任务」——`handbook/14:187`。可直接写进 T3c 的拆/不拆判定规则；反面用「目标单一/上下文集中/严格串行就不拆」（`handbook/14:37`）。
2. **子任务可机读契约＋引用而非复制**：每个小问题带「目标边界/能力权限/输出证据/验收条件」，共同约束**引用**父级（台账逐字），只补自己特有字段——`handbook/06:190-198`、`handbook/14:197`。这正好把「注释逐字抄台账」和「标路线」规范化。
3. **拆完做覆盖校验**：以「子结果**共同覆盖**原目标」为完成判据（`handbook/14:215`），方法用「需求↔实做逐条对照取集合差 / Recall 口径」（`book/chapter7.md:448,452,376`）＋「分解结果先经审核 LLM 交叉验证」（`reference-answers.md:372`）。

**要警惕（3 条）**

1. **把「拆」当默认动作** → 单一问题也被拆碎，通信/合并成本吃掉收益、上下文膨胀（`handbook/06:182`、`handbook/14:151`、`book/chapter10.md:290`）。
2. **子问题依赖没显式声明** → 把未完成的前序结果当有效输入、或未取消的分支继续烧资源（`handbook/14:195`、`handbook/13:265`）。
3. **只判「拆出来没」不判「覆盖不覆盖」** → 过早停止、漏条件、范围偏窄被放过（`book/chapter7.md:448,456,292`）；覆盖校验必须**定位到具体子问题**，不能只给总分。

## ⑦ 疑点与不确定（含「本地材料覆盖不到」的部分）

1. **本地无「≤4 个子问题」这类具体数字的论述**。grep「封顶 / 最大委派深度 / 派生任务数量 / 拆成几个 / 最多拆」在 `.md/.txt`（排除朗读版）中命中的只有原则性表述（`handbook/14:209`）与机制性上限（`handbook/13:237` 的 ForEach N / Loop 最大迭代）。**「≤4」是本项目自定，不是抄来的业界数**；本文只能提供「要封顶」的依据，不能背书具体数字。
