## ① 一句话结论

**业界在「工具选择」上的主流分工是：模型只负责「提出用哪个工具、带什么参数」这个意图，工具清单是闭世界的白名单（模型不能选清单外的东西），参数用结构化 schema（明确类型、枚举、必填、边界、示例）强校验，校验失败把结构化原因回喂给模型重选而不是程序自动修补，重试要封顶并配熔断；工具描述的重点不是「能做什么」而是「什么时候用、不能做什么」——大多数选错工具的根因是描述没写边界，不是模型太弱。**（出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md` 6.1.1／6.1.2／6.1.3／6.2.2；`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`「工具描述的艺术」「参数传递的保真性」；`资料/data - AI - 演讲/已完成/从业务本体到持续进化.知识.md` 第三项共识）

## ② 业界主流做法

### A. 工具怎么描述（让模型选得准）

1. **工具描述的核心是让模型知道「什么时候用」，不只是「能做什么」。** 原文的对照例子：写「搜索相关内容」不如写「当需要获取实时信息或查找未知事实时使用」——前者只描述功能，后者帮助模型做调用决策。
   - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「工具描述的艺术」）

2. **清晰列出边界条件（做不到什么、不接受什么输入），往往比描述能力本身更重要。** 原文判断：「大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做什么」；文件搜索工具必须明说「只能按文件名匹配，不能搜内容」。
   - 出处：同上（「工具描述的艺术」）

3. **参数描述用具体例子代替抽象规范。** 不要只写「RFC3339 格式」，要写「`2024-03-15T14:30:00Z`」；不要只写「E.164 格式」，要给 `+8613888888888` 这种可直接套用的例子。返回值也要写清（返回 JSON 数组、每个元素含哪些字段）。
   - 出处：同上（「工具描述的艺术」）

4. **给每个工具附 1-5 个真实调用示例，能明显提升参数准确率。** 原文给的量级：某些基准上从约 72% 提升到 90%（数值因任务而异）。理由：JSON Schema 只能描述类型，表达不了「时间戳是秒还是毫秒」「过滤条件怎么嵌套」这类隐式约定。
   - 出处：同上（「工具描述的艺术」）

5. **选错工具时，先检查工具描述，而不是换更强的模型。** 原文：「大多数工具选择错误的根因在于描述不准确——边界不清、缺少反例、参数含义模糊」。
   - 出处：同上（「工具描述的艺术」）

6. **面向 Agent 的 Tool 设计清单（handbook 版）。** 名称与描述要说明业务目的、适用条件与非目标；输入 Schema 用明确类型、枚举、边界和示例，避免让模型拼接任意请求；输出区分结构化结果、面向模型的摘要和原始证据引用；明确是否只读、有无副作用、是否可逆；错误用稳定分类，告诉 Harness 能否重试、要不要修正参数、还是转人工。
   - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.2.2「面向 Agent 的 Tool 设计」）

7. **工具粒度：对应「一个可描述、可授权、可观察、可验证的业务动作」。** 太粗则一次调用影响面过大、审批和验证难精确；太细则要模型编排大量低级步骤，增加错误与成本。
   - 出处：同上（6.2.2；另 6.1.3 案例：`change.create` 与 `production.deploy` 必须是两个 Action，不能包成一个模糊工具）

### B. 闭世界 / 白名单（不让模型选不存在的东西）

8. **模型「看得见工具」≠「有权调用」，两者必须分开。** handbook 明确三个必须区分的事实：模型看见某工具＝描述进入上下文；Harness 注册某工具＝系统知道怎么调用解析；当前用户和任务获得授权＝这次行动可以发生。「若『出现在 Tool Schema 中』就等价于『可以调用』，最小权限、用户委派和阶段性只读模式都无法成立。」
   - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.1.1）

9. **MCP 网关的准入默认拒绝：ACL 从服务级白名单起步，再向高风险工具和参数细化。** 「输入 Schema 校验只保证类型和结构合规，并不证明业务授权成立。」
   - 出处：`资料/技术书籍/ai-agent-handbook/12_第 9 章 AI 网关与统一流量治理.md`（9.3.5「安全边界：默认拒绝与不可绕过的部署条件」）

10. **工具白名单/枚举是「语义 CI」的第一级检查项。** DataBuddy 五级语义 CI 的 L1 明列「YAML、安全解析、必填、枚举、UUID、路径」；L4 明列「Action 白名单」。即「允许哪些动作」是事先定义、可机检的封闭集合，不是运行时临时解释。
    - 出处：`资料/data - AI - 演讲/已完成/从业务本体到持续进化.知识.md`（「五级语义 CI」L1／L4）

11. **企业侧「默认拒绝 + 按需开白」是明确纪律。** 字节安全白皮书：内部系统接入分「只读查询型 / 写入型 / 消息型」，只读查询型在通过准入评估、配好网关白名单后推荐允许；写入型默认不允许（除非无法用只读满足且风险可控）。
    - 出处：`资料/字节安全白皮书.md`（7.2.1.3「内部系统准入实践」、场景 A/B）

12. **匹配不到就明确返回「未找到」，不硬凑。** 工具按服务器分组做两层匹配时，「若两层匹配的候选相似度都低于阈值，则应明确返回『未找到』，让 Agent 改写需求重试、用基础工具手工实现，或创造一个新工具」。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「层次化匹配与降级」）

### C. 参数/输出强校验与「校验失败怎么办」

13. **模型提议、程序校验、程序放行——这是核心分工。** handbook：模型产生的自由文本只能作为 `purpose` 的候选输入，「能力名称、参数类型、影响范围和身份必须由确定性代码解析与校验」；Action 有生命周期 `REQUESTED → VALIDATED → AUTHORIZED/WAITING_APPROVAL → RUNNING → SUCCEEDED/FAILED/CANCELLED`。
    - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.1.1／6.1.2）

14. **「中间态 + Harness」：不应由模型直接生成可执行物（如 SQL）。** DataBuddy 四项工程共识之三：「让模型提出计划，让协议决定能否执行」；强类型中间态五段式 `IntentSpec → SemanticContext → SemanticPlan → ExecutionPlan → EvidencePack`，底部关键分工写明「**模型：理解与提出计划 ｜ 语义编译器 + Harness：验证、授权、执行、审计与失败关闭**」。
    - 出处：`资料/data - AI - 演讲/已完成/从业务本体到持续进化.知识.md`（第三项共识、第五段「强类型中间态」）

15. **校验失败不做自动修补，而是把结构化原因回喂。** handbook：错误采用稳定分类，「告诉 Harness 能否重试、需要修正参数还是转人工」。chapter4 在「提议者-审核者」处给了同一原则的正例：「审批失败后不应简单重试，而应将拒绝理由作为工具调用结果加入 Agent 的轨迹……从提议模型的视角看，审批拒绝就像一次工具调用失败，返回了错误信息和修正建议」。
    - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.2.2）；`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「执行工具」事前审批段）

16. **程序自动「智能修正」参数是反模式。** chapter4 专节点名 Cursor 2026 的静默转换：参数层把中文弯引号悄悄转成直引号，导致模型「看到的」和「工具操作的」不一致，模型反复失败却无法诊断；静默追加参数同理。结论：「模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差」。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「参数传递的保真性」）

17. **重试要有上限并配熔断。** chapter4 的拒绝熔断器：「当分类器连续多次拒绝操作时，系统不应无限重试（会浪费资源，还可能导致死循环），而应转为请求用户手动判断」。本仓教学计划里的 NL2SQL 状态机也把「反思修正」封顶为 ≤3 次。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「Sidecar 机制」拒绝熔断器）；`资料/计划:石油AI智能体项目学习计划.md`（6.2「NL2SQL 状态机」）

18. **「先校验，再执行」是可信取数的既定链路。** Datastrato 第六轮收敛：用户问题→语义对象→Compiler→SQL→Query Engine，中间插入 policy check / freshness check / lineage check / audit log，再 execute。原始判断：「SQL 有结果但业务不能用」——「可信取数要把校验做进执行路径」。
    - 出处：`资料/data - AI - 演讲/已完成/《从元数据到 Data Agent：企业如何从“能问数”走向“可信取数”》刘镔辉｜Datastrato 解决方案架构师.知识.md`（第 5 轮）

19. **只读工具的正确执行形态是「制品模式」：模型只产出制品，执行交给确定性系统。** erp-agent 实验：LLM 只生成 SQL 制品，数据库执行查询，LLM 不亲自搬数据——省 token、避免模型手算出错；并用独立参考实现（不走 SQL 的 Python）做结果校验，`temperature=0` 求稳。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/chapter5/erp-agent/README.md`

20. **参数级治理：Schema 校验通过还要叠加业务策略。** handbook 给了一张四行表——
    | 工具场景 | Schema 校验 | 业务策略还必须约束 |
    | --- | --- | --- |
    | 数据查询 | 字段类型、分页参数 | 数据库或数据集范围、行级权限、可执行操作 |
    | 文件读取 | 路径或文件标识格式 | 允许目录、租户归属、符号链接与数据分级 |
    原文警示：「使用字符串前缀判断『只读 SQL』并不可靠，应结合受限数据库账户、受支持的查询接口与资源端权限」。
    - 出处：`资料/技术书籍/ai-agent-handbook/12_第 9 章 AI 网关与统一流量治理.md`（9.3.7「REST-to-MCP 与参数级治理」）

### D. 一次选一个 vs 一次选多个 / 批量编排

21. **默认形态是「一次一个工具、看到结果再定下一步」（ReAct 循环）。** 感知工具与执行工具的设计都围绕「每次调用 → Observation → 下一步」展开；执行工具因为副作用要严格控制调用顺序。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「感知工具」「执行工具」；只读性带来缓存与并行红利一段）

22. **批量/多工具场景用「代码编排工具调用」降低上下文开销。** chapter4 的比方（此处直述机制）：不让模型一次调一个工具、把每个中间结果都搬回上下文，而是一次生成一段脚本，中间变量留在执行环境，只把最终结构化结果返回——token 消耗可降约两个数量级。这属于「代码作为通用 Agent 元能力」范式。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「能力的表达形式」末段「再往前一步：让代码来编排工具调用」）

23. **任务分解后逐子任务分派/编排有独立机制（不是让一个大工具全包）。** handbook 第 11 章：Task→Subtask 的分解、分派、并行执行与结果聚合；调度「根据任务当前状态决定哪些工作可以执行」。
    - 出处：`资料/技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md`（11.4「协作机制：任务分解、分派、并行执行与结果聚合」）

### E. 已知失败模式

24. **工具太多会直接伤害选择正确性。** chapter4：「工具数量超过一百个时，即使最先进的大模型也容易在工具选择上出错」；实验 4-1 记录 4B 模型在全量注入 120+ 工具的 schema（超 50K tokens）后「指令遵循能力严重退化」——典型表现：面对「查询股价」错选 Web Search 而非专门的 Yahoo Finance 工具，或「忘记」工具列表里的某些工具导致任务失败。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「工具太多怎么办」开头；「实验 4-1 主动工具发现」）

25. **只按工具名做静态白名单，挡不住参数级越权。** handbook 原话：「仅按 Tool 名称做静态白名单，无法区分『读取一条测试记录』和『导出整个生产库』」；还给了反例案例——把用户对草稿的同意错误解释为允许生产发布，根因就在「Policy 只按 Tool 名称匹配，错误返回 ALLOW」。
    - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.4.1；6.5.3 错误审批案例）

26. **第三方工具的两个攻击面：描述投毒与同名遮蔽。** 工具 description 会原样进入上下文，恶意服务器可夹带指令（描述投毒＝提示注入的变种）；多个服务器提供同名工具时可「遮蔽」正规工具把调用引走（tool shadowing）。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter4.md`（「第三方能力的安全风险」）

27. **上下文超阈值被压缩会丢细节，进而诱发幻觉/选错。** 面试速查：「上下文接近阈值 → 压缩 → 细节丢失 → 幻觉」；配药是「提示词控制：所有回答必须来源于知识库」。
    - 出处：`资料/录音 面试考点速查.md`（Q43「减少幻觉手段」）

28. **「执行成功」不等于「任务完成」。** handbook 反复强调：Tool 成功只等于执行成功；远程 Agent 声明完成仍需委派方按契约验收。
    - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.2.1 末、6.4.2）

## ③ 分歧取舍

1. **全量注入工具 vs 按需检索工具。**
   - 全量注入：实现最简单，召回率 100%（小集合时够用）。
   - 检索/主动发现：token 成本低且不随工具数膨胀，但引入嵌入索引与路由基础设施。
   - 量化证据（`资料/技术书籍/ai-agent-book/ai-agent-book/chapter4/active-tool-selection/README.md` 离线基准，可复现）：35 个工具时 all-tools 3,857 tokens、retrieval(top-5) 551 tokens，两者召回率都 100%；目录涨到 400 个工具时 all-tools 涨到 40,258 tokens，retrieval 仍约 540 tokens。**该 README 同时明确写了适用边界：「小工具集（总数 <10）」「全部相关」「单轮任务」时被动全量方式可能够用。**
   - 取舍：工具数少时不要上检索式路由。

2. **一次一个工具（逐步） vs 代码一次编排多个。**
   - 逐步：可控、可审计、每步都有 Observation，适合有副作用或需逐步验证。
   - 代码编排：token 省得多，但中间态不进上下文、可观测性下降。
   - 取舍：只读、无副作用的批量场景可倾向代码编排；有副作用/需审批时逐步。

3. **校验失败：回喂重选 vs 程序自动修补。**
   - 本地材料一边倒地反对自动修补（chapter4「静默输入转换/静默参数注入」专节点名其为使模型无法自诊断的系统性故障），支持「回喂结构化原因、模型重选」。
   - 但回喂重选会消耗轮次，需要重试封顶 + 熔断（见②.17）。

4. **专用工具 vs 通用执行器（code_interpreter + Skill）。**
   - chapter4 默认取向是「通用工具优于专用工具，除非存在明确的安全、权限、性能理由」；四种退回专用的情形：安全/权限/审计、屏蔽平台差异、使用频率极高、参数结构复杂。
   - 只读问答、参数结构化的查数与找文档，属于「参数结构复杂 + 权限/审计」一侧，倾向结构化专用工具而非开放执行器。

5. **路由（选工具）与结果判定必须分权。**
   - 「模型负责产生候选动作，Harness 负责协议校验和动作放行」；检查项含工具选择、函数名、参数类型、必填字段、枚举值能否被稳定解析。
   - 出处：`资料/技术书籍/ai-agent-handbook/22_第 17 章 模型调优.md`（17.5.2，连续段 780-784）；`资料/技术书籍/ai-agent-handbook/12_第 9 章 AI 网关与统一流量治理.md`（9.4.3）
   - 取舍：T4 只判「配哪个工具」，不判「这个工具跑出来的结果对不对」。

## ④ 反例踩坑

1. **把「选工具」交给模型的自由发挥、无闭世界清单** → 模型可能选不存在的工具或错选。反例：4B 模型全量注入 120+ 工具后错选 Web Search 而非 Yahoo Finance（`资料/…/book/chapter4.md` 实验 4-1）。
2. **工具描述没写「不能做什么」** → 模型自行猜测边界，调用失败（`资料/…/book/chapter4.md`「工具描述的艺术」）。这是「选错工具」的头号根因。
3. **程序静默修正参数/静默追加参数** → 模型看到的和工具操作的不一致，反复失败无法诊断（`资料/…/book/chapter4.md`「参数传递的保真性」，Cursor 2026 实例）。
4. **只按工具名做白名单/校验** → 区分不了「读一条测试记录」和「导出整个生产库」；只读判断靠字符串前缀不可靠（`资料/…/handbook/08_第 6 章…md` 6.4.1；`资料/…/handbook/12_第 9 章…md` 9.3.7）。
5. **Schema 校验通过就当授权通过** → handbook 原话「输入 Schema 校验只保证类型和结构合规，并不证明业务授权成立」（`资料/…/handbook/12_第 9 章…md` 9.3.5）。
6. **校验失败无限重试** → 死循环、浪费资源；需要拒绝熔断器转人工（`资料/…/book/chapter4.md` Sidecar 段）。
7. **把「HTTP 成功 / 会话结束 / 模型自述完成」当业务成功** → 分权红线，路由/执行成功不等于结果正确（`资料/…/handbook/08_第 6 章…md`；`资料/…/handbook/12_第 9 章…md` 9.4.7）。
8. **工具描述投毒 / 同名工具遮蔽** → 第三方工具把调用引走或注入指令（`资料/…/book/chapter4.md`「第三方能力的安全风险」）。
9. **同一指标每次问出不同结果** → LLM 概率性生成选取不同字段；Datastrato 的解法是复用 verified metric、界面弹确认框，命中就走固定规则，「不再经过大模型重新生成」（`资料/data - AI - 演讲/已完成/《从元数据到 Data Agent…》….知识.md` 第 4 轮）。
10. **上下文逼近阈值被压缩丢细节** → 幻觉/选错（`资料/录音 面试考点速查.md` Q43）。

## ⑤ 对本项目适用性（只读问答、单租户、工具集小）

1. **「工具集小」决定了不该上检索式/主动发现。** 本地基准明确把「总数 <10 的工具」列为被动全量方式的适用场景（`资料/…/active-tool-selection/README.md`）。本仓是只读问答、工具集小，**不需要**嵌入索引、两层语义路由、`discover_tools` 元工具这一整套基础设施——那是给上百上千工具准备的。直接全量把工具清单给模型 + 闭世界校验即可。

2. **T4「恰好配一条」的闭合世界对账，本质是 harness 侧的确定性校验，与业界分工一致。** 业界做法是「模型提议 → 程序按 schema/枚举/白名单校验 → 程序放行」（handbook 6.1.2；DataBuddy「模型提出计划，协议决定能否执行」）。本项目的「漏配/多配/编号对不上都拒」正落在这个分工上，且方向正确。

3. **「拒绝原因发回给模型重配（不做自动修补）」与业界一致，且是本地明确支持的取向。** chapter4 反对程序自动修补、主张把拒绝理由作为一次「工具失败」回喂（见②.15、②.16）；本项目的做法对得上。需补的是「重试封顶 + 熔断/转人工」（②.17）。

4. **工具描述应落成本仓可机检的字段。** 按②.1-②.6，每个工具的说明至少要有：什么时候用（触发条件）、不能做什么（边界/反例）、参数示例、是否只读。这是「让模型选得准」投入产出比最高的动作，比换模型划算。

5. **只读特性是天然红利。** chapter4：感知类（只读）工具结果可安全缓存、多个调用可放心并行。本仓只读问答可复用这一点（同一子问题/查询可缓存），但若引入并行需与应用侧确认。

6. **数字题的「查询计划」应走「制品模式 + 先校验再执行」。** erp-agent（`资料/…/chapter5/erp-agent/README.md`）与 Datastrato 第 5 轮（`资料/…/从元数据到 Data Agent…`）都指向：模型只产出结构化查询制品，执行与只读校验交给确定性系统，不亲手搬数据。本仓教学计划的 sql_guard（AST、只允许 SELECT、白名单表、强制 LIMIT）是同一思路的现成参照（`资料/计划:石油AI智能体项目学习计划.md` 6.2），但注意该文件是**教学版架构**，只作形式参考。

7. **单租户降低了「身份/租户绑定」的优先级，但不等于可以省掉「参数级范围约束」。** handbook 的参数级治理表（②.20）里「行级权限、数据集范围」在单租户下可弱化，但「只读、可执行操作种类、返回列范围」仍需约束。

## ⑥ 值得抄三条 / 要警惕三条

### 值得抄三条

1. **闭世界白名单 + 模型只提议、程序决定能否通过。** 工具清单是事先定义的可机检封闭集合；模型选到清单外、参数不在枚举内、必填缺失一律不通过。参照：DataBuddy L1（必填/枚举/UUID）与 L4（Action 白名单）；handbook「模型提议 → 确定性代码解析校验」。（②.10、②.13、②.14）
2. **校验失败把结构化原因回喂给模型重选，绝不自动修补参数。** 并把重试封顶、配熔断转人工。参照：chapter4「拒绝理由作为工具调用结果加入轨迹」+ 拒绝熔断器；handbook 错误稳定分类。（②.15、②.16、②.17）
3. **工具描述写「什么时候用 + 不能做什么 + 参数示例」。** 边界与反例优先于能力描述；实测加示例可把参数准确率从约 72% 提到 90%。参照：chapter4「工具描述的艺术」。（②.1-②.5）

### 要警惕三条

1. **不要为「工具集小」的场景上检索式工具路由/主动发现/层次化组织。** 那是给 50+、上百工具准备的；小集合上反而增加故障面。本地基准把「<10 工具」明确划给被动全量方式。（③.1、⑤.1）
2. **不要做静默参数修正或程序自动修补。** 会造成「模型看到的 ≠ 工具操作的」系统性偏差，模型无法自诊断。（②.16、④.3）
3. **不要只按工具名/只做 Schema 校验就放行。** Schema 合规 ≠ 业务授权；只读判断不能靠字符串前缀。（④.4、④.5）另需警惕「多配」：模型一次选多个工具时应被程序对账拒绝，而不是将就执行。

## ⑦ 疑点与不确定

1. **本地材料没有专门讲「一个子问题恰好配一条工具」的闭合对账工序。** 业界讲的是「工具选择准确性」和「闭世界枚举/白名单」，没有「逐条编号对账、漏配/多配即拒」的现成范式。本项目 T4 的「恰好配一条、编号对不上都拒」更接近「集合相等」的机检，本地无同类原文可引，属**本地材料覆盖不到**。

2. **「校验失败回喂重选」的具体反馈措辞/格式，本地无范式。** chapter4/handbook 都只说「把结构化原因/修正建议回喂」，没有给出「拒绝原因应该包含哪些字段、怎么写」的模板。需要自行设计。

3. **「数字题的查询计划」具体字段，本地无。** erp-agent 只给了「SQL 制品」这一层，没有独立的「查询计划」结构；本仓 T4 要求数字题附带查询计划，其字段形状需自行定义（可参考 DataBuddy 的 `SemanticPlan/ExecutionPlan` 五段式作灵感，但那是语义层方案，不是本仓合同）。

4. **「报告题 → 找文档」的工具设计，本地无专章。** 本地只有「感知工具/搜索类工具的返回格式与分页」（chapter4）可间接参考，没有「找报告/找文档」这类检索工具的描述与参数设计范式。

5. **本地材料覆盖不到的部分**：MCP 官方规范原文、OpenAI/Anthropic function calling 官方文档原文、各厂商 JSON Schema 方言差异、工具选择的量化基准（如 BFCL）本地均无；`资料大纲-3` 提到的公众号 `*.webarchive`（含《DataBuddy 数据语义驱动的企业 Agent Runtime 实践》）不可读，未纳入。

6. **`资料大纲-2` 记录的资料侧文件异常（编号错位、空壳章）不影响本文引用，但机械化提取时需留意**（见该大纲「疑点/缺口」第 3 条）。

7. **本文引用的教学计划文件（`资料/计划:石油AI智能体项目学习计划.md`）描述的是教学版架构**（FastAPI 单体 + LangGraph + LiteLLM），与本仓 appv2/runtime 九段流程不是同一套设计，**只作形式/接口参考，不可当合同来源**（该文件与 `资料大纲-3` 均已声明）。
