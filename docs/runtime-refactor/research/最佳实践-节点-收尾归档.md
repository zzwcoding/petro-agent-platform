## ① 一句话结论

业界把「任务收尾」当成**一次有纪律的状态迁移**，而不是「agent 循环停了就算完」：先分清**执行状态 / 候选证据 / 业务完成判定**三件不等价的事（执行跑完 ≠ 业务完成），由**代码（Harness/核验器）而不是模型**提交「完成」；再把过程事实**只追加地写进事件日志**、把成果**不可变地存进产物库**（带来源、版本、权限、保留期），并用**冷热分层 + 保留策略 + 压缩四步**防无界增长；审计留痕必须能回答「谁、何时、凭何权限、做了什么、影响到什么」，且**原始事实不可改写、结论只能引用证据派生**；失败/中断的收尾要**显式落状态、显式对账、显式告知**，绝不允许静默结束（宁可写「未知/失败」，不可无声消失）。本项目是**只读问答、单租户、多轮**：无外部副作用使幂等压力近乎消失，真正要守的是四条 —— **完成判定归核验器、任务边界与会话边界分开、归档只追加不原地改、任何写失败都要发提示不留无声缺口**。

## ② 业界主流做法（逐条注出处）

### A. 任务结束怎么判：「流结束 / 执行结束」不等于「任务结束」

1. **一次任务要同时关联五类互不等价的信息**：执行状态（Runtime 给的运行结果信号，回答「这次执行有没有跑完」，不回答「业务目标是否达成」）、节点运维状态（Worker/租约/依赖健康）、候选证据（日志/Trace/快照/Artifact/模型原始响应的原始材料）、Evidence（被成功标准明确引用的证据）、业务 Outcome（由业务应用或获授权核验器依证据＋标准做出的最终判定）。
   出处：`资料/技术书籍/ai-agent-handbook/13_第 10 章 Agent 异步任务与自动化流程.md` §10.1.2（第 28–42 行）。原文一句：「它回答『这次执行有没有跑完』，不回答『业务目标是否达成』。」
2. **「模型只能提出完成申请，Harness 才能提交完成状态」；验证强度按风险分五级**（结构验证 / 环境验证 / 确定性验证 / 独立模型验证 / 人工验收）。核验器返回的是**结构化缺口 + 失败证据 + 可修复性**，验证失败是新的 Observation，不是简单结束。
   出处：`资料/技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md` §4.6.2（第 376–388 行）。
3. **「请求超时只表示调用方未在期限内取得结果，不能证明执行已经停止」**——所以「连接断了 / 流关了」都不能直接当作任务结束或失败，必须在后台有独立标识与查询路径。
   出处：`13_第 10 章...md` §10.2.1（第 58 行）。
4. **任务执行状态机给出一组合法状态与转换**：`waiting / queued / running / hold / succeeded / failed / killed / skipped / mark_successed`，并明确**业务 Outcome 另按验收规则维护**（执行调度状态 ≠ 业务结论）。
   出处：`13_第 10 章...md` §10.2.3.3（第 102–122 行）。
5. **运维侧「强制标记成功」是允许的，但有硬约束**：只能在获授权范围内改变执行状态，且**必须留下完整审计记录（谁、何时、原因、原状态、新状态）**，不能跨越层级直接判定业务 Outcome。
   出处：`13_第 10 章...md` §10.1.2（第 40 行）。
6. **「完成」与「进步 / 事实」要分权**：一次流程执行完整、甚至打出高分，也只说明「稳定地产出像成果的东西」，不自动等于真实目标达成；结论与证据应分离记录。
   出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter9.md`（「可验证闭环的边界：当『完成』不等于『进步』」段，第 306 行起）。

### B. 归档什么、归档到哪、怎么防无界增长

7. **状态要用三种互补表示，不能互相替代**：`Event Log`（记录发生过什么，适合追踪因果/审计/重建）、`Snapshot`（某一时刻的聚合视图，适合快速读取）、`Checkpoint`（可安全恢复执行的位置，除 Snapshot 外还含 Continuation、幂等与环境依赖）。「把每次状态保存都称作 Checkpoint，则会掩盖某些工具事务仍在进行、不能安全重放的事实。」
   出处：`资料/技术书籍/ai-agent-handbook/07_第 5 章 信息：上下文、状态与可复用能力资产.md` §5.3（第 248–258 行）。
8. **事件日志只追加、有顺序性**：每当 Agent 完成一个具业务意义的动作（生成计划、申请租约、发起/收到工具调用、等待人工确认、提交最终结果）就追加一条**不可随意改写**的事件，按顺序可还原完整演进；顺序保证避免「审批已成功却被重复发送」这类边界错误。
   出处：`13_第 10 章...md` §8.2.2（第 75–77 行，注：正文标题为第 8 章 §8.2.2；文件为 `11_第 8 章 Agent 状态存储与语义资产.md`）。
9. **事件不会无限累积——保留要分层，且保留期是显式策略**：「对近期任务保留细粒度事件，对稳定完成的任务形成可验证快照，并依据业务、合规和审计要求设置保留周期。关键不在于永久保存每一段模型输出，而在于确保影响任务正确性和外部动作的事实始终可追溯。」冷热分层：运行中低延迟热存 / 已完成可检索温存 / 长期不活跃按策略归档。
   出处：`资料/技术书籍/ai-agent-handbook/11_第 8 章 Agent 状态存储与语义资产.md` §8.2.2（第 83 行）、§8.7（第 425–427 行）。
10. **成果进产物库要「可寻址、可保留、可交付」，且带完整元数据**：每份 Artifact 需有稳定身份，并附带**来源任务、创建时间、版本、生成 Agent、输入依据、审批状态、权限范围、保留策略**。用户看到的应是可检索/引用/审计的成果，而不是一堆难解的目录名。
    出处：`11_第 8 章...md` §8.3.5（第 171–177 行）。
11. **已完成的产物不可原地修改**：一旦进入 Artifact Store 就不应再被原地改，后续变更生成新版本——这样引用方始终知道自己读的是哪一份。「避免某个 Agent 在不知情的情况下使用被覆盖的结果。」
    出处：`11_第 8 章...md` §8.3.4（第 169 行）。
12. **「压缩不是摘要，是四步有纪律的状态迁移」**：`Commit`（结构化事实先提交到权威状态/Workspace/资产库）→ `Compact`（把可叙述历史转成带来源与覆盖范围的摘要）→ `Rebuild`（用新摘要＋当前状态＋最近消息重建上下文并检查关键约束）→ `Validate`（对目标、未解决项、权限模式、关键证据做完整性检查）。并给出**压缩必须保留的 8 类事实清单**（目标与成功标准与不可变约束；已确认事实及来源并区分事实/假设/建议；已做决定及原因与被否决方案；已执行行动与工具结果与副作用；当前 Plan/Todo/阻塞/下一步；Artifact 与工作区路径与外部对象 ID；用户偏好与审批结果与权限模式；失败尝试及避免重复的原因）。
    出处：`07_第 5 章...md` §5.2（第 140–177 行）。
13. **大记录「退出窗口、但不退出任务」**：原始大结果写 Workspace/Artifact Store，活动窗口只留摘要 + 首尾或关键片段 + 内容类型 + 大小 + 生成工具 + 权限范围 + 可继续读取的稳定引用（带读取版本/时间）。例：完整安全扫描存 `evidence/security-scan.sarif`，Context 只留漏洞数与阻断项摘要与文件引用。
    出处：`07_第 5 章...md` §5.2（第 163–230 行）。
14. **生产级压缩是分层的，且「归档式摘要」逐轮保留独立记录**：以 Claude Code 为参照的五层（工具结果预算控制 → 噪声直接删除 → API 层微压缩 → **归档式摘要：像 git log 那样保留每轮独立记录，而非像 git squash 合并成一条，保留对话的逻辑脉络** → 全量压缩作为最后手段，并配「连续失败熔断器」）。
    出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md`（第 1045–1075 行，生产级分层压缩机制）。
15. **离线提炼保留三层数据、记录与整理分开**：不可变原始轨迹（用于审计）+ 单次运行分析记录（本次成败与经验草案）+ 对多条同类轨迹归纳出的面向未来的知识文档。正式文档写清**适用场景、推荐策略、禁止做法、例外条件、证据来源、最近验证时间**，而不是复述某一次任务全过程。把记录与整理分开，避免「一次偶发成功或网络故障立即改变 Agent」。
    出处：`ai-agent-book/book/chapter9.md`（第 75–77 行）。
16. **上下文资产按成熟度分级演进（raw → extracted → knowledge → skill），成果才值得进长期库**：「并非所有临时文件都应自动进入长期记忆或知识库；只有经过提取、校验、分类和权限确认的成果，才适合被进一步组织为可检索知识、经验条目或业务对象关系。」
    出处：`11_第 8 章...md` §8.3.5（第 181 行）；raw→extracted→knowledge→skill 与 Provenance 硬约束见 `资料/data - AI - 演讲/已完成/《Agent 数据底座的进化论：从存储系统到认知系统》.知识.md`（第 125–160 行，可溯源：Provenance 硬约束 + 证据链 DAG）。

### C. 审计留痕记什么（谁/何时/做了什么/结果）

17. **最小证据链由四类信息构成**：①**主体与范围**——用户、Agent、子 Agent、服务身份及其租户、应用、会话、任务、Trace 和消息轮次标识；②**意图与授权**——用户目标、指令来源、可用工具、权限范围、人工审批、当时生效的策略版本；③**执行事实**——模型请求与响应、检索与记忆操作、工具参数与结果、进程文件网络凭证等实际副作用；④**结果与证据**——操作状态、受影响对象、风险命中位置、原始事件引用、时间戳、检测规则或模型版本。
    出处：`资料/技术书籍/ai-agent-handbook/17_第 13 章 Agent 的可观测性.md` §13.4.2（第 501–518 行）。
18. **原始事实只追加、结论只能引用证据派生**：「原始事实宜采用追加写入并保留稳定标识，检测结论通过引用证据形成派生记录，避免为修正结论而改写原始事件。」且不能把「模型提出调用意图」直接当成「工具已经成功执行」。
    出处：`17_第 13 章...md` §13.4.2（第 515 行）。
19. **审计数据本身是高敏资产**：需最小采集、脱敏、独立存储、访问控制、加密、租户隔离与保留期限管理；「完整审计不等于无边界地保存全部内容」。
    出处：`17_第 13 章...md` §13.4.2（第 515 行）；脱敏具体规则集（API Key/令牌/身份证/手机/邮箱等占位符替换、规则引擎先于落盘）见 `ai-agent-book/chapter3/log-sanitization/README.md`。
20. **身份链「人 → Agent → 能力 → 行为 → 资源」，每次调用都记审计日志**：企业级身份框架把治理对象从「人→资源」重构为一条授权与审计链；对访问内部系统的流量，每一次调用都记审计日志供异常分析；「默认拒绝＋按需开白」并全程保留变更与访问审计记录，便于事后追溯与责任界定。
    出处：`资料/字节安全白皮书.md`（身份七原则第 116 行；行为审计第 386 行；默认拒绝＋审计记录第 414 行；日志脱敏红线第 167–169、1308–1327 行）。
21. **trace ID 全链路贯穿是留痕的骨架**：网关层做「校验调用来源 / 生成 trace ID / 检测 token 用量」，trace ID 全程带（→ 服务 → agent 调用 → 日志）。
    出处：`资料/录音 面试考点速查.md` Q26（第 340–357 行）。

### D. 失败 / 中断的收尾（怎么不静默失败）

22. **「Agent 失败」不是一个可执行的诊断——先分类再决定收尾动作**：瞬时模型/网络错误→有界退避；参数错误→修正；环境缺失→重建；权限拒绝→等待或终止；重复探索→重新规划；业务条件不满足→明确缺口。「盲目重试只会增加成本和风险。」
    出处：`06_第 4 章...md` §4.6.1（第 368–370 行）。
23. **状态信号缺失绝不能推断失败，必须回权威状态对账**：「轮询、回调、Watch 是状态变化信号，不是唯一事实源——任何信号缺失或中断，必须以权威 Task State 重新对账。」单次轮询失败不得直接推断 Task 异常；判定异常应基于租约/心跳，租约失效后才转入 `unknown` 并启动对账。
    出处：`13_第 10 章...md` §10.2.4（第 124–134 行）。
24. **恢复内容要有清单，且幂等是设计选择不是默认**：恢复通常包括业务状态、等待条件、事件位置或版本、工作区引用、外部操作记录；新实例需重新取得有效执行权（不能恢复一份旧心跳就继续提交）。Checkpoint 不等同外部副作用幂等。常见幂等手段：任务唯一键、幂等键、去重账本、事务性 outbox/inbox、租约与 fencing token、对账与补偿。
    出处：`13_第 10 章...md` §10.1.3（第 44–54 行）。
25. **失败归因要结构化、定位「首个错误」**：标出主要错误类别、首次不可接受行为的位置、对应工具调用或模型输出，并附可复核证据；归因记录用 JSON/YAML，引用步骤号/工具名/观察证据，区分根因与后果、判断可恢复性并给置信度；保存时连同任务目标、环境状态、Agent 版本、工具集版本、完整轨迹一起存，供回归。错误类别表里专门有一类「**模型执行异常：输出中途截断、无故停止、超时，或没有完成收尾动作就结束**」——这正是「没有收尾」被当成一类可检测缺陷。
    出处：`ai-agent-book/book/chapter7.md`（「失败归因：从整条轨迹定位首个错误」段，第 434–470 行）。
26. **负面结果也要入库**：「失败实验、被拒提案和停止原因写入日志。否则进化模块只看到幸存方案，会反复探索已经证伪的路径。」
    出处：`ai-agent-book/book/chapter9.md`（「可验证闭环的边界」段，第 316 行）。
27. **重复失败要有熔断，别在坏记录上持续烧钱**：全量压缩配「连续失败熔断器」，「生产数据表明，大量会话会被困在反复压缩失败的循环中」。
    出处：`ai-agent-book/book/chapter2.md`（第 1069 行）。

### E. 多轮对话下的收尾（一次任务结束 vs 整个会话结束）

28. **Task 与 Session 是不同权威对象、边界不同**：Task 是异步执行的最小业务单元，有独立持久标识和自己的业务 State，可**跨等待、恢复、人工审批，甚至跨多个 Session 续跑**；Session 组织相关交互与上下文，其边界不等同于一次进程拉起。跨 Session 续跑需 Runtime 显式装载经授权的 Task State 并把当前 Session 与该 Task 关联，而不是默认两 Session 天然共享上下文。
    出处：`13_第 10 章...md` §10.1.1（第 9–26 行，含对象关系表）。
29. **Call / Session / Task 三个边界要分开保留**：`Call`（一次请求或恢复，秒到分钟）、`Session`（一段连续交互边界，分钟到数天）、`Task`（围绕一个可验收目标，可跨 Call/Session/进程/节点）。「一个 Session 可以发起多个 Task；一个长 Task 也可以在多个 Session 中被查看、干预和恢复。将 Task ID 绑定为消息线程 ID，会限制后台执行、多人协作和跨渠道续接。」
    出处：`07_第 5 章...md` §5.3（第 236–246 行）。
30. **动作可跨回合、先发起后靠事件收尾**：事件驱动架构把「用户消息、工具返回、外部回调、定时触发」统一建模为事件流，由事件循环驱动；动作可以跨越回合、中途被打断、被更紧急的事抢占——所以「这一回合的流结束」完全不等于「这个任务结束」。
    出处：`ai-agent-book/book/chapter6.md`（第 29–47、117–128 行）。
31. **多轮里的「状态栏」是给模型看的运行状态快照**：时间戳跟踪等元信息「也为调试和审计提供信息」；且**状态栏投毒是真实风险**（模型几乎无条件相信状态栏，状态摘要若来自可被外部污染的数据源会被反向利用）。
    出处：`ai-agent-book/book/chapter2.md`（状态栏第 849–981 行，投毒警告第 736、976–979 行）。

## ③ 分歧取舍

1. **「完成」由谁定**：一派倾向让模型自报完成（实现简单、省一次判定），一派坚持**模型只能申请、Harness/核验器才能提交**（可审计、可分级）。本地材料一边倒地支持后者（`06_第 4 章...md` §4.6.2、`13_第 10 章...md` §10.1.2），并且把它和「执行状态 ≠ 业务 Outcome」绑在一起。取舍点在于**验证成本 vs 误判成本**：只读问答误判成本低（答错可重查），但「把没查完当成查完」会污染归档，因此仍需一个廉价的结构化完成门禁。
2. **归档粒度：全量原文 vs 提炼摘要 vs 两者并存**。分歧在于「省存储」与「可追溯」的对抗。本地材料的折中很清楚：**大原文退出上下文但不退出任务**（`07_第 5 章...md` §5.2）、**原始事实只追加、结论派生引用**（`17_第 13 章...md` §13.4.2）、**归档式摘要逐轮保留而非 squash 合并**（`ai-agent-book/book/chapter2.md`）。即：不是二选一，而是「不可变原档 + 可读提炼 + 稳定引用」三层。
3. **日志/审计写在哪、写多少**：一派追求「全量留痕便于排查」，一派主张「最小必要 + 脱敏 + 保留期限」（`17_第 13 章...md` §13.4.2、`字节安全白皮书.md`）。本地材料的立场是后者，但强调**影响正确性与外部动作的事实必须始终可追溯**——所以是「按事实价值分层保留」，不是一刀切少记。
4. **同步收尾 vs 异步收尾**：内置调度（收尾逻辑在 Agent 进程内，实现简单）vs 外置调度（收尾/等待/重投由独立系统管理，可释放资源、可弹性）。本地材料给的判据是规模与等待时长：小规模、等待不可预测性低用内置；大规范、等待跨越数天用外置（`13_第 10 章...md` §10.2.5 内置/外置责任对比表）。本项目单机单租户，天平偏内置。
5. **失败是「重试」还是「如实收尾」**：本地材料反复反对盲目重试，主张先分类、能修则修、不能修则**显式落一个失败/未知状态并留痕**（`06_第 4 章...md` §4.6.1、`13_第 10 章...md` §10.2.4）。分歧只在「哪些错误算可重试」，而清单（瞬时网络/参数/环境/权限/业务条件）是可操作的。

## ④ 反例踩坑

1. **把「流结束 / 连接断开 / 超时」当成任务结束**：超时只说明调用方没在期限内拿到结果，不等于执行停止（`13_第 10 章...md` §10.2.1）；信号缺失必须以权威状态对账，否则会发生「任务其实还在跑却被判完成」或「任务已死却被无限等待」（§10.2.4）。
2. **让模型自报完成、且把「流程跑完」当成「目标达成」**：`ai-agent-book/book/chapter9.md` 明说这是「稳定地产出像成果的东西」而不推动真实目标；`chapter7.md` 的 AndroidWorld 反例里 Agent 32 步「没有任何一步返回错误」，最后自行宣告完成，验收却发现记录不存在——**没有报错不等于做对了**。
3. **审计为「修正结论」而改写原始事件**：本地材料明确禁止——原始事实只追加、结论只能引用证据派生（`17_第 13 章...md` §13.4.2）。
4. **审计把敏感内容无边界全量入库**：Prompt、模型响应、工具结果常含个人信息/业务数据/凭证，审计数据本身是高敏资产；凭证禁止入库，需最小采集、脱敏、独立存储、访问控制、保留期限（`17_第 13 章...md` §13.4.2；`字节安全白皮书.md` 日志脱敏红线与 BadCase）。
5. **归档导致无界增长 / 存储成本随任务量超线性上涨**：`11_第 8 章...md` §8.3.5 点名「若缺少分层策略，存储成本将随任务量线性甚至超线性增长」；反复压缩失败而没有熔断器，会让会话困在烧钱循环（`ai-agent-book/book/chapter2.md`）。
6. **只保留成功/幸存轨迹，丢掉负面结果**：进化模块会反复探索已证伪路径（`ai-agent-book/book/chapter9.md`）。
7. **静默截断 / 静默失败**：工具结果截断必须显式标示（`ai-agent-book/book/chapter4.md` 第 224–226 行「静默截断是危险的」）；收尾期的归档/日志写失败同样不能无声吞掉——这正是本项目 T9「写失败也发提示、不留无声缺口」的业界同义要求。
8. **把 Task ID 绑成消息线程 ID**：会限制后台执行、多人协作与跨渠道续接，也导致「会话结束」被误当作「任务结束」（`07_第 5 章...md` §5.3）。
9. **状态栏/摘要被外部污染**：模型几乎无条件相信状态栏，若摘要来自可被污染的数据源，会被反向利用（`ai-agent-book/book/chapter2.md` 状态栏投毒）。

## ⑤ 对本项目适用性（只读问答、单租户、多轮）

- **无外部副作用 → 幂等压力大幅下降。** 本项目是只读问答，没有「写数据库/发消息/发布」等外部动作，`13_第 10 章...md` §10.1.3 讲的幂等键、outbox/inbox、补偿这一整套基本用不上；重跑只是重新查一遍，不会重复产生副作用。T9 里真正需要「幂等/去重」的只有**归档与日志写入本身**（避免重复插一条归档、避免重复发 done），这属于简单的唯一键/去重账本，不需要重型幂等机制。
- **单租户 → 多租户隔离、权限过滤、租户级保留策略可简化，但不能省。** `17_第 13 章...md` §13.4.2、`11_第 8 章...md` §8.7 的租户隔离/一致性/成本三分，本项目只需保留「审计与归档按保留期分层」这一条；身份链「人→Agent→能力→行为→资源」的完整审计链（`字节安全白皮书.md`）可退化为开发期身份桩（`X-Dev-User`）下的单主体留痕。
- **多轮 → 「任务边界」与「会话边界」必须分开，这是本项目 T9 的核心。** 一次提问 = 一个 Task；一次会话可能包含多次提问 = 多个 Task（`07_第 5 章...md` §5.3、`13_第 10 章...md` §10.1.1）。收尾信号 `done` 应绑定**Task 结束**，而不是「本轮输出流结束」或「会话关闭」。归档也应归档「这一次任务」，会话级只保存跨任务共享的上下文/摘要。
- **只读问答 → 完成判定可走「确定性验证」为主。** `06_第 4 章...md` §4.6.2 的五级验证里，本项目最贴合的是「结构验证（schema/必填/格式）」＋「确定性验证（规则/引用可溯源）」，独立模型验证与人工验收可作为兜底；「模型只能申请完成、核验器提交完成」这条原则应原样落到第 ⑧ 段核验节点与第 ⑨ 段收尾之间。
- **归档对象可映射到本项目产物**：黑匣子归档 ≈ Artifact Store 的不可变成果（带来源任务/时间/版本/权限/保留策略，`11_第 8 章...md` §8.3.5）；操作日志 ≈ Event Log / 审计日志（只追加，记谁/何时/做了什么/结果，`13_第 10 章...md` §8.2.2、`17_第 13 章...md` §13.4.2）；结束信号 done ≈ 状态机把 Task 从 running 推进到 succeeded/failed（`13_第 10 章...md` §10.2.3.3），失败态必须显式落库并发提示。
- **大记录防膨胀可直接抄四步法**：Commit（结构化事实先进权威状态）→ Compact（带来源与覆盖范围的摘要）→ Rebuild → Validate，并对照 8 类必保事实清单自检（`07_第 5 章...md` §5.2）。

## ⑥ 值得抄三条 / 要警惕三条

**值得抄三条**

1. **完成判定三分离 + 「模型申请、核验器提交」**：把「执行跑完」「证据齐」「业务完成」三件不等价的事显式分开，收尾状态由代码依据核验结果提交，不采信模型自报。（`13_第 10 章...md` §10.1.2；`06_第 4 章...md` §4.6.2）
2. **归档三层结构 + 只追加 + 不可变**：`Event Log（不可改写的事实）＋ Snapshot/提炼文档（可读视图）＋ Artifact（不可变成果，带来源/版本/权限/保留期）`，结论只引用证据派生，绝不回头改原始事件。（`11_第 8 章...md` §8.2.2、§8.3.4–8.3.5；`17_第 13 章...md` §13.4.2）
3. **失败/中断显式收尾 + 对账**：状态信号缺失一律回权威状态对账，失败按类别决定收尾，最终**显式落一个 succeeded/failed/unknown 状态并发提示**，绝不留无声缺口；归档/日志写失败本身要有兜底提示。（`06_第 4 章...md` §4.6.1；`13_第 10 章...md` §10.2.4）

**要警惕三条**

1. **警惕「流结束 = 任务结束」的偷懒判断**：本项目是多轮，一轮输出流结束只代表这一回合的模型调用结束，任务可能还在后台、可能等待澄清、可能刚发起未收尾。（`13_第 10 章...md` §10.2.1、§10.2.4；`ai-agent-book/book/chapter6.md`）
2. **警惕归档无界增长与压缩踩踏**：无冷热分层会让存储成本超线性上涨；反复压缩/重复归档失败要有熔断与去重，否则会话困在烧钱循环。（`11_第 8 章...md` §8.3.5；`ai-agent-book/book/chapter2.md` 熔断器）
3. **警惕审计做成「无边界全量存」或「为好看而改写」**：审计数据本身高敏，需最小采集＋脱敏＋保留期；原始事实不得改写。本项目虽是单租户只读，但归档里若混入用户隐私或凭据同样违规。（`17_第 13 章...md` §13.4.2；`字节安全白皮书.md`）

## ⑦ 疑点与不确定（含「本地材料覆盖不到」的部分）

1. **「黑匣子归档」这个提法的直接对应物，本地材料没有专章。** 最接近的是 HandBook 第 8 章「Event Log + Checkpoint + Artifact Store + 冷热分层」（`11_第 8 章...md`）与 ai-agent-book 第 9 章「不可变原始轨迹 + 单次运行分析 + 知识文档」三层（`ai-agent-book/book/chapter9.md`）。但「把一次任务的完整记录**提炼成一个黑匣子**并入库」的端到端工程做法（谁触发、入库事务边界、失败重试、与状态机的耦合）本地没有成体系描述，需回 `teach-petro-agent` 合同册或另找资料。
2. **「操作日志统一写专门日志库（建任务 / 挂起决定 / 收尾）」的统一格式本地无专章。** 材料给的是**原则**（只追加、含谁/何时/做了什么/结果、原始不可改、结论引用派生——`17_第 13 章...md` §13.4.2、`13_第 10 章...md` §8.2.2）与**字段清单**（§13.4.2 四类、§10.1.2 强制成功记录五要素），但没有一份「操作日志 schema / 表结构」。资料大纲-1 也自陈「限流、配额、并发控制、审计留痕的完整网关设计在本书基本没有专章……需另找资料」。
3. **结束信号（done）作为协议层收尾语义，本地几乎无覆盖。** 材料讲的是状态机推进（`running → succeeded/failed/killed`）与「请求超时不能证明执行停止」（`13_第 10 章...md` §10.2.1、§10.2.3.3），但没有「SSE/事件流如何发一个规范的 end-of-task 信号、客户端如何区分『本轮结束』与『任务结束』」的协议级实践。这是大纲里 ⑧ 网关/通信面（`15_第 12 章 Agent 分布式通信.md`）的边缘，本次未精读。
4. **「归档写失败也要发提示、不留无声缺口」的具范式本地无专条。** 可类比的两处是「静默截断是危险的」（`ai-agent-book/book/chapter4.md` 第 224–226 行）与「信号缺失必须以权威状态对账」（`13_第 10 章...md` §10.2.4），但「写归档/写日志失败时的降级与告知策略」需要本项目自行规定，不能从本地材料直接抄。
5. **多轮会话级收尾（整段会话的归档与关闭）本地只给了边界区分，没给会话级归档做法。** `07_第 5 章...md` §5.3 区分 Call/Session/Task，`13_第 10 章...md` §10.1.1 讲 Task 跨 Session，但「会话结束时要不要归档、归档什么、与任务归档如何避免重复」本地无明确方法。
