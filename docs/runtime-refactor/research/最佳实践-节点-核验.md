## ① 一句话结论

**核验（grounding check）在业界不是「一个总分」，而是「逐条断言 → 逐条材料」的对齐判定，且这一判定在能机械化的部分**优先用确定性代码**、把举证责任落到结构化证据上。** 与本项目 T8 最贴的两条业界做法是：**（a）「把答复里每个事实断言与工具返回值逐条对齐，取第一条无法溯源或与工具返回矛盾的断言」**（技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md 第 453 行表末行）——这正是 T8「逐句查有没有材料撑着」的行业原话；**（b）验证器要能被「按专家标签」校准成精确率/召回率两个数**（技术书籍/ai-agent-book/ai-agent-book/chapter9/trajectory-verifier/calibration.py）——这直接回答了 T8 的「拦多了误杀、拦少了放过」必须**量化**而不能凭感觉。对本项目（只读问答、答案＝复述材料）：**「数值/字符串必须在材料里找到」这条硬约束使零模型核验的适用面远大于一般 Agent**，本仓 `verify_draft` 一族（runtime-refactor/recon/A2-核验规则与归属审.md）方向正确；**最大风险不在路线，而在（1）子串匹配的边界、（2）单向/恒过盲区、（3）核验的召回与误杀从未被量化**（见 ⑤、⑥）。

## ② 业界主流做法（逐条注出处；凡 2b1a 已详述只给指针）

### A. 逐句「有没有依据」怎么机检

1. **逐条断言对齐工具返回值，取第一条无法溯源/矛盾的断言。** 「做对了但说错了」（环境状态对、告知用户的信息错）的定位法原文：**「把答复里的每个事实断言与工具返回值逐条对齐，取第一条无法溯源或与工具返回矛盾的断言」**。这是「逐句核验」在业界最直接的一句话。出处：`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md`（下文简称 book ch7）第 453 行（错误类别表「对用户的信息反馈错误」行）与第 476 行。

2. **机检形态＝「断言列表 + 每条断言的 `supported_by`」：无 supported_by 的断言即判 FAIL。** 客服 Agent 三层验证器的「过程层」（process_rules）里有一条 `_grounding`：遍历 `trajectory["claims"]`，**任一 claim 缺 `supported_by` 就返回 `fail` 并带「turn N: unsupported claim: …」证据**；claim 全有 `supported_by` 才 pass。**注意它是纯代码规则（读结构化字段），不是让模型判「有没有依据」。** 出处：`技术书籍/ai-agent-book/ai-agent-book/chapter9/trajectory-verifier/verifier.py` 第 159-177 行（`ProcessVerifier._grounding`）。**这是 T8 最贴的机制化原型：把「逐句有没有依据」落成「逐句 claim → 有无 supported_by」。**

3. **验证强度按风险分级（结构 / 环境 / 确定性 / 模型 / 人工），模型只能「申请完成」、Harness 才能「提交完成」，Verifier 返回结构化缺口。** 出处：`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md`（下文简称 hand ch4）§4.6.2（第 376-388 行）。**T8 落在「确定性验证」这一层**（可编码成功条件）。2b1a §二第 1 条已详述，此处只指路。

4. **三层验证器坚持「下两层用环境真值与程序规则，LLM 质量评判永不替代前两层代码闸」。** 结果层读环境真值、过程层用程序规则（业务规则/隐私/**事实依据**/承诺—行动一致性）、质量层才用 LLM/Rubric；示例默认确定性 `HeuristicQualityJudge`，无需 API Key。出处：`技术书籍/ai-agent-book/ai-agent-book/chapter9/trajectory-verifier/README.md` 第 3-16 行。**对 T8 的意义：把「事实依据」放在过程层用程序规则做，是业界已选的架构，不是权宜之计。**

5. **能写成程序化断言的继续用断言，LLM 评判只用于确实无法机械判定的维度；确定性检查更便宜、更稳定、更适合长期回归。** 出处：book ch7 第 300-302 行（验证方式谱系，「向右移动并不意味着放弃左侧」）。2b1a §二第 6 条已引。

> **小结（A）**：业界主流是「**结构化 claim 列表 + 每条 claim 的 supported_by 字段 + 代码规则判有无**」，与本仓「行 → 引标辖域 → 观察数值是否在断言文本复述」（A2 `_assertion_chunks`/`_supported`）是**同一范式的两种切分粒度**：业界切「claim」，本仓切「行+引标」。

### B. 引用质量怎么判定（引标对不对、引用的材料是否支持这句话）

6. **引用质量用「蕴含判定」机检，不靠模型自评：citation recall＝每条陈述至少一个引标且被引段落蕴含该陈述；citation precision＝去掉该引标后陈述是否仍被其余引标蕴含（判「无关引标」）。** 出处：`https://arxiv.org/html/2305.14627`（ALCE，arXiv 2305.14627）；2b1a §二第 4 条已详述。**要点：这是「小分类模型 + 子串匹配」而非大 LLM，与本仓子串匹配同侧。**

7. **「引用存在 ≠ 引用正确」：不能因为「它自己带了引标」就认定有据，必须用整行文本对引标逐一重判。** 本仓已落地（A2 R-A2-19「引标序号自身不作数，防自证」，修一）。业界对应＝citation precision 的「去掉该引标后陈述是否仍被其余引标蕴含」。出处：runtime-refactor/recon/A2-核验规则与归属审.md 第 171 行（R-A2-19）；2b1a §四第 6 条。

8. **答案溯源要能回溯到「具体文档、段落与版本」，用户验证与审计的基础；配版本快照、回滚、时效检测、引用分析。** 出处：`技术书籍/ai-agent-handbook/11_第 8 章 Agent 状态存储与语义资产.md`（下文简称 hand ch8）§8.5.6（第 307-311 行）。2b1a §二第 3 条已引。

9. **可溯源是硬约束 + 来源类型映射初始置信度；冲突用 `refuted_by` 表达、对外提供 `chain.conflicts` 查矛盾。** 出处：`资料/data - AI - 演讲/已完成/《Agent 数据底座的进化论：从存储系统到认知系统》.知识.md`（下文简称 ContextSeek）§6.1-6.2（第 125-160 行）。2b1a §二第 11 条已引。

### C. 「无据改写」「矛盾分源」的业界对应

10. **无据改写（本仓 INV-1）的业界对应＝「不能溯源就该进明确缺口，而不是硬答」**：业务条件不满足要明确缺口，而不是盲目重试或编造；Verifier 应返回结构化缺口、失败证据、可修复性。出处：hand ch4 §4.6.1（第 368-370 行）、§4.6.2（第 388 行）。本仓落地形＝无据断言改写为「未找到（材料未披露）：…」（A2 R-A2-18）。

11. **矛盾分源列明（本仓 INV-4）的业界对应＝不让模型自己「调和」矛盾**：ContextSeek 用 `refuted_by` + `chain.conflicts` 暴露冲突，综合置信度用 Noisy-OR；主流倾向是如实分列（按来源/版本/可信度）或把判断留给用户。出处：ContextSeek §6.4（第 144-159 行）；book ch7 第 590 行（孤立分块「各自独立但相互矛盾」强答会给用户混乱信息）。本仓落地形＝`_contradiction_members` 分源块（A2 R-A2-23、INV-4）。

12. **幻觉设为一票否决（Veto）：无论其他维度多优，出现编造虚假信息即判零分。** 出处：book ch7 §Rubric 四准则第 3 条（第 320 行）。**对 T8 的意义：核验应是「一票否决闸」（发现无据即改写/拦），而不是与其他好项加权平均。**

13. **跨源材料不得冒充题眼证据：出处名/报告名与内容任一含锚才算对齐，窗内无对齐材料时如实声明「不作题眼归属断言」。** 本仓已落地（A2 R-A2-25/R-A2-28、`_attribution_block`）——这正对应任务书「引用的材料和问句点名对象对不上号时发提示」。

### D. 核验的召回与误杀（拦多了误杀、拦少了放过）

14. **验证器的质量必须「按专家标签」算成精确率与召回率两个数，而不是只看总分或人工感觉。** 客服轨迹验证器的 `calibration.py` 对每个维度、对 `expert_labels` 计算：`precision_on_failures = tp/(tp+fp)`（**拦得准不准＝误杀率反面**）、`recall_on_failures = tp/(tp+fn)`（**漏得少不少＝放过率反面**）、`support`（样本数）、`exact_label_agreement`。出处：`技术书籍/ai-agent-book/ai-agent-book/chapter9/trajectory-verifier/calibration.py`（`calibration_report` 全函数）。**这是 2b1a 未点出的关键条目：T8 的「改写多了误杀、改写少了放过」在业界是一项**可标定指标**。**
   - 注意其配套纪律：**一个总分无法归因**，必须逐维诊断 + 保留证据轮次（README 第 7 行「`demo.py` 对比只有一个总分的输出与带证据的多维诊断」）。
   - 真实模式要求「低置信度或高风险轨迹交给第二个验证器或人工复核」（README 第 55 行）——**低置信度不等于放过，而是升级处置**。

15. **失败归因用「规则先筛、LLM 再定位」：至少三类可先用规则筛出嫌疑轨迹，比全量喂 LLM 更便宜也更准。** 出处：book ch7 第 458、476 行。2b1a §二第 9 条已引。**对 T8 的意义：确定性核验天然是「规则先筛」那一层，定位首错的职责可与它分工。**

> **小结（D）**：业界对核验质量的量化口径＝**「按专家标签的 precision/recall（对失败维度）」**，本仓 `verify_draft` 目前只返回「改写了几行/被引序号/是否分源」，**没有与人工标注过的一致性度量**——这是 T8 与业界最直接的差距（见 ⑤、⑥）。

## ③ 分歧取舍

1. **逐句机检的切分粒度：业界切「claim 列表」vs 本仓切「行 + 引标辖域」。** 业界（trajectory-verifier `_grounding`）把断言抽成独立 `claims` 数组、每条带 `supported_by`；本仓（A2 `_assertion_chunks`）按「行内引标 `[n]` 切辖域」。**取舍**：claim 粒度更贴近「逐句」，但需要一次「答案 → claim 列表」的切分（本仓零模型，这一刀只能靠引标/行边界，无法做语义原子化）；行+引标粒度零模型即可执行，代价是「末引标后的尾部文本不属任何辖域」（A2 D-A2-09）、「整行仅 `[n]`」等边角。

2. **引用质量判定用哪一档：子串匹配 / NLI 小模型 / LLM judge。** ALCE 选 NLI 蕴含小模型（可复现、便宜）；本仓当前是**纯子串匹配**（最简形态）；2b1a §三取舍二把「中文 NLI 蕴含小模型」列为「比子串强、比 LLM 判便宜可复现」的第三档（**待裁**）。**T8 是零模型段，第三档若引入即破坏「零模型」，须先裁是否允许。**

3. **核验「拦到哪一档」：无条件改写 vs 低置信度升级。** 业界（trajectory-verifier README 第 55 行）主张「低置信度/高风险 → 第二验证器或人工」；本仓是**一刀切改写**（无置信度概念）。**取舍**：一刀切简单可复现，但把「像是有据但匹配不上」和「明显编造」同等处置＝增加误杀；引入置信度则需要「匹配强度」这类本该由模型给的信号，T8 零模型下**只能用匹配覆盖面近似**（如命中比例），是**待裁**。

4. **核验结果的呈现：单点返回值 vs 结构化缺口 + 证据。** 业界要求 Verifier 返回「结构化缺口、失败证据、可修复性」（hand ch4 §4.6.2）；本仓 `verify_draft` 只回 `(文本, 改写数, 被引序号, 是否分源)`。**取舍**：结构化的信息量大、可审计，但需要设计载体（2b1a §五已列「适用、建议补齐」）。

5. **矛盾处置：分源列明 vs 加权裁决。** 本仓与主流均选**分源列明/暴露**（INV-4；ContextSeek `refuted_by/conflicts`）；ContextSeek 另给了 Noisy-OR 加权做「综合置信度」。**本项目零模型，加权裁决需置信度模型，不适用；分源列明是正解。**

## ④ 反例踩坑（含子串匹配的假阳/假阴、把「没报错」当对）

1. **「全程无报错」被当成「正确」——静默失败。** AndroidWorld T3A：32 步无一步报错、Agent 自行宣告完成，验收却发现数据根本不存在；第 8 步思考里模型已写「我看不到图像内容」却既没停也没报告。**教训：错误信号缺失 ≠ 事实正确；核验不能只看「有没有报错」。** 且根因是 Harness 观察通道缺失、不是模型能力——**误记为模型能力就会去换模型，方向全错。** 出处：book ch7 第 468 行。2b1a §四第 1 条已引。

2. **子串匹配的假阳性（拦错，把对的也改了）。** 本仓已自陈：数值匹配为**子串包含**，`"52"` 会命中 `"1520"`、`"52.3"`（A2 D-A2-10/D-A2-15）。**业界对应**：trajectory-verifier 的 `_privacy` 也是「`str(value) in reply`」子串判定（verifier.py 第 141-143 行），同样面对子串越界问题——**说明子串是行业通用做法，其假阳是已知代价，不是本仓独有缺陷。**

3. **子串匹配的假阴性（放过，把编造漏了）。** 本仓已自陈：矛盾分组以**全角「：」**切 subject 且按原文精确分组——半角冒号/写法差异（空格）会被拆成不同组，真矛盾漏判（A2 D-A2-20/D-A2-31）；值比较取「：」后原文字符串，格式差异即算不同值，可能**误判**矛盾（D-A2-32）。

4. **支撑方向单向（只查「材料有的被复述」，不查「断言多出的编造数」）。** 本仓：`_supported` 只查「被引观察的数值是否在断言里复述」，**不查断言里多出的、观察没有的数字**——「有据行内编造额外数字」不被拦（A2 D-A2-11）。

5. **「恒过」盲区（零数值 token 的观察/断言恒判支撑）。** 本仓：纯文本卡零数值 token 恒判支撑，**语义充分性完全不查**（A2 R-A2-12/D-A2-12）；且无引标但有数字的行可经「窗内对齐」放行，答案面会出现**无出处序号的数字行**（D-A2-21）。出处：runtime-refactor/recon/A2-核验规则与归属审.md。

6. **只溯源不校验会「自证」。** 「引标序号自身不作数」（A2 R-A2-19）；业界对应＝citation precision 要判「去掉该引标后陈述是否仍被其余引标蕴含」。出处：2b1a §四第 6 条。

7. **一个总分无法归因。** τ²-bench 成功率下降时单分数不告诉你「没检索到 / 关系想错 / 补了无依据内容」；必须拆逐维诊断。出处：book ch7 第 368 行；trajectory-verifier README 第 7 行。

8. **「做对了但说错了」被整体成功率掩盖。** τ²-bench 带信息告知要求的 704 次运行失败 240 次，162 次是信息告知出错，80 次（占失败 1/3）环境状态正确但告知错误。出处：book ch7 第 466 行。**教训：核验必须覆盖答案面的告知内容，不能只看环境状态。**

9. **LLM judge 的长度偏差与奖励作弊（作为「为什么本仓选零模型」的反证）。** 更长回复更易得高分；Agent 找捷径拿高分却没完成；需显式惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。出处：book ch7 第 310、324 行。

## ⑤ 对本项目适用性（只读问答、单租户）

**已落地且高度适用（本仓 T8 核验族，全部零 LLM、纯函数；锚定 commit e4b75f1，覆盖 `appv2/runtime/graph.py` L668-L1047）：** 见 `runtime-refactor/recon/A2-核验规则与归属审.md`：
- **逐句有据机检**：`_assertion_chunks`（行 → 引标辖域）＋ `_supported`（被引观察的数值须在断言文本复述）＋ `_scope_usable`（空壳辖域重判）＋ `_window_aligned`（窗内对齐放行）——对应业界「claim → supported_by」（trajectory-verifier `_grounding`）与「事实断言逐条对齐工具返回值」（book ch7 第 453 行）。
- **无据改写（INV-1）**：`verify_draft` 把无据断言改写为「未找到（材料未披露）：…」并计数（A2 R-A2-18）。
- **矛盾分源（INV-4）**：`_contradiction_members` ＋「多来源不一致——分源列明（禁止无出处调和）」块（A2 R-A2-23）。
- **引用与题眼对不上号发提示**：`_attribution_conflicts`/`_attribution_block`——跨源引用「按出处如实区分，不得并入题眼断言」（A2 R-A2-24…28）。
- **剥发射残留**：`strip_emission_fences`——确定性剥离答案面 JSON 通道残留，零误伤域外 JSON（A2 R-A2-03…07）。

**为什么只读问答特别适合零模型核验：** 答案只能是材料的复述，于是「数值/字符串必须能在材料里找到」是一条**可机检的硬约束**（2b1a §五）——一般 Agent（写代码/发消息/改数据）没有这条约束，只能靠模型评审。

**适用、建议补齐（标「适用」）：**
- **给核验配「按人工标注的精确率/召回率」度量。** 业界用 `calibration.py` 对 `expert_labels` 算 `precision_on_failures`/`recall_on_failures`（trajectory-verifier）；本仓 T8 应建一张「已知漏网/误杀样本」清单作专家标签，量化「改写多了误杀、改写少了放过」——**这是 T8 与业界最直接的差距，也是对 A2「D-A2-…」34 条疑点做回归的载体**（book ch7 第 458 行「规则先筛」、README 第 7 行「单总分 vs 带证据多维诊断」）。
- **核验结果结构化：返回「结构化缺口 + 失败证据 + 可修复性」**（hand ch4 §4.6.2），而非只回改写行数（2b1a §五已列，**待裁**）。
- **一票否决口径**：无据断言/编造数值即判不合格，不被其他好项抵消（book ch7 Rubric Veto）——本仓「改写」已是此形态，可显式记为一票否决。
- **回读权威源校验 ID/Hash/Status**，防引用旧版本结论（2b1a §二第 12 条，S7 回读权威源，**待裁**）。

**不适用（标「不适用」）：**
- **多次采样自洽（SelfCheckGPT/语义熵）**：本项目有权威材料库，直接对材料核验更准更省，且需多次 LLM 成本（2b1a §三取舍五）。
- **LLM 质量层评判**：T8 是零模型段，质量层（Rubric/LLM judge）不属本节点；如需质量评判应另设节点，**且不得替代过程层代码闸**（trajectory-verifier README 第 5 行）。
- **多租户权限过滤**（hand ch8 §8.5.6）：单租户，暂不落地。
- **GraphRAG 跨实体关系推理**（hand ch8 §8.5.5）：本项目问答粒度更细，未涉及。

**待裁：**
- **是否允许引入中文 NLI 蕴含小模型**做「语义蕴含」第三档——一旦引入即打破 T8「零模型」（2b1a §三取舍二；本仓 docstring 自陈「细化批可换更强实现」，A2 D-A2-12）。
- **是否给核验加「匹配覆盖面 = 置信度」的近似的低置信度升级路径**（对齐 trajectory-verifier README 第 55 行「低置信度 → 第二验证器/人工」），还是维持一刀切改写。
- **溯源粒度**是否从「行内 `[n]` 引标 → observation index」细化到「文档 + 段落 + 版本」（hand ch8 §8.5.6）。

## ⑥ 值得抄三条 / 要警惕三条

**值得抄三条：**
1. **「逐条断言对齐工具返回值、取第一条无法溯源/矛盾」+「claim 无 supported_by 即 FAIL」——把「逐句有没有依据」落成结构化字段的代码规则**（book ch7 第 453 行；trajectory-verifier verifier.py 第 159-177 行）。本仓 `_supported`/`_assertion_chunks` 已是同范式，可进一步把「claim → supported_by」显式化。
2. **核验质量按专家标签算精确率/召回率（`precision_on_failures`/`recall_on_failures`）**（trajectory-verifier `calibration.py`）——把 T8 的「误杀/放过」变成两个可标定的数，用 A2 的 D-A2-… 疑点清单当专家标签建回归集。
3. **无据 → 明确缺口（不硬答）、矛盾 → 分源列明（不调和）、幻觉 → 一票否决**（hand ch4 §4.6.1/§4.6.2；ContextSeek `refuted_by`；book ch7 Veto）。本仓 INV-1/INV-4 已落地，方向正确，守住即可。

**要警惕三条：**
1. **子串匹配的假阳/假阴。** 数值先做**边界 token 化**（区分 `52` 与 `1520`/`52.3`）；中文标点/全角半角先归一化再分组切分（A2 D-A2-10/D-A2-20/D-A2-31/D-A2-32 是现成反例清单）。业界子串判定（如 verifier.py `_privacy`）也有此代价，**须靠回归集守住，不能假设「匹配上就对」。**
2. **单向 / 恒过盲区。** 只查「材料有的被复述」不查「断言多出的编造数字」（D-A2-11）；零数值观察/断言恒过、语义充分性不查（D-A2-12）；放出无出处数字行（D-A2-21）。**应把已知漏网类型名单化，作为回归用例固定下来。**
3. **把「无报错」当「正确」、把根因误记为模型能力，以及「一个总分无法归因」。** 静默失败（AndroidWorld T3A 第 468 行）与「做对了但说错了」（第 466 行）都说明：核验要独立于「有没有报错」，且要能逐项归因（book ch7 第 368 行；README 第 7 行）。

## ⑦ 疑点与不确定（含「本地材料覆盖不到」的部分）

1. **本地材料没有一篇专讲「纯程序零模型核验」的完整方法论。** 最接近的两处是 handbook/ch4 §4.6.2 的五级验证强度表，与 trajectory-verifier 的 `_grounding` + `calibration.py`（后者是**实验代码**，不是正文章节）。**本文第二节 D 组「按专家标签校准召回/误杀」是从 `calibration.py` 源码读出的事实**，非某章论述；诚实标注。
2. **「逐句」在零模型下的切分是硬约束。** 业界把答案切成 `claims` 数组（语义原子化，通常靠模型或标注）；本仓无模型，只能按「行 + 引标」切，**语义原子化这一刀做不到**——「一个长句里混了有据与无据两个事实」在本仓会被判成同一断言（A2 D-A2-23 空壳重判即此形）。**这是零模型的固有边界，本地材料未见解法。**
3. **本仓核验的召回/误杀从未被量化。** `calibration.py` 提供了业界口径（按 `expert_labels` 算 precision/recall），但**本仓没有对应的专家标签集**；A2 的 34 条 D-疑点是「只列不判」的自陈，**不等于已标定的漏网率**。要量化须先建标注集（见 ⑤「适用」第 1 条）。
4. **中文/石油领域下「蕴含判定」的表现未知。** ALCE 用英文 TRUE 模型、AIS 用人工，能否迁移到中文 + 表格数值断言未验证（推断，无本地证据）。
5. **本仓锚定 commit e4b75f1（`graph.py` L668-L1047）。** 若代码已变，行号、函数清单与 D-A2-… 疑点须重核；A2 的疑点是该版本的自陈，不代表当前实现。
6. **「grounding / attribution / faithfulness / 忠诚度」在资料里混用**（hand ch8 叫「答案溯源」，ALCE 叫 citation quality，AIS 叫 attribution，面试速查叫「忠诚度」，trajectory-verifier 叫 factual_reliability）——本文按「答案被所给材料支持」统一理解，具体定义以各自原文为准。
7. **本仓「分源列明」的召回去向未在 A2 覆盖范围内**（A2 只覆盖 `graph.py` L668-L1047 纯函数段）：两个来源矛盾时的 UI/接口呈现须另查 `_finalize`（L3746-3762）与 citation 帧（A2 D-A2-19 提及「cited 集合/引用块/citation 帧三处语义不同」）。
8. **本地材料覆盖不到的空白（如实说没有）：** 本地**没有**「引用应如何随流式增量出现」的协议（hand ch6 §6.5 只讲事件类别/游标/背压）；**没有**「中文答案逐句可点击引用」的生产级做法（资料大纲-1 §六自陈 chapter7「答案逐句附带可点击引用」未展开）；**没有**「核验器本身的 A/B 灰度与线上回归工程」（book ch7 有评估方法论，无上线回归流程）。
