## ① 一句话结论

业界的共识是：**反问不是默认兜底，而是在「歧义会实质改变结果」时才付的成本**；而且大多主张「**先探查、拿候选，再拿候选去问**」，而不是一上来就向用户抛开放问题——本地三本材料都能支撑这一点，但**「反问封顶（连续问几次停）」与「默认时间窗该不该设」这两点本地材料没有直接论述**（详见 ⑦）。

## ② 业界主流做法（每条注出处）

### 2.1 什么时候该反问、什么时候自己往下走

1. **判据＝「歧义是否实质改变交付内容 / 责任 / 执行边界」**。原文：「任务信息以能够支撑执行和验收为准。目标和约束已经清楚时，可以直接推进；只有歧义会实质改变交付内容、责任或执行边界时，才需要进一步澄清。」——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:189`
2. **反问（ASK）不是默认兜底，先想办法把不确定性降下来再说**。原文：「`ASK` 不是默认兜底。过多审批会让用户形成机械确认，也让 Agent 失去连续性。应该优先通过更窄 Tool、参数约束、预览、资源范围和 Sandbox 降低风险，只在目的或后果无法由策略充分判断时请求人工参与。」并给了「风险示例 → 建议默认策略」表（读取类 ALLOW 并记录范围；发送/发布/删除/改生产数据 ASK 或 DENY）。——`技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md:313,315-321`
3. **目标/交付/依赖已清楚就别再确认，避免决策瓶颈**。原文：「目标、交付物、负责人和依赖已经清楚时，就应允许执行者开展工作。」「要避免所有局部决定都等待主管确认，形成决策瓶颈。」——`…/14_第 11章 Multi-Agent 协作与编排.md:153,151`
4. **「先最小流程，必要时才升级」**：能用单次调用/简单流程解决就不引入重流程；Agent 系统是用延迟和成本换性能，要权衡这笔交换是否值得（反问同理：用一轮交互换答案正确性）。原文见「从简单到复杂」原则。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:374`
5. **澄清放在「执行前」的正面范式**：OpenAI Deep Research / GPT-5.6 引入「意图澄清过程」——收到需求后先问「你偏好使用哪个数据源？需要分析哪些技术指标？」，弥合「用户说了什么」与「用户真正想要什么」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:253,255`

### 2.2 澄清与「先探查再动」（discover / 检索前置）的关系

1. **检索瀑布把「歧义处理」当成探查的一个阶段**：DataBuddy 运行时 S0–S8 里，**S6＝「资格与歧义：过滤 / 重排 / 混淆 / 拒答」**——即检索（探查）流程内部就带消歧与拒答，而不是先停下来问用户。——`data - AI - 演讲/已完成/从业务本体到持续进化.知识.md:291`
2. **「先召回候选，再让用户确认」是消歧的推荐形态**。原文（Datastrato 可信取数）：「消歧靠**匹配过程**：客户问『总资产』时，系统在指标库检索出三个类似指标，让客户确认问的是哪一个（AI 生成候选 + 检索召回 + 用户确认）；客户说不清楚时，把几个候选指标的定义和别称列出来供选择。」——`data - AI - 演讲/已完成/《从元数据到 Data Agent：企业如何从“能问数”走向“可信取数”》刘镔辉｜Datastrato 解决方案架构师.知识.md:269-270`
3. **NL2SQL 生产失败，根因常是「默认问题已足够明确」这个隐含假设**。原文拆出四个不确定性：口径不唯一 / 定义不一致 / 表字段多版本 / 结果可信度无法保证。结论：「企业真实难题往往不在 SQL 语法，而在业务语义、数据可信度与上下文。」——`data - AI - 演讲/已完成/《从人用数据，到 Agent 用数据：下一代数据底座之变》.知识.md:88-103`
4. **强类型中间态**：DataBuddy「五段式」把自然语言理解与执行解耦（IntentSpec → SemanticContext → SemanticPlan → ExecutionPlan → EvidencePack），其中 SemanticContext 就是「候选实体/指标/关系/规则/可信样例」；分工是「模型：理解与提出计划 ｜ 语义编译器 + Harness：验证、授权、执行、审计与失败关闭」。——`…/从业务本体到持续进化.知识.md:295-313`
5. **探查与执行可以分阶段**：Plan Mode「只读探索—写入计划—人工确认—进入执行」，探索阶段只开放只读工具。——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:163`

### 2.3 问题分解（大问题拆成子问题）

1. **模型的本职之一就是分解**：LLM Agent 收到请求后「先解析真实意图（用户说的往往不是他真正想要的），再将模糊或复杂的任务拆解成可执行的步骤」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:111`
2. **何时该拆成子任务，有明确判据**。原文：「只有当工作存在独立交付、不同责任或明确依赖时才拆成子任务；同一成员连续完成的内部步骤不必逐项建成任务。」子任务「其价值仍要回到父 Task 的目标上判断」。——`…/14_第 11章 Multi-Agent 协作与编排.md:183,187`
3. **计划要回答「怎么拆、谁来干、依赖怎么排、哪里能并行」**。——`…/14_第 11章 Multi-Agent 协作与编排.md:191-197`
4. **分解要有封顶**：团队级停止条件需在开始前约定，含「最大委派深度、派生任务数量、单项任务重试次数、结果返工轮次、连续多轮没有新增有效产物/状态进展时的处理方式」。——`…/14_第 11章 Multi-Agent 协作与编排.md:209`
5. **分解的三种控制档位**：轻量 Todo（目标明确、步骤少）/ Plan Mode（影响面大、需审阅）/ Planner–Executor（长任务、多依赖、可并行）。——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:123-129`
6. **「固定子任务→工作流；需动态决策→自主 Agent」**：可清晰分解为固定子任务的场景用工作流，只有需要动态执行路径时才用自主 Agent。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:374`
7. **长任务分解范式**：Anthropic 把复杂任务分解为「初始化 Agent（设环境、分解任务列表）」与「执行 Agent（每会话增量推进并留清晰交接产物）」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:513`

### 2.4 反问的封顶与体验

- **直接论述：本地材料没有**（grep「封顶 / 追问次数 / 最多问 / 连续追问 / 一次只问」无结果）。相邻可借的做法：
1. **少而准＝体验原则**：过多确认会让用户形成「机械确认」，也让 Agent 失去连续性（原文见 2.1-2）。——`…/08_第 6 章…md:313`
2. **把「用户认知边界」建模出来，别一次问完**：τ²-bench 用 `known_info` 界定用户知悉范围、`task_instructions` 规定透露方式；`known_info` 里没有的信息「用户并不知情，因而无法主动陈述，Agent 只能通过提问和引导用户查询来获取」——即渐进式信息透露（Progressive Information Disclosure）。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:87,254`
3. **反问卡的内容模板**：审批请求应包含「Agent 想做什么、为什么、以谁的身份、作用于什么对象、预计影响、参数和差异、是否可逆、失败如何处理，以及批准范围（仅本次 / 当前 Task / 一类受限动作）」。——`…/08_第 6 章…md:334`
4. **不确定就澄清而不是硬猜**：失败归因把「仓库里有两个同名配置文件时直接选一个，既不说明也不追问」列为「需求理解与歧义」类失败。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:448`
5. **多候选歧义要追问到具体对象**：评估边界例「如果用户有多个女儿且分别看不同的医生，应追问是哪个女儿」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:362`

### 2.5 「默认值」该不该设、怎么标注

1. **默认值按风险分级，而不是一律无默认**：低风险读取给 ALLOW 并「记录范围」；发送/发布/删除/改生产数据才 ASK/DENY。——`…/08_第 6 章…md:315-321`
2. **安全类默认取「故障安全」一侧**：Harness 的约束层「采用故障安全默认值，所有能力默认关闭，必须显式开放」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md:285`
3. **口径/参数由接口决定，不交给模型猜**：运维问数实现「Bot 先解析用户意图确定查询条件（等级/状态/时间范围/业务线），调用事件中心 API 执行结构化查询……统计口径由查询接口的参数决定，不交给模型从原始明细中自行推算——确保每个数字都可追溯到一次明确的 API 调用」。——`技术书籍/ai-agent-handbook/44_塔斯汀万店连锁的智能运维闭环实.md:72`
4. **默认值要写明适用条件，别当固定要求**：经验条目「查询不到日志时扩大时间窗口」必须再判断「当时是窗口太短，还是数据根本没有采集」，「经验的来源和不适用条件，能帮助团队避免把一次现场处置变成所有任务的固定要求」。——`技术书籍/ai-agent-handbook/28_第 23 章 受控自进化.md:33`
5. **明确空缺**：没有讲「默认时间窗（如近 30 天）该不该设、如何标注」的直接论述（见 ⑦）。

## ④ 反例踩坑

1. **不澄清 → 做出来的不是用户要的**：失败模式表把「漏掉需求里的一个条件、把范围理解宽了或窄了」列为「需求理解与歧义处理」类失败。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:448`
2. **默认「问题已足够明确」→ NL2SQL 生产失败**（口径/定义/版本/可信度四不确定）。——`data - AI - 演讲/已完成/《从人用数据，到 Agent 用数据…》.知识.md:88-103`
3. **遇到歧义既不问也不说明，静默选一个**（同名文件直接选）。——`book/chapter7.md:448`
4. **反问过多 → 机械确认 + 决策瓶颈**。`handbook/08:313`、`handbook/14:151`
5. **纯业务未定义的问题，硬让 AI 猜**：「衣服送洗 vs 洗衣房在哪，业务没定义清楚 → AI 也搞不清」；正解是「严格限制意图范围（如 10 个标签），边界模糊用导航思路分大类再分小类」。——`录音 面试考点速查.md:313-322`
6. **未验证的澄清结果直接进长期记忆，会被后续当事实重复引用**。「更适合沉淀为团队记忆的，是经过任务结果、外部数据、其他成员或人工确认的信息」。——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:252`

## ⑤ 对本项目适用性（只读问答、单租户）

1. **反问触发条件可以收紧**，因为本项目只读、无副作用：按 `handbook/08:315-321`「读取类 ALLOW 并记录范围」的思路，**读操作默认自己走**，反问只在「对象/口径/时间歧义会实质改变答案」时触发（判据用 `handbook/14:189`）。
2. **「先探后问」与本项目「三段（查资料→拆小问题→反问）」天然契合**：第一段「查资料」正对应 DataBuddy 的探查阶段与 Datastrato 的「检索出候选」；第三段「反问」应尽量基于**已检索出的候选**（如名词的多个含义、多个同名对象），而不是开放提问。出处：`DataBuddy:291`、`Datastrato:269`
3. **问题分解可直接采用「独立交付/不同责任/明确依赖」判据**，并给分解设封顶（深度、子问题数、返工轮次）——`handbook/14:183,209`；单租户下无跨租户隔离开销，封顶只服务「不烦人 + 不烧 token」。
4. **S6 式「过滤/重排/混淆/拒答」可内置**：把「歧义处理」做进探查阶段，能消掉的当场消掉（拒绝/择一），消不掉的才升级成反问卡。出处：`DataBuddy:291`
5. **默认时间窗「近 30 天」**：本地材料支持「默认值按风险分级、可设但须注明」（`handbook/08:315-321`、`handbook/28:33`）与「口径由接口参数决定、不由模型猜」（`44_塔斯汀…:72`），据此**可推断**：应把「无时间词 → 默认近 30 天并注明」写成**程序里的确定性规则**，而不是让模型自由裁量。**注意：这是本调研的合理延伸，本地材料没有直接讲『默认时间窗』**（见 ⑦）。
6. **单租户简化了豁免判断**：不需要 `handbook/08` 那套跨租户 DENY 逻辑，反问与默认的边界判断更简单。

## ⑥ 值得抄三条 / 要警惕三条

**值得抄（3 条）**

1. **反问判据一句话**：「歧义会实质改变交付内容/责任/执行边界才澄清，否则直接推进」——`handbook/14:189`。可直接写进 T3 的判定规则。
2. **先探后问 + 候选反问卡**：先检索出 2–3 个候选，再让用户在三选一（`Datastrato:269`）；反问卡内容照 `handbook/08:334` 的模板（做什么/为什么/影响/可逆/范围）。
3. **分解要封顶**：分解深度、子问题数、重试/返工轮次在开始前约定（`handbook/14:209`）；分解判据用「独立交付/不同责任/明确依赖」（`handbook/14:183`）。

**要警惕（3 条）**

1. **把反问当默认兜底** → 用户机械确认、Agent 失去连续性（`handbook/08:313`）。
2. **对「默认问题已足够明确」不设防** → NL2SQL 式生产失败（`《从人用数据…》:88-103`）。
3. **遇到歧义静默选一个**（既不问也不说明）→ 被明确列为失败模式（`book/chapter7.md:448`）；差异/默认值必须显式暴露给用户。

## ⑦ 疑点与不确定（含「本地材料覆盖不到」的部分）

1. **本地无「反问封顶 / 连续追问次数上限」的专门论述**。grep「封顶 / 追问次数 / 最多问 / 一次只问 / 连续追问」在 `.md/.txt`（排除朗读版）中**无命中**。可借的只有任务级封顶（`handbook/14:209`）与体验原则（`handbook/08:313`），**不是对话追问轮次的直接经验**。
2. **本地无「默认时间窗（近 30 天）该不该设、如何标注」的直接论述**。grep「默认时间 / 时间窗 / 时间范围」命中的都是运维告警窗口、经验库起始时间等，**与本主题不同**。⑤-5 的结论含推断成分。
