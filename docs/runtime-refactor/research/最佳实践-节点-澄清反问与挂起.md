## ① 一句话结论

本地三本材料把「反问」当成**成本而不是默认动作**，主流形态是「**先探查拿候选 → 交一张一次性、带选项的结构化卡/表单 → 用户一次回填 → 从挂起点重建后续跑**」：**挂起是一等状态**（`WAITING_INPUT` / `WAITING_APPROVAL`），**恢复要按 Checkpoint 重建而不是往历史末尾续贴消息**，**超时必须有明确默认行为且「超时本身不构成批准」**，**封顶靠「少而准 + 预算/无进展检测 + 被问方耐心上限」而不是靠一个固定次数**。但**「连续反问 N 次就截断」这个具体数字、以及「反问卡一次给几个选项」的量化建议，本地材料没有直接论述**（详见 ⑦）。

## ② 业界主流做法（每条注出处）

### 2.1 反问卡怎么设计（一次问几个、给不给选项、选项怎么来、怎么让人好回答）

1. **主流是「一次性表单」，不是逐条一问一答**。原文：「Agent 在面对**信息不完整**的用户请求时，不是逐条一问一答，而是**动态生成一个自包含的 HTML 表单**来一次性澄清意图……用户**一次提交**即可补全全部信息；前端把表单汇总成 JSON 交回 Agent，Agent 解析后继续任务。」表单内置**级联逻辑**（字段按前项显示/隐藏、下拉选项随另一字段动态变化）。——`技术书籍/ai-agent-book/ai-agent-book/chapter5/dynamic-form/README.md:140-143`
   - 验收示例（订机票）：出发城市、出发日期、旅行类型（单选 单程/往返）、**返程日期（仅往返时显示）**、舱位（下拉）、**免费托运额度（随舱位动态变化）**。——同文件 `:145-151`
   - 实测闭环：「解析 JSON → 继续任务」由 Agent 输出摘要完成。——同文件 `:167-175` 与「真实运行输出」节
2. **卡上的「选项」应来自「探查得到的候选」，而不是凭空给**。τ²-bench telecom 把**用户认知边界显式建模**：`known_info` 只含姓名/号码/所在国家，真正的故障原因不在其中——「用户并不知情，因而无法主动陈述，Agent 只能通过提问和引导用户查询来获取」。这是**渐进式信息透露（Progressive Information Disclosure）**在任务定义层的实现，不是靠提示词「不要一次说完」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:87`（任务定义结构见 `:44-89`）
3. **审批/反问卡该写什么，有现成字段清单**。原文：「审批请求应包含：Agent 想做什么、为什么、以谁的身份、作用于什么对象、预计影响、参数和差异、是否可逆、失败如何处理，以及批准范围是仅本次、当前 Task 还是一类受限动作。」——`技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md:334`
4. **卡用「声明式界面」，客户端用受信组件渲染，不让模型生成任意代码**。原文：「**A2UI** 适合让 Agent 输出声明式界面，例如表单、卡片、列表和动作。客户端使用本地受信组件目录渲染，而不是执行模型生成的任意代码。」——`技术书籍/ai-agent-handbook/08_第 6 章….md:439`；A2UI 承载审批表单的时序图见同文件 `:450-451`
5. **卡片事件要携带「选项与决策结果」**。外部语义事件表里 `Approval` 一行：内容＝「预览、风险、选项与决策结果」，用途＝「呈现 HITL 控件」；且「用户真正需要的是任务状态、可见说明、行动、证据和**可操作选项**」。——`技术书籍/ai-agent-handbook/08_第 6 章….md:403-414`（Approval 行 `:409`）
6. **小卡片式反问的真实产品范例**（运维闭环案例）：
   - 卡片带**动作按钮**：「值班人员点击卡片上的『认领』按钮……所有群成员看到卡片状态变更为『已认领 by @xxx』」——`技术书籍/ai-agent-handbook/44_塔斯汀万店连锁的智能运维闭环实.md:68`
   - **两选项评价卡 + 可选一行说明**：「只有两个选项——『AI 准』或『AI 不准』。如选『AI 不准』，可选填一行说明」——同文件 `:82`
   - **一键触发式反问**：点「一键 RCA」按钮即由系统匹配 Skill 组合并给诊断报告，把「开口问」变成「点一下就够」——同文件 `:138`
7. **选项生成要抗漂移**：dynamic-form 约定英文 `name` 标识，校验用「先按约定 name 找，找不到再退化到语义/文本关键词」的鲁棒匹配，容忍模型偶发命名漂移；离线 schema 则完全稳定。——`技术书籍/ai-agent-book/ai-agent-book/chapter5/dynamic-form/README.md:129`

### 2.2 挂起（interrupt）与恢复（resume）的语义：停在哪、从哪接、等多久、超时怎么办

1. **挂起是一等状态，不是失败、不是结束**。任务状态表列出 `WAITING_INPUT`（缺少用户或业务信息）、`WAITING_APPROVAL`、`WAITING_EVENT`、`PAUSED`；原文：「`WAITING` 不是失败，`PAUSED` 也不是结束。只有把这些状态显式化，上层 Runtime 才能在等待期间释放计算资源并准确恢复；**交互界面才能说明 Agent 在等什么**；观测系统才能区分执行慢、审批慢和工具慢。」`WAITING_INPUT` 的允许下一步＝「接收输入后恢复，**或超时结束**」。——`技术书籍/ai-agent-handbook/06_第 4 章 任务：编排、长程推进与协作流转.md:68-81`（表 `:68-78`，判语 `:81`，`WAITING_INPUT` 行 `:72`）
2. **Task 与 Session 解耦，Task 可跨等待/恢复续跑**。「Task 可以跨越等待、恢复、人工审批等多个阶段持续存在，也可以跨多个 Session 续跑。」跨 Session 续跑要**显式装载经授权的 Task State**（业务参数、已完成步骤的 Checkpoint、**待恢复的等待对象**、副作用记录），不能默认两个 Session 共享上下文。——`技术书籍/ai-agent-handbook/13_第 10 章 Agent 异步任务与自动化流程.md:11-13`
3. **「停在哪」＝Checkpoint 必须记等待条件**。「一个有效的 Checkpoint……应包含恢复所需的关键状态：当前任务阶段、已完成步骤、未完成步骤、工具调用结果引用、工作区版本、子任务状态、**等待条件**以及状态版本等。」关键边界（应主动形成 Checkpoint 的位置）＝「外部调用发起前后、长时间计算完成后、**人工确认前后**、工作区发生重要变更后，以及任务准备交接给其他 Agent 时」。——`技术书籍/ai-agent-handbook/11_第 8 章 Agent 状态存储与语义资产.md:89,91`
4. **「从哪接」＝唤醒入口在外部，恢复要重建而非续贴**。
   - 暂停/等待前：「任务进入等待前，编排层应保存**继续点和等待条件**；重要增量应随执行推进及时保存，不能全部留到收到终止信号时才写出。」「唤醒入口位于休眠沙箱之外。定时器、消息入口或请求路由组件先接收事件，再恢复环境并交付任务。」——`技术书籍/ai-agent-handbook/10_第 7 章 Agent 运行时与沙箱.md:117`
   - 恢复时：「**恢复前，Harness 要把用户新要求提交到 Task State，判断现有 Plan、权限和后台任务是否仍有效，再重新构建 Context。直接把一条用户消息追加到长历史末尾，可能无法覆盖已经进入执行队列的旧计划。**」——`技术书籍/ai-agent-handbook/08_第 6 章….md:385`（Steering/Interrupt/Resume 整节 `:381-385`）
   - 恢复时要重查清单：「恢复时重新检查目标、外部条件、工具是否实际执行、权限是否仍有效、工作区是否变化以及剩余预算。」——`技术书籍/ai-agent-handbook/06_第 4 章….md:272`；`Continuation` 应含「目标、当前 Plan、已确认事实、失败尝试、Artifact、**等待项**、剩余预算和权限模式」——同文件 `:274`
   - 外部连接可能已失效：「环境恢复后，应重新检查其可用性。文件即使得到保留，外部连接、临时凭证和远端登录状态也可能已经变化，服务端口同样需要检查。」——`技术书籍/ai-agent-handbook/10_第 7 章….md:119`
5. **「等多久」：跨度极大，且要专门定义超时默认行为**。
   - 时长跨度：「等待时长从分钟级到数天级不等，直接影响资源利用率和系统复杂度。」——`技术书籍/ai-agent-handbook/13_第 10 章….md:138`
   - 超时默认行为（关键）：「**审批超时——hold 状态超过阈值后的默认行为（拒绝、继续保持等待或升级处理；超时本身不构成批准）**。」——`技术书籍/ai-agent-handbook/13_第 10 章….md:297`
6. **挂起的实现路径**：「HITL 的实现路径除了『调度器暂停 Task + 外部审批回调』，还可以借助工作流引擎的人工节点。Apache Airflow 在 3.1.0 版本引入了 Human-in-the-Loop 能力……人工节点支持暂停/恢复功能。」——`技术书籍/ai-agent-handbook/13_第 10 章….md:158`；「人工审批（将流程挂起等待人工确认）」列为典型业务节点——同文件 `:241`
7. **等待期要不要常驻进程，取决于恢复能力而非部署形态**。原文：「若状态只在内存里，等待期间需要保留进程；**若支持持久化等待与恢复，也可以释放执行资源**。」——`技术书籍/ai-agent-handbook/13_第 10 章….md:140`；对照表「Agent 进程是否常驻＝取决于等待与状态恢复能力；具备恢复条件时可释放执行资源」——同文件 `:151-156`
8. **事件续传机制（恢复的通信侧）**：每个事件要有「单调序号或可恢复游标」，客户端「从最后确认位置续传，服务端支持去重」——`技术书籍/ai-agent-handbook/08_第 6 章….md:460`；产品实现里用 `Last-Event-ID` 续接、按 ID 幂等处理，并可 `List Events` 补齐——同文件 `:499`。抽象档位：`S3 任务句柄`（凭标识查询，不自动保证事件重播）与 `S4 持久通道`（续传点＝(通道,序号)）——`技术书籍/ai-agent-handbook/15_第 12 章 Agent 分布式通信.md:73,171`；且「流结束与业务任务结束是不同边界」，MCP 2026-07-28 已移除传输层 SSE 续传，断流后业务幂等由应用处理——同文件 `:84`

### 2.3 多次反问的体验与封顶（别把人问烦）

1. **少而准，别把反问变默认兜底**。原文：「`ASK` 不是默认兜底。过多审批会让用户形成机械确认，也让 Agent 失去连续性。」——`技术书籍/ai-agent-handbook/08_第 6 章….md:313`
2. **被问方有耐心上限**。τ²-bench 重设计把「用户模拟器行为过于机械」补成三件事：「情绪（首次修复失败后表现出不满）、**耐心上限（沟通效率过低时终止对话）**、以及事实锚定要求。」——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:258`（τ-bench→τ²-bench 五处重设计见 `:252-262`）
3. **封顶的相邻机制＝预算 + 无进展检测**（而非固定次数）：
   - 「步骤数、总时长、Token 与费用、工具调用次数、子任务并发数、高风险动作次数都应进入预算。**预算接近阈值时，Harness 可以要求模型收敛范围、停止新委派、优先完成可交付部分或请求用户选择**。」——`技术书籍/ai-agent-handbook/06_第 4 章….md:83`
   - 无进展信号：「连续调用相同工具且参数高度相似、反复得到同一错误、Plan 长时间不变、工作区没有新增事实、模型在少数行动间循环。」——同文件 `:374`
   - 对照（另一文件）：团队级停止条件含「最大委派深度、派生任务数量、单项任务重试次数、结果返工轮次、**连续多轮没有新增有效产物/状态进展时的处理方式**」——`技术书籍/ai-agent-handbook/14_第 11章 Multi-Agent 协作与编排.md:209`

### 2.4 反问 vs「默认值 / 自己往下走」的取舍

1. **三分决策：ALLOW / DENY / ASK，优先用更窄的约束把不确定性降下来**。「应该优先通过更窄 Tool、参数约束、预览、资源范围和 Sandbox 降低风险，只在目的或后果无法由策略充分判断时请求人工参与。」风险示例→默认策略对照表：读取类 ALLOW 并「记录范围」；发送/发布/支付/删除/改生产数据 ASK 或 DENY；跨租户/绕过安全控制 DENY。——`技术书籍/ai-agent-handbook/08_第 6 章….md:311-321`
2. **有「执行前确认门」的正面范式**：Plan Mode 把过程分为「只读探索—写入计划—**人工确认**—进入执行」，`plan_exit` 触发人工确认，获批后才进入可改工作区的阶段；计划与 Todo 落在持久状态里，**能跨调用恢复**。——`技术书籍/ai-agent-handbook/06_第 4 章….md:163`
3. **真实用户初始表述往往很含糊，Agent 必须主动找用户澄清**（τ²-bench 原文：「真实用户的初始表述往往只是『我上不了网』，Agent 必须主动找用户澄清需求」）。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:87`
4. **「不追问就硬猜」被列为失败**：失败归因把「仓库里有两个同名配置文件时直接选一个，既不说明也不追问」归入「需求理解与歧义」类失败；且建议「规则无法确定作用域时，应允许模型保留原文并请求澄清，而不是把猜测性修改算作通过」；边界评测应把「**先澄清**」列入可接受动作。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:448,500,523`
5. **同领域消歧的落地做法（先分类/打标签，再检索/回填）**：面试速查「意图识别消歧」给出三层解法——调权重、打标签（物品 vs 服务分类）、大模型先分类再过滤。——`录音 面试考点速查.md:183-192`
6. **「只在真正紧急时才打断」但需权衡**：异步事件处理里，非紧急事件应入队批量处理，只有紧急打断才「提前制造安全点」；原文「实践中只在真正紧急时才打断，非紧急的事件则放入队列批量处理」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter6.md:200-226`

### 2.5 挂起期间的用词/话术与「不让用户空等」

1. **让用户看见「在等什么」**：`WAITING` 状态显式化后「交互界面才能说明 Agent 在等什么」（见 2.2-1）。——`技术书籍/ai-agent-handbook/06_第 4 章….md:81`
2. **外部事件类别与话术要素**：`Progress`（当前阶段/Todo/里程碑）、`State`（Running/Waiting/Paused/Completed）、`Approval`（预览、风险、选项与决策结果）；「用户真正需要的是**任务状态、可见说明、行动、证据和可操作选项**」（模型内部隐藏推理不必暴露）。——`技术书籍/ai-agent-handbook/08_第 6 章….md:403-414`
3. **异步消息 + 已读未读 + 避免重复打扰 + 通知即召回**：「用户沟通工具应支持异步消息模式（用户不一定在线），提供**已读/未读状态追踪**」；「Agent 根据紧急程度、用户状态……综合决定渠道的选择，既保证不错过重要的消息，又**避免重复打扰**」；「通知机制同时也是**用户召回机制**」。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter6.md:91,95`
4. **取消/中断的回执要分清状态**：「用户发出 Cancel 或 Interrupt 后，Channel 要尽快确认请求已经进入状态机，并**区分『已收到取消』和『底层 Action 已安全停止』**。」——`技术书籍/ai-agent-handbook/08_第 6 章….md:462`
5. **「信息告知」本身是被评分的维度**：τ²-bench 704 次运行失败 240 次，其中 **162 次是「信息告知」出错**，80 次（占失败三分之一）「环境状态正确，但信息告知错误」——说明「答对了但没把该说的说清楚」是真实失败形态。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:466`

## ③ 分歧取舍

1. **一次问全（表单）vs 逐轮一问（多轮）**：dynamic-form 主张「一次性表单 + 一次提交」（`chapter5/dynamic-form/README.md:140-143`）；τ²-bench 是逐轮渐进透露（`book/chapter7.md:87`）；手册强调「少而准」（`08_第 6 章….md:313`）。**取舍判据**：字段少且互不依赖 → 一卡多问；字段有前后依赖 → 一次性「级联表单」；口径类歧义 → **先探查给候选，再拿候选去问**（同 `最佳实践-节点-澄清.md` 引用的 Datastrato「先召回候选再让用户确认」）。
2. **挂起期是否常驻进程**：内置异步（保进程，简单但等待期占资源）vs 外置调度（释放资源，但要对调度 API/恢复接口）。原文明确「取决于恢复能力，不由『内置』这一部署位置单独决定」。——`13_第 10 章….md:140,151-156`
3. **恢复语义：续贴消息 vs 重建**：手册明确反对前者——「直接把一条用户消息追加到长历史末尾，可能无法覆盖已经进入执行队列的旧计划」。——`08_第 6 章….md:385`
4. **超时默认行为三选一（拒绝 / 继续等待 / 升级）**：原文并列给出，无唯一答案；但**共识是「超时本身不构成批准」**。——`13_第 10 章….md:297`
5. **续传机制选型**：事件游标/`Last-Event-ID`（`08_第 6 章….md:460,499`）vs 任务句柄查询（`15_第 12 章….md:73`）vs 持久通道（同 `:171`）。协议层在收敛中，MCP 已移除 SSE 续传（同 `:84`）——**不能从「用了 SSE/用了 MQ」推导出「能续传/能恢复」**。

## ④ 反例踩坑

1. **占位符诱发幻觉**：同步格式下为未完成工具塞「占位结果」以容纳打断，「系统仍可能在后续思考中『编造』一个工具结果，误以为工具已经返回」；且「模型在训练时见到的绝大多数轨迹中，工具调用之后紧接着就是真实的结果，它从未学会如何处理『结果还没回来』的情况」。**推论到本仓**：反问挂起时，未取得的材料必须显式标「未完成/待用户」，不能伪装成已得。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter6.md:212,226`（五条规则见 `:206-226`）
2. **机械确认**：过多审批「会让用户形成机械确认，也让 Agent 失去连续性」。——`技术书籍/ai-agent-handbook/08_第 6 章….md:313`
3. **恢复重复副作用**：Checkpoint「不等同于外部副作用幂等：若外部写入已提交而 Checkpoint 尚未落盘，重跑仍会产生重复副作用」。——`技术书籍/ai-agent-handbook/13_第 10 章….md:50,271-275`
4. **等待期间环境已变，批准后不重校验就出错**：「用户批准后，Harness 仍要重新校验对象版本和策略，防止**等待期间环境已经变化**。」——`技术书籍/ai-agent-handbook/08_第 6 章….md:334`；恢复后外部连接/凭证/端口可能已变——`10_第 7 章….md:119`
5. **无事实锚定 → 两个模型互相确认**：τ²-bench 指出缺少事实锚定约束时「模拟用户会顺应 Agent 的引导确认问题已解决，评估随之退化为两个模型之间的相互确认」。**推论**：反问卡若诱导性过强（如默认高亮某个选项、文案暗示「应该是这个吧」），会得到假澄清。——`技术书籍/ai-agent-book/ai-agent-book/book/chapter7.md:89`
6. **仅凭 idle 判完成**：「QCA……返回 `session.status_idle`，且 `stop_reason.type` 为 `requires_action`，应读取 `stop_reason.event_ids` 处理待响应动作，**不能仅凭 idle 判定完成**。」——`技术书籍/ai-agent-handbook/08_第 6 章….md:499`
7. **无进度/无预算 → 死循环烧钱**：「在异步与定时场景下（无人在场监督），死循环 Agent 在数小时内累积出非预期账单是真实风险。」——`技术书籍/ai-agent-handbook/13_第 10 章….md:303`

## ⑤ 对本项目适用性（只读问答、单租户）

**可以直接搬的**：

- **挂起态显式化 + Checkpoint 记「等待条件」**（`06_第 4 章….md:68-81`、`11_第 8 章….md:89`）。本仓「从停下的地方接着跑」正对应此模式：把「已取得的材料、当前阶段、待用户回答的问题、继续点」写进状态，用户回答后**从权威状态重建**，而不是把新回答 append 到历史末尾（`08_第 6 章….md:385`）。
- **反问卡内容清单**（`08_第 6 章….md:334`）：可裁剪为「问什么 + 为什么问 + 每个选项的含义 + 选择后会发生什么」。
- **话术：说明在等什么**（`06_第 4 章….md:81`、`08_第 6 章….md:403-414`）。本仓是交互式问答，用户就在线等，更要避免「卡一弹出来、人不知道发生了什么」。

**需要降级/裁剪的**：

- **只读 → 绝大多数「审批类 ASK」不适用**。手册的 ALLOW/ASK/DENY 表主要针对写/发布/删除/支付（`08_第 6 章….md:315-321`），本仓无副作用动作，反问的触发条件应收窄为**「口径/对象/范围歧义会实质改变答案」**，而不是风险审批（与 `最佳实践-节点-澄清.md` 2.1 的判据一致）。
- **单租户 → 多副本恢复/执行租约/围栏/多租户隔离不需要**（`11_第 8 章….md:103,161`、`13_第 10 章….md:297` 的租户隔离维度）。本仓**进程内同步挂起 + 简单持久化**即可，不必引入外置调度或租约机制。
- **交互式问答 ≠ 长任务异步**：手册的 HITL/异步大量面向「用户离线、等待分钟到数天」（`13_第 10 章….md:138`）。本仓是「用户在场、立即选」的短等待，**不必把等待期资源释放/唤醒入口/持久通道这一整套搬进来**（`10_第 7 章….md:117`、`15_第 12 章….md:73-84`）。
- **「不计轮不计时」与手册一致**（等待态不进预算、可释放资源），但 **「连续反问到 6 次截断」这个具体封顶值本地无直接依据**（见 ⑦）；手册给的相邻机制是「预算接近阈值请求用户选择」与「无进展检测」（`06_第 4 章….md:83,374`），可考虑把「6 次」实现为**无进展/低增益检测**而非纯计数。

**结论**：本仓真正要抄的是**机制骨架**（挂起态显式、Checkpoint 记等待条件、恢复重建、超时默认、话术说明在等什么），而不是**企业级长任务的重型设施**（外置调度、租约、持久通道、多租户隔离）。反问卡形态上直接对齐 dynamic-form 的「一次性、带级联、一次提交」。

## ⑥ 值得抄三条 / 要警惕三条

**值得抄**：

1. **反问卡 = 一次性、带级联的结构化表单，而不是逐条追问**（`chapter5/dynamic-form/README.md:140-151`）。
2. **挂起态显式化 + Checkpoint 记「等待条件/已确认事实/继续点」，恢复时重建 Context 并重校验**（`06_第 4 章….md:274`、`11_第 8 章….md:89`、`08_第 6 章….md:385`）。
3. **反问走统一结构化事件（含「选项与决策结果」），话术以「说明在等什么」为准并给可操作选项**（`08_第 6 章….md:403-414`）。

**要警惕**：

1. **别把反问当默认兜底、别机械连环问**；封顶要有，但不能用一个固定次数掩盖「没探查就乱问」——手册的「少而准」与 τ²-bench 的「耐心上限」都指向**问的问题要有增益**（`08_第 6 章….md:313`、`book/chapter7.md:258`）。
2. **别把恢复实现成「往历史末尾插一条用户消息」**（`08_第 6 章….md:385`）；**别用 idle/无输出判定「已完成」或「已挂起」**（`08_第 6 章….md:499`）。
3. **别忽略超时默认行为与「超时≠批准」**（`13_第 10 章….md:297`）；**别让「未取得的材料」在挂起/恢复中伪装成已得**，否则诱发幻觉（`book/chapter6.md:226`）。

## ⑦ 疑点与不确定（含「本地材料覆盖不到」的部分）

**本地材料覆盖不到（如实说没有）**：

1. **「连续反问 N 次就截断」这一固定封顶值**：grep「封顶/追问次数/最多问/连续追问/连问」无直接论述。相邻证据只有「少而准/机械确认」（`08_第 6 章….md:313`）、预算与无进展检测（`06_第 4 章….md:83,374`）、模拟用户耐心上限（`book/chapter7.md:258`）。**「6 次」是本仓产品决策，不是本地材料的推荐值。**
2. **「反问卡一次给几个选项」的量化建议**：材料里有「一次性表单含多字段」（`dynamic-form/README.md:145-151`）和「两选项评价卡 + 可选一行说明」（`44_塔斯汀….md:82`），但**没有「选项个数上限 / 是否总配一个『其他/自由输入』」的论述**。
3. **「等待期间不计轮不计时」的机制定义**：手册讲「等待态不进预算、可释放资源」（`13_第 10 章….md:140`、`06_第 4 章….md:81`），但**没有「等待不计入对话轮次/超时计时」这种计数语义的直接表述**。
4. **反问卡的 UI 组件选型**：A2UI 被明确标注「仍处于活跃演进阶段（稳定线 v0.9 系列，v1.0 为候选版本）」，建议「资产稳定、适配层承接变化」。——`技术书籍/ai-agent-handbook/40_GenUI：让 Agent 从给出答案走向交付结果.md:368`

**引用时要注意的**：

5. **本主题最强相关材料偏「企业级长任务 / 有副作用 / 多租户」**（handbook 第 4、6、7、8、10、12 章），将其**降级套用到「只读问答 + 单租户 + 用户在场短等待」**时，哪些设施必要、哪些是过度设计，**需 Owner 判断**（本文件 ⑤ 给的是建议，不是结论）。
6. **handbook 引用的协议行为有时效性**：MCP 2026-07-28 移除 SSE 续传等结论来自白皮书，实际接入版本可能不同（`15_第 12 章….md:84`）。
7. **ai-agent-book 的异步打断（chapter6）与「反问挂起」不是同一件事**：前者是「任务执行中被打断/抢占」，后者是「Agent 主动停下等输入」；本文件只在「未完成状态要显式标注、避免幻觉」这一点上借用其教训，**不把「打断三策略」整体搬为反问答疑机制**。
8. **与 `最佳实践-节点-澄清.md` 的交叉**：那份文件已引用 「审批请求字段清单」（ch6:334）、τ²-bench 渐进透露（chapter7:87）、「少而准/机械确认」（ch6:313）等条目，本文件复用同源证据，**注意不要把两文件当独立佐证重复计数**。
9. **本文件未读到的相邻材料**：`资料大纲-2` 指出的「HandBook 无专门『澄清反问』章」、`资料大纲-3` 指出 `本体论/` 目录无可读文本、公众号文章为 `.webarchive` 未抽取——**这些缺口可能含额外做法，本次未覆盖**。
