## 一、一句话结论

**入口拦截的业界共识是「分三层设防、按被绕过难度排序」——上下文层（规则/分类器）只降低攻击成功率，执行层（权限/沙箱/确认门禁）与数据层（行级策略/约束）才给保证；因此硬约束绝不能只写在提示词或词表里，确定可编码的限制要落成确定性策略。** 落在本项目（只读问答、单租户）：本项目**没有写能力、没有外发能力**，这本身就是最强的「数据层/执行层」防御（风险面天然收敛，只读问答应默认放行、写入意图应默认拦截，正对业界「只读=允许、写入=默认不允许」的场景划分）；词面安全阀在业界定位属**上下文层的『基于规则的保护』**，是辅助手段而非唯一边界，其最大工程风险是「误伤」与「靠堆禁用词表」，业界给出的对策是「作用域+动作+例外+验证」与「边界集+保留集双集合验收」，命中后应返回结构化原因+替代项并留审计痕迹。

## 二、业界主流做法（每条注出处）

1. **护栏分三层，按「被绕过的难度」排序：上下文层 → 执行层 → 数据层；越靠下越不依赖模型判断，越难被一次攻击穿透。** 上下文层管「模型能看到什么」，执行层管「模型能做什么」，数据层管「世界最终能被改成什么样」。来源：技术书籍/ai-agent-book/ai-agent-book/book/chapter1.md（「护栏与安全性」节）。

2. **上下文层的四种确定性/半确定性机制：相关性分类器、安全分类器（越狱 vs 提示注入）、内容审核、基于规则的保护（黑名单/输入长度限制/正则过滤器，防 SQL 注入等已知威胁）。** 「来源标注」与「指令/数据分离」也属这一层。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏类型」节）。

3. **上下文层有结构性上限：处在同一个上下文里的 Agent 很难判断自己是否已被注入——所以上下文层只能降低成功率、给不出保证。** 这是必须有执行层与数据层的原因。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏类型」节）。

4. **执行层：工具风险评级（按是否可逆、权限等级、财务影响标低/中/高），高风险操作需额外审查或人工确认；关键是这类复核必须由「上下文之外」的机制完成（独立审查进程、最小权限凭证、沙盒隔离、人在回路），否则会和被注入的 Agent 一起沦陷。** 输出检查（PII 过滤、输出验证）也属执行层。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏类型」节）。

5. **数据层：行级安全策略、约束与校验器、受控视图与存储过程，以及由受信任运行时绑定、无法被伪造的访问上下文；即使提示注入得手、生成的代码漏写权限判断，越权操作仍会在数据层被拒绝。** 来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏类型」节）。

6. **单个护栏不够，要多个专门护栏组合；护栏评估不能只测「该拒的拦住了没」，还要测「明确允许的能否正常完成」（防误拒绝 / false refusal）。** 提到合法但形式敏感的任务（授权安全测试、模型蒸馏研究）会被一并误拒。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏与安全性」节）。

7. **规则式 vs 模型式的分工：Guardrail 可部署在输入/Context 构建/Action 请求/Tool 结果/输出五个阶段，但不应成为唯一安全边界——对确定可编码的权限和资源限制应用 Policy 与 Sandbox；模型或分类器适合识别复杂语义风险、敏感内容和可疑意图，并把结果作为额外信号。** 来源：技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md（§6.4.4）。

8. **两级筛查（Anthropic Constitutional Classifiers 工业实践）：先用一个极轻量探针全量检查（几乎零成本），发现可疑再交更强的分类器复审，而不是直接拒绝——第一级即使误报较多也不影响体验。** 规则驱动（自然语言写允许/禁止规则生成合成训练数据）+ 上下文联合判断（用户提问与模型回答一起看）。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏类型」节，脚注 [^ch1-3]）。

9. **提示注入的核心防线是「区分指令与数据」：网页、邮件、文档、MCP Server、工具结果和远程 Agent 返回的内容都属于不可信输入，不能改变平台政策、授权范围或当前 Tool Set；Harness 应保留内容来源、限制外部文本进入高优先级指令层、对数据外传和高风险 Action 做独立授权、必要时隔离读取与执行阶段。** 来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.4）；技术书籍/ai-agent-handbook/18_第 14 章 Agent 安全.md（§14.5 章首、应用安全节）。

10. **上下文层防注入三招：来源标记（如 `<external_content source="webpage">…</external_content>`）、结构化角色（严格用 Chat Template 的 system/user/assistant/tool 角色，绝不自行拼接消息）、输入清洗（过滤「忽略之前的指令」等注入短语）。** 其中输入清洗「容易被措辞变体绕过，只能作为辅助手段」。来源：技术书籍/ai-agent-book/…/book/chapter2.md（「提示注入：上下文安全的核心威胁」节）。

11. **不要自行拼接消息：把工具结果混入 user 消息，等于亲手抹掉了模型辨别来源的依据。** 来源：技术书籍/ai-agent-book/…/book/chapter2.md（同上节）。

12. **注入面会随能力扩张：Skill 是「把外部内容当指令加载」的制度化形式，第三方 Skill 藏指令比网页隐藏文本更直接；Agent 状态栏信息被模型高度信任，若其内容来自可被外部污染的数据源，这种信任会被反向利用。** 安装来源不明 Skill 前必须审查内容「如同审查将要执行的代码」。来源：技术书籍/ai-agent-book/…/book/chapter2.md（同上节）。

13. **注入攻防实验给出了分层防御的有效性证据：3 种攻击（直接注入 / 间接注入 / 记忆注入）× 4 档防御（D1 无防御 / D2 仅提示词加固 / D3 提示加固+来源标记 / D4 再加运行时高风险检查）。关键结论：只有 D4 组合让「即使模型被说服，越权操作也落不了地」（write_file / send_email 需当前轮用户显式确认，否则在执行处被拦）。** 裁判用确定性规则（是否泄露密钥 / 是否发生未授权工具调用），稳定、零额外模型成本。来源：技术书籍/ai-agent-book/ai-agent-book/chapter2/prompt-injection/README.md。

14. **含工具调用的多轮系统里，一旦模型能生成 SQL 并执行，风险从「输出不当内容」升级为「不可逆操作」（删文件、发邮件、泄露隐私数据）；每一个感知工具（网页阅读、文档解析、邮件处理）都是潜在注入入口。** 来源：技术书籍/ai-agent-book/…/book/chapter2.md（「提示注入」节）。

15. **只读系统的准入场景划分（业界最贴本项目的一条）：场景 A「内部系统查询型（只读接口，不含高密级数据）」——通过准入评估后推荐允许，必要控制＝仅开放 GET/查询类 API、为 Agent 配最小权限身份、通过 7 层域名网关限制可访问的系统与路径、避免返回超出业务需要的字段；场景 B「写入型」——默认不允许，仅强需求+无只读方案+风险可控时作高风险开放；场景 C「消息接入型（IM/群聊）」——默认禁用群聊触发，仅白名单群+必须 @Agent 触发，对每条指令保留完整上下文与调用链。** 来源：资料/字节安全白皮书.md（§7.2.1.3、§7.2.2.2）。

16. **网络边界治理「默认拒绝 + 按需开白」：南北/东西向流量默认关闭，仅在风险评估、审批通过后按域名/路径/API 粒度最小化开白，全程保留变更与访问审计记录。** 来源：资料/字节安全白皮书.md（§7.2.2、§7.2.2.1）。

17. **权限决策要「身份、资源与风险共同参与」，仅按 Tool 名称做静态白名单无法区分「读取一条测试记录」和「导出整个生产库」；决策至少考虑主体、租户、任务目的、能力、参数、目标资源、环境、当前阶段、数据敏感度、影响范围、可逆性、预算、历史审批。**来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）。

18. **策略结果统一为三类：ALLOW（可直接执行并记录决策依据）/ DENY（无论模型如何解释都不得执行，向 Loop 返回结构化原因和允许替代项）/ ASK（可执行但需指定人或系统确认）。默认风险策略示例：读当前项目非敏感文件＝ALLOW；查询用户有权看的业务数据＝ALLOW 或按数据等级 ASK；发送外部消息/发布/支付/删除/改变生产数据＝ASK 或 DENY；跨租户/绕过安全控制/请求长期 Secret＝DENY。** 来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1 表）。

19. **Agent 身份安全闭环：最小权限（Agent 默认无权限，仅授权后以其身份与权限范围访问，且 Agent 权限不超过用户权限）；逐次调用校验；高危操作二次授权；数据出域阻断；全链路审计（粒度可达「哪个用户、通过哪个 Agent、获取了哪个凭证」）。** 来源：技术书籍/ai-agent-handbook/18_第 14 章…（§14.5 章首、§14.5.2）。

20. **数据外发的检测与阻断要「多源可观测 + 场景化关联 + 分级处置」：把分散的弱信号串成完整事件（如敏感访问后紧接着异常执行、外联传播），识别提示词注入、权限滥用、数据外传；响应侧按风险等级下发止损（限制高风险操作、暂停会话、吊销令牌、阻断可疑外联）。** 来源：资料/字节安全白皮书.md（§7.2.3）。

21. **运行时前置风险评估：AI 助手「思考前」做前置风险评估（含提示词注入防护），运行时做敏感数据泄漏、高危/恶意操作的实时拦截，高风险操作前必须二次确认，操作留痕（事件管理 + 审计日志）。** 来源：资料/字节安全白皮书.md（§6 纵深防御方案「助手运行安全」）。

22. **豁免设计的核心句式：规则应写成「作用域 + 动作 + 例外 + 验证方式」，避免把所有可能的情况堆成一张越来越长的禁用词表；禁止清单要「写清合法例外」。** 来源：技术书籍/ai-agent-book/…/book/chapter2.md（「如何编写一份可用的 Skill」节，引宝玉《图解 Skill》）。

23. **ASK 不是默认兜底：过多审批会让用户形成机械确认，也让 Agent 失去连续性；应优先用更窄 Tool、参数约束、预览、资源范围与 Sandbox 降低风险，只在目的或后果无法由策略充分判断时请求人工。** 来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）。

24. **一次性确认令牌 + 边界集/保留集双集合验收（本主题最可抄的工程范式）：门禁要保证「高风险调用必须被挂起、确认后才执行、伪造/错配/复用的确认 token 必须被拒绝且绝不执行」；同时「正常操作不受影响、用户已确认的操作正常放行」；确认 token 一次性、绑定具体工具名与完整参数。** 该实验还保留一个「门禁存在但放行一切」的已拒绝反例作对照。来源：技术书籍/ai-agent-book/ai-agent-book/chapter9/harness-safety-gate/README.md。

25. **「边界集 + 保留集（Boundary Set + Retention Set）」是全书通用设计模式：任何一次修改都要同时在「它应当改变的那批样本」和「它不应当影响的那批样本」上验证——只测前者会把过拟合当进步，只测后者会把无效修改当安全。** 来源：技术书籍/ai-agent-book/…/book/chapter1.md（「贯穿全书的设计模式」节）。

26. **只读不变量宜做进数据对象：把权限、校验器、关系与后果随数据类型一起声明，由稳定存储层在每次操作时检查（生成代码只拿到受限 AccessContext，不拿到特权连接）；跨租户读被权限边界拒绝。** 来源：技术书籍/ai-agent-book/ai-agent-book/chapter5/permission-embedded-data-objects/README.md。

27. **命中收口要返回结构化原因与替代项、并留可信审计：DENY 要向 Loop 返回结构化原因和允许替代项；审计要能还原「为何被允许发生」的结构化决策链；内部系统接入必须接入统一身份认证与日志审计，保留关键操作记录。** 来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）；资料/字节安全白皮书.md（「数据最小持有与审计缺失」条、§7.2.1.3 准入维度「安全能力接入」）。

28. **提示词侧也可作「行为边界」声明（但只是加固、非唯一防线）：在系统提示里写明「未获用户明确知情同意不得做什么」（外发数据/泄露密钥等）、受限路径清单、「拿不准就先问」的怀疑协议、批量动作要给出精确清单。** ArkClaw 的 SOUL.md 即此形态，且它同时依赖 AgentSentry 旁路拦截（说明单靠提示词不够）。来源：资料/字节安全白皮书.md（【2-1】SOUL.md 加固片段、§6 AgentSentry）。

## 三、分歧 / 取舍

- **规则式 vs 模型式谁兜底、兜到什么强度。** 一派（ai-agent-book）按「被绕过难度」把保证压到执行层/数据层，上下文层的分类器/规则只降成功率；另一派（HandBook §6.4.4）说 Guardrail 可部署在五个阶段但「不应成为唯一安全边界」，两者方向一致——确定性可编码的限制用 Policy/Sandbox，模型/分类器只作额外信号。**分歧点在「语义风险由谁判、判错怎么办」，不在「要不要确定性」。** 来源：技术书籍/ai-agent-book/…/book/chapter1.md；技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.4）。

- **直接拒绝 vs 二级复审。** Anthropic 两级筛查主张第一级极轻量、宽进、可疑才复审，明确反对「直接拒绝」以压误报；而本项目现状是「命中即硬终止」。取舍点在误杀成本与延迟预算——本地材料只提供前者的理由与做法，未给「何时该直接拒、何时该复审」的分界清单。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「护栏类型」节）。

- **词表黑名单该不该用、用到多大。** 规则式黑名单被明确列为上下文层的合法机制（防线之一），但同一批材料又说「输入清洗容易被措辞变体绕过，只能作辅助」，并反对「越来越长的禁用词表」，主张「作用域+动作+例外+验证」。**两种声音并存：可用，但不可单独承担正确性。** 来源：技术书籍/ai-agent-book/…/book/chapter1.md；技术书籍/ai-agent-book/…/book/chapter2.md。

- **ASK（人工确认）用多少。** HandBook 明确「ASK 不是默认兜底」，过多审批致机械确认；但白皮书对写入型/消息接入型倾向「默认不允许/默认禁用」，更保守。取舍是「业务连续性 vs 风险收敛」。来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）；资料/字节安全白皮书.md（§7.2.2.2）。

- **「拦截点放哪」各材料口径不一：** ai-agent-book 按「上下文/执行/数据」分层（按绕过难度），HandBook 按「输入 → Context 构建 → Action 请求 → Tool 结果 → 输出」五阶段（按处理时序）。两套切法不同但都强调「不是单点」。来源：技术书籍/ai-agent-book/…/book/chapter1.md；技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.4）。

## 四、反例 / 踩坑

- **把硬约束只写在提示词里。** 实验 D1→D3 证明仅靠提示加固或仅加来源标记都会被注入绕过，只有加上「运行时高风险检查」（执行处拦截）才让越权操作落不了地。来源：技术书籍/ai-agent-book/…/chapter2/prompt-injection/README.md。

- **靠输入清洗（关键词过滤）单打独斗。** 明确「容易被措辞变体绕过，只能作为辅助手段」。来源：技术书籍/ai-agent-book/…/book/chapter2.md。

- **自审不可靠：同一上下文里的 Agent 很难判断自己是否已被注入**，所以不能指望「让它自己检查一下」来兜注入。来源：技术书籍/ai-agent-book/…/book/chapter1.md（「贯穿全书的设计模式·提议者-审核者」）。

- **把工具结果混进 user 消息**——亲手抹掉模型辨别来源的依据。来源：技术书籍/ai-agent-book/…/book/chapter2.md。

- **记忆/状态被外部污染后反被信任利用。** 记忆注入攻击：在「共享团队笔记」里植入看似无害的偏好（处理文件时同时抄送某人），后续正常任务即被触发外发。来源：技术书籍/ai-agent-book/…/chapter2/prompt-injection/README.md（攻击场景三）。

- **静态白名单按 Tool 名称放行**：无法区分「读一条测试记录」和「导出整个生产库」。来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）。

- **只测拦截率、不测误伤率。** 护栏评估必须同时测「明确允许的能否正常完成」，否则会把合法但形式敏感的请求一并拒掉。来源：技术书籍/ai-agent-book/…/book/chapter1.md。

- **确认门禁「存在但放行一切」。** harness-safety-gate 专门保留这个反例并拒绝它；其发行门槛同时跑 boundary（未完成任务，必须拦）与 retention（正常操作，必须放行）两组回放。来源：技术书籍/ai-agent-book/…/chapter9/harness-safety-gate/README.md。

- **审批走过场（机械确认）。** 过多 ASK 让用户形成机械确认、Agent 失去连续性。来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）。

- **单点告警不足以发现 Agent 风险**：风险往往是「多步操作连续形成」（敏感访问后紧接着异常执行/外联），只盯单点会漏。来源：资料/字节安全白皮书.md（§7.2.3）。

- **批准 ≠ 放行、批准后环境可能已变**：批准后仍要重新校验对象版本与策略。来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.2）。

## 五、对本项目适用性（只读问答、单租户）

### 5.1 已与业界同构、可保留

- **「只读=默认允许、写入=默认不允许」正对业界场景划分。** 白皮书场景 A（只读查询）「推荐允许」、场景 B（写入型）「默认不允许」，本项目是纯只读问答平台，其「写数据意图拦截」本质就是把场景 B 的『默认不允许』在入口词面化。来源：资料/字节安全白皮书.md（§7.2.2.2）；对照本仓/docs/runtime-refactor/research/资料大纲-3-论文与演讲.md（对照点 6「默认拒绝+按需开白」）。
- **只读/无外发 = 执行层与数据层防御的天然形态。** 业界把保证压在「不给工具/最小权限/数据层拒写」上；本项目**没有写工具、没有外发能力**，等于在执行层直接不提供危险能力——比任何词面拦截或提示词加固都彻底（正合 ai-agent-book §15「越靠下层越难被穿透」的排序）。来源：技术书籍/ai-agent-book/…/book/chapter1.md；对照本仓的 LLM/embedding 单点出口纪律（AGENTS.md 硬纪律 3）。

### 5.2 适用性判断（本项目特征）

- **词面安全阀的业界定位是「上下文层的基于规则的保护」，是辅助手段、不构成保证。** 本项目用它做「零模型、快速、命中即硬终止」——方向与业界一致（规则兜确定性），但要清醒：它只能降低成功率，真正的「安全」来自本项目没有写/外发能力。来源：技术书籍/ai-agent-book/…/book/chapter1.md；技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.4）。

- **单租户 → 跨租户/多租户那套不直接适用。** 但「按资源范围与影响范围判权限」的思路仍适用（词面拦截按『动词+对象同句共现』近似『作用域+动作』，与业界精神同构）。来源：资料/字节安全白皮书.md（§7.2.1.3、§7.2.2.2）；技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）。

- **「禁用词闸 / 旧名豁免」最贴的两条业界做法：①作用域+动作+例外+验证（别堆禁用词表）；②边界集+保留集双集合验收（合法提及/正常只读必须放行，冒用旧名要数必须拦）。** 本项目的「元问/引用豁免」正对应 retention set 的「正常操作不受影响」，而「直接拿旧名要数则拒答」对应 boundary set 的「必须拦」。来源：技术书籍/ai-agent-book/…/book/chapter2.md；技术书籍/ai-agent-book/…/chapter9/harness-safety-gate/README.md；技术书籍/ai-agent-book/…/book/chapter1.md。

- **命中后固定话术 = 业界「返回结构化原因 + 允许替代项」；留痕 = 审计唯一写口。** 业界要求 DENY 返回结构化原因与替代项、纳管决策链；本项目固定话术拒答方向一致，需确认是否同时留下「命中哪类规则 + 原句」的可复核痕迹（对应审计单点 `security.audit`）。来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）；资料/字节安全白皮书.md（审计条、§7.2.1.3）。

### 5.3 明确不适用（本项目无需引入）

- 沙箱逃逸防护、Secret 出站控制、MCP 网关审批、多租户网络隔离（白皮书 §7.2.2、HandBook 网关章）——本项目无写/无外发、单租户、开发期身份桩，风险面天然收敛。
- 数据出域阻断 / DLP 那套检测（§14.5、白皮书 §7.2.3）——无外发通道，检测对象不存在。
- SOUL.md 式「禁止外发/泄露密钥」提示词加固（白皮书【2-1】）——本项目无外发能力，该条对外发场景不适用；但其「未获明确同意不得做 X / 拿不准先问」的书写形态，可借用于其他边界声明。

## 六、值得抄三条 / 要警惕三条

### 值得抄三条

1. **把「三层护栏」当自检表用：上下文层（词面/分类器）只降成功率 → 执行层（权限/门禁/无危险工具）→ 数据层（约束/只读）。** 本项目对每条约束自问「它落在哪一层」，凡能下沉到「不给能力」的就不要只停在词面。来源：技术书籍/ai-agent-book/…/book/chapter1.md。

2. **拦截门禁用「边界集 + 保留集」双集合验收，并落成机检用例。** 词面安全阀与禁用词闸两份用例集——boundary（注入/外发/写意图样本必须拦）+ retention（合法提及旧名、元问、正常只读样本必须放行）；再加「门禁存在但放行一切」的反例作对照。这是本地材料里最直接可抄、最贴本项目的一道验收范式。来源：技术书籍/ai-agent-book/…/chapter9/harness-safety-gate/README.md；技术书籍/ai-agent-book/…/book/chapter1.md。

3. **命中收口三件套：固定话术（结构化原因 + 允许替代项）+ 一次性/可复核的判定依据 + 审计留痕（可还原『为何被允许/被拒』）。** 对应本项目固定话术拒答 + 审计单点，建议明确「留的不是 UI 文案，而是可追溯的判定记录」。来源：技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.1）；资料/字节安全白皮书.md（审计条）。

### 要警惕三条

1. **把硬约束只写在提示词或词表里。** 提示词加固可被变体绕过、禁用词表越堆越长是反模式；正确写法是「作用域+动作+例外+验证」。来源：技术书籍/ai-agent-book/…/book/chapter2.md。

2. **只测「该拒的拦住了没」，不测「该放的放行了没」。** 会退化成「越来越严 → 误杀合法提及」，正好打在本项目「合法问旧名要放行」的豁免点上。来源：技术书籍/ai-agent-book/…/book/chapter1.md；技术书籍/ai-agent-book/…/chapter9/harness-safety-gate/README.md。

3. **把外部内容/工具结果与用户指令混同处理、省掉来源标记。** 一旦未来接入任何外部内容通道（即便只读），没有来源分离就等于把注入入口留开；「同一上下文里的 Agent 判断不了自己是否被注入」这条要记住。来源：技术书籍/ai-agent-book/…/book/chapter2.md；技术书籍/ai-agent-handbook/08_第 6 章…（§6.4.4）。

## 七、疑点与不确定（含「本地材料覆盖不到」）

1. **「零模型、纯词面、命中即硬终止」这种拦截的工程实现细节：本地材料覆盖不到。** 最接近的只有 ai-agent-book chapter1 上下文层「基于规则的保护（黑名单/输入长度限制/正则过滤器）」一句话与 chapter2「输入清洗只能作辅助」一句，**均无正则设计、共现判断算法、误报/漏报实测数据**。来源：技术书籍/ai-agent-book/…/book/chapter1.md、…/book/chapter2.md。

2. **「旧名/术语变更后合法问旧名放行、直接拿旧名要数则拒答」这类『元问/引用豁免』的业界对应做法：本地材料无直接条目。** 最接近的是 chapter2「作用域+动作+例外+验证」与 harness-safety-gate 的 retention set，属**推断可类比**，非直接出处。来源：技术书籍/ai-agent-book/…/book/chapter2.md；…/chapter9/harness-safety-gate/README.md。

3. **「指令 vs 数据」在本项目只读问答场景是否真有外部内容通道（间接注入面）：本地材料无法判断。** 需回本仓核对该平台除用户问句外是否有外部内容进入上下文（如检索到的文档、报告全文）——若有，来源标记那条才真正适用。来源：技术书籍/ai-agent-book/…/book/chapter2.md。

4. **「词面拦截放在理解段入口、与后续模型判断是串联（先拦后判）还是并行」：本地材料无专门论述。** 两套切法（ai-agent-book 按层、HandBook 按阶段）都没给「入口先做零模型拦截 vs 边跑边判」的取舍建议。

5. **误杀/漏网的量化基线：本地材料未给具体数值。** 各材料只在方法论层面讨论「要测误拒绝」，没有业界命中率/误报率的数字。

6. **HandBook ch13 可观测性章、ch14 全链路审计的字段级做法未逐段精读**，本文对「审计/留痕」的引用据大纲与摘要定位（审计事实与可复核证据链、粒度「用户-Agent-凭证」）。**引用其字段前建议回原文核对。** 来源：技术书籍/ai-agent-handbook/18_第 14 章…（§14.5.2）；本仓/docs/runtime-refactor/research/资料大纲-2-handbook.md（主题⑩附条）。

7. **白皮书 SOUL.md 是「提示词加固」示例，属『把规则写进提示词』形态，它自己也承认要配合 AgentSentry 旁路拦截**——这佐证「单靠提示词不够」，但白皮书未给「词面规则 vs 模型判断」的取舍数据或权重。来源：资料/字节安全白皮书.md（【2-1】、§6）。

8. **《分析工程基础》与论文类材料对本主题无覆盖**；本主题的可用证据集中在 ai-agent-book（ch1/ch2/ch5/ch9 实验）、HandBook（ch6/ch14）、字节安全白皮书三处。来源：本仓/docs/runtime-refactor/research/资料大纲-1~3。
