## ① 一句话结论

**「读题」这一步的业界主流不是把「角色 + 格式 + 数据」压成一段提示词，而是：三层分离（静态指令前缀 / 动态数据按节注入 / 输出契约独立冻结）、动态数据追加到末尾不污染前缀、来源标记区分「指令 vs 数据」、输出格式用最窄可用契约并要求程序侧稳定解析。**（出处：`资料/技术书籍/ai-agent-handbook/07_第 5 章 信息：上下文、状态与可复用能力资产.md`；`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md`）

## ② 业界主流做法

### A. 提示词/上下文怎么组织

1. **System Prompt 不是仓库里一个长字符串，而是每轮「动态编译」出来的。** 多个来源按优先级合并、冲突被处理、超预算内容被压缩/移除，最终得到本轮模型视图。分层示例：Platform Policy / Agent Contract / Tenant Rule / Runtime Reminder / Selected Skill / Tool Descriptors。
   - 出处：`资料/技术书籍/ai-agent-handbook/07_第 5 章 信息：上下文、状态与可复用能力资产.md`（5.1 Context 构建管线）

2. **指令层与数据层必须分节、分责任，不能拼成同一层文本。** 若全拼成一层，Harness 无法判断冲突来自哪里，也无法独立版本与回归；平台策略不可被项目文档覆盖，用户最新要求不能突破企业安全边界，工具返回的外部内容不能自动升级为系统指令。
   - 出处：同上（5.1「这套分层解决的是责任问题」）

3. **Token 预算不是静态百分比，按阶段动态分配。** 为不可覆盖规则/当前目标/状态保留固定下限，为最近交互/检索知识/Skill/工具 Schema 分配动态额度，并预留模型输出空间；进入工具密集阶段时工具定义权重上升，进入综合阶段时证据与验收条件更重要。优先级函数同时考虑：约束强度、任务相关性、时间有效性、来源可信度、执行依赖、信息增量、Token 成本。
   - 出处：同上（5.1「优先级与 Token 预算」）

4. **每次模型调用生成 Context Manifest，记录「模型究竟看到了什么」。** 至少含 source_type/source_id、scope、version、trust_level、permission_basis、selected_reason、token_count、transform（原文/摘要/截断/去重/引用化）、content_hash。用于解释遗漏、评估两版本差异、安全审计。
   - 出处：同上（5.1「用 Context Policy 与 Manifest 管理模型输入」）

5. **静态前缀一旦确定不改，动态信息追加到末尾（KV Cache 约束）。** 系统提示词/工具定义哪怕多一个空格也可能使首个不同 token 之后的缓存失效；动态信息（时间戳、用户状态）应作为新消息追加末尾，而不是改写系统提示词。提示词的排列顺序「首先由缓存经济性决定，其次才是语义逻辑」。
   - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md`（435-447、560-572）

6. **渐进披露：少量目录常驻、完整正文按需加载。** 不把所有知识一次塞进去，先给「名称 + 短描述（何时使用/何时不使用 + 反例）」，需要时再加载正文。三层：发现层（名称/短描述/适用条件）→ 选择层（Harness 按任务/权限/环境解析候选）→ 执行层（真正需要某步才读细则）。
   - 出处：`book/chapter2.md`（757-824，Agent Skills）；`资料/技术书籍/ai-agent-handbook/07_第 5 章 ….md`（5.5 Skill 与渐进式能力披露）

7. **结构化提示用 Markdown + XML 双层：** Markdown 管人机共读的层次，XML 标签名本身携带语义（`<working_directory>` 比「当前目录：」更精确）。流程驱动优于规则堆砌——给 SOP（分步 + 「若…→…」），比给上百条零散规则更能让模型知道「现在处于哪一步、异常怎么处理」。
   - 出处：`book/chapter2.md`（606-662）

8. **位置偏好：把最关键信息放开头或结尾。** 模型对上下文开头和结尾注意力更高，中间易被忽视。
   - 出处：`book/chapter2.md`（496-500，引 Lost in the Middle）

9. **按执行阶段切换系统提示词 + 工具集，历史全程共享。** 同一会话里，相位切换「只换 system prompt、只换 tools」，历史（需求/代码/评审）完整保留，每次请求＝`[system(当前相位)] + history`。
   - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/chapter10/staged-system-prompt/README.md`

### B. 指令与数据的边界

10. **来源标记 + 结构化角色 + 输入清洗，是上下文层的三层防线。** 外部内容注入前用 `<external_content source="webpage">…</external_content>` 包裹并标注来源；严格用 chat 角色（system/user/assistant/tool）传信息，「不要自行拼接消息」——把工具结果混进 user 消息等于抹掉模型辨别来源的依据。
    - 出处：`book/chapter2.md`（722-738）

11. **关键防线是「区分指令与数据」：网页/邮件/文档/工具结果/远程 Agent 返回全属不可信输入，不能改变平台政策、授权范围、Tool Set。** 上下文层防御只是第一道，只能降成功率，执行层还要权限/沙箱/独立审查兜底。
    - 出处：`资料/技术书籍/ai-agent-handbook/08_第 6 章 行动：受控执行、验证反馈与交付准备.md`（6.4.4）

12. **拼接反模式会导致灾难性后果（有量化消融证据）。** 保留所有规则内容但打乱组织结构（去标题、拆散有序流程成无序集合），任务成功率下降超过 30%；移除工具描述性文本，工具调用错误率增加 45%。
    - 出处：`book/chapter2.md`（710-720，实验 2-4）；`资料/技术书籍/ai-agent-book/ai-agent-book/chapter2/prompt-engineering/README.md`

13. **多个「错误上下文管理模式」：** 动态系统提示词、动态用户配置、工具定义动态排序、滑动窗口历史——都会破坏前缀一致性或丢关键信息（实验中滑动窗口 Agent 常陷入重复调用循环，因为「忘记」已获得的结果）。
    - 出处：`book/chapter2.md`（540-554）

### C. 结构化输出怎么要、怎么读

14. **模型负责产生候选，Harness 负责协议校验与放行。** 检查工具选择/函数名/参数类型/必填字段/枚举值/结构化输出能否被 Harness 稳定解析。
    - 出处：`资料/技术书籍/ai-agent-handbook/22_第 17 章 模型调优.md`（17.5.2）

15. **格式不稳定的两条修法：SFT 固化协议（少量示范固化 JSON schema/工具调用/术语/流程）或约束解码。** 判断标准是「会做但不会按要求做」→ 用 SFT 立协议；解析失败的「可接受率」取决于任务与奖励设计，不应把固定阈值当普遍标准。
    - 出处：`book/chapter8.md`（397、405、803）

16. **「输出格式修复、JSON 解析容错」正被结构化输出与原生工具调用内化——每一轮内化消灭的都是「翻译」「脚手架」这类适配层代码。**（即：宽容解析层是可被逐步淘汰的补丁，不是长期架构）
    - 出处：`book/chapter1.md`（408）

17. **强 JSON Schema 只能描述类型/约束，表达不了隐式约定**（时间戳秒还是毫秒、过滤条件如何嵌套）；这类隐式约定靠 1-5 个真实调用示例最容易传达，加入示例后工具调用准确率可从约 72% 提升到 90%。
    - 出处：`book/chapter4.md`（82、106）

### D. Few-shot 该不该给、给几个

18. **只在「输出难以用规则精确描述」时给示例（风格、结构化报告格式、语气分寸），给 2-3 个覆盖边界情况的高质量示例，胜过 10 个大同小异的示例。** 对模型本就擅长、规则易说清的任务，示例只是浪费 token。
    - 出处：`book/chapter2.md`（684-690）

19. **示例位置要固定。** 放系统提示词则成静态前缀的一部分（对所有请求生效）；或伪造一组 user/assistant 消息放首轮。无论哪种，示例都在上下文靠前区域，一旦确定必须**字节级稳定**——「按请求动态检索最相关示例」等于每次改写前缀，缓存持续失效。因此生产系统通常为每类任务准备**固定示例集**，而非逐请求挑选。
    - 出处：`book/chapter2.md`（688）

20. **示例与「禁令清单」是两种边界写法，效果不同。** 禁忌清单越写越多会让模型越不稳定；写法上应「作用域 + 动作 + 例外 + 验证方式」，避免把所有情况堆成越来越长的禁用词表。
    - 出处：`资料/技术书籍/ai-agent-book/ai-agent-book/book/chapter2.md`（790-796，引宝玉《图解 Skill》）

## ④ 反例踩坑

1. **动态系统提示词**：在系统提示词里加一行 `Current time: {{now}}`，使首 token 延迟从 0.5s 涨到 3-5s，账单几乎翻倍。（`book/chapter2.md` 439）
2. **规则打乱组织**：内容不变只打散结构 → 任务成功率下降 >30%，模型跳过关键业务规则。（实验 2-4）
3. **删工具描述**：工具调用错误率 +45%。
4. **文本格式化消息**（`USER: … ASSISTANT: …`）：偏离训练格式，导致重复执行、忽略工具结果、该调工具却生成文本、格式解析错误。
5. **滑动窗口历史**：破坏前缀一致性 + 丢关键工具结果 → Agent 陷入重复调用循环。
6. **按请求动态挑示例**：等于每次改写前缀，缓存持续失效。
7. **模糊规则留裁量**：「根据任务情况选择合适的计费类型」这类规则导致行为极不稳定（同任务不同时间得不同分类）。（`book/chapter2.md` 668-682）
8. **把外部内容写进高信任区**（如把网页片段写进状态栏/Skill）：信任被反向利用，成为注入面。（`book/chapter2.md` 736）
9. **未验证的兜底当降级**：本地材料明言「没有经过验证的兜底路径，应返回可解释的失败，而不是以『自动降级』为名改变业务契约」。（`handbook 12_第 9 章 AI 网关与统一流量治理.md` 111）

## ⑤ 对本项目「读题步」的适用性（只读问答 / 单租户 / 两行式输出契约）

现状锚点（仓内实测记录，供对照，非合同）：
- 任务书＝静态骨架（场景/任务/三样例/红线）＋动态活体数据（名录/术语/本体对象/数据水位/库族），两者现嵌在同一段任务书正文中段，**指令与数据未分节**。（`docs/runtime-refactor/arch/P6a-票堆V2-80系列前半.md` A-P6a-06）
- 根因诊断：「身份 / 格式 / 路由」三类内容被压进同一段提示词，参照对象都把三类拆开。（同上 A-P6a-01）
- 解析现状＝**两级宽容**：两行合同式（理解：/指标候选：）优先，全缺降级 JSON 子串（中文主键＋英文别名逐键取值，缺键不编造），两级全空如实上报、不阻断。（`docs/runtime-refactor/recon/C-理解与legacy决策节点.md` R-C-09）
- 下游按**字面**依赖理解步输出：回声检测闸靠 `first.startswith("理解：") or "指标候选" in draft[:100]`；指标白名单闸、理解旁白灰条、直答通道都依赖两行式文案。（`docs/runtime-refactor/arch/P7a-交接包与挂账清单.md` 133/155；P6a A-P6a-09）

逐条适用：

| 做法 | 适用性 | 理由 |
| --- | --- | --- |
| 指令层/数据层物理分节（不同段/不同文件，数据永不与指令同段） | **高度适用** | 直接对应 P6a 已诊断的「三职合一 / 指令数据未分节」根因；与 80b 三层重组方向一致 |
| 静态前缀冻结 + 动态数据追加末尾 | **适用（有前提）** | 与仓内「对话链只追加」架构（P6a A-P6a-10）同向；但动态活体数据若每轮变化，需按「每轮数据放末尾、公共前缀稳定」设计，不能嵌回骨架 |
| 输出格式冻结到「消费面可稳定解析」 | **高度适用** | 下游三个消费面（白名单闸/灰条/直答）按字面依赖两行式，故两行式**必须逐字冻结**；这正是 P6a A-P6a-07「机读合同面零触碰」 |
| 统一 JSON 替代两行式 | **方向对但缓行** | P6a A-P6a-09：分类靠枚举字段更好，但消费面要同步迁移，不混进止血批 |
| 解析宽容（两级降级） | **现状保留，但要看定位** | 本地材料把宽容解析视为「正被结构化输出内化淘汰的补丁」（`book/chapter1.md` 408）——可保留，但不应作为长期架构依赖 |
| 来源标记区分指令/数据 | **部分适用** | 单租户、只读问答，注入面比开放网页 Agent 小；但用户原话仍是不可信输入，来源标记思路（把用户原话与指令分节）仍值得用 |
| Few-shot 示例 | **谨慎** | 本仓 Owner 已拍板「判断依据是原则不是例子集——收窄判断面，边界对照例与新增样例全部不采用」（P6a A-P6a-03）；与本地「2-3 个边界示例」的通用建议**冲突**，本项目以 Owner 拍板为准 |
| Context Manifest / 每次记录「模型看到了什么」 | **适合但属外延** | 只读问答单轮语境简单，Manifest 价值主要在回放与审计；仓内已有留痕体系（J recon），是否加一档理解步 Manifest 待裁 |
| 分阶段切换 system prompt + 共享历史 | **适用** | 与仓内「相位合同首次进入追加一次」的追加链同构 |

## ⑥ 值得抄三条 / 要警惕三条

**值得抄：**
1. **指令与数据物理分节**——数据层单独渲染、单独消息块/文件，永与指令同段（`handbook 07` 5.1；本仓 P6a 已诊断待落地 80b）。
2. **静态骨架冻结 + 动态活体数据追加末尾**——保住前缀稳定（`book/chapter2.md` 446），与仓内「只追加」架构一致。
3. **输出契约按消费面冻结、模型管判断程序管格式**——两行式逐字冻结、判别面可放宽（P6a A-P6a-07；`handbook 22` 780-784）。

**要警惕：**
1. **判断面用大量边界示例/禁令清单**——越写越多越不稳定，且锚窄判断面（`book/chapter2.md` 690；本仓 Owner 已拍板弃用）。
2. **淘汰/替换模型时忘测解析稳定性**——不同模型对消息模板/结构化输出敏感性不同，换端点可能「分数升但解析崩」（`handbook 22` 780）；本项目以两行式＋JSON 降级两级解析，换模型须重跑解析兼容。
3. **按请求动态挑示例 / 动态改写前缀**——缓存持续失效（`book/chapter2.md` 688）；仓内活体数据每轮变，必须确认它加在末尾而非回灌骨架。

## ⑦ 疑点与不确定

1. **「读题/理解」这类前置纯判别步该给模型什么、不该给什么，本地材料无专章。** 最接近的是「分阶段系统提示词 + 跨相位共享历史」（`chapter10/staged-system-prompt`）与「按需披露」（Skills），但都面向多步任务，**没有**专门讲「一步纯读题该喂多少数据」的取舍。属**标题/章节推断**，非直读结论。
2. **few-shot「给 2-3 个边界示例」与实际项目「零新增例子」直接冲突。** 本地是通用 Agent 场景结论，本项目 Owner 已就本业务拍板相反做法（P6a A-P6a-03）。本文并列呈现，裁决权在 Owner。
3. **「宽容降级 vs 严格契约」在只读单步场景的具体阈值，本地无量化依据。** 只有「可接受解析失败率取决于任务与奖励设计，不应把固定阈值当普遍标准」（`book/chapter8.md` 803）这类定性说法。
4. **静态骨架的三样例（few-shot）该不该保留、放哪，本地无针对「运行时常量样例集」的专门结论。** 通用结论只说「固定示例集、缓存友好」（`book/chapter2.md` 688），未涉及「样例是否会锚窄领域判断」。
5. **本地材料未覆盖：** ①纯读题步的「不给什么」（负向清单）无专门论述；②两行式这类**自定义文本契约**的解析宽容度设计，两本书只讲 JSON/工具 schema 与结构化输出，未讲自定义非 JSON 文本格式的读法；③单租户只读场景下「来源标记」的收益/成本本地无实测。
6. **外部书是通用工程白皮书，与「油田数据问答」业务无关**——只能借做法，借不到业务语义；业务口径仍须回 `teach-petro-agent/docs/business-setting.md` 与合同册（`资料大纲-2` 疑点 1 同款结论）。
7. **`资料/技术书籍/ai-agent-book/index.md` 编号为旧版**，正文 `book/chapterN.md` 与 `chapterN/` 实验目录才是新编号（`资料大纲-1` 说明）；本文引用一律以 `book/chapterN.md` 与对应实验目录为准。
