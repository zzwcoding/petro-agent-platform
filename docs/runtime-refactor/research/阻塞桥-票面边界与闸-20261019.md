## 五、验收机检化建议（断言形＋端到端＋反向判据）

**A. 环内不阻塞（单元，sqlite 底座，零外部依赖）**

- 用例名：`tests/infra/test_v2_bridge_nonblocking.py::test_in_loop_call_yields_event_loop`。
- 形：在 `async def` 测试体内起心跳 `async def beat(): while True: await asyncio.sleep(0.005); ticks+=1`，`asyncio.create_task(beat())`；
  再触发**环内同步调用链**（A 案＝`await` 该 async 调用点；B 案＝直接 `await` 新 async 口），期间让被调协程 `await asyncio.sleep(0.1)`（用 monkeypatch 把 `_execute`/`_load` 等替成慢协程）。
- 断言：`ticks >= 10`（心跳在调用在途时持续跳动）。
- **反向判据（证明修复前必红）**：把实现回退为 `pool.submit(...).result()` ⇒ `ticks <= 1`（循环被占死，心跳在 `.result()` 期间一次不跳）⇒ 用例红。**此即「修复前会红」的机检形**。

**B. 六处桥逐个不阻塞（参数化，防只修一处）**

- 用例名：`…::test_all_six_bridges_offload[pg_executor|pg_waterline|pg_store|pg_faq|closing|core]`。
- 断言：每个参数下心跳 `ticks >= 阈值`；`pg_wells` 随 `pg_waterline` 参数覆盖（复用同一桥）。
- 反向判据：任一参数 `ticks <= 1` ⇒ 该桥未修 ⇒ 红。

**C. 端到端（跑批中并发读口不被饿死；Owner 复验，写进回报）**

```bash
# 跑批在途时并发打详情口——改前会被工具/模型在途的同步桥占住而排队
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w 'detail=%{time_total}s\n' -H 'X-Dev-User: aqiang' \
    'http://127.0.0.1:8001/api/v2/chat/runs/<run_id>' &

```
