## 一、现象与根因复述

- 现象：3 并发跑批时云端「点击对话」`GET /api/v2/chat/runs/{run_id}`（`appv2/api/chat.py:340-341`）被阻塞 **4–11s**，容器 CPU 近 0%，静态资源恒 40ms。
- 根因：六处桥的有环分支 `with ThreadPoolExecutor(max_workers=1) as pool: return pool.submit(lambda: asyncio.run(aw)).result()`
  在**事件循环线程**上 `.result()` 同步等结果 ⇒ 服务器环被整段占死（CPU 近 0＝在等 I/O，不是算）。
- 三处 docstring 自称「不阻塞事件循环」与实况相抵（`execution/core.py:466-467`／`bookkeeping/closing.py:275`／
  `knowledge/pg_faq.py:7`）——属待改措辞（姊妹件第一节判「需逐字稿」）。
- 服务器环占用链（共同前缀，六处共用）：

  `POST /api/v2/chat/asks`（`api/chat.py:231`）→ `await runtime.ask(...)`（`:297`）→ `AgentRuntime.ask`（`runtimev2/orchestration/runtime.py:175`）
  → `_spawn`（`:464`）→ `asyncio.create_task(self._drive(...))`（`:465`，**跑在服务器环**）→ `_drive`（`:469`）
  → `await build_graph(...).ainvoke(...)`（`:498`）→ langgraph **async 节点**（`orchestration/graph.py:336+`）。

  节点是 async，但其内调的相位函数全是**同步签名**，桥在同步函数里 `.result()` ⇒ 阻塞的就是 `_drive` 所在的服务器环。

## 三、契约真源原文（specs/）

- **同步签名面（接口定义节的 `def` 行＝同步性事实，未见「必须保持同步签名」的显式硬要求）**：
  - `specs/execution.md:36`：``def execute(state: RunState) -> ExecutionOutcome: ...``
  - `specs/knowledge.md:25-28`：``class KnowledgeStore: def evidence(self, q: SemanticQuery) -> list[Evidence]: ... / def metric_by_name(self, name: str) -> Evidence | None: ... / def aliases(self) -> dict[str, str]: ... / def families(self) -> dict[str, list[str]]: ...``
  - `specs/query.md:25-27`：``def validate(self, plan: QueryPlan) -> PlanCheck: ... / def run(self, plan: QueryPlan) -> QueryOutcome: ...``；`specs/modules.md:79-81` 同形。
  - `specs/bookkeeping.md:78-79`：``def call_model(state, caller: str, messages: Sequence[Mapping[str, str]], *, system: str | None = None) -> str: ...``
  - `specs/modules.md:90`：`Seam: QueryEngine / SQL 执行器`；`:67`：`Seam: KnowledgeStore（查台账这一可替换面）`。**Seam 只钉「可替换面」，未钉 sync/async。**
- **已在册点明本缺陷（对策＝async）**：
  - `specs/gateway_adapter.md:83`（行为 4 逐字）：「**`async` 是硬要求**：`complete` 是协程（真实 I/O）；**不得在事件循环内同步阻塞调用**。断言：`inspect.iscoroutinefunction(complete)`。」
  - `specs/gateway_adapter.md:129`（风险 2 逐字）：「**同步桥阻塞事件循环** → 对策＝行为 4（async 硬要求）。检测＝`::complete_is_async`。」
  - `specs/modules.md:605`（卡级修正①）：「① **async**（真实 I/O，运行时是 async；同步桥会阻塞事件循环）」。
- **ADR-0003 相关裁决原文**（`docs/adr/0003-并发模型不上MQ.md`）：
  - `:7`：「loop 内 LLM 调用天然串行（步间数据依赖），无任务内并发冲突；每步超时防挂死拖垮事件循环；」
  - `:10`：「决策：**本期单实例 asyncio＋全局闸，不上 MQ**」。→ 单实例 asyncio 的前提是**环不被同步占死**；桥的 `.result()` 直接与 `:7` 的「不拖垮事件循环」相抵。ADR 未直接裁决桥形态。
- **结论**：`_run_sync` 桥本体**无 spec 原文**（specs 只在行为 4／风险 2 点缺陷、在接口定义节点同步签名）。因此 A 案＝零合同改动；B 案＝改四处接口定义节（`execution.md:36`／`knowledge.md:25-28`／`query.md:25-27`／`bookkeeping.md:78`）＝**动合同**。

## 四、内部协程与 DB 环绑定结论

- **各自建、非共享池**：`pg_executor.py:138`／`pg_waterline.py:96`／`pg_faq.py:98`／`pg_store.py:161` 都在内层协程里
  `db = ConnectionManager(self._specs)`——**逐调用新建专用管理器**，`finally: await db.dispose()`。
- **为什么在「新环线程」里跑不炸**：`ConnectionManager` 的资源按**当前运行环**分桶（`infra/db.py:234-255 _resources()`：
  `asyncio.get_running_loop()` → 该环无桶则 `_build()` 一套引擎＋两张会话工厂）。管理器是**在新环内构造**的，
  故池/连接天然与该环同源；`db.py:172-174` 与 `:237-242` 明写「asyncpg 连接绑创建它的环——跨环复用即抛
  `RuntimeError: ... attached to a different loop`」，此处不触发正是因为**池不共享**。
- 现成机器证据：`tests/infra/test_v2_db_loop_scope.py::test_engine_sets_are_scoped_per_event_loop`
  （三次 `asyncio.run`＝三个环 → 三套引擎，断言 `len({id(engine)}) == 3`）＋`::test_same_loop_reuses_one_engine`。
  该件自述「以 sqlite 单测底座钉语义」，且**修复不得破此件**（姊妹件第三节同判）。
- 细节：`__init__` 先在 `None` 桶建一套（`db.py:205`，无环语境），`readonly()` 再按当次环建第二套；
  `dispose()` 关**全部**桶（`:461-468`）并在取用时剔除已关环条目（`:257-262`）——不残留、不跨环复用。
- `closing._run_sync` 无 DB：走 `gateway_adapter.complete` → 网关用 app 级 `ConnectionManager`（`create_app(db=...)`），
  同样靠「按环分桶」在桥工作环内新取一套引擎，故不炸；代价＝每桥工作环新增引擎/池条目（环关闭后由 `_drop_closed` 剔除）。

## 七、A 案的线程/环语义

- **线程池上限**：`anyio.to_thread.run_sync` 默认容量＝**40**（`anyio.to_thread.current_default_thread_limiter()`）；
  stdlib `asyncio.to_thread` 用环的默认 executor，上限＝`min(32, cpu_count+4)`（3 并发 run 远不触顶）。
- **每次调用新建 `ThreadPoolExecutor(max_workers=1)` 的成本**（现状桥内）：每调用＝新池＋新线程＋新事件环＋新
  `ConnectionManager`（再建 1–2 套引擎/池）＋环退出销毁；`dispose()` 关引擎。A 案后**产线不再走此分支**（走本线程
  `asyncio.run`），成本项只剩「外层 offload 的一次线程切换」＋内层嵌套时的一次池/环（§六 A 案嵌套说明）。
- **`asyncio.run` 在新线程建环仍安全**：与 §四同结论——`ConnectionManager` 在协程内构造、按当前环分桶建引擎，
  无跨环复用；`tests/infra/test_v2_db_loop_scope.py` 即此语义的机器钉。
- **注意**：`asyncio.run` 每次新建/关闭环，故 app 级 `ConnectionManager` 的 `_resources_by_loop` 会累积
  「已关环」条目，靠 `_drop_closed`（`db.py:257-262`）在下次取用时剔除——现状既有语义，A 案不改。
