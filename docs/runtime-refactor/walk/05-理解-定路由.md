## 一、现状（这一段现在从头到尾怎么做）

模型读完题、回一段应答。代码解析后**分两个出口**：
- 应答里有**行首「直接回答：」**行（`parse_direct_reply` 命中）→ **走直答**：`draft_kind="direct"`、`next_intent=answer` → **立刻收口**（免起草、**免核验**）；
- 否则 → `next_intent=decision` → **走完整流程**（澄清→匹配→前置→查→作答→核验）。

**关键**：两个出口**并列**，选哪个**全靠模型当次判断**，没有任何程序把关；**直答是唯一不过核验的出口**。

已做的止血（V2-80a 已落地）：任务书的例外条款**改写成一条判断原则**——「这句话是否**可能**与油田数据业务有关」；可能有关（哪怕一点关联/含糊/拿不准）＝两行式；只有**确定无关**（寒暄/道谢/道别）＝直答。**但这仍是提示词层面的原则，没有程序闸。**

设计过、**未落地**的程序闸（V2-80c）：模型认领直答后，拿**用户原话**过业务词面闭世界，含任一实词＝**拒认直答、程序确定性转两行式**。

## 三、最佳实践对照（`research/最佳实践-节点-定路由.md`，本地材料）

- **模型只出「结构化枚举分类」，代码按枚举分派**；路由**只判「走哪个入口」，绝不判「结果对不对」**。（handbook 9.4.3／9.4.7）
- **三权分立**：入口选择 / 结果判定 / 状态恢复各有权威归属；**禁止把「会话结束、HTTP 成功、模型自述完成」当业务成功**。（handbook 9.4.2/9.4.7）
- **默认倾向**：安全/事实侧 **fail-closed**（默认走保守一侧）；但**两边代价都真实**（误拒绝也是失败），阈值不该当普遍标准。（handbook 9.3.5）
- **语义路由的硬前提**：分类器**经过评估**且**有回退路径**；无回退的自动切换不如可解释的简单策略。（handbook 9.2.3）
- **直答/轻出口**：本地无专章，但支持「**给直答加确定性兜底闸**」（相关性分类器＋确定性分层护栏）。（handbook 9.4.x）
- **枚举字段 vs 格式分叉**：枚举更好、消费面要迁移（与 04 已定的统一 JSON 方向一致）。
- 缺口：本地**无**「拿不准默认哪侧」的量化裁决、**无**直答防滥用专章、**无**本仓同型事故对证。

## 五、我的建议 ＋ 重写规划（草案）

1. **路由改为「枚举分类 + 代码分派」**：模型在统一 JSON 里出一个路由字段（如 `route: "full" | "direct"`），**代码按枚举值分派**，不再靠「有没有某一行」猜。
2. **默认倾向 fail-closed**：判据＝「是否**可能**与油田数据业务有关」；**可能有关/含糊/拿不准 → 走完整流程**；只有**确定无关**（寒暄/道谢/道别）→ 直答。
3. **直答加确定性兜底闸（V2-80c 落地）**：模型认领直答后，**拿用户原话**过业务词面闭世界（油田/井/指标/台账/数据库/报告…），含任一实词＝**拒认直答、程序确定性转完整流程**——把「模型猜错」的最坏后果从「编造直达」变成「多走一遍流程」。
4. **直答仍免核验**，但**只在「确定无关/纯寒暄」这个窄口**（业务问题被闸挡住，永远走完整流程）；此题已由闸保证，不必给寒暄上核验。
5. **灰区明确归属**：「系统自身能力问句」（我能问什么）与「预测类」（明年油价）——**归完整流程**（它们与业务有关）。
6. 保留不变：任务书每 run 一次；模型原话不入对话层。
