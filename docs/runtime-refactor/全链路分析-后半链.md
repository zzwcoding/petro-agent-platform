## §2 逐环节分析与修复方向

### 2.1 四组病灶的环节定位

**A 组·删句误伤（#1 #2，机制同源）**：核验面（`verification/core.py:394-442`）对**无引标行**的判据是"含数值记号即无据断言→整行离场"。修前 `number_tokens` ＝**任一数字串**（`git show c9345d7 -- .../rules.py` 可见旧实现），于是 `W-22`、`2026 年 11 月 1 日`、`34-5` 全部算"数值断言"：#1 删 5 行、#2 删 7 行，交付分别断在**裸标题**与**冒号**。此两题不是模型问题（草稿完整、内容有据），是**核验输入侧判据过宽**＋**行级引标漏标**触发；F1 件一（判据收窄为小数/千分位/紧邻单位）后复刻为 0 删。**修复方向＝程序接管（已落）**；另需注意：删句的交付效果**在帧里看不见**（帧＝起草稿），复核必须看 `state.draft` 或真机交付。

**B 组·视野=答案上限（#4 #5 #17）**：
- #4：答案要"杆断井平均"，正确值 443 ＝ (512+521+295)/3，但**含该三值的「检泵作业明细」表在 obs id=29，被 24 帽切出窗外**；窗外只剩"月平均 428"。模型按"在场唯一平均值"作答——属**材料面截断**而非"看见选错"。
- #5：16.5／12.5 MPa **在整 run 79 条观察里都不存在**（1.2 节"尾管固井碰压 12.5"、3.3 节"环空加压 16.5 点火"切片未进检索），故"卷内未检索到"是**窗外真实、库内为假**（谎称无据族）；同时 A-W11／Y-21 两井值同窗并列 → ③④错配。
- **修复方向＝材料面**：①报表行集切片（`agg_row` 同族或"命中问句的整表"）不承检索族 24 帽；②检索切片保席按"题面数值清单"命中（问题是给了值的——值应作为检索锚）；③核验面补**对象↔值配对**对账（形态判据：同一对象被赋两个值且行内无分井说明→列增补面，不删句）。

**C 组·报告口径值无标注（#6 #7 #8 #9 #10）**：这五题链＝`knowledge/doc_retrieve`，窗内 100% report 片段，**引擎注记段里根本没有"台账未绑定/非权威"之类注记**（只有 window note）——所以"引擎注记转述要求在场但模型没执行"的准确表述是：**要求在场（④条＋`ENGINE_NOTES_HEAD`），但对应的注记本体不在场**，模型没有可转述的东西；而 V1 的 `DATA_CHAIN_FALLBACK_NOTE`（"以下为报告库检索结果（非权威数值）"）**没有迁进 V2**（全仓 V2 代码 0 处"非权威"）。根因＝**②提示词缺失＋④输入材料缺失**（不是模型不听话）。
**修复方向＝程序接管**：收口面按被引材料信任级（`trust_of`）程序补一句口径标注（如"以下数值取自报告口径，非台账权威值"），或材料面把标签渲染成用户可读信任级；**不加条款**（加条款也只能靠模型自觉，而这五题模型无注记可转述）。

**D 组·白话化（#10 #11–#17）**：见 §2.2 专项。

**E 组·归属错位（#18）**：题眼不含油田名（"第五章""1 月""Y-21…"），检索把 34-5 与 34-8 的同名月报一起送窗，模型选了 34-5 的机器队/船日。**核验前该发现的两环**：①**定案（工具匹配）**——`retrieval_need` 锚里无油田/报告名绑定（决策稿 `response` 里 anchors 只有"第五章/1 月/修井/船日/井号"），检索无法收窄；②**材料面**——观察块标签只有"信任级｜来源｜井"，**没有结构化油田字段**，模型只能靠报告名字符串自己分源（⑤条要求"逐个来源分别作答"却无机器可读依据）。核验面 F1 件四（行级油田归属闸）已能咬住该形（真机证据即此帧）。**修复方向＝材料面补字段＋定案面锚绑定**（读题/澄清环应把"XX 油田 YY 月报"作为锚落进 `retrieval_need`）。

### 2.2 重点：白话化三层失效解剖（为什么条款＋示例＋词表全没用）

**事实面（三层都在场）**：⑨条（`prompts/constants.py:243-244`）逐字给出禁则＋**反例＋正例**："不要把内部说法整句甩给用户（『召回 51 支/送窗 12 支』应写成『检索到 51 条材料，其中 12 条用进了答案』）"；术语白话表（`constants.py:255-259`）给出 `召回＝检索到的材料；送窗＝用进答案的材料`。三层齐备。

**实测（121 帧）**：仍以「召回/送窗＋数字」形甩内部计数者 **8 题**（#11–#17＋数-降2；EB4 终判记 9，口径差 1 属计数式口径）。**没有任何一题给出完全合规的白话句**——两题（C-澄清、C-反2）用了白话量词却仍保留"召回"二字，属半白话。

**决定性的输入侧证据**：这 8 题的答案包里，同一句话以**内部腔原文**出现两次——
```
（材料段）[13]（report｜检索供给窗声明（缺位名单））检索窗注记：缺位来源（预算未及）：《…》
（引擎注记段·提示词尾）召回 46 支/送窗 11 支；已召回未送窗 35 支；矛盾来源同窗并立（各留代表支）：《…》；缺位来源（预算未及）：《…》；节级摘要展开节内切片 +5 支（摘要命中→节内补席）
```
（`run-b6ac1cf4` 实测；生成单点 `appv2/retrieval/domain.py:427`。）

于是产生了**条款内部的对撞**，三层全部失效的机制如下：

1. **同一义务的分裂**：⑨条前半句命令"**如实点名未覆盖来源（含检索窗注记的未进窗来源）**"，④条命令"**引擎的降级/未绑定/拦停注记必须如实转述**"；而"未进窗来源名单＋召回/送窗计数"是**同一行不可分的原子文本**。要履行转述义务，就得搬这一行；搬这一行就带出内部计数。三层全部只谈"输出形态"，**没有任何一层告诉模型如何"拆句保义"**，模型的最省力策略＝照抄。
2. **白话表是映射、不是改写**：`召回＝检索到的材料` 只声明"召回"指什么，**不禁止写"召回"**——模型完全可以在写"召回 46 条材料"的同时自认已合规（这正是 C-澄清、C-反2 的形态）。
3. **反例与输入同形（示例反噬）**：⑨条反例是『**召回 51 支/送窗 12 支**』，输入注记是「**召回 46 支/送窗 11 支**」——**同一模板、只差数字**。示例不但没建立"禁形"，反而把该模板强化成"系统标准表述"。
4. **位置（recency）**：白话表结束在提示词第 ~730 字符（前 12%），而内部腔注记是**提示词的最后一段**（尾 260–890 字符）——模型落笔前读到的最新、最像"系统口径"的文本，就是它要"如实转述"的那一行。
5. **量词面还多一道诱导**：注记用"**支**"（检索片段量词），白话正例用"**条**"；模型改量词不改词，正好产出"召回 46 条材料"这种半白话。

**结论**：白话化不是"条款不够多/示例不够好"的问题，而是**输出侧三层（禁则＋词表＋示例）对撞输入侧一次原文（且是尾段）**——在 221/291 次携带该注记的调用中，输入侧始终提供现成的内部腔词形。加第④层条款必然同样失效（三层实证 0 合规）。

**非条例类修法（四条，按优先级）**

1. **程序接管·注记面改写制（首选，零新条款）**：在生成单点 `retrieval/domain.py:411-436 build_window_note` 处**直接产出用户语形式**并**拆两段**：用户可见段（"检索到 46 条材料，其中 11 条用进了答案；另有 35 条这次没读到（不在本轮视野，故不作断言）；本次未查到的来源：《…》"）＋机读段（保留 `recalled/sent/missing` 结构化键进 payload，供 `verification.disclosure_text`／`engine_disclosure_line` 与前端用）。同时同步 `verification/rules.py:321-345`（披露行比对源）与 `handlers.py:1130-1153`（缺位段提取）的匹配字面。
2. **位置**：把引擎注记段从"提示词尾"移到**材料段之前**（或改为增补面/前端展示位）——消除"最后读到内部腔"的 recency 效应。注意 ④条"不得静默丢弃"要求**不许删**，只能改形或改位。
3. **结构化**：计数不再以自由文本进窗，改由**程序**在交付面拼白话句（模型只写结论，注记只进机读面）——与 EB3 D2"交付面分层"同思路。
4. **不选 few-shot／核验面词表**：⑨条已自带反例＋正例（另有白话表 8 词），仍 8/121 复发（示例无效已实证）；核验面加"内部腔⇄白话"词表＝新增语义词表（违"禁语义词表"纪律），且属下游拦截，成本高、误伤面大。

## §3 横向结论：后半链共性病灶 top 3

**top1｜输入侧已把字面定形，输出侧条款/词表/示例一律不起作用（白话化是极端样本，不是孤例）**
白话表＋⑨条＋反例三层齐备、禁形 8/121 复发、合规 0 题；同批还有"本报告"照抄（#3，报告原文自指）、"召回/送窗"照抄（#10–#17）、检查话术照抄等——**模型的最省力策略是转述输入**，而 ④/⑨ 条又**命令**它转述引擎注记。结论：后半链的措辞/口径类病灶，修法只能落在**材料面与注记面的渲染单点（程序接管）**，加条款是给已经失效的层次再加一层。**佐证**：输入注记 221/291 次在场，其中**内容与反例同模板**（『召回 N 支/送窗 M 支』）。

**top2｜"视野＝答案上限"：答案窗是 100% 报告片段，关键行集还被 24 帽切走**
18 题渲染块**无一例外全为 `report`**（零台账/权威行集）；121 帧中 60 帧 obs>24，样本内最高切掉 84%（150→24）。直接后果：428 vs 443（#4，443 那张表在窗外）、16.5/12.5"卷内未检索到"（#5，整 run 无该观察）、"已召回未送窗 22~27 支"（#17，帽切 70 支）。这些题的失败**根因不在起草能力，而在挑选与帽面**。修法：行集/报表切片豁免帽、题面数值入检索锚、帽内保席改成"按问句命中"而非"按信任级截断"。

**top3｜核验面只判"有没有据"，不判"配得对不对"——且删句判据曾以"数字"为触发**
核验面的判据面＝引标可解析＋值∈被引材料；因此"值全对但**对象↔值配对错**"（#5 跨井混配）、"**口径错**"（#4 全员平均当杆断平均）、"**归属错**"（#18 跨油田）都通不过判据；而修前的数值判据又把井号/日期当数值断言，误删 #1/#2 的整段正文（交付断在裸标题/冒号）。方向：**把正确性前移到"谁进窗"与"交付装配"**（程序化的对象↔值配对、信任级标注、来源全称），核验面只保留"有无据＋归属对账（F1 件四）"这类形态判据。

**附注（观测面陷阱，复核必读）**：text 帧在**核验前**发出（`answering/core.py:310-313`），所以**帧里保存的是起草稿**；核验的删句/增补只在 `state.draft`（`verification/core.py:320`）与真机交付可见——这正是"批内 121 帧残尾采样 0、Owner 手工复跑却断在裸标题"的直接原因，也是 `parsed.answer_text` 取"末条 text 帧"会拿到**最后一段草稿**（#1 得到那行"说明：…"）的原因。任何以后半链为对象的复核与判分，都应改读核验后的终稿。
