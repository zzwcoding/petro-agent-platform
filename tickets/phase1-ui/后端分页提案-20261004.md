## 二、建议

### 2.1 ① 整表端点补 page/pageSize 参数与回显条款（hasPagination=no 且量级可增长）

- **名单**：kb reports/tasks/libs/activities、faq items/candidates、gateway models/drills、chat sessions/messages/assets——**graph net 除外**（剔除理由见 §5.3 裁决项③）。对应 §一 表 hasPagination=no 行共 11 端点，各端点现读法与合同册出处随表随 §3.1 清单。
- **实施路径**＝各册补条款 → `tools/contract_coverage.py export` 重跑（owner 注记自动保留——AGENTS.md 纪律 8）→ 后端走 `ReadOnlyRepository.paginate`（app/infra/db.py:390，`page_size` 默认 20 在 ：395——评审遗留⑤行号修正版）。成本在合同升版不在实现：分页助手与信封形（Page[T]＝items/total/page/page_size，00 §4.1 回显口径）在仓内已有两处现成先例（gateway spend-logs 全程 SQL、semantics `_paged`），施工批照抄形状即可。

### 2.2 ② 「有页但前端未消费/内存切片」3 项单列

1. **semantics metrics/terms——后端真 SQL 分页、前端 pageSize=500 整表拉**：真 SQL 分页在案（semantics/service.py:284 `_paged`，默认 20），但 B3 台账口径/术语下拉以 `pageSize=500` 整表拉（faq.js:281）——分页形同虚设，下拉消费面应改按需分页/检索。
2. **kb fragments 缺省读法——分页为内存切片非 SQL**：全库扁平清单读法强制携带 page/pageSize（缺任一 400），但分页实现为全量载入后内存切片（kb/service.py:1097-1120）非 SQL；且片段排序键合同未冻结（B2.md:123）——量级增长后性能与排序确定性双缺口，随 §3.1 合同升版一并根治。
3. **D1 聚合 caller/model 信封未消费**：`GET /api/gateway/spend-stats` caller/model 面为后端真分页（默认 15），前端 D1 花费聚合表 client 模式整表消费、信封分页未消费（UI-06 转来登记）——前端切换 server 模式或合同撤页归并，二选一交 Owner。

### 2.3 ③ 备查：「下拉整表拉取」条目（并入②备查）

B3 台账口径/术语（faq.js:281，pageSize=500）、B3 slice 下拉（faq.js:311，`page=1&pageSize=500`——与②-2 同端点不同消费面）、B5 报告下拉（UI-05 T8 转来——GET /api/kb/reports 整表拉作下拉源）——三处下拉整表拉取登记备查：下拉属 UI 消费面，根治随对应端点分页升版（§3.1）或下拉改服务端检索，交 Owner 拍板施工批时一并定。
