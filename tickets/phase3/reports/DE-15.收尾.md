## 选型（票面形态 a/b 二选一）

**选 a）store 层 per-key 更新（JSON 键级 UPDATE）**，对照 b）单写者串行化：

- **锁面**：b) 的锁是进程内约定，任何写者忘持锁即静默丢更新（fail-open），
  且必须罩住 TaskStore.save/finish_with_activity 全部调用点；a) 的原子性在
  单条 UPDATE 里（fail-closed），写口只有 merge_branch_status 一处，绕不过。
- **复杂度**：b) 需 per-task 锁生命周期管理（建锁/清锁）＋继续维护分离行
  本地镜像（R1-15①点名的形状漂移面）；a) 删镜像、列归属一条规则讲清。
- **成本**：a) 多两条方言表达式（PG `||`／sqlite `json_set`，各 3 行，均有
  测试钉）；b) 零方言分支但把正确性押在调用方纪律上。演示底座单进程是 b)
  的适用前提，但多 worker/未来多进程部署下 b) 直接失效，a) 不受影响。

## 关键实现发现

- **PG 绑定双重编码坑**：补丁参数若携 JSONB 类型绑定，SQLAlchemy 的 JSON
  绑定处理会对已序列化字符串再 dumps 一次——落库成 jsonb 标量字符串，PG 对
  「对象 ‖ 非对象」的 `||` 语义是把两值装进**数组**（实测 `[{}, '{"wiki":…}']`）。
  修法：补丁按纯文本绑定＋SQL 内 `CAST(… AS JSONB)`；空对象用常量片段
  `'{}'::jsonb`。
- **sqlite json_set 文本参数坑**：文本参数按 SQL 字符串插入（双重编码成
  `'{"state":…}'` 字面量），须 `json()` 包一层先解析才以 JSON 本体落列。
- **键路径守卫**：sqlite 路径串拼 `$."<key>"`，branch 键按白名单形
  `[A-Za-z0-9_-]+` 校验（G-02 wiki/graph＋DE-06 chunk_check 同族闭世界），
  越形抛 ValueError 不静默。

## 偏差/疑点

- **save 契约边界**：`_reload_branch_status` 的 refresh 要求行已存在——save
  对不存在行由「静默插入」变「抛错」。现网调用方（管线/重建任务体）均先
  `tasks.get` 装载，不可达；登记备查。
- **每次 save 多一次 SELECT**（reload branch_status）——管线每步一次，量级
  演示级，换取消除抹键面。
- **种子助手顺手修正**（测试位内）：外键链 lib→report→task 原一次性 add——
  sqlite 默认不强制外键侥幸过、PG 真强制即炸；改逐父行 flush（store
  confirm_upload 同款惯例）。
- **两方言表达式语义核对**：PG `||` 顶层键浅合并＝sqlite json_set 逐键整替换，
  「只覆盖 patch 顶层键」两侧同语义（PG 门控测试钉）；jsonb 列 PG 侧键序
  本就按 jsonb 内部序存储（G-02 既有行为），本票无变化。
- **R1-15②**（warn 为 additive 态提醒）落 IngestTaskRow.branch_status 列注记
  ＋set_branch_status docstring（消费方按 violations>0 判，勿依赖 state 枚举）。
