# 「LLM 问数＋确保准确」演进方案（修订二稿）——入口层 LLM 受约束产源槽位意图、链体确定性装配

> 面向 Owner 的设计稿 · 2026-10-05 · 修订二稿（吸收独立评审 9 条意见，处置见第 8 节与附录 B）。依据：设计仓调研、主仓现状、开源生态三份材料＋本仓代码两轮逐处核读（清单见第 9 节）。

## 0. 结论（先读这三句）

1. **架构主张：LLM 只做一件事——把自然语言问句翻译成受约束的「源槽位」查询意图；SQL 永远由现有确定性装配器生成；身份与派生字段一律服务端重推导。** LLM 全程不产 SQL、不碰权限身份字段、不自我审批。这不是折中，是开源产品化路线的主流形态：WrenAI 让 LLM「面向语义层（MDL）规划」、SuperSonic 让 LLM 产出语义查询（MQL）、join 和公式由语义层代写——均不让 LLM 直接写 SQL（README 声称，未实测）。
2. **准确性来源不变：靠治理管道，不靠换更强模型。** 语义资产（C1 台账投影＋golden 样例）＋执行校验（安检三闸＋装配器收口）＋评估回归（影子对照＋评测批）。设计仓 frontier 共识原文：「全行业……收敛到了同一件事——把大模型的自由度收敛进『语义资产＋执行校验＋评估回归』的治理管道」（docs/frontier-upgrade-plan.md:21-27）；「准确率是上下文工程喂出来的……AT&T 用上一代 GPT-4o 登顶 BIRD，裸模型 GPT-5 排 31 名」。本方案是把这条共识做完，不是推翻它。
3. **对当年「零模型」决策：链体六站零模型不动；放开的口子只在统一入口裁决层——那里本来就有 LLM 在跑。** 现网意图裁决已是 LLM（petro-main 分类，caller=chat.intent.verdict，超时 8 秒失败兜底，service.py:1367-1419 已核读）。需要 Owner 补拍：拍板记录 2026-10-04「问数链零 LLM 意图识别（复用 D2 slots，票 94）」是链内 N7.1 的确认（N7.1 本方案下依然零模型），入口层意图精解析是其延伸决策（tickets/phase2/拍板记录-20261004.md:67-68）。

## 1. 背景与差距

### 1.1 现状（主仓核读）

阶段 2 上线的问数链全程零模型调用（chains.py:1038）：

- **入口路由靠词面**：确定性信号＝「指标台账命中＋DATA_QUESTION_RE 时间/数量/排名词面」（service.py:1295-1301；词面正则 domain.py:1177-1181）。评审核证：「哪几口井采得最狠」既不命中词面正则（「几」不在数字字符类、无最高/最低/排名词）也无默认窗——这类问法现网到不了数据链，正是不放 LLM 时的覆盖缺口。
- **可出数指标只有 3 个**：MEASURE_COLUMNS 白名单（domain.py:1127-1131）；完成率/递减率等派生比值一律降级解释链（chains.py:1052-1074）。
- **无过滤无对比**：QueryPlan 无维度过滤字段、无双窗对比形态。

三条即 Owner「我要 LLM 问数」的实际缺口：**问法宽容度、表达力、带置信标注的可信出数**。

### 1.2 当年为什么选零模型（设计仓材料，如实引述）

1. **防解析漂移**：票 94——站 1「复用 D2 slots 做确定性校验……零模型调用……不设第二个理解型 LLM 节点（两次解析会引入『解析漂移』需仲裁）」。
2. **口径资产未就绪**：C1 台账阶段 2 才现成、阶段 3 才开语义写口（teach roadmap:62-94）；没喂上下文不放 LLM。
3. **评测闸未建**：评测批挂阶段 3；没有回归闸，坏了发现不了。

**判断：当年零模型是「准确性的供给条件不具备」之下的最安全实现形态，当时是对的。**

### 1.3 现在凭什么放开口子（评审修订后措辞）

1. **安检闸状态如实分层**：水位闸（N7.4a）与外表审批（N7.4c）经 R1~R4 审查与实战在役；**行级闸（N7.4b）当前是预埋恒真形状——机制在、防护空**（谓词恒空＝WHERE 恒真，query_store.py:11-14；Owner 拍板「管理员数据域＝全量」）。所以「意图错了执行层兜底」只对水位与外表成立；对行级，兜住 LLM 意图错误的是本稿机制 1/2 的字段白名单与台账绑定，而非行级闸——不夸大。
2. **入口层 LLM 可靠性模式已上线**：「超时→JSON 坏→链名越界→确定性兜底，不许问挂」（service.py:1367-1419）；LLM#plan 单问层照抄，跨问熔断为新增（评审意见 8）。
3. **治理链排期已到**：阶段 3＝C1 写口（C2 提案→语义 CI→台账+1）＋评测批（teach roadmap:62-94）。
4. **调研证据齐（引用勘误后）**：BIRD 人类 92.96% vs 榜首 ~82%、**Spider 2.0 实际任务榜首仅 65%**（docs/frontier-upgrade-plan.md:21，本会话核读原文）；开源生态调研材料另记载 Spider 2.0 纯提示法 1–6%（出自其 sources 所列 spider2-sql.github.io 榜单页，本会话未直接核对——T-01 前核到原始出处，核不到就删）。双向证明：自由 LLM 问数不可信、受约束 LLM 问数是正路。

**判断：沿用其前提（准确靠治理管道）、升级其对策（机器仲裁解决解析漂移）、有据推翻其实现形态（入口层只做词面解析）——三句如实写进合同变更票。**

### 2.2 一个问句的四条路径

1. **快路（现状保留）**：确定性信号齐（指标台账命中＋DATA_QUESTION_RE 词面，service.py:1295-1301）→ 现行零模型解析直进六站链，LLM 不参与零额外成本。
2. **慢路（触发式，V1 主推）**：现网 verdict LLM 本就可判「状态机六站链」（17 链清单在其提示词内，service.py:1388）——当 verdict 选六站链而快路信号不齐（词面不足/确定性解析缺件，如「哪几口井采得最狠」既不命中 DATA_QUESTION_RE 也无默认窗）时触发 LLM#plan 填源槽位→validator 重推导→双路比对（有确定性解析可比时）：一致直出并标注；不一致按 F56 档位分派；validator 拒→既有澄清帧（有界一次）或现行降级解释链。两段串行最坏 8s+8s，但仅发生在现状会流去检索链/降级的场景——多一次调用是覆盖增值的代价。**候选优化（阶段 C 评估）**：选链＋填槽合并单次调用（需 verdict 提示词改造并评估对 17 链分类质量的影响，V1 不做）。
3. **影子路（阶段 A）**：LLM#plan 与现行路并行、只落日志不生效；影子报告含两个触发式验证分桶：「触发但快路可解」（过宽）与「该触发未触发」（过窄）。
4. **故障路（双层，恒在）**：单问层——超时/坏输出/越界→现行确定性路由；跨问层——连续 N 次失败或滑动失败率超阈值→自动降为快路-only＋告警，恢复需人工。

### 2.3 关键决策

**D1 LLM 放入口层，不放链体。** 链体保持零模型全确定性，三个直接收益：F7 幂等重跑前提保住（审批挂起恢复整节点重跑消费持久化 plan，不重调 LLM——否则批过的外表集可能与重跑后执行的不一致）；19 类帧与 17 链闭世界零改动；可靠性模式直接照抄现网。**拒绝项**：LLM 放 N7.3 链内（全景树原设计）——破坏幂等、合同改动面大、收益相同。

**D2 意图结构＝QueryPlan 槽位的源槽位子集，不发明第二结构。** 装配器/血缘卡/审批比对**消费** QueryPlan 零适配；ctx 钉入与 resume 消费为新缝（L-05）。这同时是防幻觉手段：字段闭世界，没有自由文本空间。**拒绝项**：新造意图 DSL——第二真源，违反 dp4 同款纪律。

**D3 双路仲裁，快路优先，算子先定义后实现。** 确定性信号齐不烧 LLM；LLM 只在需要时出场，其产物必须过与确定性解析同源的收口纯函数。比对算子与触发谓词进 L-01 验收，影子双分桶验证触发式。票 94 的「解析漂移」顾虑正面解决：两个解析的分歧由机器归一化比对裁决，分歧本身就是置信度信号（借鉴 XiYan 多候选＋选择器思想，降到意图级——SQL 级多候选在本场景无必要，因为 SQL 只有一个出口）。

**D4 SQL 唯一出口＝装配器（否掉自由 SQL 路线）。** 证据与理由见 1.3.4 与架构节末尾：agg 三表闭世界里合法 SQL 空间极小，装配器已完全枚举；自由 SQL 只添风险（注入/非法 join/写操作）几乎不添覆盖；Spider 2.0 证明真实库上自由生成崩塌；Vanna 已归档、Dataherald 停维，纯 text-to-SQL 框架不可依赖。外表集唯一产源为确定性词面比对（Draft 拒填 external_tables——防幻觉外表名把不涉外表的查询推进人工审批）。

**D5 披露与生效同批（评审意见 2 采纳）。** verdict additive 意图来源键＋血缘卡①口径行 LLM 路来源后缀（行内文字，五要素键序不动）；前端渲染同批落地——A1.jsx 现状白名单渲染只取 chain/confidence/slots 三键（A1.jsx:850-853），additive 键虽会经 `_wire_verdict` 下发（剥 `_` 前缀即随行），但不落渲染＝没披露。登记通道沿用 A1 册 additive 先例（verdict.source 2026-10-02、rewrite subtype 2026-10-04，A1:301-302）。

**D6 模型无关＋跨问熔断。** gateway.complete 单点（B6）、caller=chat.intent.plan 归因记账；归因记账同时是熔断数据源（连续失败/失败率超阈→自动降快路-only＋告警，人工恢复）；模型可插拔，选型影子期出数据后 Owner 定（开放问题 3）。

## 4. 演进路线（先小后大，每阶段带闸与回退）

## A.3 开源生态调研摘要

**格局**：两条路线并存、分工明确。路线 A『LLM 直接写 SQL＋工程护栏』是榜单主流：BIRD test 榜首 82.95%（闭源 GrainSQL），开源 XiYan-SQL 75.63%、蚂蚁 Agentar-Scale-SQL 81.67%；GPT-4o 裸写约 70%。路线 B『LLM 产出受约束的语义层调用』是产品化主流：WrenAI、SuperSonic 让 LLM 面向已治理的指标/维度/关联生成中间查询再翻成 SQL，文档声称降低幻觉，但都不公布 BIRD/Spider 数字。量化结论：学术库（BIRD）75-83%，逼近人类 92.96% 仍未达；真实企业库（Spider 2.0，千列多方言）纯提示法跌到 1-6%，最强 agent 到 2026 年才爬到 76%（Lite 榜）；多方言修复类 BIRD-CRITIC 约 44-48%——场景越真实准确率越低。**适用判断：有建模、口径固定的分析问数（油田属此类）走语义层约束+模板兼容；探索型/开发者自助走直写+校验+人在环。** 另注意 Vanna 已归档、Dataherald 停维，纯 text-to-SQL 框架淘汰快。

**八种准确性模式**：①Schema RAG/样例库检索增强（Vanna、DB-GPT、Dataherald、SQLBot 共同底座）；②语义层绑定（WrenAI MDL、SuperSonic Headless BI）；③候选集成+选择器（XiYan-SQL、Agentar-Scale-SQL，榜单 SOTA 主力）；④生成后校验与置信度（WrenAI 干跑校验、Dataherald 评估器 0-1 分双档）；⑤自纠错循环（XiYan 精炼器、DB-GPT 报错回喂）；⑥领域微调专用模型（XiYanSQL-QwenCoder 3B-32B 单模型 BIRD test 69%，可私有化）；⑦人在环+权限边界（Chat2DB 客户端确认、Vanna SQL 仅管理员可见、行级列级权限）；⑧公开榜单评测驱动（区分学术榜 75-83% 与真实企业库 1-6% 的落差）。注：各项目机制均为其文档/README 声称，未实测。
