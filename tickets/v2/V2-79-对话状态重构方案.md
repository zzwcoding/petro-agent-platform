# V2-79 · 对话状态重构方案（对话/任务/过程三层分离）

状态: **待 Owner 拍板** ｜ 起草: 2026-10-13 ｜ 来源: Owner「我需要的是一个高性能高可用的企业 agent，不是临时修补的玩具——调研正常的 agent 对话设计，分析数据库里各种对话上下文，给我详细完整的重构方案」

---

## 0. 一句话结论

现行设计把「系统指令、模型过程原话、对话」三种东西混在一条消息历史里，导致：上下文随过程膨胀（库里单 run 最高 60.5 万字）、每次调用全量携带（token 浪费 70%+）、模型把过程记录当对话模仿（复读/标签照抄/误判直答的全部根因）。重构为业界标准的**三层分离**：对话层（自然对话）、任务层（每次调用现拼、不入史）、过程层（结构化轨迹、按需有界渲染）。预期每次调用 token 降 ~70%，模仿面清零，存储有界。

### 1.4 每次调用的真实构成（context.py 编译契约）

```
messages = [system(角色红线), *RunState.history(token≤12000 截断), 当前指令轮(任务书/决策指令+材料+常驻块)]
```

- 一次 run 2~4 次 LLM 调用，**每次都全量重发历史**——中位 run 每次调用带 ~8k tokens 历史，其中 95% 是过程垃圾；
- 截断策略「保首尾、弃最旧中间」——超限时被弃的可能是关键决策上下文（任意性）；
- 历史在 checkpoint **无界存储**（60 万字 run 实锤），调用视图有界但存储不治理。

### 1.5 已暴发的症状（全部同根因：过程记录以「助手轮」角色在史）

| 症状 | 日期 | 机制 |
|---|---|---|

| 同参重投（V2-37 立项根因） | 更早 | 「模型没有记忆自己做过的事」的另一半：过程记了但形态不可靠 |

## 2. 业界参照（调研结论）

> 详证见附录 A（来源均为官方文档/工程博客）。提炼四条铁律：

1. **消息历史＝自然对话**：user 原话 ↔ assistant 最终回答。OpenAI 对话状态、LangGraph messages state 皆如此；没有框架把 prompt 模板或系统指令记进对话历史。
2. **系统指令走 system 通道**，每次调用现拼；不入史、不重放。Anthropic context engineering：指令与对话分离，"trust the per-call assembly"。
3. **过程轨迹独立于对话**：工具调用用结构化 tool 消息（非 assistant 散文）；思考/决策不入 messages（LangGraph 的 scratchpad 模式）；要给后续轮看时，**有界、结构化、按需渲染**。
4. **长对话治理是标配**：token 预算＋旧轮摘要化（LangGraph summarization/compaction 模式），摘要替代原文而非丢弃。

**本系统的反模式对照**：任务书入史（违 1、2）、决策 JSON/台账以助手轮在史（违 3——业界以带类型条目承载，见附录 A2）、伪标注轮（违 1、A4）、无摘要的截断（违 4——只有截断没有摘要）。

## 3. 目标架构：对话状态三层分离

### 3.1 三层定义

| 层 | 内容 | 生命周期 | 进模型面？ |
|---|---|---|---|
| **对话层 `dialogue`** | 用户原话、助手终稿、澄清/审批等真实用户输入——**一条不多** | run 生命期＋追问播种传承 | ✅ 以 user/assistant 消息轮（自然对话形） |
| **任务层（现拼）** | system 角色红线＋本轮任务书/指令＋观察材料＋常驻台账块 | 单次调用，用完即弃 | ✅ 以 system＋当前 user 轮（**不入史**） |
| **过程层 `process_notes`** | 紧凑过程档案：[{phase, title, digest}]（理解一句话、决策要点、台账一行摘要、拒因） | run 生命期；追问轮可选有界渲染 | ⚠️ 按需渲染进**当前指令**（有界），永不以对话轮出现 |

### 3.2 RunState 字段级改动

```python
# 删除
history: list[dict[str, str]]                      # 三层混装时间线（28 处写入点）

# 新增
dialogue: list[dict[str, str]]                     # [{"role","content"}] 自然对话（无指令/无过程/无标注）
process_notes: list[dict[str, str]]                # [{"phase","title","digest"}] 有界过程档案（每轮 ≤200 字）
# 保留（结构化状态本来就有，过程信息的事实载体）：
understanding / metric_candidates / tool_matches / subtask_results /
observations / executed_payloads / decision_error / user_hint …
```

### 3.3 节点读写矩阵（重构后的唯一真相表）

| 节点/时机 | 读 | 写 dialogue | 写 process_notes | 写结构化状态 |
|---|---|---|---|---|
| 受理（ask） | — | append(user=**用户原话**) | — | — |
| N1 安全闸拒答 | dialogue | append(assistant=拒答话术) | reject 条目 | — |
| 理解步 | dialogue 末条（原话已在）＋任务书（现拼） | — | 1 条 {phase:understand, digest:理解一句话} | understanding/metric_candidates |
| 决策步 | dialogue＋process_notes 摘要（渲染进当前指令）＋材料 | — | 1 条 {phase:decision, digest:决策要点} | tool_matches/… |
| 台账（工具执行） | — | — | 1 条 {phase:tool, digest:参数→结果一行} | observations/executed_payloads |
| 澄清挂起/回收 | dialogue | append(user=用户补充) | clarify 条目 | user_hint |
| 审批回收 | dialogue | append(user=批准/驳回) | approval 条目 | — |
| 作答步 | dialogue＋材料＋understanding | — | 1 条 {phase:draft, digest:—} | draft |
| 核验 | 材料＋draft | — | 1 条 {phase:verify, digest:支撑/改写数} | verdict |
| 收口（finalize） | — | **append(assistant=终稿)**（唯一写手） | — | answer/status |

要点：**dialogue 的写入收敛到 4 处**（受理/收口/澄清回收/审批回收），对比现在 28 处混装写入。终稿由收口单点写——「草稿≠终稿」的双记录问题自然消失。

### 3.4 每次调用的消息组装（compile 新契约）

```
messages = [
  {system: 角色红线（现有 SYSTEM_PROMPT）},
  *dialogue（自然对话轮；token 预算内全量，超限旧轮摘要化——见 3.6）,
  {user: 本轮任务书/指令 ＋ 观察材料 ＋ 常驻台账块（现拼——与现行为一致，但不入史）},
]
```

- 理解步任务书、决策指令、作答指令的**内容不变**（钉过的逐字稿全保留）——变的只是「用完即弃，不再落史」；
- 决策步要看的「本 run 已做什么」：从 process_notes 渲染一个**有界摘要段**（≤400 字）拼进当前指令（替代原「读全量台账史」——同参防重已有 V2-37 机器闸双保险）；
- 作答步要看的理解锚：state.understanding 渲染进当前指令（已有 anchor_line 机制）。

### 3.5 追问播种（_seed_history 新形）

```python
seed = 前轮.checkpoint.dialogue        # 只有自然对话：问、答、澄清、审批
# 旧格式 checkpoint（history 字段）→ 读兼容抽取（4.2）
# 可选：附前轮过程摘要一段（≤300 字，Owner 拍板是否开）
```

「我刚刚问了什么」类问题在新形下模型直接看到 `[user: 我能问什么][assistant: 您好我是…]`——无需任何标注即可复述。

### 3.6 长对话治理（compaction——业界标配补齐）

- 预算：dialogue 视窗 token 上限（建议 4000 tokens＝16k 字，独立于任务书预算）；
- 超限触发：旧轮对（user+assistant 成对）摘要化为一条 `[{role:'system', content:'（前情摘要）…'}]`——摘要由小模型生成或规则抽取（首版规则抽取：每轮问句原文＋答案首行，零模型成本）；
- 摘要落 process_notes（不覆盖原 dialogue——原史仍在 checkpoint 全量可查，压缩只作用于模型视图）。

### 3.7 本次要杀死的反模式清单

1. ~~系统指令（任务书）入对话史~~ → 现拼现用；
2. ~~模型过程原话以助手轮在史~~ → 结构化 process_notes；
3. ~~伪标注轮（上轮答案：/直接回答：标记入史）~~ → 自然对话形，标记永不落史；
4. ~~无摘要的任意截断~~ → 摘要化压缩；
5. ~~终稿与草稿双记录~~ → 收口单点写终稿。

## 附录 A · 业界参照来源（调研摘录——官方文档原文，2026-10-13 核对）

**A1 · 历史放什么、指令放哪**

- OpenAI 对话状态：对话即「items」（messages/tool calls/tool outputs），历史是真实交互台账——"Conversations store items, which can be messages, tool calls, tool outputs, and other data."（developers.openai.com/api/docs/guides/conversation-state）
- 系统指令**不进历史**：OpenAI 用顶层 `instructions` 参数随请求携带；Anthropic 把 system 作为独立顶层参数、不占 messages 数组；LangGraph——"Chat models accept context using messages — with developer instructions as a system message"（docs.langchain.com）。历史只追加增长，指令层不随之膨胀。
- Anthropic context engineering：system prompt 应是 "minimal set of information that fully outlines your expected behavior"（anthropic.com/engineering/effective-context-engineering-for-ai-agents）。

**A2 · 中间过程的承载形态：带类型的结构化条目，不是自由文本混写**

- Anthropic：工具调用是 assistant 消息里的 `tool_use` 块，结果以 `tool_result` 块放**下一个 user 消息**回传（platform.claude.com/docs/en/build-with-claude/tool-use/overview）。
- OpenAI Responses API：running input list 里模型输出 `function_call` 条目、应用追加 `function_call_output` 条目；reasoning 条目按 provider 要求**原样回传**，"preserve every item in the response's `output` array"（developers.openai.com/api/docs/guides/function-calling）。
- LangGraph：消息即 state（`add_messages` reducer），全 state 由 checkpointer 按 super-step 存快照（thread_id 主键），"In production, use a checkpointer backed by a database"（docs.langchain.com/oss/python/concepts/memory）。
- **对本系统的映射**：业界在消息流里用**带类型条目**承载工具调用；本系统不走 provider 原生 tool 协议（决策 JSON 走文本通道），等价物＝工具台账以**结构化 process_notes** 存 state、需要时以有界摘要进当前指令——形态不同、纪律相同（类型严格区分、不以 assistant 散文混写）。未来若迁 provider 原生 tool 协议，可升级为 typed entries。

**A3 · 上下文膨胀治理（四类首选，Anthropic/OpenAI 均已产品化）**

- Compaction：接近窗口上限时摘要化重启——"taking a conversation nearing the context window limit, summarizing its contents, and reinitiating"；Claude Code 实作保留决策/bug/实现细节、丢弃冗余工具输出；警告 "overly aggressive compaction can result in the loss of subtle but critical context"。
- 工具结果清理（最轻量）："Tool-result clearing is the safest lightest touch form."——Anthropic context editing（`trigger/keep/clear_at_least/exclude_tools`），清掉的结果替换为占位文本，"Your client application maintains the full, unmodified conversation history"（platform.claude.com/docs/en/build-with-claude/context-editing）。
- 结构化笔记：把 to-do/关键状态写到窗口外持久层——"persistent memory with minimal overhead"。
- Sub-agent 隔离：子代理干净上下文干focused活，只回主代理 "a condensed, distilled summary (often 1,000-2,000 tokens)"。
- LangGraph 裁剪机检红线：`trim_messages`/`RemoveMessage` 之外，"make sure that the resulting message history is valid"——裁剪后必须仍是合法序列。
- OpenAI 已服务端产品化 compaction：`context_management`＋`compact_threshold`，压缩项 "carries forward key prior state and reasoning"（developers.openai.com/api/docs/guides/compaction）。

**A4 · 上一轮答案的呈现：原样 assistant turn，无伪标注**

- OpenAI：续接＝"include the model's previous response output as input"，"By using alternating `user` and `assistant` messages, you capture the previous state of a conversation in one request"——上一轮答案原样以 assistant turn 回放，并保留其结构字段。
- 逐页核对上述官方文档，**没有任何来源建议把上一轮改写成伪标注轮**；且 provider 端结构规则间接封死此路：assistant 消息承载模型自身输出（tool_use/phase/reasoning 都定义在其上），工具结果必须走独立类型，伪造/裁剪不当产生 invalid history。本系统的「上轮答案：」「直接回答：」标记轮正是这类结构污染——重构后对话层零注记。
