## 二、已定案结论（Owner 已裁决/字节级实证，接手窗不要翻案重查）

1. **Owner 裁决①（引擎语义保持）**：出口明细不能超过 50 条是系统设定，答案遵守
   即为正确——引擎 LIMIT 语义（QUERY_DEFAULT_LIMIT=50，domain.py:38；
   effective_limit 只封顶不抬底 :168）**零改动**。改的对象是装配层，不是引擎、
   不是答案措辞阀门。
2. **Owner 裁决②（修源头）**：不许只加阀门——把装配可见支数与引擎出口对齐是治本；
   行数对账只作诚实记账面（有差额须声明），不作拦截面。
3. **聚合总数不受 LIMIT 影响（Owner 提问已答死，SQL 级证据）**：排名型 SQL＝
   `SELECT 井, SUM(值) … WHERE 窗 GROUP BY 井 ORDER BY 合计 LIMIT n`
   （pg_executor.py:167-185）——SUM 在 SQL 内对**窗内全量行**计算，LIMIT 只截
   **输出行数**（井数），不截求和数据面。铁证：数-限1 排名合计 Z-16=5839.63 吨，
   而 50 行日值最大可能和 ≈ 46.07×50≈2300 吨——5839 必然来自全窗求和。
   「全年总数/平均」类同理安全。明细型（井×日行）是唯一 LIMIT 暴露面（设计如此）。
4. **程序自己知道截断**：Q15 原始 run 的 agent_v2_step manifest 记着
   `步骤 answer：…预算 24 支截断（24/51）`——机器可查，但模型面零告知、用户面
   零披露、答案合同无行集对账规矩。静默截断＝设计缺陷的一部分。
5. **系统性波及（不止 W1）**：抽检实锤 NQ-D4（24/88——「90 obs 支撑 0」题）、
   NQ-M10（24/47——「材料堆放」题）同帽。Q15 归因报告中所有「N obs 在窗」类
   结论（A′ 材料堆放、MR 交付塌方、W3/W4 单侧交付等）需在「模型只见 24 支」
   光线下重审（见第五节附 E 全量扫描）。
6. 信任级排序在场（context.py:162：agg 权威表＞台账＞检索，同序保持入栈序）——
   数据链行集（agg_row）恒排最前，24 帽下数据行先被保留；检索族（fragment）题
   被截的是检索片段。两族受截形态不同，修法要分开看（见第五节附 A）。
